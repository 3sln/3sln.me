# Multi-account browser sessions and consent: independent review

Date: 2026-10-14. Phase 1 design/security/interoperability review. No runtime, SDK, frontend or build changes are authorized by this record. Human signoff remains blank. The session and UI proposals were cross-read; remaining interface decisions are recorded below. Findings are grounded in current source, not implementation evidence for the proposed feature.

## Current boundaries and proposed direction

Current [HTTP sessions](../../packages/runtime/http.mjs) use one HttpOnly, SameSite=Strict provider cookie containing a session token. The [identity service](../../packages/identity/service.mjs) checks the live account/session and CSRF for owner mutations; logout revokes that session. The console and authorization shell currently deny framing. The [federation authority](../../packages/runtime/federation.mjs) resolves the requested handle into one owner shard before storing a request and later requires authorization by that owner. None of these current behaviors implements a browser account vault or an embedded account chooser.

Multiple signed-in accounts should mean several independent, revocable provider-local sessions retained by this browser. It must not merge identity records, credentials, recovery authorities, application connections, preferences or permissions. A selected console account is a presentation choice; every operation must still identify the particular live session and intended owner it uses.

Recommended first implementation: a bounded, encrypted and authenticated browser vault cookie plus existing per-owner live session records; explicit same-origin account selection; a protected provider account picker; and top-level/popup authorization as the reliable consent boundary. Account choice inside a provider-owned iframe can be considered separately, with no embedded authorization by default and no preconsent identity/session-state return to the embedding application.

## Vault alternatives and authority limits

| Option | Benefit | Required limit or tradeoff |
| --- | --- | --- |
| Bounded encrypted cookie carrying independent session references | Avoids a new central actor on ordinary owner requests; existing per-owner revocation remains authoritative | Strict bytes/count limits before decode, authenticated issuer/version/key ID/expiry, and live validation of the selected member; concurrent cookie responses can lose membership updates |
| Opaque cookie pointing to a server-side browser vault | Serializes add/remove/switch and enables immediate vault-wide revocation | Adds durable storage and a browser-wide authority read unless another bounded selector credential is introduced; do not promise both fully stateless requests and immediate central revocation |
| Separate cookie per owner | Independent additions avoid cross-owner Set-Cookie overwrites and a coordinator capability over future accounts | Bound total cookies/bytes, authenticate before routing and select one owner; authoritative inventory, cleanup and membership concurrency still need explicit treatment |
| Browser storage holding session bearers | Easy UI access | Reject as default: exposes every retained account to provider script/XSS and service-worker/debug/storage surfaces |

For a cookie vault, adopt explicit small bounds (for example five entries and a total encoded value below a conservative 3 KiB budget, finalized against real browser headers). Reject duplicate cookies/owners, unsupported versions, malformed encoding, unsafe timestamps, excess entries, unexpected properties and truncated/tampered ciphertext before account actor lookup. Use a purpose-separated key and exact host/origin binding, with no plaintext passwords/recovery material. Encrypted content protects account identifiers from casual cookie-value inspection; HttpOnly and TLS remain essential. Encryption does not prevent replay or provide per-owner revocation.

No owner hint outside the authenticated envelope may direct a database/DO lookup. After envelope validation, ordinary console access validates only the selected member's live session, status and authority epoch. The account picker may explicitly perform bounded validation of the retained list, but do not turn every API call, asset read or push click into an all-account fanout. Display cached labels as unverified/stale hints until validated; never derive authority from badges, aliases or display names.

Adding an account requires completing its existing login/activation gates. Never save pending signup/recovery tokens as authenticated members. Vault fullness needs an explicit remove/replace choice; do not silently evict or log out a different account. Switching must not extend session expiry, revive a revoked session or reset its device security history. Key rotation must define which old vault envelopes remain readable and for how long; invalid envelopes fail locally rather than falling back to attacker-controlled routing fields.

## Switching, tabs and logout

The most serious confused-deputy case is tab A displaying owner A while a second tab changes a globally shared selected cookie to B. A late mutation or read from A must not silently execute against B. Require an explicit intended owner plus selected-session/generation binding on private API requests; validate it against the authenticated vault and live session. Mutations additionally require exact provider Origin and the corresponding CSRF authority. Resource IDs in request bodies are not enough: generic preferences, profile, quota and delete operations may have no owner in their URL.

Choose and document tab semantics: either a shared default account with stale-tab conflicts, or per-tab nonsecret selectors whose matching member is authenticated on every request. A selector is never a session token. Every switch clears private visible content, cached query results, form fields, worker jobs, uploads, prepared dispatch capabilities, iframe MessageChannels, consent snapshots and notification context before loading another owner. Late success and failure must both be fenced; an A 401 must not log out B. Cross-tab messages may invalidate state but cannot install a bearer or authorize a switch by themselves.

Switch/add/remove are POST operations with exact Origin, CSRF and membership checks; GET or notification navigation cannot mutate the globally selected account. Refuse stale or concurrently changed state rather than guessing. Two Set-Cookie responses can overwrite one another in a stateless vault. This can cause membership loss, but must never restore a session revoked at its owner record. Do not claim transactional multi-tab membership merges without a serialized authority.

“Sign out this account,” “remove its saved entry” and “sign out all accounts on this browser” need distinct semantics. Revocation precedes the success claim; removing a cookie entry alone leaves a copied session usable. For logout-all, process only the bounded authenticated members, report incomplete revocation honestly and avoid dropping the only retry authority before necessary cleanup finishes. Expiry/removal of A must not clear B. Credential recovery, account suspension and server-side revocation remain authoritative even if an old vault cookie is replayed. A migration from the single-session cookie must define one precedence and clear the legacy cookie; never alternate between two independent session sources on different routes.

## OAuth request identity is not a suggestion

Today `beginAuthorization` requires `identity`, resolves an active owner, and stores the request within that owner's shard. The SDK's `beginLogin(identity, …)` therefore cannot silently authorize a different account selected later. The picker must show the required identity and either select that retained member, request its login, or explicitly start a new request for a different identity. Existing request/resource/connection snapshots and approval revisions cannot be copied to the replacement request.

A provider-first discovery flow without a requested identity is a separate design choice: bound client, redirect, PKCE challenge, state, requested scopes, expiry and browser transaction before owner choice, then bind the selected owner exactly once. Define storage/rate limits and request routing before implementing it. Pending requests must never choose an owner from whichever cookie happens to arrive at approval time. Continue exact redirects, PKCE/state checks, live owner epoch and reviewed resource/connection revision checks. OAuth security guidance explicitly requires CSRF defenses and protects authorization flows against session/issuer confusion. [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)

## Application-requested logout, switching and fresh login

An application's “sign out” normally removes its local SDK credentials and, when requested, revokes only its own authorized grant/connection scope. It does not authorize deleting the provider browser vault, terminating another application's grants, logging out unrelated accounts or changing the user's active console account. App-triggered provider logout requires an explicit provider-owned confirmation naming the affected account/session; it cannot be an embedded GET, postMessage command or redirect side effect. A revoked app token cannot become a general logout credential.

Expose an app-triggered “choose another account” or “sign in again” as a request to open the protected authorization flow. It must not disclose whether any matching provider session exists before consent. Cancel/error callbacks are generic and bound to the initiating client transaction; no retained account count, old/new UUID or session liveness accompanies them. Switching to another owner restarts a handle-pinned request rather than retargeting its stored authority.

Fresh login is distinct from continuing an existing session. If a client requests reauthentication, the protocol must state the required assurance and maximum age, and the provider must actually obtain fresh supported credential proof for the selected account before satisfying it. A silent cookie refresh or picker click is not fresh authentication. Bind proof to the request, account and current session/authority generation, with short expiry and no replay across clients. A fresh login also does not restore a revoked application grant: current consent, scope ceilings, resource bindings and connection/revocation generations must still be checked. Old tokens and prepared operations remain revoked after reconnect or reauthentication unless newly issued under current reviewed authority.

## Iframe privacy and browser limitations

A provider iframe is origin-isolated from the embedding site's ordinary DOM reads; that does not make the embedder a trusted consent surface. It can overlay, crop or obscure the chooser and trick a user into clicking a real control. Exact registered-client `frame-ancestors` is necessary for a dedicated embedded route and checks the whole ancestor chain, but registration alone does not neutralize a malicious allowed client. Keep generic console/recovery pages unframeable; require final permission approval in a trusted top-level/popup surface for the initial slice. A framed choice should not change the global console account or grant application access. [CSP Level 3](https://www.w3.org/TR/CSP/#directive-frame-ancestors)

The current Strict cookie cannot simply be reused as an authenticated third-party iframe session. Browser storage-access policies may require explicit user activation and additional cookie attributes; partitioned cookies are scoped to the embedding top-level site and do not expose the provider's existing unpartitioned account vault. Do not weaken the normal owner-session cookie to `SameSite=None` merely to make the picker convenient. A distinct short-lived chooser capability, if added later, must have only picker/continuation authority. Provide top-level redirect or a user-opened popup whenever cookies, storage access, embedding policy or popup behavior prevents the embedded flow. [Chrome Storage Access API](https://privacysandbox.google.com/cookies/storage-access-api), [CHIPS](https://privacysandbox.google.com/cookies/chips)

Before approval, the SDK must receive no account list, selected handle/UUID, account count, logged-in flag, session expiry, preference values, connection status or account-specific error. Use fixed bounded iframe geometry and generic readiness/fallback messages so size and event payloads do not deliberately disclose account state. Do not promise absence of every browser timing side channel; the actionable contract is no designed preconsent identity/state disclosure or account-specific endpoint oracle.

If using postMessage, validate exact registered origin, the specific WindowProxy, request ID, unpredictable transaction nonce and bounded message schema on both sides. Use an exact targetOrigin, close ports/listeners on navigation or cancellation, and never accept a parent-supplied origin as proof of its own authority. Replacing an iframe/window must invalidate prior messages. Completion returns only a one-time code for the approved request; account identity and granted data become available only through the already-bound authorized exchange. No provider session token, vault cookie, CSRF token or private account list crosses the channel. [WHATWG cross-document messaging](https://html.spec.whatwg.org/multipage/web-messaging.html#security-0)

## Notifications and owner isolation

A push endpoint belongs to a browser/device, while notification permissions and enrollment belong to particular owners. Define whether one physical subscription supports several owner enrollments and ensure revoking A does not inadvertently unsubscribe B. Notification tags and stored routing metadata must include an unambiguous provider/owner discriminator so identical message IDs cannot replace another owner's notification.

Use a minimal, owner-controlled account label to distinguish notifications; it is visible on an OS lock screen and must follow that owner's preview/privacy preference. No remote icon fetch or private profile lookup is needed on every push. Notification data is an untrusted locator, never switching authority. A click opens a fixed provider route, validates the intended owner and live retained session, and explicitly asks for that account when unavailable. It must never show A's notification content inside B's current view or silently approve actions with B's session. Avoid placing session capabilities or plaintext message content in URLs. Service-worker messages must be scoped to the intended owner/tab generation; pending tasks must revalidate ownership after a switch.

## Required implementation tests

- Tampered, oversized, duplicate, expired and wrong-origin vaults fail before any owner lookup; a valid selected member touches only its owner, with bounded explicit picker reads.
- A/B tabs race switch, login completion, logout, cookie response order and recovery. Stale A reads/mutations cannot execute as B, and A failures cannot erase B's UI/session.
- Missing/expired/revoked A leaves B usable. Logout-all partial failure is honest; replaying an older cookie cannot revive a revoked member. Legacy-cookie migration is deterministic.
- App-requested logout revokes only its own authorized scope; provider logout needs explicit confirmation. Fresh-login requests cannot succeed from a stale cookie/picker click, and reauthentication cannot revive revoked grants or resources.
- Same-provider multiple accounts retain independent credentials, recovery, app permissions, preferences and outboxes. Vault-full and pending-account cases do not silently evict or activate.
- A request pinned to A cannot approve under B; changing account creates a fresh request and consent snapshot. PKCE/state/redirect/window mismatch fails without returning private account state.
- Embedded chooser under allowed, unapproved and nested attacker origins; overlay risk is resolved by top-level final consent. Third-party-cookie denial, storage access denial, popup blocking, cancellation and restart all have a usable nonleaking fallback.
- postMessage spoof/replay/old-window/extra-port/oversized-message cases reveal no account state before consent and cannot switch or authorize.
- Notifications for A while B is active, shared device subscriptions, expired A, logout A, same message ID and clicked stale push never display/mutate another owner.

## Pending decisions and cross-review

Cross-read: [session proposal](../architecture/multi-account-sessions.md) and [UI proposal](../architecture/multi-account-ui.md). Both preserve per-owner live authority, a bounded encrypted vault, top-level final consent, minimal notification routing and no preconsent app account inventory. The UI explicitly treats an iframe launcher as the first slice and an authenticated embedded picker as a separate compatibility/security decision; this is a proposed scope choice, not implemented browser support.

Concrete findings sent to the authors:

1. The initial session draft combines reporting logout-all partial failures with clearing the entire vault. That discards the credentials needed to retry failed revocations. Retain failed entries under a clear signed-out/cleanup UX, retain a narrowly scoped revocation continuation, or explicitly limit the promise to local removal. Do not report known complete server logout when it is unknown.
2. Ordinary active-owner routing and request-local OAuth owner choice need different explicit selectors. Define a request-bound saved-member selector authenticated against the vault and live session for consent; never accept a raw caller UUID as authority or route all saved accounts for ordinary requests. Include server-checked session/epoch identity, not only expected owner, so same-owner recovery/relogin cannot validate stale consent or prepared work.
3. Existing SDK authorization is handle/owner-bound. UI steps that imply an arbitrary owner can be chosen after the request starts must instead filter to the bound owner or restart a new request. A provider-first request requires new bounded pre-owner authority design.
4. Notification click wording must not imply an unauthenticated GET globally changes the selected account. Use a validated request-local destination or an explicit provider switch with its normal authority checks; preserve the user's other open private view/draft.

The UI author has reconciled these points: exact-owner approval is retained for current requests, private cross-owner replacement is explicitly gated, unresolved logout revocations retain narrow retry authority, and inactive notification destinations require confirmation before global switching. A cross-owner replacement would span different owner actors, so its atomic handoff/crash behavior still needs a concrete protocol; no distributed transaction is implied. The backend wording is pending final reconciliation. Remaining provisional choices include exact AEAD/key provisioning and byte limits, recovery of the chooser when the active member expires, concurrent stateless cookie response handling, fresh-login assurance and app intent shape. The UI cannot solve server membership races with localStorage locking. No runtime implementation, browser compatibility, deployment or human approval is claimed by this review.

## Phase-two coordinator cross-review

Separate per-owner cookies remain a legitimate alternative: their observed-cookie maximum is not a global device/account limit, and bounded cryptographic parsing need not imply an all-owner database fanout. The coordinator buys authoritative inventory and serialized membership/cleanup at the cost of more credential custody, rotation, storage and control-plane RPCs.

The coordinator's preferred next design adds one authoritative per-device membership record, while ordinary owner requests continue using an AEAD snapshot and one live owner session. This resolves lost membership writes at the coordinator; it does not make browser Set-Cookie response ordering atomic. Request-local/per-tab owner selection must compare `X-Bindle-Account` and session context to a member of the authenticated snapshot, not require equality with the vault's default `activeOwner`. That default serves initial discovery only when an explicit tab selector is absent. The earlier global-active wording must be reconciled before implementation.

A substantive new risk is capability amplification through reconciliation: a stable coordinator capability copied from an old A-only cookie could later retrieve B's newly added session. That is device-wide authority over future accounts, not snapshot-scoped authority. The backend author agrees with the stronger proposed default: rotate the coordinator capability whenever a member/session is added or replaced; bind previous capabilities to immutable `(owner, session ID)` sets; and allow their repair/inventory only over the current intersection of those sets. An old capability must never retrieve a new owner or replacement session. Limit retained prior-capability history and lifetime; once outside that window, require sign-in rather than silently widening authority. The current parent decision and final implementation remain pending. In particular, an old A-only capability plus fresh authentication for C may authorize a new snapshot for its current A intersection and C; it must not acquire an unseen B through the coordinator's full inventory. Fresh login cannot launder an older restricted capability into authority over every stored member.

This trades seamless recovery for bounded authority: if the response carrying the new snapshot/capability is lost, the old cookie may not recover the newly added account without fresh authentication. State this clearly. The same old-scope restriction must apply to inventory, install/replacement, switch and cleanup APIs, not only one listing route. Coordinator mutation authorization needs both the authenticated capability and explicit expected revision/operation incarnation; client-supplied snapshots never replace durable membership wholesale.

Logout cleanup requires an independent, bounded, purpose-specific capability and expiry when no live member remains. Its only authority is retrying exact already-requested revocations; it cannot return session tokens, list new members, reactivate old members or begin ordinary owner operations. A failed owner revocation leaves copied older session snapshots potentially usable until revocation or session expiry: marking coordinator entries retry-only cannot revoke a direct snapshot while the ordinary hot path intentionally avoids the coordinator. Report that limitation instead of claiming instantaneous logout.

Membership reservations, pending replacements and cleanup jobs must be separately bounded. Rejecting a sixth account or a stale installation after a session has been minted requires targeted revocation/compensation of that new session, or a documented bounded pending installation; do not leave unlimited orphan sessions through repeated full-vault logins. Initial device-vault creation and inventory require rate limits and expiry/garbage collection, with no unauthenticated arbitrary actor creation before capability verification.

### New provider-owned authorization entry

A proposed pre-owner entry request can support account choice without relaying the chosen identity to the application. It is a new authority stage: pin registered client, exact callback, PKCE challenge, client state, requested scopes/methods, intent, nonce and expiry before selecting an owner. Keep it independent of browser account presence and bounded against public-client/nonbrowser request spam. GET only renders the provider page; selection is an authenticated provider POST.

Entry selection must record one durable chosen-owner/session binding and stable new owner-request ID before any redeemable approval is possible. Retries recover the same decision; they cannot create multiple independently redeemable requests on different owners. Creating the owner-sharded request is a recoverable cross-record handoff, not an assumed atomic transaction. Replay of the entry or a stale selector after another choice must fail or resume the exact existing handoff. A different account choice starts a fresh entry/decision and fresh resource review, never copies a prior owner's selected resources.

The old identity-pinned API retains exact-owner behavior. The new entry must explicitly distinguish identity constraint from a non-authoritative display hint, and fresh-login intent from ordinary consent. End-session entries cannot mint grants or revoke unrelated sessions; their callbacks disclose only the approved operation result, not session presence. No UI or SDK convenience method can bypass these server bindings. This new protocol needs exact request schemas, bounded storage/rate limits, crash/replay tests and source review before implementation is called complete.

## Preliminary frontend source audit

As phase-two source work began, the shared API wrapper gained explicit owner/session-context headers and a local generation fence, while cookie-free prepared form dispatch continues to omit owner/session/CSRF headers. Independent review found three additional boundaries: delayed malformed JSON must check the context fence before exposing an old 401; a request-local B projection must not replace console A's CSRF; and disposing the API provider must invalidate outstanding requests as well as clear all installed context. The frontend author corrected these. [Independent regressions](../../tests/browser/multi-account-audit.mjs) pass **3/3** against that source checkpoint. These are API/state tests with controlled response timing, not complete backend vault or multi-browser evidence.

The picker token proposal is acceptable only as a bounded private CSRF/continuation proof tied to the authenticated capability, revision, exact origin, purpose and expiry. It is not standalone membership authority. Validate target scope before owner routing and avoid an unbounded durable challenge row on every inventory read. Native navigations, downloads and routes that cannot send custom headers also need an explicit safe owner-selection rule; they cannot silently fall back to a newly changed default account for an old private view.

## Implementation checkpoint and independent security review (2026-10-14)

The console slice was implemented with independently named per-account cookies (see [session authority](../architecture/multi-account-sessions.md#implemented-choice-independent-per-account-cookies-2026-10-14)); the coordinator and its capability-amplification blocker were not adopted. An independent adversarial reviewer (agent, security lens, read-only, with probe scripts against the real Node adapter) audited the diff. Confirmed strengths: authentication and selector checks precede any owner routing; AEAD associated data binds origin/purpose/name; tab isolation holds because CSRF is per session; cleanup custody never authenticates; same-owner relogin revokes its predecessor; Node keeps separate Set-Cookie lines; notification clicks never switch accounts.

| 4 | More than eight members locked out inventory/logout-all; >10 relevant cookies broke all API requests | Low, reasoned | Fixed: no total-count throw on ordinary requests; inventory and logout-all enumerate up to 20 and expire forged/revoked members; regression test |
| 5 | `session_context_conflict` during revocation was treated as already revoked | Low, reasoned | Fixed: retried by token alone. Remaining: a suspended account's `unauthorized` drops custody without revocation |
| 6 | Logout-all left a coexisting legacy cookie that later re-authenticated | Low, hardening | Fixed: removing the last member expires the legacy cookie |
