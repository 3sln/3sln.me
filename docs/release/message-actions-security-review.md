## Recommendation and current boundary

Support bounded declarative forms and cosmetic message CSS inside an opaque-origin sandboxed renderer. Shadow DOM can scope that styling inside the frame. A trusted host broker owns destination review, submission, optional identity proof and local result history. The sender supplies data and presentation, never executable code or account authority. Keep recipient, identity disclosure, final submit/confirmation and result status in trusted chrome outside sender styling. Remote resources are blocked before parsing/mounting and require a separate deliberate decision. Cross-origin application backends can be supported through exact declared/verified endpoint delegation; a blanket same-origin rule is unnecessary.

The current implementation is deliberately narrower: [content.mjs](../../packages/messaging/content.mjs) reconstructs a small formatting allowlist without attributes, styles, forms or URLs. [messageDetail](../../apps/web/src/ui/release-inbox.mjs) mounts the result only in an iframe with an empty sandbox and no-referrer. Existing web-archive validation does not activate its bundled images or CSS. The CSP includes `sandbox` in a meta element, but that directive is not effective there; the actual iframe attribute supplies the current sandbox restriction. Other supported meta CSP restrictions still matter. This design must not be described as already implemented.

## Browser facts that determine the design

- **Shadow DOM is not a security principal.** It isolates component structure/style rules, not document origin, network access or account credentials. Closed mode is not a strong security mechanism. Host selectors, inherited properties and positioning also need treatment; CSS scoping alone is not clipping. [Mozilla Shadow DOM guide](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM).
- **`setHTML()` addresses XSS, not all message policy.** It removes XSS-unsafe constructs even when requested by a custom sanitizer. It does not replace this product's form, URL, CSS, resource and disclosure rules. Re-serializing sanitized markup and inserting it through `innerHTML` loses the original context-aware safety. The method is currently documented as limited availability, so unsupported browsers need a safe fallback. The former WICG draft now points implementations to the HTML Standard. [Mozilla `setHTML()` documentation](https://developer.mozilla.org/en-US/docs/Web/API/Element/setHTML), [HTML sanitization standard](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html), [WICG migration notice](https://wicg.github.io/sanitizer-api/).
- **Sandbox and CSP are complementary.** Omit `allow-same-origin`; a fixed host-authored helper can use `allow-scripts` without granting sender scripts. Native forms, top navigation, popups and downloads remain restricted unless explicitly enabled. CSP `sandbox` cannot be enforced through meta or report-only delivery. Set `form-action 'none'` explicitly; it does not inherit `default-src`. Do not depend on inconsistent form redirect enforcement for endpoint containment. [Mozilla iframe documentation](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe), [CSP sandbox](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox), [CSP form-action](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/form-action).
- **Credential omission is per request.** Fetch's `omit` excludes ambient credentials and ignores returned credentials for that fetch. It neither configures image/CSS loads nor makes navigation anonymous. `crossorigin="anonymous"` uses same-origin credential mode rather than a universal omit policy. CORS controls response sharing; it is not proof that a request had no side effect. Direct requests still disclose network metadata; Mozilla also documents nonconforming client-certificate behavior on some preflights. [Fetch credentials](https://fetch.spec.whatwg.org/#concept-request-credentials-mode), [HTML crossorigin behavior](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/crossorigin), [Mozilla CORS credential caveat](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#preflight_requests_and_credentials).
- **CSS can cause network disclosure without script.** URL-bearing styles and fonts are request sources; conditional rules can make requests depend on state. A broad image/proxy allowance defeats a restrictive default policy. CSS also exposes environmental measurements, so cosmetic support needs bounded policy and resource treatment. [CSP exfiltration considerations](https://www.w3.org/TR/CSP3/#security-exfiltration), [CSS values and privacy considerations](https://www.w3.org/TR/css-values-4/#privacy).
- **Notifications are a reduced interface.** The supported action count may be zero and excess actions can be omitted; the equivalent operation must remain available in the app. A notification click is not evidence that a user reviewed a form, endpoint or optional identity disclosure. [Notifications standard](https://notifications.spec.whatwg.org/), [Mozilla notificationclick support](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/notificationclick_event).

## Concrete renderer and resource proposal

1. Normalize supported HTML form markup or a versioned declarative action attachment into the same bounded internal action/field model. Authors need not hand-write JSON to use ordinary form markup. HTML can propose fields and a target, but it cannot manufacture trusted app delegation, a recipient capability or permission to identify the owner. Validate that model independently of its presentation. Bound total bytes, action/field/option counts, string lengths, nesting and validation complexity. Initially support ordinary text/textarea, finite choice, checkbox and date/number fields with simple bounded constraints. Do not accept arbitrary regex evaluation, file upload, password/payment/autofill credential fields, custom elements or script hooks. A field's descriptor ID, type and cardinality are authoritative; DOM names, hidden controls and `formaction` cannot add authority or parameters. Reject duplicate/unknown IDs. Define disabled/unchecked/empty/multivalue serialization explicitly rather than inheriting accidental FormData behavior.
2. Create a fresh isolated renderer per displayed message/revision. A static host-authored document sets CSP before receiving any sender bytes. Use an opaque sandbox with only the fixed helper's script allowed by hash/nonce; no `allow-same-origin`, forms, popups, downloads, top navigation or storage access. Explicitly deny network, workers, nested frames, objects, base URLs and native form actions. Restrict Permissions Policy features too. The helper and sanitizer policy are app assets, not sender-selected modules. Never interpolate sender markup into the helper script or its surrounding document.
3. Inside that protected environment, sanitize into the actual final Shadow DOM context using `setHTML()` with a product-owned configuration; use a tested fallback sanitizer/reconstruction path if absent. Do not first parse/mount hostile content in the authenticated parent and then remove resource attributes. Avoid a sanitize → serialize → unsafe parse pipeline. Restrict all URL-bearing attributes/elements as well as script: `srcset`, `poster`, SVG references, `base`, refresh metadata, external stylesheets, resource hints, `ping`, form overrides and custom protocol links. Trusted helper code constructs controls from validated descriptors or reconciles allowed form controls exactly to them. A staged sanitize → traverse → install handlers → mount pipeline fits this model. Native `setHTML()` belongs to Element/ShadowRoot, not DocumentFragment; a template element and its content are a candidate staging mechanism only after the actual browser behavior is tested. A detached element is not assumed network-inert. Remove `action`, `formaction`, `target`, `formtarget`, `form` associations and all overriding native submission behavior before mount; no externally associated control may join the form. Bind handlers to validated node/descriptor maps held in closures, never `document[name]`, named globals or clobberable form properties. `preventDefault()` alone is not the boundary; sandbox and `form-action` still prevent native fallback if handler installation or execution fails.
4. Allow cosmetic CSS through a reviewed parser/policy, not URL blacklist regexes. Bound rules, selector complexity, dimensions, animations and total content height. The enclosing iframe clips visual content; author rules cannot reach the parent's review controls. In-frame fake app chrome remains possible, so show a persistent outer message/source boundary and review actual outgoing values outside it. Native form submission stays disabled: helper-owned controls validate and collect values, then ask the parent to review. Test the actual behavior rather than assume a sandboxed native submit event/validation sequence works.
5. Remote-resource consent should resolve a finite manifest into bounded, decoded inert assets once, independently of CSS selectors or field values. Reconstruct references to those vetted local resources; do not permit CSS to issue arbitrary requests to a nominally trusted proxy. Keep fonts, SVG, HTML and remote stylesheets excluded initially unless separately audited. Enforce MIME, byte and image-dimension/decode bounds. A proxy has no cookie jar and strips ambient or caller-supplied auth; it rejects redirects and private/loopback/link-local/metadata addresses, validates DNS/address use and refuses arbitrary URL forwarding. Cache keys and logs must not expose owner credentials. Loading even a unique proxied tracking URL can disclose that someone fetched the message, so label the opt-in accurately.
6. Link clicks become typed open-link requests; trusted chrome displays the resolved destination. No native sender-controlled navigation/popup fallback. Opening an external site is separate from credentialless submission: that site may receive its normal browser cookies. Do not promise that no-referrer makes the visit anonymous.

The frame channel accepts only a bounded action ID and values for the displayed message/revision. Verify the concrete frame/window source, establish a fresh private MessageChannel and revoke it on navigation, re-render, owner change or close. Opaque frames share the string origin `null`; accepting all messages with that origin is insufficient. A `postMessage` from a frame is a request for review, not authorization to sign or submit. No cookie, session/CSRF token, private key, raw app grant or submission capability enters the message DOM/helper. [Browser messaging security guidance](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage#security_concerns).

## Lazy fallback and staged traversal

A pinned, self-hosted, content-hashed DOMPurify adapter is a reasonable fallback when the required native Sanitizer behavior is absent. Its upstream documentation warns that later mutation/context changes can undo sanitization; defaults include SVG/MathML, `USE_PROFILES` overrides `ALLOWED_TAGS`, and unsupported environments may return their input unchanged. It supports returning a DOM fragment. Check support explicitly, use a reviewed HTML-only configuration without conflicting options, and preserve the upstream Apache-2.0/MPL-2.0 license/provenance. [DOMPurify documentation](https://github.com/cure53/DOMPurify).

Lazy-load the fixed reviewed asset, never a URL from the message or a mutable CDN release. Use an internal adapter with the same structural/action validation for native and fallback paths, not a global fake `setHTML` API. Loading may share a module promise; sanitizer instances/hooks/configuration must not leak policy across messages. Missing, offline, integrity-failed or unsupported loading leaves safe inert text/formatting and no active controls. Do not temporarily show unsanitized content while waiting.

Native function presence alone does not establish that the selected configuration or template staging works. Probe the actual required safe API behavior; test both paths against one fixture corpus. Sanitization and post-traversal policy happen with networking already blocked. Traversal may remove unsafe nodes/attributes and construct trusted controls/listeners using bounded literal values; it must not reintroduce unchecked URLs, event attributes, custom elements or string-built HTML. Do not feed unsafe parsed closed-shadow trees to the fallback. After any structural transformation, verify the final node/control model; handlers retain references/IDs in closures and cannot be redirected by DOM clobbering. CSS/resource validation stays independent of either sanitizer.

Required additional tests: force native unavailable, native present but incompatible configuration, fallback load failure/offline, concurrent lazy loads and owner switch mid-load; compare allowed controls and normalized submissions across native/fallback; prove no resource request before traversal; test parser namespace/mutation fixtures and no handler/native-form fallback after exceptions. All are implementation gates rather than claims from this document.

## Submission and optional identity proof

The trusted broker resolves the action from the saved immutable descriptor; the frame cannot select arbitrary URLs, headers, methods, resource IDs or signing bytes. Exact HTTPS target, method, app identity/delegation, descriptor digest, source message revision, expiry and recipient capability are revalidated at dispatch. First-use or changed destination requires visible review. Known delegated backends may be cross-origin; a verified app identity does not grant access to arbitrary destinations or account APIs. Reject userinfo, fragments and unsupported schemes, and define exact path/query normalization once. Never automatically follow redirects with fields, capabilities or signatures; a manually observed redirect can only propose the separately reviewed navigation described below.

Use an explicit action-specific recipient capability, narrowly bound to action/message/recipient and lifetime, where the destination requires authorization. It is a separate authority from the owner's session and an app's broader data grant. Keep it out of URL/history/referrer, rendering, analytics and notifications. No arbitrary sender-specified Authorization header or reuse of the shared owner API client. Browser outbound requests use `credentials:'omit'`, no-referrer, no-store, strict deadline/response bounds and redirect rejection. Separate reading/preparing/reviewing an action from dispatch: those local account operations may use normal owner authentication and prepare a short-lived dispatch capability bound to the reviewed transaction, owner-copy/history authority, destination, method and input digest. The actual browser-to-broker submission uses `credentials:'omit'` plus only that narrow prepared capability; broker-to-target dispatch also has no cookies or ambient authentication. Construct outbound headers afresh. The external postback capability alone never authorizes local owner history writes. This is an authenticated, bounded preparation followed by narrowly authorized cookie-free dispatch, not an anonymous public relay. Server egress may avoid client IP/TLS identity exposure but introduces provider visibility, SSRF and abuse costs; both choices need honest disclosure. Never retry through native forms, `no-cors`, navigation or a credentialed client after failure.

An optional account signature is an intentional stable-identity disclosure, even if no name/email field is included. It must not occur when viewing, loading an image, previewing a notification, focusing a control or checking whether the account can sign. A signing service must accept a typed authorized action operation, not arbitrary bytes/challenges supplied by message HTML. Reuse the existing assigned identity key purpose only through a domain-separated signature profile that cannot verify as a login, recovery, conversation membership or general resource authorization.

The profile must bind a protocol/purpose identifier, exact audience/endpoint and method, immutable action/message revision digest, canonical outgoing field/body digest, capability context, unique operation ID, issuance/short expiry and intended signer identity/key version. Define deterministic encoding and verifier test vectors before implementation. Show destination, transmitted fields and identity on the trusted review surface. Do not quietly add email/profile metadata. Receiver nonce/idempotency verification is mandatory for effects; a valid signature proves a particular key's assertion, not account ownership at another service, informed consent to arbitrary text, or that a business operation succeeded. Migration and key rotation need historical verification rules rather than redirect-based retargeting of an already authorized signature.

Persist the operation ID and bounded submission state before sending. Reserve per-owner/app/destination action, signing, egress and retained-history budgets before costly work. Duplicate clicks and OS/console races reuse one operation; an unknown network outcome is `unknown`, not failure or permission to create another effect. Reconciliation uses a documented receiver result/status contract; exactly-once effects require receiver deduplication. Cancellation after dispatch cannot promise rollback. Signout/account switch fences any late UI result or further dependent request.

## Postbacks and notification actions

A postback is a validated append-only owner-local presentation revision, linked to the operation and original action/message revision. Preserve the original and all retained intermediate states with visible history. It neither edits another participant's copy nor creates a conversation reply unless that separate effect was declared and approved. The current view may show the final state by default, but prior content remains reachable. Concurrent results need CAS/conflict behavior; a response cannot overwrite newer owner changes, resurrect erased content, change the source author or silently add actionable authority. Render every returned body through the same hostile-content pipeline. Never execute response HTML or trust returned new endpoints/actions/grants. Distinguish receiver-declared success from a verified external business effect; sanitize errors and bound result bytes/revisions/retention.

OS buttons may execute only fixed no-input actions explicitly enabled for a known/verified app destination with the narrow recipient capability and approved low-risk semantics. Sender labels such as “low risk” do not authorize this shortcut. Recheck expiry/revocation/message revision and current owner context on click, including when the service worker has restarted. Structured notification action data carries only opaque local references, never capabilities, signed URLs, personal form fields or account keys; separately displayed title/excerpt obey owner privacy settings. New identity disclosure, payment, destructive actions, unknown destinations and all forms open foreground review. Unsupported/omitted buttons and generic notification clicks also open the appropriate message. Opening, dismissing or displaying a notification never sends an action. An expired session should lead to sign-in/review, not credential resurrection or a background authority bypass.

## Result presentation, redirects and summary heuristics

The latest requested behavior can fit the same authority model: opening a message shows its local pending/submitting operation; an eligible notification button can open that view while its previously enrolled fixed action dispatches. Other cases still need foreground review. A local postback appends a retained presentation edit. A result with no richer display uses a bounded Submitted/Error status; transport uncertainty must still say pending/unknown rather than falsely claim either outcome.

HTTP redirect responses and `postback_blank` are display instructions, never permission for transport to follow redirects or repeat POST. The server broker may inspect a non-followed redirect and validate its Location as a navigation proposal; direct browser manual redirects expose an opaque-redirect response, so the implementation cannot assume access to its headers. Keep the actual action request on its originally approved exact target, then apply separate navigation policy. [Browser Response types](https://developer.mozilla.org/en-US/docs/Web/API/Response/type).

Opening a proposed destination requires an approved HTTPS URL with no userinfo or sensitive capability/signature/body parameters copied into it. A newly unapproved destination gets trusted review. Never forward the original Authorization, identity proof or form body. Use a new context with noopener/no-referrer; ordinary cookies at that destination may apply because this is a browser visit, not credentialless submission. Delayed completion may lack transient activation and have its popup blocked; offer an explicit Open result button rather than bypass browser policy. [Browser window-opening behavior](https://developer.mozilla.org/en-US/docs/Web/API/Window/open).

A returned `postback_blank` HTML body opens only in a dedicated trusted viewer that applies the same opaque sandbox/sanitization/resource controls. Never create an unrestricted app-origin blob URL, use `document.write`, or navigate directly to attacker-controlled HTML with the account origin. Result MIME/bytes, operation binding and consent still apply. Retain the result/history record before display where possible; failure to open a tab must not repeat the external effect.

Summary heuristics are presentation only: use explicit bounded metadata first, then eligible visible heading/subject/text, with a neutral fallback. Treat all extracted labels as literal untrusted text, not Bab templates, DOM markup, verified provenance, action authority or risk classification. Exclude password/authentication controls, private field values, hidden nodes and CSS-concealed text; bound length and handle bidi/control characters without allowing impersonation of trusted chrome. No model inference or outbound summarization is required. Tests must cover metadata disagreement, hidden form values, long/malicious labels, denied remote resources, unavailable styles and a notification whose description could not safely be derived.

## Outbound transport implementation and operator trust boundary

On 2026-10-14 the coordinator accepted the narrow transport plan for reversible implementation. This reviewer authored the transport slice, so this section is an implementation record, **not independent approval of that code**. A separate backend reviewer has been asked to cross-read it; human decision fields remain blank.

The broker must intersect exact `FORM_POSTBACK_ORIGINS` with current operator-reviewed federation client origins. Registering a client alone does not open egress. An empty configured list disables the transport. These domains are an explicit egress trust decision: approval permits the bound form to address paths on that external app origin. No caller supplies a proxy destination independent of the retained message/form binding. Only canonical DNS hostnames using HTTPS port 443 are accepted; IP literals, credentials, fragment targets and arbitrary headers/options fail. The first transport profile is URL-encoded POST with at most 16 KiB of body and a bounded idempotency key. Other form encodings require a separate reviewed profile.

[Node transport](../../packages/apps/node-form-fetch.mjs) resolves only public IPv4 A records, rejects mixed unsafe answers, and passes the selected address into the actual fresh HTTPS socket's lookup callback. Hostname/SNI and ordinary TLS certificate verification remain enabled. It never follows a redirect or reuses a pooled socket. IPv6-only destinations are unavailable in this initial Node port.

[Worker transport](../../apps/worker/form-fetch.mjs) requires the `global_fetch_strictly_public` compatibility flag, uses only global fetch and separately screens A and AAAA answers from the fixed Cloudflare DNS-over-HTTPS endpoint. Public IPv6 support is a conservative global-unicast subset; special, documentation and transition ranges fail closed. Cloudflare documents that the flag routes global fetch as public Internet traffic; without it same-zone calls can bypass normal Worker/security routing to the zone origin. [Cloudflare compatibility flags](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#global-fetch-strictly-public).

**Worker DNS screening is not connection pinning.** A DNS change between screening and fetch remains possible. The adapter does not claim parity with Node's selected-address connection guarantee, nor proof against a compromised operator-approved domain. It must never receive a VPC/service-binding fetch implementation or use a private network binding. Exact origin approval, public routing, TLS, screening and no redirects bound the practical profile; deployments requiring hard destination-address pinning need the Node port or an independently secured egress gateway. `resolveOverride` cannot generally pin arbitrary third-party app hosts because its zone restriction ignores cross-zone overrides. Raw sockets are not a universal replacement because Cloudflare IP destinations are blocked. [Request resolveOverride](https://developers.cloudflare.com/workers/runtime-apis/request/), [TCP restrictions](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/).

DNS JSON is a provider-specific format, not a standardized wire protocol; unexpected fields/shapes needed for the result, truncated answers, unknown address types or query mismatch fail closed. [Cloudflare DNS JSON documentation](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/make-api-requests/dns-json/).

Both adapters construct headers from scratch, do not carry session/bearer/cookie headers, never maintain a cookie jar, and discard Set-Cookie. Worker fetch additionally uses `credentials: omit`, manual redirects and no-store. Only bounded Content-Type, Location and Bindle-Target response hints are returned with status and at most 128 KiB of bytes; redirect bodies are discarded. A returned Location is navigation data, never another server fetch or repost. Timeouts default to five seconds and cannot exceed ten seconds, including DNS and body reads. Cancellation/timeout after sending is an unknown external outcome; the broker must not automatically retry or replace its operation ID. Adapter concurrency is an additional local bound, not a substitute for the broker's durable owner/source/global admission budgets.
