# Public-handle email bridge — independent design review

Date: 2026-10-13. Status: independent cross-review complete; design and human signoff remain provisional. Scope: optional paid-account inbound email, classification, sender continuation, abuse/cost controls and recovery. This document does not authorize runtime changes, DNS, deployment, outgoing mail or public contract publication. Human signoffs remain blank.

## Existing implementation and primary-source facts

The current [Worker entrypoint](../../apps/worker/index.mjs) exports fetch/scheduled handlers, not an inbound email handler. The [outgoing adapter](../../apps/worker/email.mjs) uses fixed system senders under the separately configured sender domain. [Deployment evidence](../deployment/email.md) records one recipient-confirmed notification send, not a verified inbound bridge, arbitrary sender role, classification pipeline or notification retry guarantee. The existing [message rules](../../packages/messaging/messages.mjs) match grant, MIME and collection and apply bounded metadata actions; they do not implement arbitrary classifier-driven age deletion. The [work budget](../../packages/runtime/work-budget.mjs) durably debits covered attempts and prepaid service leases; admission is not an invoice estimate and failed work is not generally refunded.

Cloudflare's current receiving API exposes SMTP envelope sender/recipient, headers and raw stream. Immediate `reply()` requires valid DMARC, permits one response per event, constrains the response recipient/sender domain and rejects overly long References chains. `setReject` supports permanent SMTP rejection. These platform checks do not prove mailbox ownership, prevent application-level duplicate sends or authorize a later notification. [Email handler API](https://developers.cloudflare.com/email-service/api/route-emails/email-handler/)

The receiving domain proposed for public handles is the bare provider domain, while existing allowed system senders use its `sys` subdomain. The existing `EMAIL` binding is not evidence that a same-receiving-domain `reply()` sender is operationally permitted. Establish each exact transport/sender separately. Envelope return addresses can also be provider bounce mailboxes rather than the person shown in From; a permitted automatic reply destination is not automatically the mailbox to bind as the conversation author.

Inbound Routing and outbound Sending are distinct. Current pricing lists arbitrary-recipient sending on Workers Paid, 3,000 monthly included sends and $0.35 per further thousand; inbound Routing is listed unlimited, while its Worker execution is separately billed. “Unlimited inbound” does not fund parsing, storage, AI, per-owner work or abuse. Current inbound maximum is 25 MiB; the application should select a smaller explicit budget rather than accepting that as a safe account default. [Email pricing](https://developers.cloudflare.com/email-service/platform/pricing/), [Email limits](https://developers.cloudflare.com/email-service/platform/limits/)

`@cf/cloudflare/clef-flash` is a hosted structured decision model accepting state and typed questions and returning option probabilities. It is not a dedicated spam scanner or identity verifier. On the review date its official page lists 24,576 context tokens and $0.038 per million input tokens, with no output-token charge; long state can be truncated. These are dated platform facts, not measured project costs or accuracy. [Clef-flash model](https://developers.cloudflare.com/workers-ai/models/clef-flash/)

At that unit rate, 10,000 calls of 2,000 input tokens cost $0.76 for inference alone before allowances, retries, mail, compute and storage. This arithmetic illustrates why a covered-write count is not an AI spend ceiling; monthly revenue of a $5/year plan is only about $0.42 before those other costs. Specify separately bounded classification frequency/token spend and service subsidy, then measure real token usage and false-positive rates. A model's probabilities are not calibrated project confidence guarantees.

## Independent criteria before reading the proposal

| Boundary | Required behavior and adversarial cases |
| --- | --- |
| Product eligibility | Off by default. Activation requires current paid entitlement and explicit owner consent covering public reachability, classification and finite quotas. Resolve only established public aliases; private associated emails are not lookup keys. Disabled, unknown, expired or unsupported aliases receive the same bounded generic unavailable result. Public success necessarily reveals some reachability; do not claim elimination of that oracle. |
| Alias lifetime | Preserve nonrecycled assignment/owner identity, including paid lapse and account deletion. A delayed job pins owner UUID, assignment, ingress generation and entitlement snapshot, then rechecks current authority before effects. Reactivation does not release an old queue into a new relationship. A transfer never silently redirects mail or reuses the old provider's namespace. |
| Authenticity | SMTP envelope, visible From and Reply-To are different facts. Reject ambiguity/duplicate critical headers and CRLF injection. SPF/DKIM/DMARC authenticate domain/path properties, not the particular human or an application's verified-email account. Forwarded valid mail may not satisfy a strict automated-reply policy; preserve a bounded receipt/review path without inventing proof. |
| Trusted headers | Raw Authentication-Results, Received, ARC and purported Cloudflare/spam headers are untrusted unless the ingress adapter proves their provenance, duplicate-stripping and exact trusted producer. A substring such as `dmarc=pass` or a Cloudflare-looking header name is insufficient. Nested forwarded email authentication headers are never imported as current transport evidence. |
| Retained mail versus membership | Automated, authentication-code, bulk/list and no-reply mail becomes an ordinary owner receipt if permitted. Human-like mail may propose a pending conversation. Neither classification, email delivery nor recipient acceptance creates an independently signed sender identity or releases conversation history. The initial mail retains attributed-email provenance rather than a fabricated sender signature. |
| Sender continuation | Bind one expiring single-use continuation to exact message digest, recipient owner/resource, sender mailbox candidate and consent generation. GET/link scanners do nothing. Require an explicit authenticated sender account action plus fresh mailbox proof where needed. New accounts finish normal verified-channel, primary credential and tested recovery. Existing same-account, different-account and other-provider flows cannot bypass identity/admission requirements. Continuations contain no reusable contact capability, shared conversation secret or body; redact tokens from logs/referrers and reject arbitrary return URLs. |
| Email association | An email already associated with another account cannot be silently moved, merged or disclosed. Mailbox reassignment is possible; an old association or new challenge cannot grant all historical mail/conversations. Shared aliases, delegated mailboxes and forwarding do not prove the original author's identity. An accepted-before-signup request stays pending until the verified account and recipient agree on the actual signed participant. |
| Immediate and accepted notices | At most one bounded initial explanation and one eligible accepted-before-join follow-up, with separate persistent ledger entries and current-state checks. No repeated reminders, attachments, original body, third-party Reply-To target or attacker-supplied URL/subject reflection. Follow-up requires a valid reply destination/authorization and currently pending continuation; it must not reveal recipient approval to arbitrary forged From values. |
| Disabled service replies | Prefer a generic rejection in the original SMTP transaction. An unsolicited promotional response after accepting mail creates backscatter, account-state leakage and autoresponder loops. If the platform cannot provide the intended temporary/permanent rejection, document actual behavior; do not fabricate SMTP semantics. Suppress outbound mail rather than weakening reply safety to advertise signup. |
| Classifier authority | Fixed, versioned typed questions and finite validated labels/confidence. Body and headers are input data, never instructions or executable rules. AI cannot accept peers, prove ownership, send mail, fetch links/images, alter scopes or delete content. Distinguish spam risk, automation and conversation-likelihood; legitimate codes/receipts are not spam merely because automated. Timeout/error/uncertainty preserves a bounded unclassified receipt with no challenge. |
| Content/privacy | Bounded raw bytes, MIME parts/depth/header lengths and decoded sizes before persistence/AI. No archive expansion, remote assets, attachments-to-model or executable HTML. Do not expose auth codes, bodies or email addresses in logs, prompts beyond necessary classification input, generic notifications or public profile/discovery. Cold bytes and reconstruction/ledger metadata join the owner-key encrypted bucket backup boundary; live provider plaintext custody remains explicit. |
| Retention | Only explicit owner rules may age/delete chosen receipts. Use trusted receipt time, rule revision and object version, not sender Date or a classifier score alone. Preview scope, retain an undo/quarantine policy where chosen, and protect pinned or converted conversations. A later classifier change cannot retroactively authorize deletion. Auto-delete of legitimate authentication mail is never an implicit default. |
| Cost and abuse | Reserve owner bytes/work and system mail/AI budgets before expensive stages; cap per sender, sender domain, owner and service without a single global hot counter. Give public ingress a finite subbudget so it cannot silently exhaust all ordinary owner work; preserve read/export/block/disable/erase access. Bound rejected/pending records and queue retries. Size/quota failure cannot force paid owners to retain giant attachments. Charge actual retained bytes; covered-attempt debits remain nonrefundable. Refund only provably unused reservations, never spent provider work or ambiguous accepted sends. |
| Crash and dedup | Message-ID and Date are sender-controlled and cannot be sole dedup/authorization keys. Bind owner/ingress generation, transport facts and content fingerprint; define bounded replay horizon and legitimate repeated-mail behavior. Persist receipt/event, quota disposition and pending actions before claiming acceptance. Separate notification stages and retry identities. Lost provider ACK gives an unknown outcome, not an automatic fresh send or exactly-once guarantee. |
| Portable interface | The bridge is a host ingress adapter feeding existing message receipts, owner rules and the public conversation contract. Do not introduce an email-specific membership bypass, hidden Cloudflare object identifiers, a new generic mail protocol or a central federation sequencer. Other hosts can supply compatible ingress/verification ports. |

## Backscatter and header trust

Automatic replies need more than a “human” score. Suppress null reverse paths, automated submissions, delivery/disposition reports, list/bulk mail, no-reply destinations and bounded loop signatures. Use a trustworthy envelope return path, never an arbitrary Reply-To. Mark responses automated and maintain cooldowns across distinct forged Message-IDs and retries. These choices follow the RFC's automatic-response destination and suppression principles; stricter product budgets remain a separate design decision. [RFC 3834](https://www.rfc-editor.org/rfc/rfc3834.html)

Authentication-Results conveys assertions inside an established trust boundary. An attacker can supply identical header names; the receiver must distinguish its trusted producer from external assertions. Pinning a text `authserv-id` without ingress stripping/provenance is not adequate. This is a concrete release gate for the Cloudflare adapter, not a claim that every raw header supplied by the API is authenticated. [RFC 8601](https://www.rfc-editor.org/rfc/rfc8601.html)

Cloudflare's current structured sending service controls Return-Path and Message-ID and permits Auto-Submitted headers. The existing adapter currently allowlists only its existing optional List-Unsubscribe header. A future bridge needs a narrowly reviewed automated-response transport/profile; do not assume the existing adapter already permits the required headers or that platform-generated IDs provide application idempotency. [Email headers](https://developers.cloudflare.com/email-service/reference/headers/)

## Required verification before implementation completion

- Real Cloudflare receive/reply/send capability tests under separately authorized deployment: actual trusted-header behavior, forged duplicate headers, forwarded mail, domain mismatch, DMARC failures, suppressed replies, outgoing bounce/suppression and account quota behavior. Documentation and existing one-message outgoing evidence are insufficient.
- Durable crash/retry matrix: before/after storage reservation, encrypted upload, receipt commit, classification, recipient acceptance, sender proof, invite commit, provider-send acceptance and lost ACK. Verify no double debit, revived admission, repeated challenge or accepted-but-lost receipt.
- Identity matrix: new signup, same/different existing account, sender email already owned elsewhere, changed mailbox, shared/forwarded mailbox, other-provider verified identity, recipient block/delete/lapse during continuation and stale accepted-before-signup notice.
- Abuse/content matrix: forged From/Reply-To/authentication headers, null sender/DSNs/auto-reply loops, many recipient aliases, repeated Message-IDs with changed bodies, changed IDs with identical bodies, MIME bombs/HTML/remote images, prompt injection, malformed model output and AI budget exhaustion.
- Retention/migration matrix: legitimate codes tagged automated, explicit age-rule changes, owner undo/pin, receipt-to-conversation conversion, old checkpoint/frontier restore, disabled ingress after paid lapse and migration without resurrecting old address authority.

## Proposal cross-review

The [proposal](../architecture/public-email-bridge.md) was read after the independent criteria above. It adopts current-paid opt-in, generic disabled-address SMTP refusal, immutable email-origin receipts/pending proposals, strict reply suppression, a separately confirmed pre-account mailbox continuation, real account/setup admission and finite cost controls. It preserves the owner-bucket backup boundary and records current parser, rule, adapter and encryption implementation gaps rather than claiming they already exist.

The proposed 30-day spam quarantine plus seven-day trash period is an explicit product choice requiring visible owner approval, correction/pinning and execution-time policy checks. It is not an independently justified safe universal expiry or a measured classifier result. Authentication mail and ordinary receipts retain no implicit destructive default. Exact rule and classification evaluations remain gates.

The final revision was reread independently against these findings:

| Finding | Final proposal disposition |
| --- | --- |
| Asynchronous classification cannot recreate an immediate reply event | Initial response needs a still-live event, durable commit and completed conservative decision inside a small deadline. Pending/expired events suppress the ordinal; no general-binding fallback. Reply failure does not undo accepted intake. |
| Mailbox proof could become account or historical-identity authority | Pre-account confirmation binds only the proposal and optional one-time notice. Final claim requires fresh proof bound to proposal, live incarnation and selected signing key; an old verified-email association is insufficient. |
| Recipient accepts before knowing the sender's key | Initial acceptance is tentative. Review the now-known identity/key unless prior explicit policy covers that exact binding. Draft replies remain local and visibly unsent until admission; emails never carry drafts/history. |
| Deleted/lapsed alias or reenabled bridge could revive stale authority | Public alias assignment/tombstones prevent reassignment; current entitlement and live bridge incarnation gate work. Disable invalidates external claims, and reenable does not revive them. |
| Dedup could overwrite changed content or discard legitimate recurring mail | Message-ID is not authority. Owner-scoped fingerprint and declared short replay horizon are required; trace variations, aliases and repeated legitimate content need explicit tests. No exactly-once claim. |
| Public email could consume ordinary app budget or amplify notices | Dedicated finite bridge subbudget, protective reserves, finite owner/global AI spend and outgoing-email limits. Durable response ordinals suppress ambiguous retries rather than assuming send idempotency. |
| Classification could hide destructive behavior | Fixed typed labels remain advisory input to explicit owner rules. No implicit destructive default for ordinary/authentication receipts; rule/item revisions, corrections, pins and recoverable proposed spam retention gate execution. |

No unresolved architectural contradiction was found in this design pass. The proposal deliberately narrows the requested response behavior: unsafe/disabled mail does not receive a fresh promotional response; the acceptance-specific email waits for independent mailbox confirmation and consent, even though full account creation may still be unfinished. Those constraints address concrete backscatter, spoofing and activity-disclosure risks, not platform-proven sender identity.

Remaining gates are concrete: exact trusted ingress-header provenance and rejection behavior; same-domain immediate-reply sender support distinct from system Sending; strict MIME limits and canonical retry fingerprints; mailbox/selected-key proof freshness and external-provider handoff schemas; reservation/notice crash fencing; model error/false-positive and cost measurements; owner-approved retention defaults; encrypted owner-bucket implementation and restore drills. Existing covered-work debits and prefunded service leases are nonrefundable; reservation reconciliation must never recreate spent work or resend an uncertain notice. Recheck dated platform limits/prices before implementation.

No implementation, DNS changes, mail transmission, model inference or runtime/browser tests were performed by this reviewer. Primary documentation, source inspection, independent design cross-review, local-link checks and whitespace verification are the evidence. This is an automated engineering assessment, not production verification or human approval.
