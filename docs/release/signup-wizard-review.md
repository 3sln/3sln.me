# Signup wizard — independent privacy and security review

Date: 2026-10-13. Status: independent source review complete; no remaining blocker found in the reviewed scope. Scope: the stepwise signup and pending-contact UI, its actions, private browser draft state, unchanged server activation gates, automatic phone/TV QR entry and the separately authorized targeted device-cancellation correction. This review does not authorize production accounts, deployment or outgoing verification traffic. Human signoffs remain blank.

## Independent criteria

- Each step asks for its own information. Back, locale changes and terms/privacy dialogs preserve appropriate native input state without copying passwords, email drafts or recovery answers into the shared Query or browser storage. Leaving signup clears its private draft. A new pending account cannot inherit another account's email or delivery-proof context.
- Only the final credential step submits signup. Terms acceptance is explicit and tied to the current server version. Duplicate submits, wrong codes, unavailable contact channels, cancelled passkeys and failed CAPTCHA leave an honest pending/error state rather than inventing an active session.
- Pending setup requires the real credential, verified email or delivered push proof, and recovery confirmation. UI flags and direct action dispatch cannot weaken server authorization. Local recovery decryption/testing remains a client check; server confirmation validates its own recovery token and requirements, not knowledge of private recovery answers.
- Retried requests use fresh CAPTCHA when the earlier token may have been submitted. Late async results and push messages stay bound to the current pending token/account/worker. Returning to sign-in must not silently approve an app or conversation.
- A denied storage API must not prevent memory cleanup. Only bounded presentation choices may persist as new wizard state; raw drafts stay in native fields or the private browser provider. User values render as literal values/text, not HTML, translated template source, URLs or error markup.

## Follow-up: automatic phone/TV QR entry

The user subsequently requested automatic device-request creation after CAPTCHA completes, with a spinner while proof/API work is pending and the CAPTCHA widget visible only when interaction is needed. The signup disposition above does not establish review of this later change. Independent criteria before the implementation draft:

- One explicit device-flow entry may consume one private proof and start at most one automatic create attempt. No proof, device secret or raw callback payload enters the Query, event payload, URL or storage. Readiness arriving while another action is busy must eventually be handled, without a repeated network request loop.
- Capture an entry/request identity across create, QR retrieval and polling. Cancel, navigation, reentry, expiry or account change invalidates old responses. An old result cannot replace a new QR, restore polling or establish a stale local session. Widget instance checks apply to success/expiry and do not make an old proof valid for a different CAPTCHA action.
- Missing configuration, proof expiry, failed creation or failed QR rendering produces an honest bounded state. Automatic retries must not create more requests or consume more challenges. Explicit retry starts a reviewed new entry; normal poll cadence honors server slowdown and expiry.
- Spinner/UI polish cannot bypass the phone's explicit signed-in approval, selected account or matching-code confirmation. Local cancellation is not by itself server-side rollback of an already consumed authorization; report remote success only after targeted revocation/fencing is confirmed.

The existing [device backend](../../packages/identity/device-login.mjs) separately verifies CAPTCHA/action/origin on creation, browser-bound secret authority for polling/cancellation, and recent active-account approval with the matching public code. The requested frontend behavior reuses these approval gates. The separately authorized cancellation correction below changes session issuance ordering and revocation, without weakening phone approval.

Initial draft findings sent to the frontend owner:

- Actual provider/DOM reproduction observed a readiness event on `documentElement` but zero events at the composition's `#app` listener. Bubbling cannot deliver an ancestor-origin event to its descendant. Provider readiness needs the actual root or a narrowly wired listener; the existing late push-proof path shared this topology.
- Preserve a known private device code as soon as creation succeeds, before QR retrieval, so cancellation during QR retrieval can best-effort cancel that pending request. Unknown-outcome creations remain bounded by server expiry; do not pretend local cancellation is guaranteed remote revocation.
- Invalidate the entry on leaving the flow and on offline/account context changes; clearing only an offline flag can make an old response appear current after reconnect. Clear the old public QR as well as its private polling authority.
- A live polling error must not retain `authorization_pending` with an already-past `nextPollAt`: the Query would schedule an immediate new poll after each error. Pause/terminalize the request or use bounded backoff with a cap and explicit recovery.

The final action/provider draft corrects these findings. Readiness now originates at the composition root, and its bounded retries carry only entry generation. A private one-shot proof gate prevents repeated create calls. Create, QR and poll results check entry and account-context generations, with synchronous cancellation/abort when leaving. A known device code is retained before QR retrieval. Offline and account transitions invalidate old work. Poll failure becomes interrupted rather than scheduling an immediate retry. Creation/QR/poll use bounded request timeouts; explicit retry starts a fresh entry and reports uncertainty if cancelling the prior request failed.

Independent actual-provider Happy DOM assertions passed for root event delivery, one private proof per entry, cancellation abort, retained cancellation code, reentry and absence of proof/code from event payloads. Four reviewer-owned action tests passed for one create attempt, cancellation during deferred QR retrieval, changed-account-context rejection of a deferred create, polling failure without automatic retry, and honest false-result cancellation/retry warnings. Together with the six signup checks and final release-state tests, the independent combined rerun passed 28/28. The older reviewer signup fixture needed a proof after the newly added pre-submit CAPTCHA guard; its initial timeout was a stale fixture and the corrected run passed.

The frontend owner’s final 18/18 Chrome run on build `1fcee438b80c6a9d365a` includes automatic proof-to-QR entry, proof delivery while busy, explicit retry and stale QR cancellation checks. Its actual local Worker flow obtains a QR without a second button, confirms the target remains unauthenticated before explicit signed-in phone approval and matching-code confirmation, and then verifies the resulting target session. These local Worker/browser checks cover the ordinary authorization flow; they do not claim a browser-level reproduction of every cancellation cookie race. No real Turnstile or production device session was exercised by this reviewer.

### Cancellation between request consumption and session issuance

The backend cross-review identified a real existing race: device polling consumed the request before saving its account session, while cancellation of a consumed request returned false and could not revoke the session. Frontend generation checks alone cannot undo an HTTP cookie/session already issued. The coordinator authorized a narrow backend correction, with this independent algorithm review before implementation:

1. Prepare a new session locally from one account revision, then consume the device request with the exact prepared session hash bound to its owner. Persist no plaintext session token in the request record.
2. Issuance may attempt only the original account compare-and-swap. It must never reload/retry session issuance after the consumed request; otherwise cancellation's revision fence could be bypassed.
3. Cancellation marks the request and commits removal of only its linked session hash. Even when that hash is not yet present, a durable account revision bump is required to fence a pre-save poll. Report success only after removal/fencing is proven; unknown persistence outcomes remain errors. Repeated cancellation must retry unfinished cleanup.
4. After session save, polling rereads the request. A canceled request requires targeted compensation and denial before returning a session result. Races with unrelated account updates need bounded CAS retries for cancellation/cleanup, without dropping unrelated sessions.

Independent final source review found no blocker in this narrow correction. The implementation preserves the single original issuance CAS, persists only the linked session hash/ID, bounds cancellation and cleanup retries at four, and advances the account revision even before the target session exists. Repeated cancellation retries unfinished cleanup; unknown persistence outcomes propagate as failures. Legacy consumed records without a linked hash return an honest unlinked result rather than revoking unrelated sessions. A missing account cannot be recreated by the stale issuance CAS.

The reviewer independently ran [the nine deterministic backend tests](../../tests/device-login-cancellation.test.mjs): 9/9 passed. They verify real session-token validity across both issuance orderings and a late response, bounded conflicts, ambiguous committed cleanup, expiry retry, wrong binding/origin, legacy rows, deleted accounts and concurrent unrelated sessions. The implementer's full `npm test` log was inspected: 637 passed, 0 failed (`/tmp/bindle-device-cancellation-tests.log`). These are local linearizable-CAS tests, not actual browser-cookie race or production Worker evidence. See the [backend cancellation review](device-login-cancellation-review.md) for persistence and binding lifetime limits.

The frontend must distinguish local UI closure from confirmed remote cancellation if the endpoint fails or cannot prove revocation. The final draft shows that uncertainty both on Cancel and when explicit retry cannot cancel the preceding request. A later start replaces the browser binding, so signed-in device management remains the fallback for an uncertain earlier session; request expiry alone does not revoke an issued session.
