## Scope and criteria

- `/` supplies useful landing content and ordinary sign-in, signup and documentation links in its initial HTML with JavaScript disabled. It does not boot the application engine, load account data into the page or require client rendering for its first paint. `/console` owns application boot.
- Any optional session probe is a bounded same-origin private request. It cannot cache identity responses, leak account data into public HTML/storage, follow an unexpected redirect or turn network failure into a broken landing page. A signed-in hint does not establish authorization for any subsequent API operation.
- Build-time locale generation uses the existing Bab catalogue and escapes translated values according to their HTML context. Locale routing stays same-origin, preserves intended console links, and does not depend on untrusted HTML or user profile interpolation. Server branding remains presentation only.
- Existing sign-in/signup links and validated OAuth continuations still reach the console. Query and fragment capabilities remain intact only where required for their existing consumer, then receive existing history cleanup. No newly introduced generic return URL or open redirect is acceptable. Root fragments are invisible to the server and need an explicit compatibility decision.
- Signed contact representation negotiation, MIME profile reads, device/email/recovery/MCP/Google callback routes and security headers retain their existing behavior at their original public URLs. Recovery retains its stricter script/frame policy. Worker and Node asset routing agree without following arbitrary asset redirects.
- The PWA retains installation identity while starting in the console. Offline landing and console documents are pinned to the same complete build generation; neither live private responses nor capability-bearing query routes enter Cache Storage. Old waiting-worker generations remain usable until their tabs release them.

## Shared-handle sign-in follow-up

The user also requested one shared handle input with explicit passkey and password actions, replacing redundant method tabs. The current provider password/passkey APIs accept local normalized handles; this slice retains that contract and displays the configured host beside the bare handle rather than adding federation or rewriting foreign identities. Bare-handle qualification must use the configured provider host and must not silently strip a foreign authority or transmit credentials to a discovered foreign host. Verified-email sign-in remains its separate existing flow. Progressive password entry must retain the intended handle, keep passwords in native/private submission state, and preserve passkey cancellation/error retry behavior. Existing server validation remains authoritative. Independent actual-Dodo/BrowserProvider DOM checks passed for one shared handle, the configured self-host hint, retention of the same native handle node/value across method changes, removal of the password field on switching back, rejection of qualified foreign/email inputs by the local-handle pattern, and bounded Spanish route selection. The separate email-login action remains available when configured.
