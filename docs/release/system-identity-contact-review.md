## Protected identities and bootstrap

Reserved internal handles must be protected in every allocation/claim path, including paid aliases, legacy local signup, rename, import and restore. Ordinary users must not create a trusted badge by spelling a protected handle or supplying profile metadata. The badge must derive from server-held bootstrap provenance tied to the exact UUID and assignment. Conflicting existing aliases require an explicit migration decision; bootstrap cannot silently reassign a permanent namespace owner or turn an ordinary account into a system identity. Deletion retains namespace tombstones. Imported documents cannot self-assert host system authority.

Bootstrap should be a generic operator capability, not a hardcoded Ray exception. Its one-use secret must be generated and stored through a private operator workflow, never printed in tool transcripts, placed in a URL, logged, cached by the PWA or retained in browser Query/storage. An atomic durable claim must fence concurrent uses and survive process restart. A crash after reservation must permit recovery of the same intended pending identity rather than allocate another system account or consume the capability into an unrecoverable dead end. Invalid, expired or replayed authority fails closed. Exact-origin/setup-browser binding and bounded request/admission work still apply.

The operator capability authorizes the protected identity assignment; it does not replace primary credential, verified contact, terms or tested recovery requirements. Pending bootstrap accounts cannot use active-account APIs or issue account sessions. Ordinary credential/recovery resume must preserve the same protected assignment without reopening arbitrary bootstrap authority. Authority shown to users must remain distinct from display text and never imply cross-provider trust merely because another host uses the same handle.

## Daily request policy: latest user instruction

The user replaced persistent/automatic connections with an explicit daily contact-token request, and then explicitly removed eligibility-loss revocation. Eligibility is checked only at authenticated issuance. The granted bearer remains valid until its ordinary expiry despite later payment or population changes; recipient manual revocation, quarantine and normal contact limits remain. Earlier receipt-time paid checks, policy epochs, beneficiary identity proof and anti-resurrection machinery are therefore superseded requirements, not implementation gates.

The intended threshold is below 1,500 active accounts versus at/above 1,500, with the active definition still awaiting the user. Active population must not be inferred from lifetime admissions or a missing registry initialized to zero. A bounded trusted population snapshot may govern issuance, with original expiry preserved across cache layers and documented propagation delay. It must not add a global per-message hot path. The current paid entitlement is checked only for new restricted-mode issuance; provisional upgrades, past-due grace and paid-name history do not establish eligibility.

The proposal explicitly accepts bearer delegation without a sender identity claim. A token must not cause the recipient to see the beneficiary's badge as proof of authorship. Only the configured recipient collection and plain/HTML text scopes are granted; ordinary sanitization, replay and rate/storage guards remain.

## Current proposal and interface checkpoint

At the coordinator's request this reviewer authored [the architecture proposal](../architecture/system-identities-contact.md); it needs another agent's cross-review before final design disposition. The owner-authenticated/CSRF-protected daily request takes only a request ID, returns a bounded URL or clear refusal, and never issues during general polling. One parent per beneficiary/UTC day/verified tier (at most four tiers) and deterministic request reconciliation prevent duplicate issuance across changed IDs or lost responses. Expiry is next UTC midnight, optionally bounded earlier by paid-through evidence; the console must show the exact timestamp. A same-day authorized replay retrieves the existing URL without extending it. Manual revocation cannot trigger silent recreation.

The generic contact implementation currently caps all retained parents at 1,000, including expired/revoked grants. Daily requests need bounded cleanup of expired internally tagged parents and side records before permanent exhaustion can be avoided. Existing messages, replay retention and ordinary recipient-created contacts must be preserved. No unbounded quota increase is proposed. Final daily limits, authoritative population definition/baseline, destination identity and bootstrap behavior remain implementation/review gates.

The latest tag refinement replaces separate priority collections. The proposal adds immutable required/optional tag policy to ordinary contacts: the server always applies required tags, validates a sender-selected subset, and preserves the resulting original endorsed delivery tags for bounded owner-rule matching. Existing unrestricted sender annotations remain untrusted for legacy grants. Server-verified issuance tier selects the required priority tag; higher-priority tags cannot enter lower-tier selectable options. Token collection scope remains an independent boundary. A same-day upgrade can issue one new parent for the new tier, while older daily grants retain their original tag scope and expiry. Exact endpoint/inbox inheritance, selection fingerprints, validation before blob writes, immutable original rule inputs and localized literal choice labels require implementation/interoperability tests.

## Optional active-population implementation review

Reviewed the portable population authority, Worker/Node adapters, owner touch/alarm integration and [active-population design](../architecture/active-population.md). The implementation uses a rolling authenticated-use interpretation, conservatively rounded to UTC days, rather than treating lifetime admissions as active users. Initial census completion and matching shard generations are required for a usable snapshot. The policy cache retains its original 60-second expiry; shard loss, malformed state and clock rollback yield unavailable. Recent suspended/deleted owners may remain conservatively counted until expiry, as documented. Product agreement on this definition and a production baseline remain unsigned gates.

The review found that catching rejected population RPCs did not bound a never-settling RPC: foreground owner use could hang on optional analytics. The implementation now bounds touch to 250 ms and best-effort invalidation to a further 100 ms. The pending timestamp is durable before the source call; only acknowledgement confirms the day. Timeout does not pretend to cancel a possibly committed touch, and retries remain idempotent. Another regression covers preserving a future retry when an earlier unrelated alarm fires. Independent focused rerun: **11/11 passed**, `/tmp/bindle-population-independent.log`, including never-resolving source and invalidation ports. No remaining blocker found in this narrow optional-accounting boundary.

The source is explicitly an eventually reconciled growth-policy metric, not a hard global authorization ceiling: a partition blocking both activity and invalidation can leave the remote count behind until repair. This limitation is stated without making login, read or recovery wait for analytics success. Policy lookup is an issuance concern, never a per-message population lookup.
