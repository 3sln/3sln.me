# Self-host fixed-name onboarding: independent review

Date: 2026-10-14. Independent design and local implementation checkpoint; no production provisioning, mail, runtime edits or browser builds performed by this review. Human decision is blank.

## Scope and existing boundary

The proposed ordinary onboarding lane uses separate enablement, key, configured names and `bo1` token purpose. It authorizes pending identities for explicitly listed ordinary names while public signup may remain closed. Existing account login and recovery must remain available. Each name has a preassigned stable owner UUID and immutable assignment UUID; a verified operator issuance operation reserves namespace entries before a usable private invitation is returned.

This is distinct from the implemented [system invitation](../architecture/system-bootstrap-operations.md) and [system bootstrap token](../../packages/identity/system-bootstrap.mjs). The existing `bs1` purpose accepts reserved handles and binds a system/developer marker. Reusing that marker, admission selector or reserved-name validation for ordinary invitations would grant the wrong identity semantics. An ordinary onboarding alias must not imply a system badge, administrator authority, subscription entitlement or exemption from contact/credential/recovery activation gates.

## Required authority semantics

- **Bearer scope is explicit.** A shared invitation containing several names lets every holder attempt every listed name. A list is not evidence that a particular person owns one name. If the operator needs person-specific entitlement, issue separate invitations or add an independently verified per-name recipient binding; do not infer it from typed display names or email.
- **Issuance and claiming are different purposes.** A separate short-lived operator issuance proof can register/reserve the exact invitation digest and names. A `bo1` holder cannot call issuance, change the list, extend expiry, substitute owner/assignment IDs, mint another token or select internal account kinds. Public `signupPlan` must never reach the operator lane.
- **Namespace precedes usable authority.** All configured ordinary onboarding names must be unavailable to competing public/paid alias claims before issuance, through a common fail-closed canonical predicate or an explicit safe enabling procedure. Once issued, durable reservations and tombstones survive configuration removal, expiry and restart. A later invitation cannot overwrite a paid alias, existing identity or permanent assignment.
- **Each name is consumed atomically.** Namespace claim binds token digest, exact name, owner/assignment and setup-browser binding. Two holders racing the same name cannot create two identities or get credentials for the winner. Other names in the same token retain independent state. Partial multi-name issuance stays unusable until all reservations are confirmed; resumption uses identical immutable claims and never recycles uncertain reservations.
- **Capacity is durable and narrowly selected.** The operator lane consumes the overall admission cap according to explicit policy. It does not silently become free-origin, paid or system admission. Deduplicate capacity by the verified per-name operation/assignment, not merely the shared token nonce, so one token with multiple names cannot charge once for many identities or charge repeatedly on retries.
- **Activation remains real.** Terms, primary credential, configured verified contact, recovery generation/download/test and any existing first-activation restrictions remain required. A name reservation is neither an active identity nor email verification. Ordinary account recovery after legitimate activation does not require reusing the original invitation.

## Interrupted setup and recovery

Before account creation, an identical invitation and matching browser binding may resume its already reserved name, subject to live expiry and issuance state. Credential work and namespace/account creation cross durable boundaries: recheck expiry and exact reservation immediately before account creation, retain uncertain results and never allocate a different owner UUID to retry a lost response.

After an account exists, the invitation must not return a new pending/setup credential or replace its primary credential. Password-based setup may resume through the credential just established; a passkey ceremony that failed before registration or a lost browser binding may need explicit operator reconciliation. Describe that limitation instead of treating possession of a multi-name link as permanent recovery authority. A claimed-name inspection response must not expose private email, credential IDs, recovery state or secret setup authority.

## Secret-link and browser handling

The user's requested `/token-onboarding/<token>` form puts a bearer capability into an HTTP path. `Referrer-Policy: no-referrer`, no-store responses, noindex metadata and immediate address replacement reduce later exposure, but cannot remove the original path from reverse-proxy/CDN access logs, browser history or copied links. Application logs must redact the segment; infrastructure retention/redaction is an operator responsibility and residual exposure must be documented.

A `/token-onboarding#<token>` entry is preferable where accepted: fragments are not sent in HTTP requests. Capture the token into private transient browser state and scrub the address before analytics, third-party widgets, dynamic imports or navigation. Neither form may persist it in Query state, local storage, ordinary preferences, service-worker caches, error telemetry or screenshots. The link contains no account password or recovery private key.

GET/HEAD must serve an inert shell; link previews and mail scanners cannot reserve a name, consume stock, create an account or approve terms. Explicit same-origin POST begin establishes browser binding; scoped inspection is read-only; deliberate selected-name claim is a separate action. Keep exact Origin/CSRF policy, rate and size limits, token purpose/issuer/expiry verification and issued-ledger checks. Login or signup success alone must not consume another available name. Back, cancel, sign-out and account changes clear private invitation state and fence late responses.

Closed public signup must remain closed through the ordinary public endpoint even when a private invitation is open. Conversely the generic public-signup-disabled UI guard must not prevent the explicitly authorized private flow. The user should see only token-authorized available names and a clear unavailable/expired/used state; disabling a button is not the server's name claim check.

## Implementation review

Independent review found two concrete issues. The frontend initially accepted a late claim response into private pending state after the invitation was cancelled or another account became current; late errors could also clear the replacement session. The author added invitation token/name/mode/account-generation fences before installing pending authority and before subsequent passkey/email/recovery actions. [Independent state regressions](../../tests/browser/onboarding-audit.mjs) pass **3/3**, including suppression of inspection after a cancelled begin. A paid plan query parameter is also excluded from this ordinary invited lane.

The backend's initial configured-name check used raw paid-handle input before lowercase normalization. [Independent durable tests](../../tests/onboarding-audit.test.mjs) reproduced a successful paid `ALICE` claim against configured `alice` before invitation issuance. The author corrected this through the shared canonical host policy in service and repository. The strengthened test removes the onboarding port and disables issuance; the configured name remains protected. All **5/5** independent tests now pass: the namespace regression; interrupted issuance remains unusable until the same reservations finish; two names consume two overall admissions while a lost debit acknowledgment does not duplicate one and missing acknowledged receipts fail closed; ordinary markers cannot be changed into system metadata and invitation replay cannot mint another pending authority while the established password can resume setup; and issuance/invitation/public-signup purposes remain separate. The tests use local SQLite and controlled credential/authentication collaborators, not external account creation.

The latest user direction narrows configurable badges to local app UI and makes badge IDs a mutable trusted identity-record property. Earlier suggestions for issuer-labelled/cross-provider metadata, name-to-badge mappings or eligibility tied to immutable assignment markers are superseded. The embedder now supplies code-owned definitions `{id,name,description,svg}`, with SVG compiled into a constrained sprite; host name policy contains only version/reserved/onboarding. An optional injected `resolveIdentityBadges` hook defaults to the trusted record's badge IDs and must be bounded and failure-isolated. Operator-signed invitation fields may initialize per-name IDs; future trusted database/admin edits may change them. Public signup/profile/recovery inputs must not set them. Labels confer no admin/system authorization or portable identity assertion and do not alter immutable name assignments. Identity/resolver responses can select known IDs but cannot supply markup, SVG, styles or remote asset URLs. The final compiler must reject active/external SVG features and bound its output. These replace intermediate policy-definition interfaces; the final compiler and projection assessment is recorded below.

Explicit host policy can replace default reserved/onboardable name lists, while ordinary onboarding alias validation remains syntax-only so existing assignments survive later policy edits. Paid claims must check canonical host policy independently of onboarding enablement. Removing a configured reservation must not free an already assigned or issued namespace entry. Optional badge failures must preserve configuration reads, login and recovery while namespace/issuance remain fail-closed. The earlier `/api/config` direct strict-policy projection reproduced a 503 initialization failure; the separated badge definition path now passes an independent regression for graceful optional projection.

## Final source checkpoint

No remaining structural blocker was found in the reviewed ordinary invitation, namespace, private browser flow, local badge compiler or injected resolver source. Earlier counts above document the finding/fix sequence; the final independent onboarding suite passes **8/8**. Its additional checks cover malformed optional badge configuration without blocking `/api/config`, a throwing or stalled badge resolver without breaking credential-based setup resumption, and an explicitly permitted formerly reserved ordinary name whose assignment survives later policy removal. Resolver input is a frozen minimal descriptor with frozen alias/ID arrays; no password hashes, session tokens or private contact data are passed. The 500 ms asynchronous deadline bounds waiting on a promise; it cannot preempt a synchronously blocking trusted embedder function. Resolver IDs are presentation only, filtered against current known definitions.

The final [compiler](../../packages/identity/badge-policy.mjs) reconstructs SVG from bounded primitive shapes and validated geometry. It refuses scripts, events, styles, animation, external references, arbitrary IDs, media, foreign namespaces and unsupported elements instead of silently accepting active markup. The one-entry exact-content cache avoids repeated parsing/digest computation for unchanged definitions, detects in-place configuration edits and returns frozen compiled records. Invalid replacement configuration cannot inherit the previous configuration's badge IDs or sprite. Input and output are bounded at 256 KiB and 512 KiB respectively. The final independent policy rerun passes **7/7**, including the cache mutation/immutability regression.

The [sprite HTTP tests](../../tests/badge-sprite-http.test.mjs) were independently rerun **2/2**: exact versioned digest URLs, GET/HEAD/conditional caching, invalid configuration and public metadata boundaries. Source review confirms `nosniff`, no-referrer, same-origin resource policy and restrictive SVG CSP; no identity lookup is necessary to retrieve the shared sprite. `/api/config` exposes only the sprite path and definition IDs/names/descriptions, never SVG source, private name allowlists or resolver input. Malformed badge definitions disable this optional presentation while login/configuration remain usable; namespace/issuance validation remains strict. The author separately reports a Chromium fixture rendering the final CSP-protected external symbol, with positive geometry and visible pixels; this reviewer did not independently rerun that browser fixture.

The [independent browser state regressions](../../tests/browser/onboarding-audit.mjs) pass **3/3**. A combined rerun with the local badge DOM fixture passed **4/4**, checking literal badge presentation as well as stale invitation cancellation. These are controlled state/DOM tests, not production browser onboarding. The previously started full core suite completed **825/825** at its local checkpoint; the coordinator owns the final integrated suite after subsequent source/test freezes, so this number does not claim coverage of later changes.

The CLI source uses private, bounded, owner-checked regular files, exclusive `0600` output and no secret stdout. It emits the usable fragment link only after exact bounded issuance acknowledgement. Lost acknowledgement or output failure leaves the same preparation available for explicit idempotent retry; it does not release names or mint replacement identities. The implemented entry is `/token-onboarding#token=…`, captured and scrubbed before application imports. The earlier path-token discussion is a threat analysis, not a claim that a path capability route was implemented. A shared multi-name link still delegates every listed name to its holders; operators needing person-specific allocation must issue separate scopes.

Remaining release checks belong to the coordinator/operator: final integrated Node/Worker/browser runs, deployed configuration and private key custody, log/referrer policy at the actual host, and any real contact-delivery verification. No production deployment, mail delivery, external account provisioning or human approval is asserted here.
