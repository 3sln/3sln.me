# Federation completion review

Date: 2026-10-12. Reviewer: independent security/architecture agent. Human reviewer/date/outcome: **pending**. This records source review and local reproductions, not production conformance or release approval.

## Initial integration boundary

The repository already contains `FederationService`, a portable controller and HTTP handler, schema validation/pinning, a separate 3sln-stack consent interface, and an account storage-operation dispatcher. These constitute meaningful domain implementation and fixture coverage. At the start of this review, shared HTTP instead returns the explicit unavailable federation manifest; the Worker federation object is not connected to the primary adapter and still references the old identity directory; Node has no completed federation composition. The public SDK parses/discovers identities and emits login intent, but lacks the complete relying-party PKCE/state/callback transaction.

Completion requires connecting real durable identity, preference/grant and resource state through both adapters, exposing authenticated owner management and registered-client endpoints, integrating consent with generated assets/CSP, and verifying a separate relying-party browser flow. An enabled flag or fixture dispatcher is not evidence of this boundary.

## HTML and archive boundary

The existing renderer reconstructs allowlisted inert tags with **no attributes**, returns a document with restrictive CSP, and renders it in an iframe with an empty `sandbox` attribute and `no-referrer`. This is an implemented defensive boundary, while richer web-archive rendering is incomplete: embedded archive assets are validated but not reconstructed for display.

Native `setHTML` sanitation would not replace the iframe's origin, navigation and network isolation. Do not insert richer untrusted message HTML into the portal DOM or add `allow-scripts`/`allow-same-origin`. If richer archives are implemented, retain the opaque-origin sandbox and no scripts/forms/top-navigation/network, bind image references only to bounded validated local archive bytes, and reject SVG, remote URLs and CSS URL loading. Any browser-native sanitation is an additional check with a safe fallback, never an implicit switch to an unsafe HTML API. Actual-browser regression must cover event handlers, malformed markup, nested documents, forms, navigation and network requests.

The current primary reference is the [WHATWG HTML parsing and Sanitizer API specification](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html): its safe methods remove script-capable markup regardless of configuration. The former WICG draft now directs implementers to WHATWG. This supports using safe sanitation as one layer; maintaining independent sandbox/network restrictions is this review's application-security recommendation.

### Native composition and scope findings

The factory uses the real sharded identity repository, projects connected native storage resources without their secrets, and supplies an assignment/recovery epoch plus app-connection generation. Node and Worker now have composition code. The following findings were sent to their implementation owners and subsequently corrected:

- A read-only routing probe originally produced **zero owner lookups and one arbitrary shard allocation**. After the fix, the same probe produces **one owner lookup and zero shard allocations**. The native suite also checks fake cookie and other opaque-locator routes.
- Native app binding originally passed `{id,generation}` where a numeric compare-and-set generation was required. The adapter now passes the generation from the stored trusted binding; first native consent passes.
- The dedicated native app registration path now records Bindle transport/provenance. The native test asserts the returned app transport. Configured client-name and ID bounds now match the native connection store, preventing late failure after consent.
- Consent inspection now authenticates before fetching the app binding or warming resources, closing the forged-cookie restoration path.
- The shared account dispatcher applies the federation epoch requirement only to explicit trusted internal Bindle contexts, preserving the existing MCP/browser invocation path. Bindle contexts require epoch, connection and the native check capability.
- Scope is now bound across admission, dispatch reauthorization, journal fingerprints and native enforcement. Reauthorization requires the captured scope; changing scope permanently removes old grant assignments. Domain and native tests now explicitly restore the original scope and still require new consent.
- The initial resource descriptor repeated the main access bearer. It has now been replaced with a child token bound to the parent, fragment, field, resource, scope and generation, with a subset of grant IDs and inherited expiry/account epoch/connection. Source review confirms that child tokens cannot read preferences or address a different resolved resource, including alias resolution. Broader sibling-field and native end-to-end regressions remain part of verification.
- Mutation journal admission is now capped at 256 live records with expiry cleanup and fingerprints bind scope, account epoch, resource generation and connection generation. Native account journals now also cap admission, expire retained entries and bind the native authority context. Current native checks execute before replay.

Federation token admission calls the account connection checker while holding a federation metadata transaction. An account dispatcher must therefore not call back into that federation token path while holding its own serial gate: the resulting account → federation → account dependency can deadlock. Native final checks should use local account connection/resource state and independent identity authority. An operation admitted before a grant revocation may finish; subsequent admission and replay must fail. Stronger atomic revocation of already admitted remote effects requires a separately designed protocol.

## Registration and public discovery policy

The current authentication profile requires registered clients and exact redirects; it does not require open dynamic registration. A verified configured registry can implement that profile, but must not be described as automatic registration or arbitrary remote schema discovery.

Self-service registration would need bounded durable metadata, exact HTTPS client-document identity and same-origin redirect policy, pinned metadata at consent, and a verified public-fetch capability for remote documents. The existing Node metadata fetcher pins validated public DNS results at the actual HTTPS dial and preserves TLS hostname verification. Its budgets must remain shared, not reset by creating one fetcher per request. Worker has no equivalent verified arbitrary-host egress in the initial implementation; DNS preflight followed by ordinary fetch is not equivalent to connection-time pinning. Browser-submitted schema JSON does not establish that its purported publisher controls the schema URL. Keep unavailable egress fail-closed or use a reviewed service binding rather than introducing ambient fetch.

The coordinator selected a curated-app implementation profile: reviewed exact client/fragment configuration, with open self-service registration deferred until a safe egress design is reviewed. The coordinator also selected explicit owner-targeted public authorization: mapping a handle to a UUID-prefixed request can reveal account existence and the stable subject. Host-level discovery remains separate and non-enumerating; targeted authorization must not be described that way. Public IP, subnet and sharded service budgets are present in the shared HTTP integration; their production capacity and resistance to targeted pending-request exhaustion still need operational verification. Missing identities must not create federation objects. These are provisional design decisions, not fabricated human security sign-off.

### Additional D067 reconciliation

A further cross-review identified incomplete D067 semantics in the earlier implementation: returning the backing resource URI and scope was not an opaque resolved reference; selecting a subset of a multi-resource field hid approved members; and a shared save did not bind/update the exact reviewed consumers. These have now been corrected in source and included in the latest 36-check run.

Parent URI, private prefix and scope configuration now remain inside provider state. Public resource locators and child tokens derive using a provider-private random field incarnation; knowing the parent bearer no longer permits offline scope guesses. Missing legacy incarnations initialize atomically before projection, and child tokens with invalid incarnations fail closed. Tokens bind a resolved public reference without making that reference a credential. Different consumers share the same field reference but receive separate tokens. Changes rotate the incarnation; old references/tokens do not regain access when old values are restored.

Child operations validate relative keys before mapping them to the private prefix. Responses restore relative object keys, including replay. Journals bind both private target and addressed public reference. Native adapters enforce scope before replay/effects. Prefix- or byte-constrained assignments deny presigning. The explicit whole-resource read-presign capability remains an exception: an approved URL reveals its storage address and can remain usable until expiry. It requires clear consent disclosure and is not represented as revocable private-reference projection. Remote range reads with a maximum-object-size constraint are disabled before I/O until the connector verifies total object size; hosted ranges retain verified full-object sizing.

Native saves require the displayed preference revision. Explicit shared updates additionally compare a digest of reviewed consumer records and apply the update atomically. The snapshot checks current grant status, retained assignment, account epoch and app-connection generation. Revoked, disconnected and wholly pruned consumers are excluded; existing consumers retain their approved method ceilings. No default save broadens a resource grant. Tests cover a stale consumer digest after revocation, separate consumer tokens, restored values with fresh references, read-only enforcement and unchanged per-app method ceilings. Old generation/scope maps are pruned so repeated replacements do not grow grant metadata indefinitely.

The coordinator resolved the scope-disabled consumer edge under D079: the review lists live assigned field subscriptions, including a retained method ceiling temporarily disabled by the shared scope. A put-only subscription under a read-only scope has no executable write authority. A later explicit revision-and-consumer-digest-reviewed shared save may re-enable that already approved method. Revoked or disconnected grants and removed assignments remain excluded. This is a provisional design decision, not human security sign-off.

## Rotating session renewal cross-review

The extension keeps the five-minute access limit and adds an eight-hour absolute refresh family. Server state stores hashes of the current and spent refresh secrets, with one-use atomic rotation, at most 128 history entries per family and 32 live families per account. Reuse revocation commits before the error is returned; parent and child-token admission both check the family. Issuer, client, subject, identity epoch, app-connection generation and original grant membership remain bound. Renewal does not perform new consent or create new grants.

The SDK keeps the rotating credential in memory, coalesces concurrent renewal and uses an SDK-owned cancellation controller so one caller cannot abort another caller's shared refresh. Sign-out/login generations prevent late session resurrection. An ambiguous renewal failure discards the old secret rather than retrying a possibly spent credential. Existing resource references are renewed by reading their recorded fragment and matching the same opaque resource ID; changed assignments require a new application read rather than silently retargeting a mutation.

Independent review requested corrections for owner isolation during family pruning, zero-second access issuance near expiry, stale-family access-state cleanup, complete family/token binding, network-delay handling of the client deadline, and orphan refresh histories during cleanup. All six corrections are present in source. The SDK derives conservative local deadlines from request start and clamps renewals to the original absolute deadline. Cleanup retains revoked-family metadata until expiry or admission-time pruning can remove its complete history.

A separate executable schema probe found valid scalar field names `constructor`, `toString` and `valueOf` rejected at approval because omitted resource/method maps inherited JavaScript object properties; `prototype` succeeded. Consent selection maps also reused inherited functions when initializing resource selections. Source corrections use own-property handling for persisted optional maps and null-prototype maps for mutable consent selections, retaining the supported field-name grammar. Independent domain tests now cover the scalar names and resource `constructor` alongside a scalar-only grant after persistence. The real-stack DOM regression covers missing optional values, unsupported method labels, resource/method deselection without mutating inherited objects, typed configuration with revision checks and subsequent approval.

Final independent focused execution: **59/59 passed** across SDK, federation domain/runtime, real-stack consent DOM and native Node tests. These include coalescing and cancellation, ambiguous-failure disposal, grant expansion rejection, delayed responses, exact-reference child renewal, rotation races, parent/child reuse revocation, recovery/disconnect rejection, absolute expiry, history and family bounds, orphan cleanup, removed-grant narrowing and isolation between subjects in generic storage. The additional native profile test verifies explicit profile-resource consent, name/avatar preview and reading, and omission of unrelated biography/email fields; preview text does not fetch the avatar URL. Worker cleanup source now retains a private owner locator for alarms and only deletes bounded expiring authorization/journal state, preserving permanent preferences. These local results do not substitute for actual Worker/browser renewal evidence or production approval.

## Follow-up: unchanged shared fields must preserve selected subsets

The coordinator identified a further authorization widening path after that check run. An independent executable reproduction configured resources `[A, B]`, approved only `A` for an app, and then changed only a scalar preference with a valid shared-update revision and consumer digest. The app's projected resources increased from one to two, and its grant gained `B`. A shared save must only authorize widening for a resource field whose assignment actually changed; unrelated or no-op edits must preserve its previously selected subset.

The first correction compared raw resource-field values. A second executable reproduction showed that a harmless `[B, A]` → `[A, B]` catalog ordering change still expanded the approved subset from one resource to two. The final correction compares sorted resource IDs and normalized effective scopes. Unchanged permissions preserve the approved subset and original selection snapshot; an actual reviewed assignment or scope change retains the intended shared-update behavior. Equivalent ordering, bare URI/empty scope, explicit false defaults and one optional trailing prefix slash also preserve the field incarnation and child credentials. Removed resources and changed scopes still narrow unreviewed grants.

Scope normalization now validates the prefix with the same logical object-key rules after removing one optional trailing slash. Repeated separators, encoded traversal and invalid byte lengths fail closed rather than becoming valid paths through repeated normalization. Source review confirms normalized scope comparisons at projection, consumer review, admission and dispatch reauthorization.

Final follow-up verification: **62/62 passed** across the combined SDK, federation domain/runtime, real-stack consent DOM and native Node suite. New regressions assert that scalar edits and equivalent resource serialization preserve `resources`/`approvedResources`, retain the original `assignedResources` snapshot, keep the approved child stable and leave unselected resource `B` forbidden. Invalid-prefix regressions and existing actual shared-scope changes also pass. This closes the reproduced widening findings; no remaining implementation blocker was identified in this focused review.

Node's cleanup wrapper invokes methods with the underlying controller as receiver and schedules bounded cleanup through the existing atomic SQLite alarm mechanism. It does not change synchronous internal readiness checks. After a Node process restart, a shard's persisted alarm resumes when that owner shard is opened; this is not a fleet-wide expiry sweep. ## Default storage and optional fields follow-up

The user requested built-in object storage for every account, using the existing shared storage allowance. Source review confirms quota accounting already combines inbox message bytes with account-wide hosted-object bytes and pending growth reservations. A default descriptor must not create a separate allowance, reset usage, generate identity keys or create a second resource on cold return.

Review requested atomic owner/pointer/descriptor binding, strict pointer-to-record ID equality, bounded duplicate detection before repair, owner checks before archive reads or mutations, permanent protection from disconnect, and preservation of the UUID through shelving. These corrections are now present in source. The archive writer previously allowed 2,000 message rows plus resource rows while its reader rejected more than 2,000 combined rows; the reader now accepts the bounded 2,200-row writer maximum. Existing accounts at the resource limit must migrate without trapping owners in a warm failure before they can remove resources.

Independent execution passed **35/35** built-in storage, federation domain and native Node checks. The four new storage checks cover concurrent initialization without signing/encryption keys, restart and cold restoration with the same UUID, corrupted-pointer and wrong-owner rejection, protected deletion, and quota sharing/deletion release. An independent executable optional-field probe passed for an already configured empty fragment: absent `min: 0` scalar and multi-resource fields can be approved and initially project no values. ## Uniform presigned object access: implementation review

The new request extends presigning to native provider URLs or constrained proxy URLs. The prior presign limitations above describe the earlier implementation and must not be treated as verification of this extension. A proxy capability must bind one operation and logical key, use at most the remaining child/access/family lifetime capped at five minutes, and recheck current identity, family, connection, grant, assignment incarnation and resource generation on redemption and replay. Issuing it requires both `presign` and the relevant read/write operation in the same child field. Public URL material must not contain a broader bearer or the private backing key/prefix.

The implementation uses bounded canonical proof verification before shard allocation, no ambient cookie authority, no-store responses, and inert attachment delivery for arbitrary object bytes. Writes require bounded exact size, declared content type and a conditional precondition, with durable one-use reservation, payload-bound idempotency and indeterminate-outcome handling. Private records retain the originating child-token hash rather than its bearer. Native URLs remain explicitly expiry-only revocable and are selected only after bounded full-object preflight supplies a stable version; the returned URL must require the exact version and requested range headers. Prefix- or byte-constrained assignments use the proxy. Native URLs cached for mint replay are encrypted in private metadata.

The first independent implementation check passed **4/4** signer and HTTP tests. The provider HMAC binds issuer, owner, opaque object-URL ID, operation and expiry; canonical URL and base64 checks reject alternate representations. Invalid proofs fail before identity lookup or shard allocation. Upload admission precedes body reads and enforces exact size, content type and conditional headers. Downloads use an attachment with an inert content type, sandbox CSP and no-store headers; URL possession supplies authority without cookies. Native S3 tests verify that its signature requires the version and range headers; this is local signing evidence, not live-provider conformance.

An independent combined signer/native Node run passed **12/12**: eight tests in `tests/federation-native.test.mjs` and four in `tests/object-urls.test.mjs`. That run includes the actual scoped proxy HTTP upload/download path, exact-body replay, restart, grant revocation and denial when `presign` lacks the underlying operation. Source review found and confirmed corrections for large-byte spread encoding, omitted upload conditional headers, mint-time key validation and exact native range-header validation. A subsequent injected-clock probe reproduced a dispatch guard gap: a one-second URL passed admission, expired during the internal RPC resource synchronization, then still performed a read because the final guard checked only the longer-lived child token. The added internal `beforeEffect` guard revalidates the URL row, its shorter deadline and its original same-field authority. Re-running that exact probe after the correction returned `unauthorized` with zero storage effects. The 12-test run predates this final guard correction; the separate repeated clock probe is its independent executable evidence.

The implemented object size ceiling remains 1 MiB. Proxy range reads fetch the bounded full object before slicing, so the full-object size bound applies. URLs expire no later than the originating child access token and are capped at five minutes; refresh does not extend an existing URL. Proxy write replay requires the identical payload and still-live authority. An uncertain write is not automatically repeated. URL/mint records are capped at 256 each and participate in expiry cleanup. This does not add native S3 write support: read-only connectors remain read-only, while writable hosted/Drive resources use the conditional proxy write path. No live S3, WebDAV or Drive service was exercised in this independent review.

The coordinator clarified that the requested read-only delegation is the fixed operation of an object URL: this extension adds no resource-token attenuation endpoint. A read URL must never authorize a write, even when its source resource token has both permissions. For any future resource-token delegation helper, SDK renewal must not replace a restricted reference with a broader fresh reference just because its resource ID matches; restrictions must be preserved or reapplied explicitly. The current SDK only renews references obtained directly through its preference reader. Native provider CORS behavior is also distinct from URL validity and must be verified or disclosed before claiming uniform browser fetch support.

Actual Worker and separate-origin browser evidence, full-suite reconciliation and production operational checks remain pending at this review point. Required final boundaries include wrong issuer/state/PKCE, code replay/expiry, optional/required consent, assignment removal and non-revival, account suspension/deletion/recovery, app reconnect generation, revoked-token reads and mutation replay, resource ownership, malformed/oversized requests, public admission limits, and strict consent/HTML CSP. All production claims remain gated.

## Distributed-name discovery: interoperability review

**Superseded by user deferral, 2026-10-12.** The proposed feature was removed from the SDK and release scope after subsequent live review found gateway retirement and unresolved availability. This section records the earlier source review only. See [live interoperability observations](distributed-discovery-interop.md) and DEVLOG.md D083; ordinary HTTPS discovery remains the supported path.

Cloudflare lists its DWeb Resolver as deprecated from July 1, 2025; the retired endpoint must not be a new runtime dependency. Kubo documents replacement DNSLink resolvers for `.eth` and `.crypto`. These resolve DNSLink locations, not an invented `_bindle` TXT convention. A custom Bindle TXT profile can be a separate explicit integration, but does not substitute for ENS interoperability. Sources: [Cloudflare deprecations](https://developers.cloudflare.com/fundamentals/api/reference/deprecations/), [Kubo release notes](https://github.com/ipfs/kubo/blob/master/docs/changelogs/v0.33.md).

The proposed SDK shape selects a resolver profile by hostname suffix, requests only `_dnslink.<hostname>` without the username, and retrieves a bounded public manifest through a configured HTTPS gateway. Standard DNSLink publishes TXT records whose value identifies IPFS or IPNS content. The current implementation deliberately supports the `/ipfs/<CID>/<optional-path>` subset; IPNS recursion, other decentralized storage protocols and independent ENS-chain verification are outside this profile. Existing ordinary DNS/HTTPS manifest discovery remains unchanged, including its direct issuer-origin check; selecting a distributed profile must never silently switch to email fallback. [DNSLink specification overview](https://docs.ipfs.tech/concepts/dnslink/).

Source review confirms separate `identity` and `requestIdentity` values: the entered alias is retained for display, while the authorization request uses the unchanged username at the declared canonical issuer host. The public DNSLink manifest is the explicit delegation boundary. All OAuth/RPC endpoints, pending login state, callback issuer and token issuer still bind to that canonical HTTPS origin. The login UI should show the alias and resolved provider origin before redirecting. Resolver and gateway requests carry no cookies, authorization bearer, code, verifier or username; no new server-side fetch endpoint is required.

CID parsing converts CIDv0 to CIDv1 for a CID-isolated subdomain gateway. Parsing a CID is not verification that downloaded manifest bytes match its DAG/content root: this browser profile trusts the configured resolver and gateway over TLS. It must not claim trustless CID verification. Subdomain gateways provide the intended per-content origin separation; this is distinct from ordinary shared path gateways. [IPFS gateway guidance](https://docs.ipfs.tech/concepts/ipfs-gateway/).

The documented maintained ENS resolver response uses a string status, lowercase `ttl`, and unquoted TXT content; the parser accommodates these variants. Final source review confirms bounded concatenation of quoted TXT chunks, one optional trailing directory slash, the actual 63-character DNS-label bound for CID hostnames, a persistent fatal UTF-8 decoder, `cache: 'no-store'` for resolver requests and rejection of duplicate suffix profiles. The SDK exposes the capped TTL but keeps no separate discovery cache. Canonical request identities pass the existing hostname parser, and the login element explicitly displays the alias-to-provider resolution before navigation. [Maintainer example response](https://github.com/ipfs/boxo/issues/771).

No remaining source/interface blocker was identified for this deliberately bounded profile. It expects a direct, unambiguous TXT answer for the queried name; recursive CNAME/IPNS resolution is not implemented. Actual resolver/gateway availability, browser CORS and independently retrieved published manifests remain separate deployment evidence. The SDK agent reports 25 passing SDK/i18n checks, including four new discovery tests; this reviewer did not rerun those tests or perform additional security probes under the coordinator's current instruction. Full browser and build evidence remains owned by the coordinator.
