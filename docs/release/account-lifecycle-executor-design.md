# Executable account lifecycle: integration design

Independent architecture review, 2026-10-13. This is an implementation design under the user's authorization, not a claim that automatic warning, suspension or purge currently executes. The coordinator owns final policy reconciliation in DEVLOG and the lifecycle specification. Reviewer/date/outcome: ___ / ___ / ___. The separate [activation and retention review](account-activation-retention-review.md) records tested activation and conservative paid-history protection.

## Scope and policy

Implement account-local durable phases with existing account alarms and the account mutation boundary. No global service is consulted on every resource operation. Keep identity assignment permanent; only hosted account data is eligible for purge. External S3, WebDAV and Google Drive object bytes are untouched. Paid history protects every automatic warning, suspension and deletion phase, including after cancellation or expiry. Reversible cold shelving remains available to paid accounts.

The coordinator's proposed baseline is three days after activation for an unused account, a seven-day suspension-warning period, then a thirty-day suspended deletion-warning period. Established accounts enter review after 365 days without qualifying use and receive longer grace according to prior active tenure. These values are proposals to implement and reconcile, not deployed behavior. One bounded formula worth evaluating is a multiplier of `1 + min(11, floor(priorActiveTenureDays / 365))` on the seven- and thirty-day grace periods. Derive tenure from first meaningful use through last qualifying activity, not from time spent waiting on failed notices. Persist the selected policy version and durations when an episode begins. Later configuration changes must not shorten an already communicated deadline.

Arm the initial clock only after trusted completed activation. `rememberSignupOrigin` and `identityKeychain` can run while an identity is still pending; neither is evidence of activation. Add an idempotent activation fact carrying identity ID, activation time and revision. Older identities without trustworthy activation or paid-history provenance remain under review until migrated conservatively.

Qualifying activity means successful owner use or an authorized application's meaningful resource use. Initial builtin creation, signup bootstrap, alarms, provider callbacks, automatic push acknowledgments, failed requests and unsolicited inbound messages do not establish continued owner use. Otherwise a sender could keep abandoned accounts alive indefinitely. Record successful meaningful use separately from generic HTTP access or background housekeeping. An authenticated return or explicit reactivation is sufficient to cancel an inactivity episode; no purchase is required to return.

## Durable state and portable interface

Use one versioned `lifecycle/state` record per account with `owner`, policy version, phase, monotonic generation, activity epoch, activation/first-use/last-use times, captured financial-review context, phase start/deadline, next scheduled attempt and bounded job cursors. Corrupt state, backward clocks and impossible deadlines hold transitions for review. Never infer an inactive account from a missing timestamp or coerce an unknown phase into active.

Suggested module operations are `recordActivation`, `recordActivity`, `status`, `step`, `reactivate`, `assertAccess` and, only after cleanup integration, `commitPurge`. Inject metadata, the account gate, clock, current paid-protection reader, fresh financial-history reviewer, notice sender and cleanup ports. Provider results are plain bounded evidence; untrusted callback bodies cannot directly set a phase. The isolated module may stop at `purge-review` until the adapters and final cleanup journal are implemented, but that intermediate boundary must not be presented as completed automatic deletion.

Every step reserves work under the gate, performs remote I/O outside the metadata transaction, and re-enters the gate to compare owner, generation, activity epoch, notice/financial context and deadline before committing. Stale completions cannot advance a newer episode. Repeated alarm delivery and repeated owner confirmation must be idempotent. A bounded attempt/job ledger survives crashes; an unknown send outcome is not a successful receipt.

AccountController already wraps most `invoke` calls and part of `alarm` in its gate. A module that recursively acquires the same Node `SerialGate` can deadlock. Give the lifecycle dispatcher entries explicit ownership of short gated sections instead of nesting them beneath the existing outer wrapper. Remote Polar, mail and R2 requests must not hold SQLite transactions or an unbounded Worker `blockConcurrencyWhile` section.

## Notices and transitions

The selected notice policy is repeated provider-accepted attempts to a previously verified channel, without requiring proof that an owner read them. Record acceptance truthfully; it is neither delivery confirmation nor awareness. The execution contract should require at least three distinct, spaced scheduled attempts within each phase and at least one accepted receipt in that phase. Retrying one attempt cannot count as multiple notices.

Each attempt has a unique ID, phase generation, captured channel revision, scheduled time, lease and bounded outcome. A provider receipt commits only if the account and channel still match. The first accepted notice starts that phase's fixed deadline; retries do not shorten it or continually restart it. Without a recorded acceptance, failed or indeterminate attempts cannot advance the phase. Known suppression or bounce information holds progression too; do not claim handling of asynchronous bounces until a verified adapter actually supplies them. Lifecycle/security notices are distinct from optional unread-message preferences, while explicit channel invalidity still matters.

A missed alarm or prolonged outage may leave fewer than three spaced attempts before the communicated deadline. Retain the account rather than burst-send catch-up notices. Provide a bounded repair transition that creates a new generation and announces a later deadline, or an explicit operator repair path; an immutable expired deadline must not make an otherwise recoverable phase permanently stuck. Repeated pre-acceptance failures similarly need a durable retry/hold policy rather than an implied autonomous retry that has no scheduled alarm.

`active → warning` requires trusted activation/use history, unpaid eligibility and fresh financial review. Warning notices state the exact suspension date and how to keep the account. Normal authenticated use cancels the episode. `warning → suspended` requires the elapsed deadline, repeated-attempt evidence, unchanged activity and another current unpaid check. The committed phase immediately blocks normal authority; cold-storage work may finish afterward without reopening it.

Suspension retains data and presents a restricted status/reactivation flow. The subsequent accepted notice states the exact planned deletion date. `suspended → purge-review` requires its own completed notice interval and evidence, with fresh financial and activity checks. `purge-review → purging → deleted` additionally requires the cleanup inventory and final fencing described below. New activity or protection cancels the applicable pre-purge episode; it must not silently restart a notice deadline or restore already-deleted bytes.

## Authorization and reactivation integration

The canonical lifecycle phase belongs to account-local metadata alongside activity and billing. An identity-directory status mirror is useful for presentation or early rejection, but cannot replace the final account check. The identity row is separately sharded, and an old federation or contact bearer can outlive its update.

| Existing integration | Required lifecycle behavior |
| --- | --- |
| `AccountController.invoke` and direct internal effect methods | Enforce the current phase before normal reads, writes, cached journal returns and billable operations. Keep an explicit narrow maintenance/reactivation allowlist. |
| `warm` and `touch` | Status/notices must not restore archives or mark the account active. Remove incidental lifecycle activation from ordinary `touch`; successful qualifying activity uses the lifecycle transition API. |
| `conversationDrain` and public identity fast paths | These currently bypass the main gate. Check suspension before remote fanout or disclosure and recheck before effects. |
| Federation `validateSubject`, token exchange/refresh, child tokens and object URLs | Consult lifecycle authority, bind the current capability epoch and retain native final checks. Do not rely solely on identity `status === 'active'`. |
| Native RPC, MCP, hosted uploads, contact delivery, message/conversation ingress and beaming | Reject normal effects while suspended, including already-issued bearer capabilities and replay-cache responses. Metadata cleanup and billing evidence may still run. |
| Identity login, recovery and owner HTTP routes | Permit restricted authentication/status/confirmation/reactivation without granting ordinary account access. Never turn a suspended identity active as a side effect of login. |

A dedicated restricted-session purpose is preferable to a normal owner cookie that merely hides the landing page. All normal consumers must reject that session purpose. Reactivation verifies current identity proof, owner and episode generation, checks that purge has not irreversibly begun, cancels outstanding notice work and restores access only after required cold metadata can be read safely. Recovery retains its independent proof and mandatory-channel requirements.

Increment a monotonic capability epoch when suspension fences the account. Old short-lived OAuth grants, refresh families and resource URLs should not become usable simply because the phase later returns to active. Preserve durable contact-link and app-connection records separately; the coordinator should decide whether to revalidate them on reactivation or require new consent. Do not silently erase permanent identity relationships in order to expire temporary tokens. Already-issued native third-party presigned URLs remain usable until their provider-enforced expiry; the current bounded expiry must be disclosed, because a local phase cannot revoke a remote signature.

## Paid protection and purge races

`accountRemovalProtection().status === 'unpaid'` currently means trusted new-signup provenance and no locally known paid evidence. It is not a complete historical Polar-order proof. Any unresolved checkout row, including an expired row, must hold lifecycle advancement until authoritative reconciliation resolves it. Missing webhooks or a subscription canceled before the first successful sync can otherwise conceal historical payment.

The financial-review port must examine current subscriptions and bounded complete relevant order history with exact customer, organization and deployment bindings. Include retained/archived product history, rather than filtering only current catalog IDs. Pagination uncertainty, history outside retained catalog coverage, provider failure and mismatched context hold advancement. Positive evidence writes sticky paid protection before any Free-state replacement. Bind a negative review to the lifecycle generation and a short freshness interval; it does not authorize indefinite future deletion.

Serialize local checkout/upgrade admission with the final purge fence. Billing reconciliation and webhook handling remain permitted during suspension and purge preparation. Before every destructive batch, recheck current protection, phase generation and ownership; stop subsequent work if protection appears. An external provider transaction cannot be globally atomic with local R2 deletion. A promise to recover every late-notified payment would additionally require a defined final recovery quarantine/snapshot interval. Without that, describe the actual guarantee as protection against observed and locally admitted payment races, not a distributed transaction with Polar.

Before deleting metadata, persist a bounded, resumable manifest of every owned physical reference: message blobs, hosted objects, outstanding upload reservations, garbage records, RPC result blobs and account metadata archives. Keep cleanup ownership until confirmed deletion. Node's `FileBucket` hashes keys to filenames and has no prefix listing; deleting a shared bucket/directory or assuming R2 listing works on Node is unacceptable. Add missing write-intent inventory before implementing purge. External connector credentials may be destroyed after the reconstruction requirements below are satisfied, but the executor must never call an external object-delete method.

After owned cleanup, retain a minimal identity tombstone and permanent namespace/alias claims. Clear sessions, credentials, recovery authority and private contact associations through the repository's existing compare-and-swap/index protocol. Releasing an email lookup requires its exact old claim; deleting a raw lookup key could remove another owner's later association. Old recovery backups must not recreate a deleted account or reclaim its never-recycled name. Bound cleanup of separate federation/MCP token state and search/vector indexes; their authorization must already fail even while physical cleanup is pending.

## External data must remain reconstructible

**Preserving external bytes alone does not currently preserve their usability.** In `packages/storage/google-drive.mjs`, uploaded files are named `bindle-<version>` and their private `bindleKey` property contains only a hash of the logical key. The live mapping under `drive/object/<resource>/<hash>` supplies the actual key, file ID, logical version, size, content type and SHA-256 digest. Superseded and logically deleted versions have separate `drive/retained` rows; unfinished uploads have `drive/pending` rows. Deleting these records makes the live namespace impossible to reconstruct reliably from the provider filenames or hashes. Current reconnect also requires the retained resource row and encrypted root-folder/principal binding; it is not an import operation after account deletion.

Therefore automatic account purge must preserve both external bytes and sufficient reconstruction metadata. This is additional implementation work, not a capability of today's identity recovery file. Do not describe untouched Google Drive files as automatically usable after host deletion. Until a verified export/restore path exists, hold destruction of essential external mappings, or retain an explicitly disclosed minimal encrypted reconstruction archive. Removing hosted message/object bytes can be a separate cleanup stage; it must not make the surviving reconstruction archive unreachable by destroying its only decryption key or owner access path.

The preferred unattended preservation path is an immutable, owner-readable reconstruction manifest stored alongside the managed external files, with an optional owner download of the same format. It must be a documented connector feature with a reserved namespace and bounded costs, never an arbitrary overwrite of a user file during deletion. Use ordinary private Drive files in the owner's managed folder, with recognizable names and documented format; do not publish them or change sharing permissions. Namespace keys and application names can themselves be private. An encrypted export is useful only if the owner already holds a separate usable decryption mechanism; encryption under a server key that purge destroys does not provide independence.

A minimal format should include:

- Format/version, original issuer and historical owner/resource identifiers, provider root-folder ID and verified provider principal binding, snapshot time and monotonic mapping revision.
- Bounded manifest shards with exact byte lengths and cryptographic digests, plus one final manifest identifying the complete snapshot.
- Exact logical key, provider file ID, logical version, content digest, byte length and media type for every live entry. Keep retained/deleted versions and unresolved uploads in separately typed sections; never infer that every remaining provider file is a live object.
- Documented application bootstrap/index references where available and safe to export. Ordinary app APIs still need no `LIST`; an owner-only exporter can enumerate host metadata. Mapping recovery does not itself make an unknown app format usable or reveal which index an application expects.

Export only explicitly selected noncredential fields. Do not serialize whole resource secrets: the current sealed Google record mixes root/principal bindings with access and refresh tokens. Exclude identity private keys, recovery secrets, OAuth tokens, session cookies, app/resource bearer capabilities, private signing keys and unrelated owner preferences. Keep content reconstruction separate from the signed identity backup, so a mapping change neither rotates recovery credentials nor turns an old recovery file into current storage authority.

Google documents `appProperties` as private to the requesting application and `drive.file` as access to files created by or explicitly opened/shared with that app. Consequently a different OAuth project must not be assumed able to discover old private properties or automatically access the old managed files. Provide an owner-visible download/import path and verify any new authorization/file-selection flow in practice. A manifest file alone does not expand Google permissions. [Google custom properties](https://developers.google.com/workspace/drive/api/guides/properties), [Google Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).

For purge integration, freeze managed namespace mutation, capture the resource generation and a new monotonic mapping revision, publish immutable bounded shards outside the metadata transaction, then read back and verify the complete manifest. Commit a durable preservation receipt only after the final gate confirms the same owner, root, generation, mapping revision and lifecycle episode. Every logical put/delete and unresolved-upload reconciliation must participate in that revision scheme; resource generation alone does not detect object edits. A failed or indeterminate upload, missing/revoked folder access, changed principal, incomplete manifest or stale revision holds mapping destruction. Never interpret “export prepared” or “download offered” as an owner-held backup. Checkpointed sidecars while active can reduce suspension-time work, but only a verified current snapshot satisfies the purge precondition.

Fresh provider authorization is required to import later. Validate the selected principal/root and each referenced file's ancestry, size and checksum before publishing mappings; treat manifest contents as untrusted bounded data. An exporting host signature establishes origin/integrity, not permission to read another person's files. Import creates a fresh resource generation and requires fresh application consent, without reviving old grants, refresh families or object URLs. It must not resurrect a purged identity or transfer its permanent username. Current reconnect needs a separate import implementation to support this.

For S3 and WebDAV, current adapters derive the backing path from endpoint/bucket/prefix plus the logical key, so filenames are less dependent on a private Drive-style map. Still preserve safe connection coordinates and app bootstrap references, excluding credentials; fresh credentials come from the owner. Read-only connectors cannot be required to write a sidecar. Provide an independent owner export or retain the minimal reconstruction archive when no provider-side preservation path is available. Do not silently enable external write permission for lifecycle cleanup.

No purge, failed preservation cleanup or connector disconnect may delete external objects or sidecars. Avoid project-wide Google token revocation as an assumed per-resource cleanup operation: the current connector deliberately performs local disconnect instead. Provider-controlled deletion, subsequent external edits and the owner's own lost credentials remain outside the host's preservation guarantee.

Before enabling essential-map deletion, demonstrate restoration using exported metadata and provider files with the original host unavailable. Test exact live namespace reconstruction after overwrite and logical deletion, separately classified retained/pending files, partial shard failure, stale revisions, revoked access, wrong-principal import and malformed paths. Assert absence of exported credentials and external `DELETE` calls. Verify fresh-resource consent, read-only connector handling, provider quota/cost failures and recognizable owner access to the manifest. App-specific continuation requires its own bootstrap-format test; otherwise describe the result as recoverable files and logical namespace, not automatic application continuity.

## Alarms and operational recovery

Worker Durable Object alarms can drive bounded account-local work. Run lifecycle scheduling before the current `shelved` early return and before conversation draining. Compose its next deadline with existing quota, search, garbage and beam alarms; overwriting one with a weekly archive wake-up can lose required notices. Keep lifecycle retry state separate from unrelated paused search/garbage maintenance so one failed subsystem cannot silently suppress warnings or reactivate an account.

The Node adapter currently re-arms persisted account alarms only when `accounts.get(id)` lazily opens that account. An abandoned account will therefore not wake after a server restart. Add bounded startup alarm discovery or a small durable due-account index and scheduler. Maintain that index only when alarms change, not on every resource request. Avoid loading every account and restoring its archive during discovery. Existing Worker accounts likewise need a resumable bounded rollout/migration to arm missing schedules; no recurring global identity scan belongs in the hot path.

Node also caps timer delays at 2,147,483,647 milliseconds, about 24.9 days. Its current callback checks the stored alarm identity but not whether the wall-clock deadline has actually arrived before claiming it. Long lifecycle timers must re-arm until due rather than treat that capped timer as an elapsed thirty-day or yearly deadline. The module must independently check its persisted deadline even after adapter correction.

Expose aggregate counts for pending notices, uncertain receipts, held financial reviews, suspended accounts and failed cleanup, with bounded operator repair cursors. Never log recovery tokens, push endpoints, email codes, external credentials or message bytes.

## Selective R2 Infrequent Access

Cloudflare lists Standard storage at $0.015/GB-month and Infrequent Access at $0.01, with IA Class A operations at $9/million, Class B at $0.90/million and retrieval at $0.01/GB. IA has a thirty-day minimum charge and no Standard free-tier allowance. Reading or copying IA data incurs retrieval charges. These figures were checked on 2026-10-13 and must be inputs to an economic decision, not permanent assumptions. [R2 pricing](https://developers.cloudflare.com/r2/pricing/).

Consequently a 1 MiB object retained for thirty days saves roughly $0.0000052 in storage, less than a single $0.000009 IA write before reads. A complete IA verification read costs twice one month's per-GB storage saving. Blanket conversion of current one-MiB hosted objects during a thirty-day suspension is usually counterproductive. Compare expected storage savings against writes, reads, retrieval, early-deletion minimums, return probability and account/service maintenance budgets. Prefer larger, sufficiently long-lived metadata archives when that comparison is positive; staying in Standard is a valid result.

The existing Worker bucket binding supports streamed `put`, conditional `onlyIf`, an explicit `storageClass` and provider-validated SHA-256 integrity input. A returned checksum is available when supplied to `put`. There is no need to provision S3 credentials for this adapter. [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/). S3 `CopyObject` is another documented class-change path, but is unnecessary where only the existing Worker binding is authorized. [R2 storage classes](https://developers.cloudflare.com/r2/buckets/storage-classes/).

Implement class transition as a separate optional storage capability. Reserve the exact owner/blob reference, source version, lifecycle generation and maintenance admission; read the owned source; write identical bytes with a condition preventing resurrection or overwrite of another version; then commit tier metadata only if the original reference and generation still match. Use a known SHA-256 or a bounded source read to compute one before the destination write. Large unknown-checksum objects require a bounded two-pass strategy or remain Standard. Preserve content metadata and logical application versions. Unknown outcomes need reconciliation, not repeated expensive rewrites. Node must report storage-class switching unsupported rather than simulate cloud cost savings.

## Required verification before enabling execution

Use deterministic-clock module tests for exact deadlines, rollback, repeated alarms, notice spacing, unknown sends, accepted receipt binding, failed channels, activity during send, stale completion, policy changes and maximum ledger size. Exercise every paid-protection migration and missed/late payment case, including negative history pagination uncertainty.

Run actual Worker and Node integration checks for restart wake-up without account traffic, cold suspended status without restore, restricted login/recovery/reactivation, suspended owner and app API denial, cached replay denial, expired versus current epochs, public conversation fast paths and reactive billing protection. Test concurrent reactivation/payment against archive work and purge batches.

Use owned temporary storage to verify crash-resumable inventories, source-revision changes, orphan reservations, RPC results, index cleanup, exact email-claim release and permanent username non-reuse. Assert that external connector delete methods are never invoked. Test IA checksums, conditions, retrieval-aware cost decisions, repeated unknown outcomes and the unsupported Node path. Browser checks must display exact dates, honest acceptance status and a functioning restricted reactivation flow. Full `npm test`, Worker suites and deployment/runtime checks remain necessary once these adapters are wired; the isolated phase module alone does not satisfy completion.
