# Storage write and shared activity budget review

Initial review date: 2026-10-12; rolling-window follow-up: 2026-10-13. Reviewer: independent code-review agent. Human reviewer/date/outcome: **pending**. Production release remains gated. This document records implementation evidence and remaining verification; it does not constitute release approval.

## Existing behavior and the requested change

At the initial review, `AccountWorkBudget` metered covered logical mutations and ingest attempts separately. It used durable owner debits, a fixed 16-shard service allocation, nonrefundable prepaid leases and fail-closed handling of uncertain allocation. Source review and independent execution of `node --test tests/work-budget.test.mjs` passed **8/8** checks, covering concurrency, restart, exact partition totals, uncertain allocation, owner binding, billing entitlement and continued reads/deletion/revocation after exhaustion. The final 2026-10-13 follow-up below supersedes that separate active account meter with one shared activity allowance.

That work budget is not a count of physical bucket writes. Hosted object writes, message delivery and conversation inbox ingestion debit work, but archive writes and large stored RPC results can cause additional bucket puts. `offloadMetadata` also contains a bucket-write path, although no active composition caller was found during this review. Updating the same logical key can maintain constant storage usage while causing repeated physical writes. Quota on retained bytes cannot bound this request churn.

The requested control therefore belongs immediately before the platform bucket's `put` call, independently of logical keys, versions, payload identity, transaction IDs, access tokens and signed URLs. Every actual application-level put attempt must consume admission, including retries and upstream failures. A durable replay that returns a prior result without calling the bucket must not consume a second physical-write unit. Provider errors and uncertain outcomes must never refund admitted units.

## Agreed composition and limits

The shared activity meter now uses the following requested policy. One covered logical mutation attempt consumes one unit; each actual application-controlled bucket put attempt consumes another. Earlier test evidence below records the initial separate monthly-owner policy; the final follow-up records its replacement.

| Scope | Limit |
| --- | --- |
| Service monthly total | 10,000,000 admitted activity units |
| Foreground service pool | 9,000,000 units per UTC month |
| Archive maintenance service pool | 1,000,000 units per UTC month |
| Owner foreground rolling hour | Free 500 units; Paid, Plus and Ultra 2,000 units |
| Owner foreground rolling day | Free 1,000 units; Paid, Plus and Ultra 10,000 units |
| Owner archive maintenance pool | 16 per UTC month |
| Owner rolling-minute burst | 240 units |
| App rolling-minute burst | 120 units |
| Retained app burst records | At most 64 per account |
| Service allocation | Fixed 16 shards; prepaid leases of up to 16 |

Each pool's shard capacities must sum exactly to its configured total; foreground and maintenance together must conserve the service ceiling. Archive-only admission preserves a small path to cold storage after foreground exhaustion. Journals, inbox ingestion and hosted object writes use foreground admission. Archives use maintenance admission. Both physical bucket ports require wrapping before injection into consumers.

The new guard is independent of `WORK_LIMITS_ENABLED`. Runtime composition enables it explicitly; an enabled guard without a valid durable authority must reject writes. Isolated controller fixtures with no configured guard remain unconfigured fixtures and must not be cited as evidence that the production composition is protected.

The public bucket port should expose only bound `get`, metered `put` and `delete` methods. A generic passthrough must not expose unmetered multipart mutation methods. Trusted internal write context may carry an authenticated app identity, but must be removed before forwarding options upstream. The default owner comes from the account's durable binding. There must be no user-controlled request field that supplies owner, pool, limit, bypass or app identity.

## Admission correctness requirements

App fairness uses the stable authenticated application identifier within the owner account. It must not reset on token refresh, new family, reconnect generation, new signed URL, resource creation or logical-key changes. Transport namespaces remain explicit: the current MCP adapter uses an `mcp:` prefix. Contact and conversation origins need their own stable trusted identities where attributed. Non-app system operations still consume the owner and service budgets.

Do not use mutable ambient `currentApp` state on an account controller: conversation fanout can run outside the account gate. Pass attribution explicitly through the trusted call path. Bound app-record cardinality, and prune only histories whose entire burst window has elapsed; disconnecting an app must not erase still-live counters. Any monthly app balances added later must outlive short-lived burst histories.

Persist nonrefundable local admission before remote service allocation or bucket I/O. Never perform remote bucket or service-authority operations inside a local metadata transaction. Unknown allocation outcomes strand capacity rather than risk overspending. Reject corrupt counters, future-month state and invalid configuration. A calendar transition while a lease is being allocated must not transfer old-month admission into a fresh month.

Fixed partitions and unused local leases can strand capacity; that is an intentional conservative tradeoff. Budget state and service ledgers must not be rolled backward during restore. Changing the layout, month key or shard count requires an explicit migration rather than creating a second independent allocation ceiling. Lowering a service cap must account for already-issued leases; it cannot retroactively withdraw admitted capacity.

Review identified that independently keyed foreground/maintenance counters could over-allocate if an operator changed their percentage mid-month. The implementation now uses one `storage-write-v1/<month>/<partition>` authority ledger. One atomic reservation checks and increments both the common total and the selected pool. The ledger pins the total, foreground and maintenance limits on its first allocation and rejects a changed tuple for that existing month/partition. Total shard capacity is calculated independently of the split; maintenance receives its share and foreground is the difference. Thus a percentage change cannot create another allocation pool or increase the combined total. Already prepaid leases remain funded; policy changes that require new allocations take effect on a fresh month ledger.

Bucket refusal must leave existing objects and metadata intact. A hosted write that has reached an uncertain effect must retain its journal semantics rather than silently retry. A failed archive must retain the hot account records; budget exhaustion may delay shelving but must never cause deletion before a successful verified snapshot. Reads, deletion, logout and permission revocation must remain available after foreground exhaustion.

## Meaning and verification boundaries

The final shared allowance bounds **covered logical admission and application-level platform bucket put attempts combined**. Physical puts are a subset of admitted units, so their ceiling cannot exceed the shared allowance. It is not a universal cloud invoice ceiling. Provider-internal retries, reads, listing, retained storage, account/worker compute, metadata persistence, third-party connectors and unrelated operator credentials require separate accounting or operational controls. No current provider prices were used to infer a monetary ceiling in this review.

The application's current external S3/WebDAV write routes remain unavailable; native S3 write URLs remain disabled. Hosted writes and Google Drive writes already pass logical work admission. The physical platform bucket wrapper must not be described as a meter of every Google API request or a future external S3 upload path. Any future direct provider upload URL needs enforceable reservation before issuance, because its later requests bypass this bucket wrapper.

### Paused cleanup admission follow-up

The final constructor guard rejects foreground bucket puts with `storage_write_unavailable` (503) when either `storage/garbage-retry` or `storage/cleanup-retry` has `paused === true`. With physical metering enabled, this check runs before physical-budget admission and before upstream bucket I/O, so a refused write consumes no physical-write unit. Existing logical admission may already have occurred. Both foreground upload and stored-result consumers inherit the same wrapped port. Reads and deletion bypass put admission; archive puts bypass this cleanup-pause condition but still require their normal maintenance, owner/app burst and service admission. This preserves a bounded archival path rather than promising unlimited maintenance availability.

Independent execution of `node --test tests/storage-write-budget.test.mjs tests/storage-write-integration.test.mjs` after this change passed **17/17**: eleven budget tests and six integration tests. The new integration case sets the garbage-cleanup pause, rejects a replacement before another provider call, reads the prior object, deletes it, successfully archives and confirms that foreground usage did not increase. The second cleanup marker's equivalent admission branch was verified in source. No additional security probes were performed.

The guard is an admission check, not cancellation of a write already admitted when cleanup later pauses. It applies only while physical metering is enabled. Paused cleanup records deliberately retain outstanding ownership and stop automatic retries; restoring foreground writes requires operator repair of the cleanup condition and retry state. This change does not add automatic unpausing. No blocker was identified in this narrow safety and availability review; production operational approval remains pending.

### Rolling windows and unified activity follow-up — 2026-10-13

The active account controller now aliases `workBudget` and `storageWriteBudget` to one instance. Logical admission and physical admission consume the same owner, writer, rolling-hour/day and shared-service counters. A simple hosted put normally consumes two foreground units; additional physical outcomes may consume more. A request can consume its logical unit and then be refused before its physical stage. Both admitted stages remain charged after failed I/O. This is admission accounting, not a claim that every request costs one unit or that every admitted unit reached a provider.

The two configuration flags independently select logical and physical admission into that instance. Both enabled paths require a valid authority; explicit malformed flags are rejected. Physical wrappers still strip internal attribution when physical metering is disabled. Production compositions enable both paths; deliberately disabled fixture paths do not prove both are protected. The logical wrapper forwards only owner initialization and writer identity, so its callers cannot request archive admission or select their own unit count. Initialization binds an absent durable owner and refuses rebinding. Hosted, managed Drive, MCP, contact and conversation inbox logical admission now uses the same stable attribution as its corresponding physical stage. MCP deletion was exempted from logical admission to preserve deletion after exhaustion.

Hour/day history uses at most 1,441 chronological minute buckets, with validated row shapes and bounded counts. A save exceeding 120,000 serialized JSON characters fails closed; generated state uses ASCII keys and numeric history. Buckets expire at the end of their minute plus the window, conservatively delaying allowance recovery by up to one minute. Exact timestamps still govern minute bursts. Review corrected early minute/cardinality exits that could return a shorter retry delay than a simultaneously exhausted hour/day window. Foreground retry timing now uses the longest applicable wait; exhausted archive-month admission also accounts for an overlapping burst wait. Status timestamps represent next bucket recovery, or one-unit eligibility within that individual window when exhausted; they do not promise a full reset or availability under every other control.

Version 2 account state remains under `storage-write/v1`, preserving funded service leases and monthly accounting. Its rolling history survives month rollover, restart and paid-plan changes. Both paid plans use identical limits; current durable entitlement is checked on admission, and expiry applies Free limits to retained history without resetting usage. Migration imports the old retained minute events as minimum known history. Older hourly/daily activity cannot be reconstructed from monthly totals, and legacy maintenance events in that retained burst may be conservatively included. The old `work/month` record and old work-service credits remain untouched and are not converted into the shared meter. Earlier binaries do not understand version 2 state; counter deletion or rollback is not a supported downgrade.

The shared service ledger and its pinned monthly allocation policy remain unchanged. Consequently, recovering account rolling allowance does not guarantee admission: a depleted service partition or archive reserve can still block activity until the UTC month boundary. Fixed partitions can exhaust while capacity remains elsewhere. Raising a configured ceiling does not reset a populated ledger or retroactively change its pinned policy. Active account monthly foreground quotas from the old logical and physical meters are no longer enforced; the retained legacy module and its tests are historical compatibility evidence.

### Message API admission and HTTP response follow-up — 2026-10-13

Signed-contact multipart delivery and bearer `POST /api/messages` converge on the same recipient `receive` method. Both logical and physical admission use `contact:<parent-grant-id>`; rotating the minted bearer or switching delivery routes does not create another allowance. Completed receipt lookup precedes admission, and replay still verifies current authority and the original content fingerprint. Conversation inbox storage similarly uses the verified source identity plus conversation ID, with durable event/receipt checks before logical and physical admission. Recipient limits are checked before a denied physical stage can call the bucket. Public error CORS includes signed-contact delivery, bearer message routes and public conversation endpoints; cookie-only owner conversation errors do not gain public CORS.

These conventions were checked against Polar's maintained currency implementation and its pinned SDK enum. It does not cache account-specific status by region. Status reads must create no checkout or customer session. Provider failure while billing is enabled makes prices unavailable; disabled billing can show the explicitly provisional USD catalog. Checkout uses the selected configured currency and server-owned product/customer/return settings, with trials and discount-code entry still disabled. Price display is a catalog quote, not a promise of a final tax-inclusive total.

Reconciliation must validate the actual subscription currency and amount against that product's verified currency price. The legacy prepaid compatibility path remains USD-only and cannot reinterpret a regional amount as the former USD price. Permanent previously verified paid-handle markers remain independent of display currency. Inclusive tax needs separate order arithmetic: Polar subtracts included tax when computing `net_amount`, while `total_amount` includes it; subscription price amounts remain the base catalog amounts. Review therefore requires correct inclusive/exclusive comparisons and internally consistent tax totals, without broadening the existing discount or refund policy. [Polar order amount calculation](https://github.com/polarsource/polar/blob/main/server/polar/order/amounts.py), [subscription construction](https://github.com/polarsource/polar/blob/main/server/polar/subscription/service.py).

### Mixed-proration plan changes — reviewed implementation

The authorized extension uses immediate invoiced proration for a move up the fixed Paid/Plus/Ultra ordering and a scheduled next-period change for a move down. The pinned SDK exposes these subscription-update modes. Its request options do not expose a provider idempotency header, so a local request ID alone cannot make an uncertain remote charge safely repeatable. The implementation needs a durable bounded journal before mutation and one unresolved-change guard for the subscription; a new request ID must not bypass a timed-out change. Reconciliation reads provider state rather than blindly repeating an uncertain update.

Confirmation must bind the existing account/subscription/provider environment and the reviewed target product, currency, price and plan parameters. A stale quote must fail before billing mutation. The user should see the known annual price and timing policy without an invented exact prorated amount. A pending downgrade retains current capacity until the provider's current subscription actually changes.

Polar's implementation applies the new product before its invoice billing effect. Therefore an active subscription with the requested product is insufficient by itself to prove that an upgrade's prorated charge succeeded. The account's previous paid-through allowance must remain until authoritative evidence establishes the corresponding payment outcome; a failed or pending upgrade must not silently grant the target tier. This is a design inference from the provider's update sequence and requires focused tests and live-provider validation before release. [Polar subscription update implementation](https://github.com/polarsource/polar/blob/main/server/polar/subscription/service.py).

The subsequent explicit grace-period decision changes the pending-payment experience: a known accepted provider change, a freshly verified matching target subscription and an existing confirmed paid source may receive at most fifteen minutes of **provisional** target capacity. This is not confirmation of payment. The source confirmed entitlement must remain separately recoverable, with an immutable grace deadline no later than its paid-through deadline. A durable spent-grace marker must survive new request IDs, target changes, journal cleanup and recovery; later responses cannot restart its timer. Definitive payment failure or revocation ends provisional access immediately. Expiry restores the confirmed allowance without deleting retained content or resetting activity history. Free initial checkout and an ambiguous mutation request alone do not qualify.

Under the current owner limit of 240 covered units per minute, fifteen minutes admits at most 3,600 covered units. With a one-MiB upload bound, this conservatively limits covered physical upload attempts to 3,600 MiB; ordinary writes consuming both a logical and physical unit have a lower ceiling of 1,800 MiB of attempted upload volume. App limits, hourly/daily allowances, storage quota and the shared service ceiling apply additionally. These are admission bounds, not a complete invoice ceiling or proof that retained excess storage becomes cost-free after grace expires. ### Financial implementation review closure — 2026-10-13

The reviewed change journal is account-local, reserves its row and unresolved-change lock before the provider mutation, and performs provider calls outside metadata transactions. Quotes bind the source subscription and period, target product and parameters, actual subscription currency, provider environment and catalog revision. Immediate upgrades use `invoice`; downgrades use `next_period`. A provider timeout leaves an unknown outcome that prevents both automatic retry and a new transaction from repeating the charge. Reconciliation can resolve an accepted outcome; uncertainty may require operator reconciliation rather than an unsafe retry. The ordinary journal admits at most thirty-one retained rows, reserving the thirty-second for canceling a scheduled downgrade. Terminal rows are eligible for cleanup after thirty days; unresolved rows remain protected.

Scheduled cancellation uses the pinned SDK's `{pending_update:null}` form and its own durable request. Review confirmed provider environment and source binding before the mutation, full owner/customer/product/currency checks on the subsequent read, and replay without a second update. A changed deployment prefix, catalog mode or provider environment cannot authorize a retained pending mutation. A downgrade leaves current capacity intact until fresh provider state actually selects the lower product.

The upgrade fence retains the confirmed source snapshot while looking for a new matching subscription-update order, excluding the pre-mutation order baseline. It validates currency, owner/customer/organization/subscription/product provenance and consistent signed invoice arithmetic. This supports provider-paid zero invoices and negative prorated credits without inventing an annual cash-charge requirement. Matching failure/refund evidence takes priority over a paid order while the change remains pending. After settlement, ordinary authoritative subscription reconciliation governs later refunds; this change does not promise a separate permanent refund-revocation policy for already confirmed terms.

Provisional capacity requires a known accepted mutation plus fresh matching target subscription state, and binds target product and currency. The durable grace marker records the original start and expiry for the source subscription period. It survives service restart, and a settled first upgrade cannot create another grace interval through a chained upgrade in that same period. The consumer independently caps expiry at fifteen minutes and at the original paid-through deadline. Pending failure ends grace; expiration restores confirmed capacity and leaves retained content and activity history intact. Trusted server time and durable, non-rolled-back account metadata remain operational prerequisites.
