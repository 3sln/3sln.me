## Recommendation and current implementation

An application can use an ordinary stable Bindle identity for authored messages. Keep four concepts separate: the app identity that signs, the authenticated installation/original caller using a delegation, the recipient who permits delivery, and the recipient's independently permitted notification/profile presentation. A verified sender label comes from the checked message envelope and key binding, never from an HTML attribute, subject, contact-token possession or arbitrary app metadata. A valid signature establishes provenance, not trusted content, human status, a legal identity or permission to deliver.

The current [message receive path](../../packages/messaging/messages.mjs) validates the recipient's contact bearer and current grant, bytes, MIME, tag policy and quota. Its receipt fingerprint covers bytes and sender metadata for replay consistency; it does **not** authenticate an author. [Contact-token documentation](../spec/contact-tokens.md) records the bearer delivery authority and separately retained sender annotations. Contact signatures are the recipient's grant signatures, not the sender's message signature. Current [notification jobs](../../packages/messaging/notifications.mjs) use generic New message text and recheck notification eligibility; verified app avatar notifications are not implemented.

The current internal account keychain separates ECDSA signing from ECDH encryption and stores private keys encrypted under the provider's `KEY_ENCRYPTION_KEY`. It is not an app-facing generic signing API or a claim that the provider cannot sign. The implemented conversation public-identity route is not the proposed generic directory/identity manifest. Reuse established keys and purpose separation without claiming the signed-message profile already exists.

“Every message is signed” therefore requires a versioned transition. Keep existing retained unsigned messages and explicitly permitted old contact/v1 input labelled legacy/unverified. A new signed-message capability/profile must be explicitly admitted and must reject downgrade on a signature failure. An adapter's new wrapper signature must not relabel the original unsigned author as verified. Do not automatically broaden current MIME grants or publish a placeholder contract as if it were interoperable.

## Public-client signing and delegation

A frontend-only app cannot keep a global publisher signing secret in its JavaScript bundle, manifest, browser storage or every user's installation. Nonextractable WebCrypto keys can restrict export, but do not make same-origin application code unable to use an authorized key; the WebCrypto threat model does not turn a compromised origin into a trustworthy signer. [Web Cryptography security considerations](https://www.w3.org/TR/webcrypto/#security-considerations).

Recommended initial arrangement: the app identity's authorized owner explicitly enrolls a provider-held signer or narrowly delegates a purpose-specific signing operation. Separately, the actual user/recipient authorizes the app connection and delivery binding. The signer derives the real caller and approved connection from authenticated context, checks both delegations live, and signs a fixed message envelope through a narrow `send` operation. It never signs arbitrary caller bytes/digests, returns a private key, or infers global app-identity authority merely from a registered public client ID/origin. Existing access to a user's profile/storage resources does not grant permission to impersonate the app identity or that user.

Bind delegated authority to the app's stable identity and key purpose, original consumer/installation, exact recipient and ingress binding, connection/admission incarnation, permitted message/action profile, expiry and finite rate/byte budget. The sender chooses content within those bounds; it cannot choose a different signer, recipient, grant generation or privilege-bearing metadata. Message and action signing have separate purpose domains from login, recovery, account export and generic resource authorization.

This design supports a public client without pretending that recipient approval authorizes use of somebody else's signing key. If an app identity owner has not authorized that sender/provider delegation, only the actual user's identity can sign under the user's separate approval; UI must say that rather than invent app authorship. A future per-installation key/certificate profile needs explicit enrollment, attenuation, expiry/revocation, recovery and verification semantics; it is not implied by ordinary OAuth registration.

Provider custody and its compromise remain explicit trust assumptions. A hosted signer must enforce sender-wide and per-connection abuse limits, preserve original-caller context and reject stale/out-of-scope work. Possession of a recipient delivery bearer alone can never invoke that signer.

## Message verification and identity continuity

The signed envelope should bind a version and purpose, stable sender identity/key ID, optional validated delegation chain, exact recipient/audience and admission incarnation, immutable message/operation ID, body bytes digest and MIME, signed subject/presentation metadata, author-selected allowed tags, action/attachment digests and canonical encoding. Required recipient tags and later local read/classification/tags are separately attributed owner policy, not retroactively claimed as author-signed bytes. Avoid self-referential token signatures: bind a grant/incarnation identifier or documented capability-context digest, not a live secret in public history.

Cryptographic validation needs a pinned or independently resolved identity binding. A key carried inside the message cannot authenticate itself; a handle is an alias, not a permanent principal. Follow the proposed bounded host directory/minimal identity-document discovery, verify provider/UUID/key-purpose bindings, and pin accepted continuity. New identity lookup is read-only; no key generation from an unknown GET. Algorithm/key type is profile-defined, never arbitrary attacker-selected code. Bound message/key/document bytes, delegation depth, cache entries and lookup work; use controlled HTTPS discovery with redirect and SSRF restrictions so unique forged identities cannot force unbounded network or storage work.

The receive decision intersects valid sender proof, live recipient delivery authority, recipient sender policy, supported content profile, limits and storage/work admission. Verify before assigning a verified label, running sender-specific rules or creating a sender-attributed notification. Malformed/unknown signatures are rejected or enter an explicitly bounded unverified policy lane without privileged labels; they do not fall back automatically to old bearer delivery. Endpoint denial should not reveal private recipient approval lists, account state or other grants.

Require message-level signatures over immutable content even if an HTTP transport signature is also used. HTTP Message Signatures leaves application coverage, identity trust and replay policy to the application; using its syntax alone does not protect unsigned body fields or define who is allowed to send. Exact envelope canonicalization, signature encoding and independent verifier vectors remain mandatory. [RFC 9421 security considerations](https://www.rfc-editor.org/rfc/rfc9421.html#section-7).

Deduplicate by authenticated sender identity plus immutable operation/message ID and complete signed digest in the recipient context, with the chosen bounded lifetime made explicit. A new contact token or retry cannot make a prior delivery notify again; changed bytes under the same operation conflict. Audience binding prevents forwarding a signed message to an unintended recipient from becoming an authenticated fresh delivery. Define multi-recipient envelopes explicitly and avoid disclosing a hidden recipient roster. Crypto verification does not provide global chronological ordering; receiver receipt time and signed author time remain distinct.

Key rotation must distinguish historical verification from permission for new sends. Keep the verification material and receipt-time verification outcome needed for retained history. A later revoked key can remain attributable as valid when received while new acquisitions under that key are refused according to the revocation policy. Claimed old author timestamps cannot bypass revocation or prove a newly supplied signature predated compromise. Use accepted old-key/new-key continuity or a separately trusted recovery ceremony; an unknown new key self-signature is insufficient. A compromised old key may forge a rotation statement, so conflict/compromise recovery requires explicit trust policy rather than automatic acceptance.

Alias rename/provider migration must not reset blocks or merge two identities merely because UUID strings or display handles match. Track the pinned authority/key continuity of the stable principal, preserve original signed provenance and historical key IDs, and accept a move only through verified continuity with local policy intact. A move can update routing; it cannot authorize new scopes or restore revoked app connections. An old provider that knew private signing keys is not cryptographically excluded just because the identity moved; changing that custody assumption requires a reviewed key transition.

## Recipient app controls and capability separation

Recipient allow/disallow decisions belong to the recipient's live ingress authority. Support independent controls for message delivery, notification suppression and optional action execution; accepting an app's messages must not automatically run its forms, share profile data or disclose read state. Check the block/connection generation during commit, delayed fanout retry and notification dispatch. Blocking prevents future work and suppresses pending notifications; already received content is retained unless the owner explicitly erases it. Unblocking requires fresh admission/binding where revoked and does not replay stale queued effects or old notifications.

Policy should key exact accepted sender principals, not mutable names/avatar/client strings. A broad “disallow apps” preference cannot prove that an adversary is human: an ordinary identity can omit a self-declared app kind. Enforce authentic connection/delegation classes and exact blocked principals, and state this limitation honestly. A verified declaration of app identity is not a verified natural-person test. System/developer badges remain a distinct protected provider assertion; a signed app cannot choose one by editing its profile.

Do not put a reusable contact URL/bearer into a generally subscribed private preference fragment. If apps A and B can read that field, both obtain its bearer authority regardless of which app the owner intended to authorize. Adding a sender signature does not repair a leaked grant if the recipient accepts both signers or if the grant lacks the intended sender binding. Shared quotas also make cross-app interference possible.

Prefer a protected per-connection recipient binding exposed through a scoped resource reference with only the approved send method. The provider resolves the original consumer from authorization and checks its exact sender/recipient/incarnation, instead of accepting a caller-supplied app ID or destination. The raw delivery bearer stays sealed outside app-visible preferences. Reuse existing generic resource/contract permission machinery where it can enforce this intersection; a dedicated UI connection is not justification for a parallel authority framework. Disconnect/revocation invalidates the binding and new dispatch, including derived references; changing a mutable View or profile fragment cannot broaden it.

Generic identity-scoped contact capabilities remain useful for independent senders, but need an explicit new signed-message/sender-binding profile. Scope includes allowed content/tags, recipient, sender identity or documented sender policy, quota, expiry and incarnation. Author identity and capability are checked separately. An action capability, profile capability, conversation secret, delivery capability and app signing delegation are not interchangeable. If a deliberate unbound bearer link remains shareable, label it as such and apply ordinary recipient policy; never imply that sharing it was limited to one app.

## Sender labels, app icons and notifications

Derive the notification actor from the stored verified sender record for the exact accepted message digest. Render bounded literal name/handle/provider text and visibly distinguish self-asserted presentation from verified principal and protected service badges. A malicious signed app can imitate a familiar name/logo; retain an inspectable stable identity/provider, and never use an icon as identity proof. Private owner nicknames may improve recognition but cannot alter cryptographic attribution. Owner lock-screen/privacy preferences may require a generic label or neutral icon even when the sender is verified.

The Notifications standard's resource-fetch algorithm uses `no-cors` with credentials mode `include` for icons/images/badges and action icons. Thus assigning a sender-controlled avatar URL directly to `showNotification` is not credentialless and can disclose notification timing or ambient browser credentials. Submission `credentials:'omit'` does not change that separate fetch. [Notifications resource fetching](https://notifications.spec.whatwg.org/#fetching-resources).

Use already obtained, policy-permitted profile/app-presentation bytes, bind their provenance to the verified sender, validate and decode bounded raster images, and cache an inert local content-addressed asset. Never fetch an arbitrary remote avatar while displaying a notification. Bound encoded bytes, dimensions, decoded size, animation and CPU; reject SVG/HTML/nested external references initially. Remote acquisition uses the separately reviewed resource policy/proxy and cannot forward cookies, follow redirects or contact private network addresses. A unique tracking URL still reveals a fetch to its operator even behind a proxy, so avoid per-recipient fetches and disclose any approved acquisition. Neutral local fallback must work offline and when profile sharing is absent/revoked.

The generic identity document remains minimal public verification metadata; app branding/avatar disclosure is a separate opted profile or independently bound app-presentation resource, not a reason to add private names, email or avatars to the public identity directory. Do not broaden a contact's profile scope or use a more permissive public fallback after revocation. Cache identity/profile version and disclosure policy as appropriate; use a captured permitted display snapshot for historical content and recheck policy for new disclosure. Revocation cannot retract an image already seen. A cached asset URL must not become a public enumeration oracle for private contact relationships; choose a browser-compatible private/cache delivery mechanism and test service-worker/offline notification behavior before claiming support.

Preserve trusted service UI outside sender styling; retain a neutral application badge/provider indicator where the platform supports it. App avatar means whose message this is, not that the app can impersonate the browser/OS/service identity. Platforms may substitute or omit custom imagery, so correct sender text and console detail must work without it. Notifications carry bounded privacy-approved presentation plus opaque local action locators, never recipient bearers, app signer delegation secrets, private profile capabilities or signature-generation authority.

## Email bridges and historical data

Inbound email without a Bindle signature is not a signed original-sender message. DKIM attributes responsibility to a signing domain, which may be a relay or organization, and explicitly separates that signer from the purported author. A bridge may sign its own wrapper and report checked transport provenance, but the label must identify the bridge and claimed email sender separately. DKIM/SPF/DMARC success does not establish control of a Bindle identity or approval to join a conversation. [RFC 6376](https://www.rfc-editor.org/rfc/rfc6376).

The bridge, imported archive, legacy contact message and new native signed message need distinguishable source/verification states. Never invent original-author signatures during migration. Preserve original bytes and verification context where retained, with the wrapper's exact transformation/content digest. Reprocessing an old message must not create a fresh verified-sender notification. All verified or unverified content continues through the same sandbox, resource-blocking and action-consent policy; a signature never enables author scripts or safe-HTML bypasses.

## Required tests and unresolved decisions

| Area | Required checks |
| --- | --- |
| Provenance | Mutated body/MIME/subject/tags/actions, forged senderMetadata/public key/client ID, wrong audience, missing/expired delegation, signature-algorithm mismatch; no verified label/rules/notification before successful validation. |
| Public clients | App A asks to sign as B; unapproved installer requests global app signer; valid user resource grant lacks app signer delegation; revoked connection races signing and delivery; provider restart preserves bounds and original caller. |
| Recipient policy | App blocked during delivery/notification retry, unblock/new incarnation, copied shared fragment/reference/bearer, different app signs same copied token, broad app toggle with self-declared kind; no accidental restored authority. |
| Identity continuity | Handle rename, duplicate UUID from untrusted host, migration with/without pinned continuity, old key revocation, historical receipt versus newly backdated signature, compromised rotation and conflicting keys; no silent merge or block bypass. |
| Replay/accounting | Fresh tokens/operation IDs, duplicate delivery across grants/devices, uncertain acknowledgement, finite dedup expiry, lookup floods and expensive signatures; no repeated notifications or unbounded quota-free work. |
| Icons/privacy | Cookie-preseeded icon host, unique tracker, redirects/private IP, huge/decompression/animated/vector payload, offline cache, profile revocation, malicious service logo and unverified sender; local inert fallback and accurate labels. |
| Compatibility | Old bearer contact/v1/unsigned email, adapter wrapper, imported history, new profile downgrade attempt, unsupported client, published schema identifiers; no false all-signed claim or silent broadening. |

Open decisions: exact signed-envelope/profile URI and canonical vectors; app-owner signer enrollment/delegation format and custody; recipient sender-binding contract and migration defaults; lookup/revocation freshness and offline delivery behavior; key compromise/rotation continuity; icon acquisition/cache/privacy mechanism; deduplication/history bounds and concrete work budgets. Cross-host adapters need independent verification tests, not only two callers of the same implementation. These are gates for enabling the profile, not claims of implementation.

The architecture is viable if sender identity, delivery permission, original app caller and presentation remain independent. Final designer cross-review is recorded below. Human signoff remains blank.


## Consolidated proposal cross-review

Read the frozen [ordinary sender identities proposal](../architecture/message-sender-identities.md) and its connection to the [message action design](../architecture/message-actions.md). No structural blocker was found in the provisional architecture. It correctly separates ordinary identity, app/client association, app-owner signer delegation, recipient connection/delivery consent and notification presentation. The public-client profile initially sends only to its consenting connection owner and explicitly does not establish trustworthy service-origin assertions such as payment completion. A genuinely authorized backend/workload remains a separate provenance profile.

The proposal also preserves the current v1 bearer-contribution distinction, minimal public identity document, original-caller permission intersection, protected per-connection capability placement and live recipient block/notification checks. It acknowledges that ordinary identity fields cannot prove app-versus-human status, that cross-provider revocation has bounded knowledge, and that previously held provider keys remain a custody concern after migration. The final wording explicitly treats a blocked UUID as the accepted authority/key-bound principal with verified continuity; an untrusted provider's duplicate UUID cannot merge identities, clear a block or replace accepted keys.

Source review and primary standards research support the recommendation; no new behavior was implemented or tested by this review. The exact envelope, delegation/custody enrollment, public contract, bounded lookup/revocation freshness, icon cache delivery and durable Worker/Node/cross-provider tests remain release gates. Human signoff fields remain blank.
