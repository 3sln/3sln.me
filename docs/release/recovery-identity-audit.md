## Security boundaries

A provider signature on a public name certificate proves historical issuance of a particular issuer, stable UUIDv4 subject and name assignment. The name certificate is separate from the encrypted identity recovery payload. That private payload binds the subject, identity keychain and random recovery credential, so claiming a name does not require replacing a recovery file. Current recovery additionally needs the live account's current random credential or transaction resume credential. Missing, blocked or permanently deleted identity authority cannot be recreated by presenting a certificate. Private keys do not recreate contact grants, quota state, revoked permissions or deleted data.

The current stable identity is the account UUID. Its existing P-256 signing key and identifier must be adopted, while a distinct encryption key is generated once. A replacement recovery file does not rotate a copied signing key or make old ciphertext inaccessible. Existing password/passkey/session recovery does not revoke verified-email login policy, all application grants or provider-held credentials. Account-key rotation and compromise remediation remain separate work.

The portable file remains susceptible to unlimited offline answer guesses. Exporting private keys increases the consequences of a successful guess. Provider token revocation cannot erase a copied private key. The public name certificate excludes private keys and recovery credentials; the whole-backup proof is private and remains inside authenticated encryption. A public certificate is never a bearer recovery credential.

## Permanent handle requirements

The user subsequently required that handles never be recycled, that free names use a shared/sharded number encoded as `n.<Crockford Base32>`, and that accounts which have actually paid for a subscription may claim one short name at any later time. A handle claim must therefore outlive login records, archived data, billing state and account deletion. The existing sharded handle lookup is insufficient: it intentionally releases stale links when the corresponding account is absent.

Use a separately retained, exact-handle claim ledger with immutable owner and assignment identifier. Lifecycle changes may mark a claim blocked, retired or deleted but cannot transfer or remove it. Hash-shard the full final handle. A successful claim remains consumed through billing lapse, account deletion and interrupted setup. Allocate only after abuse checks and signup admission; admitted failures can burn a number/name instead of reopening an ambiguous claim.

Numeric allocation must use a fixed set of global lanes. For example, 64 lane counters generate disjoint numbers as `sequence * 64 + lane`. This is not a per-name collision counter, and signup takes no user-selected base. Persist exact nonnegative integers, enforce an explicit maximum and handle-length bound, and never silently wrap or change the lane count/layout. Canonical free names use lowercase Crockford Base32 after `n.`. Input accepts case differences and maps O to 0 and I/L to 1 only in this numeric namespace. Paid names may contain only digits or other permitted short-name characters, and exclude dots; Crockford substitutions must not alter their spelling.

Counter and claim history must survive backup restoration. If restoration loses authoritative issuance history, fail closed until it is reconciled; an old backup alone cannot establish that no later name was issued. Existing names need grandfathered permanent claims before new allocation is enabled. Self-hosted issuers have independent namespaces; the same text under another origin is a different assignment.

Paid eligibility must come from durable evidence of an actual provider-verified positive subscription payment, with recent owner authentication, CSRF protection, admission limits and a bounded claim allowance. A currently active subscription alone is insufficient because a trial or manual grant may be active without payment. Client plan labels and checkout-success redirects confer no entitlement. A permanent owner-bound ever-paid marker must survive cancellation and expired billing snapshots; past payment permits the first claim later. Subscription expiration never releases an already allocated name. Provider customer, organization, subscription, product, currency and environment must match the configured account and catalog before recording payment evidence.

The current first-time payment scan is deliberately bounded to two pages of 100 orders. A qualifying verified order suffices; incomplete negative history returns a reconciliation error. This candidate recognizes unrefunded USD orders for the configured annual product, at least the current annual catalog amount. Discounted/historical-price/refund policy and live provider conformance remain explicit release limitations. A previously recorded qualifying marker is permanent and survives subsequent cancellation or catalog changes; no current-plan fixture can create that marker.

A paid upgrade should add an immutable alias to the same subject while preserving the original canonical name and historical routes. Replacing the stored canonical handle would violate shard invariants and break signed contact routing. Identity recovery is subject-bound and separate from the public name certificate, so an alias claim cannot invalidate the existing backup. Alias lookup and claim must bind the original account assignment as well as its UUID, preventing a recreated record from inheriting an old alias. A paid alias cannot inherit another subject's history or capabilities.

Required namespace adversarial checks include concurrent allocation and paid claims, interrupted claim publication, deletion followed by an attempted reclaim, paid lapse, old recovery files after paid upgrades, legacy migration, counter precision/exhaustion, restored stale counters, and permanent claims surviving ordinary stale-lookup cleanup. These requirements are not assertions that the corresponding implementation or evidence already exists.
