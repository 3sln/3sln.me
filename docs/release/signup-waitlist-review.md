## Capacity and availability

The latest requested limits are 10,000 free-origin admissions and 100,000 total admissions. These supersede the earlier undifferentiated 100,000 checkpoint. Public availability is advisory; an atomic server admission decision remains authoritative for stale pages, direct API calls and concurrent final-slot claims. The landing page must remain useful without JavaScript. A public cached status must contain no account/email data, must not vary on cookies, and must not create a global durable-object read on every landing request. Temporary status failures must not advertise guaranteed capacity or silently create a paid commitment.

The existing counter consumes nonreusable lifetime admitted signup attempts, including later failures, payments and deletions. It is not a live free-account census. Separating paid signup from that stock requires an explicit policy for later paid expiry, refund and downgrade: the current entitlement function automatically falls back to free. Allowing additional paid accounts while keeping that fallback cannot by itself prove a cap on currently free accounts. The final UI and design must name the invariant actually enforced, and must preserve existing count state rather than reset it.

The proposed conservative two-counter model should use the same existing admission authority and one atomic transaction. Existing lifetime usage seeds the free-origin count exactly once; free admission increments both counts, paid-pending admission only total. Old usage above the new free ceiling must close free admission without clamping or resetting. Migration version, counters and subsequent consumption must be validated together; missing/corrupt initialized fields fail closed. This bounds historical admission cohorts, including pending/failed/paid/deleted records. It intentionally makes no current-free census claim, and old uncounted/imported cohorts still require inventory reconciliation. The account's admission kind must survive setup and recovery resumes so selecting a paid lane cannot become a free activation bypass.

## Paid setup at capacity

Paid pending-account creation needs independent IP/network/global, retained-record and service-mail bounds; selecting a paid button is not proof of payment. It may not establish an ordinary session, resource authority or a free allocation. Existing contact verification, primary credential, terms and tested recovery requirements remain mandatory. Direct action invocation and forged success redirects must not bypass them.

Checkout creation and reconciliation must bind the exact pending owner UUID and setup incarnation to the configured provider environment, organization, product and external customer. Client-supplied amounts, checkout return flags, email equality and permanent paid-name eligibility are insufficient evidence. Activation requires fresh server-verified eligible current payment; provisional upgrade entitlements and stale paid history are insufficient. Out-of-order webhook/reconciliation results cannot overwrite newer revocation/refund state. Browser cancellation must prevent new dependent requests after local setup authority is cleared.

Current source boundaries matter: the webhook route ignores non-active owners; billing endpoints generally assume active sessions; permanent paid-handle eligibility is historical; and ordinary entitlement calculation returns free after expiry. Any pending setup extension should expose only bounded checkout/status/reconciliation operations under the existing pending-token binding. It must not broadly authorize pending users for account APIs. A successful charge followed by failed setup needs a resumable same-owner path and clear outcome, without creating another identity or pretending payment has been refunded.

Polar's primary API documentation confirms that an external customer identifier selects or creates the corresponding customer, while order/subscription creation events alone may precede successful payment. The final gate must verify paid state rather than merely receiving those events. [Checkout creation](https://polar.sh/docs/api-reference/checkouts/create-session), [order creation](https://polar.sh/docs/api-reference/webhooks/order.created), [subscription creation](https://polar.sh/docs/api-reference/webhooks/subscription.created). These documented semantics are not evidence that this deployment's provider configuration or payment delivery works.

## Waitlist consent, privacy and abuse

The authorized scope is double-opt-in email waiting-list registration and its confirmation message. It does not authorize sending availability invitations or promotional campaigns. Initial submission must be generic and nonenumerating, bounded before durable storage/mail, protected against arbitrary mailbox bombing and repeated token generation, and explicit about purpose/retention. CAPTCHA alone does not replace per-mailbox/network/system mail limits.

A confirmation token must be unguessable, purpose/domain/record-generation bound, stored as a verifier rather than plaintext authority, time limited and idempotent. Email scanner GETs must not silently enroll someone: the landing step should require an explicit confirmation action. Tokens and email addresses must not enter analytics, logs, referer propagation, Query or persistent browser storage; an immutable public/offline document cannot contain them. No arbitrary return URL, recipient text or attacker HTML belongs in the confirmation message.

Only confirmed consent enters the subscribed set. Expired/unconfirmed records, retries, cancelled registrations and delayed mail callbacks need bounded retention and generation fences. Repeated submission must not extend retention indefinitely or force additional sends. Durable deduplication and uncertainty handling must not count an unknown send outcome as safely unsent. The implementation needs an explicit withdrawal path and must not treat mailbox verification as account ownership, login proof or a reserved free-account slot.
