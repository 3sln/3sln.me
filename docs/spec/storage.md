# Object storage, provider adapters, and signed URLs

Canonical proposed publication URL: `https://3sln.me/artefacts/contracts/object-storage/v1`. It is a public versioned artefact, distinct from private account resources. The version is immutable after publication. The draft JSON Schema 2020-12 in `docs/artefacts/object-storage-v1.json` defines method request variants, argument bounds, metadata and result schemas. Runtime checks additionally enforce byte limits, UTF-8 key lengths, range ordering and authority. Publication and independent interoperability review remain pending. Unlike the first draft's mandatory write contract, this contract supports capability negotiation. Required `capabilities` truthfully reports read, write, list, byte range, read/write presigning, atomic conditional writes, byte limits, and operational limits. Apps request method scopes separately. A provider may expose read/list without writes, and the UI must say so. Changing a capability never expands an existing method grant.

Objects use stable logical keys, byte payloads, opaque versions, content type, size and modification metadata. List uses deterministic ordering and opaque, scoped cursors. Reads support inclusive `{start,end}` ranges only when advertised. Writes require `{absent:true}` or exact version conditions. Deletes require exact versions. No unconditional overwrite is implied. Driver errors map to safe protocol codes; upstream tokens and errors never reach clients.

`presign` requests a read or write bearer URL, HTTP method and required headers, with lifetime at most five minutes. The corresponding explicit presign grant is mandatory. URLs may expose data until expiry even after app/token revocation; approval must disclose this and offer proxy-only access instead. Upload signing needs content length/type bounds, namespace scope and required conditional semantics. Until these constraints are enforced, the implementation rejects presigned writes and advertises them unavailable.

## Provider boundaries

- Hosted R2: implemented driver prefixes every key with the owner/resource namespace and uses native R2 `onlyIf` for atomic create/update. Range reads and normalized paginated listings are implemented. Conditional deletion is explicitly unavailable because the binding does not supply atomic If-Match delete; head-then-delete would race. Browser users never receive R2 binding credentials. [Workers binding API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).
- S3-compatible: SigV4 signing via pinned aws4fetch; region, bucket and optional prefix; conditional write conformance is provider-specific. User configuration cannot assert it is verified. Arbitrary endpoints require an operator hostname allowlist; no user-defined private/IP hosts, ports or redirects.
- WebDAV: HTTPS, restricted root and endpoint allowlist; credentials encrypted in server storage; reads/listing first. Weak or missing ETags and unreliable conditional behavior prevent write claims. XML must be parsed with bounded non-DTD parsing; external entity expansion is forbidden.
- Google Drive: implemented direct-child read/list driver uses stable file IDs as keys, excludes native documents and shortcuts, and checks current parent membership and monotonic version both before and after downloading. A detected move/version change discards bytes. This minimizes the authorization race but is not an atomic upstream folder-scope transaction; strongly isolated production roots need a separately documented policy and race conformance. Drive metadata fields are documented in the [files resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files). OAuth application setup, consent, encrypted refresh, token rotation, and real-account verification remain outstanding. No Drive writes are advertised.
- Dropbox: implemented read/list driver uses explicit folder paths, normalizes lowercase path keys and verifies returned path/revision. It uses the [files API](https://www.dropbox.com/developers/documentation/http/documentation) and requires files.metadata.read plus files.content.read scopes; use an app-folder application where feasible. OAuth setup and refresh remain deployment integration gates.
- OneDrive: implemented Graph read/list driver anchors requests to a selected drive/folder. Listings reject remote items and parent mismatches; continuation links must retain the exact Graph origin/path. [Graph downloads](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0) expose preauthenticated download URLs: the adapter sends no OAuth header to that URL, follows no redirects, and requires its Microsoft download host to be explicitly operator-approved. Files.Read is the intended delegated scope; broader permissions require independent justification. OAuth application setup, folder-move race review, approved download hosts, and live verification remain gates.

Gateway network security does not rely on string URL validation alone. Operator allowlists must include only vetted public services; custom-host approval requires DNS/private-network checks and a safe egress policy. Credentials are sent only after endpoint validation, with redirect following disabled. Disabled/unconfigured provider cards must explain the required credential or operator setup.

## Release gates

Machine schemas, normalized object metadata, bounded XML without DTD/entity expansion, namespace-bound cursors, and mocked provider conformance tests are now present. S3 root `alice` lists only `alice/`, preventing `alice-other` scope leakage. Cursors are opaque encodings scoped to resource/query, not independent authorization; every call still needs a live gateway grant. WebDAV supports bounded Depth-1 listing without cursor pagination and fails explicitly if a requested limit would truncate results. Drive/Dropbox/OneDrive cursors preserve upstream paging; callers may receive empty filtered pages with a next cursor. Sorting is deterministic within a returned page, with no cross-page snapshot guarantee.

Provider response errors map to safe codes; token-bearing response bodies are not exposed. Range reads require an actual bounded partial response. S3 SigV4 GET presigning is restricted to the namespace and five minutes; uploads remain unavailable. R2 supports native atomic conditional PUT only; S3 writes require operator-reviewed conditional capability, and must never be enabled directly from an untrusted configuration flag.

Remaining gates include live credentials and provider conformance, OAuth refresh/revocation, DNS and connection-time egress enforcement, cross-owner gateway authorization, quota/rate enforcement, audited credential encryption, cursor retention policy, Unicode/name compatibility, and durable integration tests. Mocked adapters demonstrate request construction and defensive handling, not working production accounts. The Worker currently enables S3/WebDAV configuration only; OAuth provider cards must remain unavailable until authentication and live checks pass. No remote provider account was connected or altered during implementation.
