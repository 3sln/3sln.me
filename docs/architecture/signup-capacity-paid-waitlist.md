## Capacity and migration

Keep the existing `signup:lifetime-admission` durable authority and its `lifetime` global count. Add a versioned free-origin count in that same transaction. The configured lifetime admission ceilings are100000 globally and10000 for free-origin signup. A free signup increments both counts atomically; a paid-pending signup increments only global stock. Existing records without the new version migrate the free-origin baseline from their existing global count, because every earlier signup entered as free. Never clamp, reset, release or subtract failed, paid, deleted or pending admissions. An already consumed free baseline over10000 closes free signup; it does not revoke existing accounts. An initialized version missing either count, an unknown version or corrupt counter fails closed. The documented pre-counter account-inventory gate still applies.

These are lifetime admitted cohorts, not live free/paid occupancy. An originally paid account can later receive existing free fallback behavior after paid expiry without spending a free-signup slot; the100000 global bound still covers it. No claim that concurrently free accounts are limited to10000 is made. Overall release/signup gates and existing CAPTCHA/IP/subnet/country/hour/day guards remain. Paid-pending also has a tighter separate hourly/daily admission rate so it cannot bypass stock controls by selecting a paid plan without paying. No ordinary login, recovery or account read consults signup capacity.

`GET /api/signup/status` returns only booleans and reason: `signupEnabled`, `freeSignupOpen`, `paidSignupEnabled`, `paidSignupOpen`, `signupOpen`, `capacityAvailable`, `reason`, `waitlistEnabled`. `capacityAvailable` refers to free-origin capacity and can be null on failure; explicit lane booleans drive the UI. Read-only capacity snapshots coalesce per process and use one absolute60second snapshot lifetime across process and public edge caches on Worker, keyed only by origin/configuration. User query/cookie cannot create unbounded cache keys. No counts, account identifiers or identity-factory initialization are exposed. This projection can be stale; the durable transaction decides signup. Full free/global stock returns typed `signup_capacity_reached` with a bounded `capacity` discriminator and503, without a misleading time-based Retry-After.

## Paid setup boundary

Signup accepts `signupPlan` from the exact allowlist `free|paid|plus|ultra`, default free. The selected paid plan is persisted immutably on the new pending account along with a random setup billing incarnation. The paid lane is available only with live signup gates and configured billing. Selecting paid never grants a session, ordinary owner API, resource authority or uploads. Credential creation, verified contact, and downloaded/tested recovery remain mandatory. Recovery and credential-based setup resume preserve the admission kind/plan, billing incarnation and `initialPaymentRequired` marker; recovering an unpaid pending identity still requires payment. The marker is cleared only by successful first activation after fresh paid proof; later recovery of an already activated paid-origin account does not require repurchase. no UI reset can convert a paid-origin pending identity into a free activation.

Use pending-token + setup-browser-binding + exact-origin protected endpoints only:

- `POST /api/auth/setup/billing/checkout`: `{pendingToken,requestId,currency,priceDigest}`. Plan comes from the stored account. One durable lock per owner and immutable setup incarnation prevents repeated provider checkout creation, regardless of caller request ID or currency. A reviewed public catalog digest binds organization/product/parameters/currency/price; changed pricing requires review before creating a checkout. Known replay returns the original URL; any unknown attempt blocks a new provider create until separately reconciled. Provider uncertainty becomes an explicit unknown/recheck state; do not automatically submit a new financial request. Return only a validated provider checkout URL and bounded status.
- `POST /api/auth/setup/billing/status`: `{pendingToken}`. Reconcile the exact owner's verified provider customer/subscription and return a bounded setup projection. Current active or canceled-with-valid-paid-period status, the exact selected plan, provider organization/product and UUID external customer ID must match. Past-due retained entitlement cannot activate pending setup. Provisional upgrade credit, permanent paid-handle history, a browser success URL or client price never suffice.
- `GET /api/signup/plans?currency=usd`, a public bounded plan/catalog projection must reuse the existing validated Polar catalog. It must not synthesize a binding quote from marketing amounts. Show no paid checkout option when the catalog cannot be verified.

Checkout creation must reuse existing provider validation and bind metadata to setup incarnation without accepting caller-supplied owner, product, success URL or external customer ID. Return stays on the provider's account console and resumes the same pending identity; payment does not auto-activate. If browser pending state was lost, the configured credential resumes that same owner and rechecks provider state. Do not create a new account to recover a payment.

Before `confirmRecovery` can transition a paid-origin pending account to active and return its first session, recheck eligible paid entitlement through the injected setup-billing port, after validating the existing contact/credential/recovery requirements. The identity revision CAS still prevents duplicate activation and stale pending-token replacement. Billing and identity live in separate durable records: a provider payment check is a point-in-time verified observation, not a fictitious atomic transaction with Polar. A concurrent/later refund or expiry is handled by normal live entitlement enforcement; it cannot retrospectively make a completed provider check globally atomic. No initial activation uses a pending checkout or provisional plan. A provider outage keeps setup pending and allows safe retry.

Webhooks currently skip pending identities. Any added pending-owner path must be restricted to a stored paid-setup admission/incarnation and bounded reconciliation; do not open general billing/account routes to all pending accounts. Status polling alone must also recover from delayed webhooks. Abandoned setup remains bounded by global admission stock, paid admission rates, pending-token expiry and a 24hour checkout-start deadline fixed at account creation. Credential resume cannot extend that deadline. Expired unpaid setup cannot start new checkouts; a verified completed purchase can resume the same owner rather than being silently discarded. Automatic deletion of payment-uncertain pending accounts is outside this slice.

## Waitlist consent and budgets

`POST /api/waitlist/start` takes `{email,turnstileToken,locale}` and returns a generic202 response whether an address is new, already pending or already joined. Availability is live-checked: require configured waitlist + mail transport and a closed free signup lane (including the service signup release gate), or an explicit operator gate; never infer eligibility from cached browser status. Verify exact origin and provider CAPTCHA action, apply start IP3/hour, subnet20/hour, target1/10minutes and3/day, and global10/minute,100/hour,500/day mail/work ceilings before durable admission. Existing account association is neither looked up nor disclosed.

The portable waitlist service is injected with transactional metadata, cryptography, clock and mail transport. Worker and Node use the same policy. A fixed authority has at most1000 pending challenges and10000 joined rows; email values are encrypted at rest, lookup uses keyed digest, and confirmation secrets are stored only as hashes. Duplicate requests within cooldown do not resend. Email ciphertext uses AES-GCM with HKDF-separated keys and origin/purpose/row UUID AAD; lookup uses a separately derived HMAC key. A fresh random10minute token is mailed only after durable admission. Before any external send, claim its one send attempt; ambiguous transport results are not automatically retried or refunded. No raw email/token in logs or status responses.

Root-owned mail port is `sendWaitlistConfirmation({email,token,issuer,locale})`, using an existing verified system sender. It links to `${issuer}/waitlist/confirm#token=...`. A GET renders a confirmation screen only; scanners do not subscribe. The client scrubs the fragment and explicitly calls `POST /api/waitlist/confirm` with `{token,confirmed:true}`. The one-use unexpired hash is atomically exchanged for joined status; no account, session, handle, contact capability or paid authority is created. Joined membership expires after180days. Confirmation also returns a separate deletion-only `withdrawalToken`; explicit `POST /api/waitlist/leave` requires it and `confirmed:true`. Keep this token in transient private UI state or explicitly save it at user request. A new bounded email confirmation for an already joined address can rotate withdrawal authority without changing the original membership expiry, including when ordinary signup has reopened. Removal remains available during a mail outage or disabled new waitlist admission. Every old withdrawal token is invalidated atomically by a new mailbox-confirmed management proof. Bound expiry cleanup to32 index entries per operation/alarm; it reclaims pending slots without accepting replayed old tokens. Pending capacity and joined capacity must be enforced transactionally, with no unbounded per-request sweep or per-keystroke write.

This slice sends confirmation mail only. Automatic invitations when capacity reopens, guaranteed admission reservations, recurring campaigns and an operator export/dispatch console require a separate explicit workflow. The confirmation must not promise a reserved slot or a working account. No production mail is sent by development tests. The durable send claim and email transport are separate: crash or timeout can lose a confirmation, but must not silently resend an unknown attempt. Consumed network/global/target attempts are never refunded. Unknown caller tokens are gated by IP/subnet and16 finite service lanes before the shared waitlist authority. All counts represent nonrefundable admission attempts where external work is not atomic.

## Implementation checkpoint

The new portable capacity, paid-setup and waitlist modules are wired through the shared HTTP runtime and Worker/Node resources. Paid setup uses the account invocation gate; public root/static status never initializes the identity engine. `PAID_SIGNUP_ENABLED` still requires complete billing configuration; `WAITLIST_ENABLED` requires the confirmation mail port. Existing signup release, CAPTCHA, account contact/credential/recovery, network and provider gates remain. Public cached status is advisory, authoritative stock admission uses the original durable authority transaction, and waitlist start checks live eligibility.

There is deliberately no financial retry dispatcher, automatic waitlist invitation campaign, automatic abandonment deletion, or stock refund. A provider checkout outcome that remains unknown needs explicit operator reconciliation; the UI must not invite another create. A previously returned checkout URL may also expire at the provider. This slice does not establish a safe automatic replacement for that URL: the durable lock remains until reviewed reconciliation, and repeated status polls are not a promise that every expired/ambiguous checkout becomes usable. Do not reset the lock merely because current entitlement is free. Completed purchases can resume the same pending identity after the checkout-start deadline. Source-adapter tests do not prove live Polar/email delivery or preexisting production-counter inventory coverage.
