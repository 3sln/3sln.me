# Protected system identities and conditional developer contact

Provisional implementation proposal, 2026-10-13. **Superseded in part (2026-10-14):** developer contact is now one conditional link (`GET /api/developer-contact`, see [bindle-links](bindle-links.md)); the daily-grant issuance and signed `requiredTags`/`optionalTags` sections below are historical. This replaces the unshipped developer-feedback form. The current user direction is an explicit console action to request an ordinary developer contact capability valid for the current UTC day, with protected system handles and trusted badges. ## Policy and unresolved product input

The threshold is **1,500 active accounts**: below 1,500 all eligible local account owners can obtain the developer contact; at or above 1,500 only currently paid owners can. Lifetime admission usage is not the active population. The implemented provisional definition is authenticated owner use within the last 30 days, conservatively rounded to UTC days. Product approval remains unsigned; do not publish an exact count or silently reuse lifetime admissions. The developer's qualified identity is also pending; use operator configuration for an exact local owner UUID, never discover it from a display name or an unverified email.

The earlier status-only recommendation is superseded by the portable recent-activity implementation in [active population](active-population.md). It includes generation-pinned baseline census, bounded summaries and durable retry. Recovering accounts may be conservatively included from prior authenticated activity; suspension/deletion need not subtract an already counted activity window instantly. No ordinary user supplies the definition or a population estimate.

A contact token remains a **delegable bearer capability**. This proposal deliberately makes no claim that the message author is the account that received the link. A copied link can be used until its granted expiry, including after its beneficiary loses eligibility; beneficiary eligibility controls issuance, while ordinary scope, manual revocation and daily expiry control later use. This is consistent with existing bearer contact semantics. If the product instead requires authenticated sender identity, add an explicit sender-proof contract/profile rather than labeling bearer possession as identity.

## Protected namespace and account provenance

Add a centralized reserved-handle predicate used by ordinary paid-name validation and any legacy custom-handle allocation. At minimum reserve the agreed developer handle and operator-maintained system names such as `sys`, `admin`, `administrator`, `support`, `security`, `billing`, `verify`, `login`, `notify` and `accounts`. Normalize using the existing handle rules before comparison. Free numeric allocation keeps its existing namespace. Reserving a word does not make an existing ordinary owner trusted.

Ordinary signup, paid handle claims, rename, import and restore cannot acquire a reserved alias or set system provenance. An already occupied reserved name is a bootstrap conflict requiring explicit operator reconciliation; do not overwrite its owner or fabricate a badge. Permanent alias tombstones continue across account deletion. System accounts cannot ordinary-rename away from or transfer their protected alias in this slice.

The identity record stores an operator-authored immutable marker, for example `systemIdentity: {version:1, role:'developer'|'system', bootstrapId, assignmentId}`. An owner API accepts none of these fields. Public account/profile projections expose only a bounded server-derived badge such as `{kind:'system', role:'developer'}` where the UI needs it. Badge rendering uses this trusted projection, not matching handle strings, profile text or foreign app metadata. A self-hosted system badge is an assertion by that host, not universal trust. The marker grants no administrative RPC methods or implicit app/profile access.

## Generic one-use bootstrap

Provide a local operator command that signs a versioned one-use invitation for an exact configured origin, normalized reserved handle and allowed role. Use a separate 256-bit HMAC signing key and purpose-bound claims containing the intended owner UUID, assignment UUID, random nonce, issued time and expiry of at most seven days. Optional operator-pinned contact email is private setup policy, not public badge data. The signing key and invitation are written only to new exclusive private operator files with restrictive permissions; reads reject symlinks, unsafe ownership and permissions. Do not print either authority, place it in an argument/query URL, commit it, or expose a public GET that creates it. The operator transfers the invitation through their secure workflow; development tooling must never read it into a transcript.

A proposed `POST /api/auth/system/bootstrap` consumes `{bootstrapToken, method, password?, termsAccepted, termsVersion}` under exact origin and the existing setup-browser binding. It uses the ordinary input bounds, credential validation and protective request limits. The verified invitation supplies the handle/role; those are not freely chosen by the caller. This is a distinct operator-authorized admission lane, consuming the total account ceiling but no ordinary free-origin signup slot; it is not an unmetered public paid/free bypass. Ordinary caller `signupPlan` must never select this lane.

Use a durable bootstrap attempt record with reserved owner UUID, assignment ID and bounded generation. Verify exact typed claims and signature before durable reservation. The first valid use atomically reserves the protected namespace for the full invitation digest, intended owner/assignment and setup-browser binding; concurrent uses cannot allocate another owner. The global admission authority records a nonce-and-digest receipt in the same transaction as its total-only debit, so retries cannot consume another slot. A missing receipt for a reservation already marked admitted is corruption, not a new debit opportunity. Account creation is idempotent for that exact reserved identity and namespace claim. Once the pending identity is durably created, the record becomes `consumed` and no longer returns a fresh pending token to holders of the bootstrap secret. A crash while reserved resumes only the same intended creation under the bound setup browser, or requires explicit operator repair. Do not discard an uncertain reservation or issue another identity simply because a response was lost. Expiry blocks new and resumed invitation work; already reserved uncertain work requires explicit operator repair or safe fencing, and never releases the permanent namespace. The numeric canonical handle may consume an extra allocation after an uncertain response, but reconciliation must retain one intended owner and one immutable protected assignment.

The resulting account is **pending**. Existing primary credential, verified email/push, current terms and downloaded/tested recovery gates remain mandatory. The bootstrap marker does not create a session or bypass those checks. Credential/recovery resume preserves the same protected identity. Once setup is complete, the account uses ordinary login/recovery and inbox APIs. Bootstrap grants neither an unlimited storage plan nor an administrative application authority. Initial deployment requires an inventory check for reserved-name conflicts and explicit trusted provenance; it cannot infer that pre-existing `ray` or `admin` accounts are system identities.

## Population authority and issuance-only policy

The population policy is checked **only when an authenticated owner requests a daily contact token**. There is no population, billing or beneficiary-account lookup during message receipt. The user's latest instruction deliberately accepts that a granted daily bearer token remains valid until its ordinary expiry even if eligibility changes during that day. Recipient manual revocation remains available.

The implemented provider-internal port is `env.DEVELOPER_CONTACT_POPULATION.policy()`, returning `{definition, mode, observedAt, validUntil}`. Modes are `all-active`, `paid-only` and `unavailable`. Unknown, incomplete, corrupt, recreated-shard or expired evidence never means zero users: free issuance receives eligibility-unavailable, while independently verified paid eligibility can proceed without a usable population snapshot.

The 32 source shards retain unique owner UTC expiry-day membership; a bounded background census reconciles existing identity/owner activity before usable snapshots. Per-process singleflight caches retain the original absolute 60-second deadline. No global per-message lookup is introduced. Detailed rounding, startup duration, generation pins, conservative recent lifecycle counting and cache limitations are documented in [active population](active-population.md).

Population recording remains optional for account access. The owner saves a pending timestamp before a bounded source RPC and confirms its day only after acknowledgement. Failed/uncertain calls retain retries; a stalled source or invalidation cannot indefinitely block login/read/recovery. A partition blocking both source write and invalidation can temporarily leave remote observed activity behind; this is an explicit eventually repaired growth-policy limitation, not a hard global security ceiling. These implemented semantics supersede the earlier proposed status-transition registry. Product definition and production baseline completion remain review gates.

## Explicit daily contact request

Configure `DEVELOPER_CONTACT_OWNER` as the verified local UUID of the bootstrapped developer account. Verify that the destination is active and has the expected trusted role; never discover it from display text or lazily create it when an ordinary owner requests contact.

Proposed authenticated `POST /api/developer-contact` takes `{requestId}`. The console calls it only after an explicit **Request contact token** action. Exact origin, CSRF, active session and bounded owner/service work checks precede issuance. The caller cannot supply a beneficiary, destination, grant ID, arbitrary return URL, MIME scope or expiry. A read-only account projection may report `{available, reason, recipientBadge}` without any token. There is no mint during general polling, payment changes or navigation, no background renewal and no permanent developer connection.

Issuance requires an active owner and either valid `all-active` policy or a current eligible paid base entitlement. Historical paid-handle eligibility, provisional upgrade credit and past-due grace are insufficient. Unknown authority refuses issuance with a clear reason. Payment verification is a point-in-time provider observation; the resulting grant is not revoked automatically when that observation changes.

Success is `{granted:true, url, expiresAt, recipientBadge}`. Expiry is the next UTC midnight, optionally earlier at the verified paid-through deadline for paid-basis issuance. The UI shows the actual timestamp rather than promising 24 hours after every request. Refusal is `{granted:false, reason}` with bounded reasons such as `account-not-active`, `not-configured`, `paid-required`, `eligibility-unavailable`, `rate-limited` or `recipient-capacity`. Transport/API failures remain errors; they do not fabricate either a token or a definitive refusal.

Use the existing recipient contact grant/token machinery. Issue one parent per beneficiary/UTC day/verified tier. A bounded issuer request journal ties the beneficiary, UTC day and verified tier to an attempt/parent so concurrent clicks, changed request IDs and lost responses cannot create duplicate grants. A replay of a completed daily request can return that same unexpired URL without extending it; this is retrieval, not a fresh eligibility decision. Manual revocation does not permit an old request to recreate the grant. An uncertain cross-record issuance remains uncertain until the exact deterministic attempt is reconciled; do not allocate another parent merely because the response was lost. No separate per-message beneficiary identity or eligibility check is introduced.

The parent is restricted to the operator-configured developer contact collection, independently of tag-based organization, `text/plain` and `text/html`, a small maximum message size and finite message/byte totals for that day. Suggested initial grant bounds are five messages, 16 KiB per message and 64 KiB aggregate, intersecting the destination's existing stricter receipt/storage/work limits. These values are provisional pending the coordinator's implementation choice. Existing HTML sanitization remains authoritative. No file beaming, arbitrary collection access or profile-field disclosure is silently enabled.

### Required and selectable tag policy

The latest instruction replaces tier-specific destination collections with contact-grant tag policy. Add optional immutable `requiredTags` and `optionalTags` arrays to the ordinary contact grant. Required tags are always applied by the server; the sender may choose only tags explicitly allowed by the second array. The generic contact creator controls this policy for their own inbox; developer daily issuance chooses it from trusted server configuration, not caller-supplied tier or tags.

Use the existing tag bounds: distinct nonempty plain strings, at most 64 characters each, no control characters, and at most 32 distinct values across the required/optional union. Normalize a submitted selection defensively before any asynchronous work. Reject selected values outside the required/optional union, duplicates, malformed fields and an oversized result before blob storage, message quota debit or optional classification. The effective delivery tags are the deduplicated required set plus the approved selected set. Caller omission cannot remove a required tag. Policy arrays must be disjoint at creation. A sender may redundantly name a required tag; it is deduplicated, does not create additional authority and is not presented as a selectable option. The immutable endpoint and short-lived inbox JWT must inherit the exact tag policy, just like collection/MIME limits; rewrapping a token cannot remove required tags or widen choices.

The existing `senderMetadata.tags` field is currently untrusted freeform annotation. Preserve that legacy meaning for grants without a tag-policy profile; never promote old arbitrary annotations into trusted routing tags. For a grant with explicit tag policy, the same existing field can supply the selected subset, avoiding a separate transport standard. Expose the policy during authorized contact inspection so the composer renders bounded choices rather than guessing. Required tags can be shown read-only; selectable values render as literal labels, with known system labels translated through Bab. The stored tag identifiers are stable values, not translated strings. Unknown/custom owner labels remain literal text.

Persist the server-endorsed original `deliveryTags` with the accepted message and initialize its organizational tags from that set. Keep original delivery tags separate from mutable owner tags and raw sender annotations, so later edits/rules cannot retroactively alter the original match input. Extend existing rule validation narrowly with bounded `tagsAll` matching against original endorsed delivery tags, with no regex/evaluated expressions or cascading match changes; `tagsAny` is deferred. Existing rule actions organize the recipient's unified incoming store through tags/classification; tags are never identity, login or app authority. Views are filtered projections and are not delivery destinations. Hidden legacy collection authorization remains independent for old grants; the new composer offers no collection selector. See [the message Views design](message-views.md) for compatibility and migration boundaries.

The current verified issuance tier selects a required priority tag, for example `priority:free`, `priority:paid`, `priority:plus` or `priority:ultra`. The server-held matrix also defines the bounded optional category choices, such as `topic:bug`, `topic:feature` and `topic:general`. Higher-priority values must never appear in a lower tier's selectable allowlist. Bootstrap establishes the internal legacy ingress compatibility binding, stable tags and owner rules; only trusted operator/system administration changes the developer's matrix. The caller cannot supply plan, priority, resource or grant policy. Receiver rules match priority tags to organize the inbox; there is no separate per-tier submission collection requirement.

An explicit same-day upgrade may request a new parent for the newly verified tier. Keep at most one parent for each of the four tiers per beneficiary/UTC day, with retries reusing that tier's parent, so at most four new daily parents are issued. Earlier lower-tier parents retain their original tags and expiry. Later downgrades do not revoke or rewrite a higher-tier daily parent already granted. Matrix changes apply only to new grants; existing signed tag scope is immutable. The recipient-wide retained-parent cap may still cause a clear capacity refusal.

A token remains delegable: copied tokens can be used within the same scope and expiry, regardless of the beneficiary's later payment status. They do not prove sender identity and must not acquire the beneficiary's verified badge. Normal parent revocation by the recipient, signing-key revocation, quarantine, message limits and expiry still apply. Message receipt performs only ordinary contact authorization and admission; no new population or billing hot path exists. Already received messages remain the recipient's copy.

## Bounded daily grant retention

The current generic contact registry caps all retained grants at 1,000, including expired/revoked records. Daily issuance therefore requires bounded cleanup of expired internally tagged developer-day grants and their URL/name/request-journal side state. Preserve ordinary recipient-created contacts and all independent messages/history. Keep the finite cap and return `recipient-capacity` if bounded cleanup cannot make room; do not raise it indefinitely or scan an unbounded directory.

Existing delivery-token expiry is no later than parent expiry. Cleanup must honor that invariant, use a trusted time cutoff and avoid racing a still-in-flight deterministic issuance attempt. Expired issuer request journals may be collected separately from accepted-message replay retention. Their deletion must not accept an old payload twice or recreate a manually revoked grant in its still-current day. A new UTC day permits a new explicit request with a new expiry; there is no extension of yesterday's parent.
