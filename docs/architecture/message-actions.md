# Declarative actions and forms in messages

## Local presentation and summary implementation checkpoint

The owner-authenticated message response now retains the original `source` (plain text or HTML, with its SHA-256 digest), the conservative server `render` fallback, and a separate local presentation history. `messagePresentation` accepts an immutable request UUID, expected local revision and original source digest. Ordinary successful nonempty HTML postbacks append a local result and make it the default view; `redirect` and status dispositions append outcome history without replacing the current message. New `new-tab` presentation inputs are rejected; previously stored new-tab history remains passively readable. The original body and app admission signature stay unchanged. Each result is labelled `owner-local-result`; this API does not prove that an external endpoint actually returned owner-supplied content.

The current bounds are 128 KiB per result and 32 retained history entries per message. Result blobs use durable storage reservations, the account storage quota, logical work admission and the existing physical write guard. Commit rechecks the live message/revision; an orphan reservation is cleaned after failure. Exact request retries return their retained result, changed requests conflict, and deletion atomically releases retained usage and queues every original/result blob for cleanup. The latest history revision is the CAS frontier, while `selectedRevision` and `current.revision` identify the displayed body. History reads remain authenticated owner operations; there is no public raw-HTML URL.

The common intake adapter derives bounded notification summaries for normal messages, including app messages. Parsing uses at most 64 KiB of source and 8,192 nodes; subject/title/text limits are 120/240 Unicode code points and at most two 80-code-point action labels. These are current implementation limits, superseding the earlier suggested limits below. Hidden/script/footer/form-value content is excluded. Any inline style or stylesheet makes computed visibility unknown, so extraction falls back to the subject only; it does not pretend to compute CSS. Button-only forms and explicitly marked links can yield advisory source-bound locators only for an authenticated app's exact HTTPS origin. Sanitizer/parser differences mean those locators are never submission authority: opening the message must recompile the retained source and review the operation.

The first broker profile below implements controlled app-origin dispatch; it does not implement an arbitrary HTTP proxy, prove app authorship of responses, enable automatic notification execution, or replace isolated-renderer browser verification. Optional identity signing and broader authenticated-sender destinations remain separate gates. Public history/list projections omit blob locations, request fingerprints and internal deduplication IDs.



### Controlled postback and opt-in push checkpoint

Authenticated `messagePostbackPrepare` reparses the currently displayed original signed HTML with parse5 and uses the same pure form normalizer as the isolated frontend. A request contains only its UUID, current presentation revision/source digest, form index/digest and bounded name/value pairs. The server derives the exact destination, POST method and URL-encoded content type; no caller URL, cookie, authorization header, arbitrary HTTP method, file upload, multipart body, or identity-signing request is accepted. Unsupported forms stay readable but cannot use this profile. Hidden/static choices must match the retained declaration, selected values must be allowed, and undeclared fields or duplicate scalar names fail closed.

Actual dispatch is a separate, cookie-free POST. Authenticated preparation seals the exact fields, request identity, message/source/form bindings, provider origin and account authority epoch with the existing AES-GCM credential-encryption port. At most 16 preparations per owner survive for two minutes, with expiry alarms and deletion cleanup. The response contains an opaque 256-bit dispatch capability kept only in private caller memory. The public dispatch route requires that capability, the exact provider Origin, an empty object body and no Cookie header; the ordinary owner cookie cannot substitute for it. Only its hash is persisted outside the encrypted envelope. A purpose-separated HKDF/HMAC envelope binds issuer, owner, message, random nonce and expiry; the public route verifies it before any account lookup or actor routing. Dispatch rechecks current account authority and the live message/app/source, then atomically consumes the capability and persists the pending network intent in one owner transaction before the external request. A consumed operation with an unknown outcome is never resent. The original owner-cookie `messagePostback` entry point is no longer exposed.

Submission requires the original provider-signed app admission, matching original body digest, live app connection and Messages generation, current registered app origin, and a separate operator `FORM_POSTBACK_ORIGINS` allowlist. That allowlist defaults to empty. Generic legacy/unverified messages do not acquire broker authority; their ordinary links remain independently reviewable. A local HTML result revision also disables forms in this first profile: owner-supplied presentation HTML cannot inherit the original app signature. Continuation forms require a separately reviewed internal result-provenance binding; their appearance alone does not authorize another request. Status/redirect history that leaves the signed original as the current body does not disable its original forms. `formPostbacks.enabled` is a current capability hint, not a reservation of service capacity. Every POST rechecks authorization and budget.

Before network dispatch the owner actor persists a private pending intent. At most 32 request IDs and fingerprints are retained per message until its erasure; unresolved attempts retain their deduplication fence beyond the 24-hour operation deadline. Exact retries return a retained result or explicitly unknown outcome and never repeat the external request. If a result was committed but its completion marker was lost, replay reconciles against that retained history revision. Fields, endpoint credentials and response bodies are not copied into intent metadata or public list/index projections. A stable receiver idempotency header is supplementary: the remote service may not support it, so Bindle makes no exactly-once external-effect claim.

Initial nonrefundable network limits are 10 starts per owner per UTC minute and 100 per UTC day, plus 16 finite service partitions of 625 starts per independently timed 24-hour window. These are additional to normal logical work and storage/physical-write safeguards. The broker checks room for a 128 KiB result before dispatch. Result bodies remain in quota-accounted blobs; history metadata also has a 120,000-byte encoded ceiling, with conservative headroom checked before dispatch. This may stop a message before the 32-entry maximum. Timeouts, crashes and ambiguous remote outcomes consume attempts and cannot trigger an automatic replacement request.

Fetched HTML result viewers are deferred. Forms with `target="_blank"` are unsupported and stay inert; preparation rejects them rather than silently changing their destination to inline. Successful nonempty `text/html` responses normally become retained local presentations. A `Bindle-Target: _blank` response instead retains an info status, “Submitted. Opening this response in a separate tab is not supported yet.” The returned HTML is neither exposed as a viewer result nor stored as a replacement body. Redirect responses are not followed: only a validated HTTPS Location is returned for separately reviewed new-tab GET navigation. Every non-HTML, empty or 204 success becomes a status toast without body replacement. `application/vnd.bindle.submission-status+json` accepts exactly a success/info/warning/error type, at most 500 plain-text code points, and optionally two plain-label HTTPS navigation links. No styling, JavaScript or effect descriptors are accepted. HTTP errors always remain error outcomes even if a body says success. Unknown remains distinct from known failure.

Node transport pins a validated public IPv4 DNS result to the TLS connection while retaining hostname certificate verification. Worker transport uses an explicit reviewed-origin allowlist, public A/AAAA screening and `global_fetch_strictly_public`; screening is not connection pinning and a DNS change between screening and fetch remains a documented limitation. Both transports construct a small fixed header set, omit ambient credentials, prohibit redirects and bound request/response bytes, concurrency and elapsed time. A new-tab browser visit is a distinct navigation and can use the destination's ordinary browser cookies.

Push previews require explicit `push.preview` consent, default false. Generic notifications continue to hide content; opt-in app previews identify the registered name and exact origin and include bounded derived text and at most two advisory locators. No remote icon URL or form values are sent. Clicking opens the authenticated foreground message; it never dispatches a form automatically. Preview withdrawal is checked again after notification claim, alongside existing channel/unread/quarantine and live app-connection checks. Browser/OS support and the frontend's actual isolated viewer remain separate validation gates.

## Recommendation

Allow a message to carry a bounded, authenticated action description alongside its content. Bindle renders its fields and buttons, obtains an explicit submission decision, sends a cookie-free request under that action's narrow capability, and retains the outcome as an append-only revision of the recipient's local message. The latest resulting state is shown by default; original content, submitted action and result remain inspectable in history. Submission does not create a conversation reply or disclose the outcome to other participants unless a separately reviewed action explicitly does that.

Use Shadow DOM to contain author CSS **inside an isolated message document**. Use `setHTML()` where supported as one HTML sanitization layer, with an equivalent reviewed fallback. Author JavaScript never executes. Neither Shadow DOM nor HTML sanitization is the security boundary. User controls govern remote resources; default to blocking them before any message markup is mounted. Trusted origin, identity-disclosure and submission controls remain outside author styling.

Ordinary identity messages in the new profile use a verified sender identity as specified in [message sender identities](message-sender-identities.md). Frontend-only [app notifications](app-notifications.md) instead use the owner’s explicitly approved app connection and provider-signed local provenance, without an app identity or contact token; do not relabel that record as an app-identity signature. This does not make an app connection the app’s global identity or grant it delivery/notification permission. Optional identity disclosure below concerns the recipient’s action submission, not an unsigned-message exemption.

Do not require prior app connection for every action. Support two target profiles through the same declarative description: a pinned HTTPS postback associated with the authenticated message sender, and an explicitly approved connected-app resource/contract/method. Restrict association and destination precisely rather than requiring all legitimate sender infrastructure to share one origin. An arbitrary HTML `action` attribute is never dispatch authority.

## Description and public protocol boundary

Define a versioned, inert message-action part, bound by digest to one immutable message revision. Authors may write supported native HTML forms: an authoring adapter compiles them into this bounded description and authenticates the description together with the content digest under one of the two provenance profiles below. Receivers independently extract/check supported fields rather than trusting arbitrary HTML behavior. A hand-authored JSON form is not a requirement for authors. It is a proposed optional message/conversation profile, usable for standalone contact messages too. The exact part carrier and schema require a small follow-up specification; do not silently reinterpret existing arbitrary HTML or accept unrecognized fields through today's sender metadata. Existing readers show the content and an unsupported-action indication. Existing contact grants must explicitly admit the new profile/MIME before storing it, under normal receipt and byte limits.

Reserve a future immutable action contract/schema identifier through the normal public artifact process. A candidate name is `message-actions/v1`; this draft deliberately does not advertise an unpublished URL as a working contract. No stub belongs in the public registry. The final machine definitions must distinguish the action-part schema, submission/result envelopes and optional resource-RPC adaptation.

The minimum action description is:

| Field | Required meaning |
| --- | --- |
| `id`, `revision` | Stable action identifier and immutable action-description revision. |
| `messageBinding` | Message identity, exact author/content digest and local presentation revision being acted upon. Mutable subject/title is not identity. |
| `issuer`, `proof` | Either an independently pinned issuer signature, or verified connected-app provenance and host attestation tied to the current approved connection/binding. Both bind the canonical description, parent message/content digest and all behavior-affecting fields; a caller-supplied app ID/public key is insufficient. |
| `target` | Exact HTTPS postback endpoint, or exact approved resource/contract/method and binding revision. No client-selected URL or dynamic method. |
| `association` | Proof that this sender controls the target service or has narrowly delegated this action to it. |
| `inputSchema`, `fixedArgs` | Strict bounded field types plus disclosed immutable arguments. No expression language, remote schema references or implicit hidden arguments. |
| `presentation` | Plain labels/help and optional sanitized layout hints. These cannot change the schema, arguments or destination. |
| `effects`, `identity` | Declared effect and optional identity-disclosure request. Sender claims do not determine the host's risk classification or consent rules. |
| `authority` | Opaque action-scoped capability, expiry, live action generation, usage allowance and the issuer's outcome/status interface. Kept outside author DOM and notification payloads. |
| `resultSchema` | Pinned supported result kinds (`postback`, `navigate`, `acknowledged`, `pending`, `error`), local projection policy, optional bounded inert HTML and permitted navigation origins/presentation. A response cannot replace this schema. |

An initial schema should reuse the callable adapter's strict object with at most 16 scalar fields, explicit string/numeric bounds and bounded enums. Exclude files, arbitrary nested data, passwords, authentication codes, passkeys, recovery material, executable validation and resource pickers from the first generic form profile. A displayed email field is ordinary user-entered data, never verified email ownership. Proposed initial ceilings: four actions/message, 32 KiB total description, 16 KiB encoded submission, 32 KiB result and a seven-day action lifetime. These are reviewable starting limits, intersected with smaller account/receiver limits, not throughput promises. A one-button action has no editable fields; its fixed arguments are part of the authenticated, visible description.

### Two targets, one consent model

For a connected app, resolve only an already approved resource binding. Present the exact callable revision and validate with the existing binding/command adapter; the dispatcher retains the original caller and intersects live resource/method permissions. A message cannot upgrade an assistant/app caller into the owner, install a command, request new resource preferences, borrow a contact token or acquire a profile/storage grant. New permissions use the ordinary separate review flow before the action becomes available.

A frontend-only public-client app does not need its own backend secret or standalone signing key. In the connected-app profile, the host verifies the actual registered app connection, original caller, approved method and binding revision, then attests the exact descriptor/message provenance through its existing trusted authority. To assert authorship as the app’s ordinary identity, it must additionally hold that identity owner’s explicit purpose-scoped signing delegation, bound to the recipient/connection; a registered public client or recipient approval cannot create that authority. The newer local app-notification path does not need that identity delegation: local connection provenance is labelled as such and cannot be presented as an app-identity signature. Its approved method can authenticate a local action descriptor under the same limited connection authority, with independent target/effect review. A deliberately user-authored message requires separately approved user-signing authority and is labelled with that user as author. An app name, manifest URL or arbitrary supplied public key cannot substitute for that proof. If the action is exported to another host, that host must verify an explicit attestation with issuer/audience/expiry and binding semantics; a local assertion alone is not portable authority. This is a narrowly scoped adaptation of existing connection/resource permissions, not a new app-state system. Never copy current resource grants or broad app tokens into a form. Provenance does not authorize the receiving owner's resources: when author and recipient differ, resolve only the recipient's separately approved binding and intersect the live original caller/resource permissions again at dispatch. An author-host attestation cannot select or borrow that recipient's resource grants. The attestation format and cross-host verification are implementation gates.

For a general message, the issuer grants a narrow postback capability to its own endpoint. No connected app or ambient login at that service is necessary. Proposed wire operations are `submit` and `status`, using bounded JSON bodies over POST; both use the same pinned endpoint and exact action authority. The ordinary Bindle RPC envelope can adapt these when the recipient is a Bindle resource. A plain HTTPS service can implement the same published action envelope without implementing Bindle account login. Do not turn this into a generic webhook proxy.

A minimal submission binds `{actionId, actionRevision, messageDigest, transactionId, input, fixedArgsDigest, identityProof?}`. The capability travels only in the explicit authorization field/header of this protocol. A successful result binds the same action, transaction and request digest and declares `accepted`, `rejected` or `pending`, with bounded typed display state. Transport success alone does not mean an external effect completed. `status` can resolve a known transaction without repeating its effect. Servers that cannot honor the required idempotency/outcome semantics cannot advertise this profile; arbitrary legacy forms stay inert until a reviewed adapter exists.

## Origin association and cookie-free submission

Default association is an exact HTTPS sender-service origin whose action-signing identity is independently established. Support cross-origin service infrastructure through an authenticated delegation pinned in the signed action: exact destination origin/resource, contract or submission profile, action ID/revision and expiry. An allowlisted company name, matching logo, registrable-domain suffix or `Reply-To` is not proof. A human sees the actual ASCII hostname, sender identity provenance and any cross-origin delegation before submission. Same-origin is a useful default, not a substitute for capability validation or trust.

A contact link authenticates permission to deliver to its owner; it does not authenticate the sender or endorse a form. Unsigned email/HTML cannot become an active authenticated action by claiming a name or embedding a public key. The general HTTPS action proof must bind an independently resolved/pinned issuer identity or reviewed service identity. The connected-app alternative uses the verified connection and host attestation described above; it does not require a public client to invent a private signing secret. Unknown/unverifiable descriptions remain inert. A correctly signed malicious sender is still untrusted; signature verification establishes provenance, not honesty or safety.

Use a trusted host submission broker by default. Prepare its very narrow dispatch authority after an authenticated local review, then use **no cookies on any submission hop**. Browser calls use `credentials: 'omit'`, `redirect: 'error'`, `referrerPolicy: 'no-referrer'` and a fixed content type. The broker receives only a short-lived purpose-bound dispatch capability, not the owner's session cookie. Its upstream request uses an allowlist of constructed headers, no cookie jar, no forwarded Cookie, no ambient HTTP authorization, no client certificate configuration, no inbound owner/app OAuth token and no Referer. Ignore `Set-Cookie`; never automatically follow an upstream redirect. The server broker may capture a redirect Location without following it and convert it into the validated navigation result described below; browser-to-broker fetch still rejects transport redirects. This is cookie-free submission with explicit action authority, not an unauthenticated open relay.

The dispatch capability binds the owner-copy/action revision, destination, method, schema/input digest or prepared transaction, maximum bytes, short expiry and allowed history update. It cannot read the owner's other messages or invoke arbitrary account methods. Access to the local account while reading/preparing an action still uses normal authentication; that is a separate operation from the credentialless submission. An external client holding the action capability can likewise submit without a Bindle session, but it gains no permission to write a different owner's local history.

Fetch's omit mode governs credentials for that request; it does not constrain unrelated image, style, native form or navigation requests. Browser-direct submission is a later optional profile, not the initial privacy baseline. It exposes the client's network metadata and requires explicit destination CORS support; browser/enterprise client-certificate behavior prevents promising universal anonymity. [Fetch credentials model](https://fetch.spec.whatwg.org/#concept-request-credentials-mode), [browser CORS credential caveat](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#preflight_requests_and_credentials).

Broker egress must resolve only the pinned exact public HTTPS destination, reject userinfo, fragments, ambiguous encodings and local/private/link-local/metadata addresses, and enforce address pinning or an equivalent platform egress restriction across DNS resolution and connection. No automatically followed redirects, arbitrary ports, URL templates, user-selected callback URL or response-driven second broker request. Capturing a Location as inert result data does not authorize fetching it. Request/response, decompression, time and retry bounds apply before expensive work. If an adapter cannot enforce the network boundary, it cannot offer general server-broker postbacks; this is an implementation gate, not a DNS-check-only SSRF claim.

### Optional identity proof

Default to submitting without identity disclosure. If the person explicitly chooses to identify themselves, sign a fixed domain-separated intent using their established identity-signing key: protocol purpose/version, issuer/subject/key ID, exact target audience, message/action digests and revisions, transaction/request digest, short issue/expiry times and a bounded nonce. Never sign arbitrary server text, arbitrary hashes supplied by the form, a login challenge or a reusable authorization statement.

The signature is an assertion about this exact action. It grants no conversation admission, profile fields, payment authority, account session or future signing permission. Display the identity and disclosed stable identifier outside author CSS, with the actual destination; a silent “optional” checked default is not consent. A notification shortcut never newly requests identity signing. The current provider-custodied keychain may support a narrowly injected signing port; do not export private JWKs to form code or add a general signing oracle. Existing custody and recovery limitations still apply.

The action service/issuer issues a distinct endpoint capability per delivered owner copy/action. The owner's broker can separately issue the short-lived local dispatch capability after review; it does not mint authority at the external endpoint. In anonymous mode this is a bearer capability: a holder can forward it, and the target must not call it proof of the named recipient. Where non-delegation is required, the target must advertise an identity-bound profile and require the corresponding explicit proof; it cannot silently change an anonymous action into an identity requirement after review.

## Rendering CSS and forms without executing author code

Keep each rich message in an opaque-origin sandboxed iframe. Host the message's Shadow DOM inside that document for style containment. Do not place untrusted HTML/CSS directly in the console's shadow tree and assume that isolates cookies, navigation or network effects. A closed shadow root is not an authority boundary.

For the interactive spike, a fixed trusted renderer script may run with `sandbox='allow-scripts'`, without `allow-same-origin`, `allow-forms`, popups, downloads, top navigation or custom-protocol permissions. Its restrictive CSP is active before parsing/inserting any author material: no author scripts, no network/connect, no native form submission, no frames/objects/base changes. Author styles can affect the isolated content; only reviewed style syntax and local approved assets are admitted. The fixed renderer script uses a pinned hash/nonce under the host's control. Do not rely on a CSP `sandbox` directive in a meta element: that placement does not enforce it. [CSP sandbox behavior](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox).

Use safe `setHTML()` with an explicit allowlist where available; test the exact intended configuration and template/ShadowRoot operation, not just whether a method name exists. Strip author scripts, event handlers, script URLs, embedded browsing contexts, custom elements/declarative shadow roots, navigation/base metadata and unintended submission attributes. Sanitization does not validate action authority, prevent deceptive text or implement CSS network policy. Do not sanitize, serialize, and then reparse with `innerHTML` in a less protected context. [HTML sanitization standard](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html#html-sanitization), [setHTML compatibility and safe insertion](https://developer.mozilla.org/en-US/docs/Web/API/Element/setHTML).

### Staged fragment and handler pipeline

Follow the user's proposed ordering: **sanitize → policy traversal/form extraction → install trusted submission handlers → mount**. The staged result is a fragment, but native `setHTML()` is defined on Element/ShadowRoot, not directly on `DocumentFragment`. A `<template>` element whose sanitized content can be safely extracted is a candidate for the browser spike; its parsing/resource inertness and supported sanitizer configuration must be demonstrated in each engine. Do not invent `fragment.setHTML()` or assume a detached `<div>` cannot fetch images before traversal.

Create the isolated sandbox/CSP-denied parsing context first. Sanitize author bytes there, then traverse without mounting into the trusted application document. The traversal enforces the same stricter structural policy for either sanitizer: supported forms/control types, unique bounded field names, matching action IDs, literal labels, bounded values, approved CSS and inert resource references. Reject duplicate names, external form associations, unsupported custom elements and controls outside the described action. Strip native submission destinations, `formaction`, `form`, `target`, base/navigation metadata and resource URLs before any candidate becomes renderable; preserve only validated inert action identifiers in a private descriptor map. A native URL attribute is never temporarily installed as a functioning submit target.

For HTML-authored forms, compile the supported subset into the same typed internal schema/arguments and compare its behavior-affecting fingerprint with the authenticated authoring description. A changed label cannot change destination, and an extra hidden input cannot become an extra argument. The first profile requires an authoring/receiver conformance corpus so parser normalization cannot silently produce different semantics. Unsupported markup degrades to inert content, not a best-effort weaker action.

Install trusted handlers only after policy validation succeeds. Keep authority in closures keyed by internal action IDs; never look it up through `document[name]`, clobberable form properties or author-named globals. `preventDefault()` stops normal interaction as a convenience, while sandbox restrictions and `form-action 'none'` remain effective if a handler fails or disappears. Handlers produce a typed candidate for the host review/broker; they never call an author URL, sign data or dispatch privileged commands directly. Move/adopt only reviewed nodes into the isolated message ShadowRoot. Do not serialize and reparse the sanitized tree or append new unvalidated markup during handler installation. Bind disposal and revision changes to the descriptor map and MessageChannel generation.

### Lazy sanitizer fallback

When the exact native safe-insertion path is unavailable, lazily import a pinned, self-hosted DOMPurify adapter from the application's content-hashed `@3sln/js-tools` output. Use an app-local interface returning the reviewed fragment; do not patch a fake global `setHTML()` with different behavior, fetch a latest package from a CDN while opening a message, or load anything selected by message content. The same policy traversal and handler pipeline follows native and fallback sanitization.

DOMPurify provides an HTML-only profile and a DOM-fragment return option; its documentation also warns that later unsafe markup changes can undo sanitization. Check DOMPurify's supported-environment result and never accept an unchanged-input fallback as sanitized output. Configure a tested HTML-only policy plus the project's stricter form/CSS/resource traversal rather than treating defaults as message authorization. Its profile option overrides the tag allowlist, so do not assume combining both produces an intersection. [DOMPurify official implementation and guidance](https://github.com/cure53/DOMPurify).

Native/fallback outputs need matching **security and form semantics**, not byte-identical serialized HTML. Pin the package/version, preserve the actual upstream Apache-2.0/MPL-2.0 licensing and provenance (do not relabel it MIT), test both paths with the same hostile/benign corpus and verify the lazy module's content integrity. Cache the already trusted module on first use through the existing versioned service-worker asset mechanism; optional prefetch must not load author-selected code. If it is unavailable offline or fails integrity/loading, show safe text/inert content and disable active forms until the approved renderer is available. No raw-HTML fallback. The isolated helper's CSP/build manifest must allow only the exact pinned fallback module and its fixed dependency graph, with tested module CORS/integrity and credential behavior. No wildcard script source, unsafe eval, author-selected import or remote-resource relaxation is permitted just to make lazy loading work. This adapter and its offline behavior are proposed work, not an implemented package integration.

Forms may be visible within the layout, but trusted code builds or binds their controls from the authenticated schema. Native `action`, `formaction`, `target`, `method`, `enctype`, arbitrary hidden inputs and DOM-derived destination URLs have no execution role. No automatic browser autofill of identity, password-manager integration or synthetic submission. The host receives a typed candidate only; its independent schema validation rejects additional fields and its review displays effective inputs and fixed arguments. The author cannot hide a privileged argument behind CSS or present its own approval chrome as the actual host confirmation.

Communicate via a dedicated MessageChannel established by the host with the exact iframe window and unpredictable frame-generation nonce. An opaque frame's `origin: null` alone is not authentication. Bind every message to the local owner/session context, message/action revision and current frame; discard stale channels after navigation, account switching, edits or disposal. Author HTML never supplies host event handlers, ngin Actions, dependencies, templates or executable portal modules. Use the existing 3sln stack for the trusted form/review controls; author strings remain literal data rather than Bab or UI expressions.

### User-controlled remote resources

Default-block images, remote stylesheets, fonts, media and all URL-bearing CSS/HTML before mounting the document. Reading a message, receiving a notification or focusing a field must not contact its sender. Offer per-message permission to load a bounded declared resource set, independently of action submission or identity disclosure. A user may submit a form while keeping remote media blocked.

Prefer locally stored message attachments and content-digest references. For explicitly approved remote assets, fetch only the exact signed resource table through restricted credentialless egress, once independently of form inputs; validate MIME/bytes, process inert images and rewrite the sanitized document to local bytes/blob references. No live wildcard proxy URLs in CSS. CSS selectors, fonts and conditional `url()` rules can otherwise leak values or interactions through which URLs they request, even when the proxy hides the user's IP. No resource URL may interpolate inputs, action tokens or identity. Disallow executable/vector/document payloads in the first image profile; rasterize or reject them. External CSS imports and fonts remain unsupported initially.

Explain that consenting to fetch a remote resource can still disclose a resource-specific request to its server. A proxy does not erase unique tracking URLs or timing. Applying a block after a resource has loaded cannot recall that disclosure. Limits cover dimensions, decoded size, decompression, nested references and CPU, not just HTTP Content-Length.

## Explicit dispatch, replay and changing state

Before any dispatch, revalidate live action capability/generation, message revision, schema and origin association after review. The sender cannot choose a UI label that makes a privileged effect low-risk. Password reset, payment, account deletion, credential/permission changes or sensitive data export require their own trusted application flow; generic message buttons do not inherit that authority. No submit on render, field change, focus, preview, GET, scanner visit, push receipt or background fetch.

Default to a one-use action capability with a stable transaction UUID and canonical request digest. The endpoint atomically checks authorization/revocation and records admission with its idempotency journal before applying a supported effect. Same transaction and same bytes returns its authorized existing outcome; changed bytes conflict. Different transaction IDs cannot bypass a consumed one-use capability. A schema or contract update does not change a previously admitted request. Repeatable actions require an explicit bounded profile, not fresh IDs generated after each timeout.

Remote effect and local history append are not one transaction. The client/provider persists its bounded local pending intent before dispatch, preserving the same transaction and capability under encryption for reconciliation. On timeout, cancellation or process loss, show unknown/pending; a spinner ending is not proof of cancellation. Retry only the exact operation when the endpoint's published journal semantics permit it, or query its bounded status method. Never create a fresh financial/action transaction merely because a response was lost. Retain deduplication/outcome state for the complete capability and allowed reconciliation horizon; expired authorization must not permit a private cached-result replay without the specifically scoped outcome permission.

Apply finite per-owner and per-original-consumer attempt/intent limits, plus per-action and per-destination submit/status/signing/egress budgets. All action IDs and request IDs share the owner's aggregate ceiling; minting another capability cannot reset it. Reuse the existing owner work/storage admission and HTTP attempt guards, adding only these scoped lanes where needed. Status polling, denied attempts, signature generation, remote assets and response-history writes are not free unbounded work. The service endpoint enforces its own aggregate and per-capability limits independently. No global hot counter is required for each click. The spike must select exact finite defaults and test exhaustion before enabling dispatch; missing budget configuration disables the feature. Reserve bounded pending-intent/result-history capacity before sending so quota exhaustion cannot erase an already attempted external effect. Replays retain their original transaction while still passing live authority and cheap attempt guards.

An edit or tombstone disables outstanding actions for every owner who knows the new message revision. The endpoint also checks its current action generation, invalidating prior capabilities when the issuer updates/cancels the action. A new generation requires a new description and fresh review; it cannot reuse old approval. Independent providers may learn edits/revocation at different times. Claim only local-known-revision and endpoint-live-generation guarantees, not instantaneous global invalidation during partitions. Exact coordination between an author's edit journal and a third-party action service is a conformance gate; disconnected endpoints cannot honestly promise immediate revocation.

If an old action completed before an edit, its receipt remains part of history. If its response arrives after a newer message/postback state, attach it to the original action/revision and show that ordering; do not overwrite the newer current view. Local block, owner erase, sign-out or access revocation prevents further local submissions and disables outstanding dispatch authority where revocable. They do not undo already committed external effects. Local erase can keep a minimal bounded reconciliation/tombstone record without retaining full form contents.

## Postback history and the default final view

Store separate immutable local events for `action.prepared`, `action.outcome` and a validated `message.localProjection` revision. Link the transaction, request/result digests, original message/action revisions, receipt provenance and prior projection. The latest applicable final projection is shown by default with a clear action-result label and a history affordance. Original author content stays available under the owner's normal retention; the postback does not conceal it or pretend the original author edited it.

The result can replace the local displayed state only within the authenticated result schema/projection policy: bounded status text/typed fields or an explicitly admitted bounded HTML postback. Returned HTML follows the same protected sanitize/traverse/mount pipeline in an isolated result viewer, never the portal DOM. It introduces no active forms, capabilities, new endpoints, role badges, notification permission or changed result schema. A result is endpoint-provided local outcome content, not a new sender-authored message revision merely because it contains HTML. TLS/broker receipt proves which endpoint responded; only a verified issuer signature proves author provenance. Preserve that distinction in the history label.

### Submission and result presentation

An eligible notification button opens/focuses its message and starts the already-authorized fixed-argument action, showing **Submitting…** in trusted UI while the operation is pending. The intentional click can authorize the exact advertised low-risk action under the host policy below; it never authorizes hidden fields or a fresh identity disclosure. If review, account selection, unlock or additional consent is needed, open the message at that review step before sending. Ordinary form submissions use the same progress/result handling. Prevent duplicate clicks from starting another transaction.

Interpret results using a small explicit profile:

| Result | User-visible behavior |
| --- | --- |
| Valid `postback` with ordinary local presentation | Append the outcome and retained local message revision, then show its latest final state by default with history available. |
| Valid redirect/navigation result | Offer a validated HTTPS navigation link; retain the local outcome and destination/provenance in history. |
| Form `_blank` / response `_blank` hint | Form unsupported before dispatch; a response hint retains an info status without opening or replacing HTML. Fetched HTML viewers are deferred. |
| Other confirmed successful submission (`acknowledged`) | Show **Submitted** toast and retain the outcome receipt. |
| Confirmed failure | Show **Error: <bounded plain-text description>** and retain the failure outcome. |
| Pending, timeout or ambiguous network outcome | Keep a clear pending/unknown state and reconcile the same transaction; do not label it Submitted or falsely claim the external effect failed. |

The earlier fetched-HTML `_blank` viewer proposal is deferred by the current scope decision. Native form targets never gain navigation authority: `_blank` forms stay inert, and a response hint only records the unsupported-viewer info status described above. A redirect instead supplies a candidate navigation URL: a server broker captures Location manually and returns typed inert data, without forwarding the POST or following 301/302/303/307/308 itself. Browser-direct manual redirects can be opaque; do not assume JavaScript can read their Location. If an adapter cannot inspect the redirect safely it returns an unsupported-navigation result rather than guessing.

Resolve a relative Location against the exact submitted endpoint, then validate an exact HTTPS destination under the authenticated navigation policy: no userinfo, script/data/custom schemes, credential-bearing query/fragment or arbitrary private destination. Never copy submitted fields, action capability, transaction signing proof or local dispatch token into the URL. The endpoint's URL is still untrusted data; an unexpected new origin requires foreground review displaying the actual hostname. Even a preapproved origin does not authorize arbitrary authority-bearing URL parameters. The final external tab uses GET with no form resubmission, opener relationship or referrer. A normal external visit may send that site's own browser cookies; disclose that this separate navigation is outside the cookie-free submission guarantee. Opening/displaying a result must not silently authorize another action.

Do not promise that every asynchronous completion can create a tab. If the browser blocks it or the app is no longer foreground, retain a safe explicit **Open result** link/button instead of retrying a submission. Render error descriptions as plain bounded Unicode text (proposed 240 characters); map transport/internal errors to stable safe messages without response HTML, stack traces, tokens, private form values or sensitive URL parameters.

These records belong to this recipient's copy. They are not a conversation reply, shared read receipt, delivery acknowledgement, sender-authored edit or a write to other participants' copies. Export or group disclosure requires a separately reviewed operation and audience. The submitted fields can themselves be sensitive: preserve only the bounded data necessary for the owner's chosen history/retention and encrypted archive, avoid logging inputs/tokens, and make any redaction or local erase explicit rather than fabricating an unchanged history.

Use optimistic local projection revisions and idempotent append keys. Two devices completing the same action converge on one outcome entry; competing different one-use submissions expose the endpoint's winner/conflict. Owner tags, classification, View membership and private read state remain independent. Updating a card does not mark it read, send read receipts or emit a normal conversation notification by default.

## Button-only actions in OS notifications

An action with no editable fields is eligible to be presented as a notification button, subject to channel consent, host policy, action freshness and platform support. Eligibility is not a promise that every browser/OS supports buttons or a particular number. Some platforms offer no actions; always provide a same-origin open-message fallback. [Notifications standard](https://notifications.spec.whatwg.org/).

Build notification text/actions with deterministic bounded heuristics, not an LLM by default. Prefer explicit validated notification metadata that is bound to the authenticated description and subject to the owner’s privacy settings; otherwise select a visible heading, then the message subject, then the first useful visible plain-text excerpt. Normalize whitespace and unsafe control/bidi characters, truncate at Unicode-safe boundaries, and use proposed limits of 80 characters for title, 180 for excerpt and 32 for button label. Omit hidden/non-rendered content, footers/signatures, tracking text/resources, input values and submitted results; extraction must not fetch remote resources. When visibility or relevance cannot be established safely, fall back to the subject or a generic new-message label. A heuristic can be imperfect, so its result never conveys authorization or verified sender identity.

Extract buttons only from supported visible actions with no editable fields and validated fixed arguments; exclude invisible/disabled/stale buttons, duplicate actions and actions requiring a new identity disclosure or higher-risk consent. Descriptor order provides deterministic ordering; choose at most two initially and intersect with platform support and owner settings. Host effect policy decides eligibility, not wording such as “safe” supplied by the sender. Unsupported/no-button platforms open the message. Test structural and rendered visibility without executing author code, including CSS-hidden controls and form layouts; sanitization alone is not a visibility test.

Use bounded plain labels selected by trusted host presentation. Show the verified full sender handle/provider context with the privacy-approved label; software name/icon alone is not brand or legal-identity verification, and the OS notification origin remains the host/PWA origin. Never supply a sender-controlled remote URL for notification icon/image/badge/action icon: use prevalidated locally cached raster bytes/assets or a neutral fallback, with no sender callback at notification display. Push and OS notification presentation contains only the privacy-approved bounded preview/labels; action-routing data contains only opaque local message/action locators and revisions, never a remote capability, cookie, signing key, form input or full sensitive result. Resolve authority from the local trusted account context after the click. Merely delivering/displaying/dismissing a notification has no action effect. An expired, edited, consumed or unavailable action opens an explanatory local view instead of silently substituting another action.

The notification action opens the message and, for a fixed, owner-enabled, low-risk action whose destination/effect were reviewed beforehand, treats the intentional click as consent and shows Submitting while sending. It still revalidates live authority and exact fixed arguments, has a finite use count, and cannot newly disclose identity or acquire permission. Notification origin text and the button label alone do not constitute sufficient context for arbitrary effects. Lock-screen visibility, shared devices and accidental taps mean sensitive actions always require foreground review/unlock under the host's account policy.

Service workers cannot assume a UI session, an unlocked signing key, indefinite execution or a reliable connection. If authority cannot be safely obtained, open the app; do not stash a broad long-lived owner token in notification state. Use `event.waitUntil` for the bounded authorized work, preserve pending/unknown outcomes on interruption, and sync the owner's latest local projection across devices without notification loops. No inline text forms or automatic responses in the first OS-notification profile.

## Implementation spike and decision gates

1. **Protocol fixture only.** Implement strict action/submit/result parsers and canonical digest fixtures with an injected endpoint and clock. Prove both unconnected HTTPS postback and exact callable binding can use the same review model without sharing authority. Keep draft identifiers out of the public registry.
2. **Isolated renderer fixture.** Use the real 3sln trusted UI, sandboxed iframe and Shadow DOM, the sanitize/traverse/handler/mount pipeline, native `setHTML` and lazy pinned DOMPurify paths, a typed form and no live network. Test script/event/URL variants, CSS tracking, clobbering, form overrides, stale MessageChannels, remote resources, autofill behavior, keyboard/screen reader use and author overlay deception in Chromium, Firefox and WebKit. This spike must establish actual browser support, not infer it from API existence.
3. **One low-risk postback end to end.** Use a reserved example service with exact destination association, cookie-free dispatch and a one-use capability. Test zero Cookie/ambient Authorization/Referer across all hops and refusal of redirect-following, private addresses and response-driven broker calls; separately test typed redirect capture, validated GET navigation, `_blank` form refusal and response-hint status without returned HTML. Verify idempotency, expiry, concurrent devices, edits/revocation, unknown outcomes and append-only latest-view behavior on durable Node/Worker adapters.
4. **Notification adapter.** Open the message for every action click; eligible preapproved fixed actions show Submitting and dispatch, other actions require foreground review. Separately verify button support/fallback, explicit click handling, account switching, lock-screen policy, expired actions, offline interruption and absence of secrets in push payloads. Verify the selected fixed-argument click-to-submit policy and fallback to foreground review when its eligibility is unmet.
5. **Publication/conformance checkpoint.** Finalize the action part carrier, exact machine schemas/URI, effect profiles, origin-association proof, identity-intent encoding, capability and result-retention limits. Publish actual JSON only after review and independent client/service fixtures. Broaden schema, media and action classes only with separate evidence.

Open decisions: accepted first-party/third-party issuer association proof; whether unsigned-but-user-reviewed HTTPS services ever gain an active profile; exact rich-layout CSS subset; which low-risk fixed actions qualify for click-to-submit after opening the message; local submission-field retention/redaction defaults; and third-party edit/revocation coordination. The initial recommendation remains authenticated declarative actions (issuer signature or verified connected-app attestation), exact endpoint association, blocked remote resources, anonymous cookie-free submission by default, explicit optional identity disclosure, and recipient-local retained postback history.
