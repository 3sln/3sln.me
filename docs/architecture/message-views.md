# Unified messages and configurable Views

Provisional architecture, 2026-10-13. User direction: messages and conversations belong to one user-owned logical store; Views are filtered projections, not destination inboxes or containers. ## Model and visible behavior

The owner has one logical incoming store. A message is stored once in that owner's copy; appearing in several Views does not duplicate bytes, quota usage, delivery receipts or unread state. A conversation is an independently authorized resource in the same logical account space. Its feed card is a projection of that owner's retained conversation copy, not a second transcript or a new shared global store. Earlier federated per-owner-copy and archive designs are unchanged by the navigation model.

The default **All messages** View means all retained incoming items. It is a saved projection, not a destination ID. Other defaults can be Unread, Conversations and Tagged; users can edit or create bounded named Views. Removing a View removes only its definition. It never deletes messages, revokes a contact or drops a conversation participant. Read state belongs to the underlying owner record; reading an item in one View updates it everywhere. Sender content deletion/history semantics remain defined by the conversation contract, independently of View membership.

Use an incoming-item index with opaque item ID, owner, type (`message` or `conversation`), original received time, current activity time, current owner read state, mutable organizational tags, original endorsed delivery tags and classification. A conversation summary has one stable item ID and references its underlying local resource; individual conversation events remain in its history rather than becoming duplicate feed cards. Appending an event updates the summary and relevant index fields once. The exact conversation-unread aggregation must be documented and tested; an optional shared read receipt is not inferred from an index read or server ACK.

Quarantined items remain retained incoming data and can be shown with their existing warning/safe presentation; any default exclusion must be visible in the View definition rather than an undocumented hidden store. Deleted items follow existing owner deletion rules and do not reappear merely because a View changes. Imported/archive-unavailable bodies can have truthful placeholders, never an invented empty message or silently missing history.

## Bounded View definition and query grammar

A View definition is owner configuration: `{version:1, id, name, revision, filter, sort}`. IDs and revisions are opaque. Names are bounded literal text, not translation keys or HTML. Limit the first implementation to 64 definitions per owner, names of at most 100 characters and a finite serialized definition size (for example 8 KiB). Existing default Views have stable IDs and localized built-in labels; a user-renamed label stays literal.

The first filter language is typed JSON with conjunction only:

```json
{
  "version": 1,
  "tagsAll": ["topic:bug"],
  "read": false,
  "types": ["message", "conversation"],
  "classifications": ["personal", "work"],
  "receivedAfter": 1791849600000,
  "receivedBefore": 1791936000000
}
```

Every field except `version` is optional. `tagsAll` requires every selected organizational tag. `types` and `classifications` are bounded OR-within-field allowlists; different fields are ANDed. Use existing classification values, not an open executable category language. Date bounds are finite safe integer UTC milliseconds, lower inclusive and upper exclusive, with `after < before`. A missing array is unrestricted; an empty array has one documented meaning (recommended unrestricted), and normalization must be consistent for query hashes. Reject unknown fields, duplicate values, control characters, oversized tag/value arrays and invalid combinations. No raw SQL, regex, recursive conditions, JavaScript expressions or user-selected index names are accepted. `tagsAny` is deferred; current tag-rule work only adds `tagsAll`.

Filtering uses mutable owner organizational tags. Ingestion rules instead use immutable original endorsed `deliveryTags`; these are distinct purposes. A tag can select a View without establishing sender identity, required grants or automation authority. A text-search field, if later added, must use the existing bounded search service and retain its permission checks; it is not an implicit unbounded substring scan or semantic-AI call in this first grammar.

Allow only documented sorts: received-descending and activity-descending, always with opaque ID as a deterministic tie-breaker. The default All messages View can use activity order so new conversation activity surfaces its card. Use parameterized queries over owner-local scalar and tag membership indexes, not a scan of message bodies or all cold archives. Return at most 100 items per page and a bounded server-owned continuation token. Estimate/index admission protects pathological tag intersections without changing filter semantics silently.

The initial policy invalidates continuations on every incoming-index revision change, including read/classification/tag changes that could change predicate membership even without reordering. This conservative rule may require frequent refresh on a busy feed; narrower invalidation needs separate evidence. Classification queries use stored values, with `unclassified` distinct from classifier availability, and never invoke AI.

The cursor binds owner/resource, normalized filter digest, sort, View revision if referenced, page boundary and the authorization revision. It is opaque and tamper-evident; never accept a caller-crafted SQL offset or another owner's cursor. Paging must state its consistency model. Recommended first implementation is keyset paging with an index revision: a relevant mutation that can change ordering or membership invalidates continuation with `cursor_stale`, and the client explicitly refreshes while retaining already displayed content. This avoids claiming stable snapshots that were never persisted. A write-heavy feed may need a later snapshot/high-water profile; do not add historical-version retention merely to conceal cursor invalidation. Idempotent read pages must not mark items read.

## Contact delivery: tags, not destination selection

(Updated 2026-10-14: for link-form contacts these tags live in revisioned server-side intake, not signed claims; see [links](../spec/links.md). The text below describes legacy signed grants.) New contact creation chooses owner-authorized required tags and optional tag choices. The sender chooses only from `optionalTags`; the receiver automatically applies `requiredTags`. These sets are immutable signed grant scope, inherited exactly by short-lived inbox tokens. The request cannot remove required tags, add unsupported options, select a higher priority or swap a claimed tier. Reject invalid selections before blob storage, new-attempt receipt accounting or optional classifier work. Preserve the generic contact protocol's method, MIME, body-size, quota, expiry and live parent checks.

Existing `senderMetadata.tags` is untrusted annotation under legacy grants. A grant with both explicit tag-policy arrays can interpret that field as the bounded selected subset; both absent means legacy untrusted annotation, while only one present is invalid. Explicit empty arrays forbid discretionary endorsed tags. A sender redundantly naming an already required tag is harmlessly deduplicated; the UI only offers optional choices. Do not silently promote old freeform annotations to owner tags or privileged rules. Store the server-endorsed original `deliveryTags` separately and initialize organizational tags from the endorsed union. Include sender selection in the acceptance fingerprint so changing choices under the same idempotency key conflicts. Copy inputs before awaits; concurrent submissions cannot mutate signed/accounted data.

For developer contact, issuance uses current verified tier to set a required priority tag, and optional topics such as bug/feature/general. Existing owner rules match original `deliveryTags.tagsAll` and apply bounded owner organizational tags/classification; they no longer move between user-visible inboxes. Priority is fixed at issuance for that daily grant. Daily grants remain delegable bearer capabilities until ordinary expiry/manual revocation, as requested; tags do not prove their user's identity. See [protected identities and daily contact](system-identities-contact.md).

The new composer has no destination View/collection selector. A View's ID or mutable filter must never be supplied as delivery authority. Legacy collection claims and requests still need explicit compatibility handling, below; simply ignoring them would expand authority.

## Authorization is independent of Views

Owner Views are presentation preferences. An app/MCP grant must never store a pointer to a mutable View and then follow its edited filter. Renaming, broadening or deleting a View cannot add records to an existing app grant. A tag edit cannot accidentally change an old collection permission into a broader scope. An owner query receives explicit owner authority; an app query must carry explicit grant context and cannot infer owner authority from a View ID. Query execution always intersects the caller's independently authorized record set with the requested View filter, and applies authorization again when reading a body, attachment or conversation resource.

Existing collection-based grants remain attached to stable hidden legacy authorization labels. Before dual-writing or changing any UI organization, durably snapshot each record's current authorized partition and each incoming legacy token's exact permitted partition. These labels are not user-visible inboxes and cannot be edited by View/tag operations. Existing grant IDs, collection IDs, selected methods and revocation behavior are not remapped to a tag name or a default All messages View. An app permitted to an old collection continues to receive only records bearing its preserved legacy authorization label. Moving a visual filter or changing its name has no effect.

If old owner APIs explicitly mutate collection membership, define their compatibility decision separately: either retain that explicit old owner-authorized operation in the legacy profile, or reject it with a typed migration/version response. Do not silently reinterpret it as changing a View or as modifying a different app permission. The first implementation must not claim complete old-client compatibility until this decision and its regression tests exist.

New scoped access needs a separately reviewed immutable scope document. A pinned predicate is independent of a saved View and contains the exact approved filter language/version, fields and operations. If it intentionally follows future mutable tags, consent must explicitly describe that dynamic membership: pinning the predicate text alone does not freeze its results. Prefer stable issuer-controlled access labels or explicit bounded record membership where that behavior is not intended. Changes to the scope document need a new digest/version and consent; changing a View never changes it. This proposal does not automatically ship new app/MCP scopes.

Conversation visibility is a separate boundary: a matching feed summary does not admit a participant, grant history, backfill a new member or expose old events. Apply the local conversation resource's membership/history policy to every operation. Export and read endpoints cannot use the unfiltered owner index as a shortcut for scoped clients. Aggregate counts and cursors must not disclose unauthorized records, including whether a hidden conversation exists.

## Compatibility and incremental migration

Implement one owner-local incoming index and Views over existing retained records first. It is a logical unification, not a bulk rewrite of all bodies or a second store. Existing message IDs, receipt fingerprints, timestamps, read state, conversation IDs, encrypted archive references, deletion frontiers and local approvals remain intact. Snapshot/export includes View definitions and index reconstruction metadata inside the owner's backup namespace; a View definition alone is not a backup of its matching data.

For old collection organization, derive initial saved Views or organizational tags from current labels without altering authorization labels. Record a per-owner migration version and deterministic mapping. A crash resumes the same mapping rather than creating duplicate Views/tags. Two-way compatibility writes, if supported, must have one declared source of truth. A one-time migration snapshot must not later reassign app permissions when a user renames an organizational tag. Validate retained counts and record IDs before removing redundant organizational indexes; never delete the only authority record during this UI migration.

Legacy signed contact endpoints retain exact collection claims and their signatures. New contacts may use a single internal ingress partition while exposing only tag choices to the human sender. Where a legacy grant authorizes multiple partitions, use an explicitly stored legacy default only if it is inside the signed allowlist; never choose an arbitrary partition or enlarge the token. Established programmatic legacy clients can continue submitting their authorized collection under the compatibility profile. A new destination-free contact profile must be versioned and documented before it is advertised to external providers. Hidden legacy fields can preserve old authority without reintroducing user-facing inbox destinations.

The currently published conversation v1 JSON is a provisional local submission envelope, not a unified message-store contract or the proposed federated conversation v2. Do not modify or relabel it to imply this new model. A future generic public message-store/query contract needs its own exact method/argument/result JSON schema and identifying URI, plus actual runtime vectors. Candidate names in this design are not a registry entry or publication claim. Existing public contract registry entries remain unchanged until that work is reviewed. The eventual public conversation resource contract continues to carry conversation mutations; owner Views do not create a separate private conversation protocol.

## Suggested implementation interfaces

Use a narrow owner configuration resource for `listViews`, `createView`, `updateView({id, expectedRevision, ...})` and `deleteView({id, expectedRevision})`. A bounded `queryIncoming({filter, sort, cursor, limit})` accepts a normalized filter, or resolves a View ID plus expected revision within that owner. Method names/HTTP paths are provisional adapter choices; owner configuration does not by itself authorize app access. Preference read/update and message index mutations must not require a global actor.

The UI lists Views and shows their actual filter definition. Creating or editing a View is reversible and affects only that owner's presentation. Empty results say no matching items; deleting a View explicitly says messages remain. The default All messages View supports all incoming types, and a conversation card opens the same underlying conversation resource. Required/optional contact tags use stable wire IDs and literal/translated labels; user content is never evaluated as a Bab template. Pagination refresh, offline state, archive body unavailability and stale View revision need explicit readable states rather than silently resetting unrelated drafts.

Keep implementation slices separate: (1) signed tag policy and original delivery-tag rules; (2) owner incoming query/View definitions and default navigation; (3) compatibility migration and scoped app/MCP checks; (4) separately reviewed public query/profile schemas. The existing collection-backed runtime must not be described as destination-free until the composer, owner navigation and authorization compatibility are all reconciled.

## Implemented owner-query checkpoint (2026-10-13)

The first backend slice now provides owner-only `GET/POST /api/views`, revision-checked `PUT/DELETE /api/views/:id`, and `GET /api/incoming`. The latter accepts a saved View ID plus revision, or a typed JSON filter and sort; it returns up to 100 items, an authenticated continuation and index revision. All incoming-index changes invalidate older continuations with `cursor_stale`. Deleting a View changes configuration only. `POST /api/views` accepts an optional client `operationId` (lowercase UUID v4): repeating it with the same normalized definition returns the originally created View instead of a duplicate, and reusing it for a different definition fails with `view_operation_conflict`. The console keeps one ID per unchanged create attempt. Only the 64 most recent create receipts per owner are kept. Session/Origin/CSRF protections apply through the existing owner router, and no app/MCP permission follows a mutable View.

The SQL projection maintains normalized tag membership and scalar indexes, with keyset ordering and incremental 200-record legacy backfill. It does not load the first snapshot page and filter that subset. Message bodies and archive objects are not read for filtering. Added tables duplicate bounded metadata, not message bodies; their storage/SQL operations contribute physical overhead and are not free merely because they are projections. Filter count, output size and input grammar are bounded; this is not a claim that every allowed SQL query reads a constant number of index rows.

Retained conversation event messages now produce one stable card per source origin/owner/conversation ID. Its received time is the first retained event and activity time the latest retained event. Conversation tags/classification live in a persistent owner overlay initialized once from retained local metadata, never replaced by a new reply. The subject still follows the latest retained event. Before an owner chooses a card read state, unread means any retained event is unread; an explicit read action records a local seen-event watermark, with later arrivals unread even if timestamps tie or arrive out of order. Counts are maintained by deltas, and endpoint rows use indexed first/last lookups rather than rescanning full histories per write. Deleting an event updates the projection; deleting the final retained event removes its card, without deleting the conversation resource. Conversation invitations remain ordinary incoming messages, and rooms without retained delivered events remain available through the existing conversation-list API. Owner `PATCH /api/incoming` updates a conversation card using `id`, `expectedRevision` and optional `tags`, `classification` and `read`. Cards expose `organizationRevision`; marking read additionally requires `expectedActivityRevision` matching `activityRevision`, so stale UI cannot mark an intervening unseen arrival read. These actions emit no shared receipt and do not rewrite legacy per-event read flags or partitions. Ordinary messages retain their existing message-update endpoint. The overlay survives deletion of every retained event and subsequent arrivals to that same conversation. Empty-room feed hooks are not implemented in this slice. The persisted overlay and its generation are owner configuration, not disposable derived indexes; complete future export/restore must carry them alongside View definitions.

The original collection catalog, record partitions and scoped app/MCP APIs remain in place unchanged. No authority migration, new public query contract publication, destination-free frontend or provider-conformance claim is made by the backend slice. Frontend integration and the final compatibility policy remain separate checkpoints.
