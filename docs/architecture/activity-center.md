# 3sln.me activity center

Provisional host design, 2026-10-20; documentation only. [Core activity interop](../spec/activity.md) defines admission and provenance; this document owns the UI, policy, SDK mapping, and extraction plan. User direction keeps notifications and messages from installed apps in core and moves peer-to-peer communication into a separate app. “App messaging” below means app-to-owner activity, including rich app content and local postbacks, not peer communication.

The [DEVLOG scope decision](../../DEVLOG.md#2026-10-20--scope-reduction-messaging-leaves-core-manifest-extensions-activity-stays) and [NOTES](../../NOTES.md) are source records. Their broader app/integration unification is compatible with this design: built-in and third-party integrations use the same app attribution and controls. Resource discovery, preference-change webhooks, and manifest extension selection need their own designs. The older NOTES messaging robustness work now belongs to the separate messaging app.

All new choices here remain unsigned at the [decision record](../release/activity-design-review.md#decision-record). This task explicitly excludes DEVLOG edits, so implementation discrepancies and proposed reconciliation are recorded here for a later authorized ledger update. No existing source, public artifact, or production gate changes through these documents.

## Feed and organization

Activity is an account-scoped feed of notifications, alerts, and messages from installed app connections. Each row has trusted registered app name and exact origin, subject, received/updated time, unread status, and qualified app tags. An optional icon uses validated locally cached assets or a neutral fallback. Host chrome distinguishes app priority requests, system classification, owner tags, expired/retracted content, and local submission results. Content cannot style that chrome or supply a system badge. Historical rows keep their admitted attribution when an app renames, disconnects, or changes domain.

The app association is a permanent implicit facet, not a removable `app-message` tag. The feed supports app, app-tag, owner/system-tag, unread/read, active/archived, and date facets. A tag appears under its app; two apps' `receipt` tags remain separate even if their labels match. Labels are literal localized presentation data, following [tags](tags.md); app labels never become bab templates or tag identities. The service bounds facet cardinality and pages long tag lists rather than letting random tags create unbounded UI work.

Account-local lexical search covers subject and safe extracted text, combined with these facets. It runs over the activity partition and rechecks source access, terminal state, and owner before returning results. Search snippets identify app revisions versus owner-local postback results. They do not load HTML resources or index private submitted fields into general snippets. Semantic search, if offered later, requires a separate privacy and service decision; it is not a prerequisite for activity. Saved filters reuse the Views concept: overlapping projections of retained items, never authority partitions. There are no conversation cards or participant filters in core Activity.

Opening an item shows its current applicable presentation, original/app revision history, local submission history, and trusted source context. Preserve the existing safe HTML and form pipeline. Form availability is explicit; content admission alone does not enable it. App replacements invalidate prepared forms and stale open frames, and show “Updated by app” rather than pretending a postback changed the app's signed statement. If a response to an already dispatched old form arrives late, attach it to its source revision in history; it cannot replace a newer app revision's current presentation. Retraction or expiry leaves only inert retained history.

Opening a detail deliberately marks only the displayed app revision read after it loads. Background refresh, search, preview, notification display/dismissal, and submission results do not. A stale read action cannot consume a concurrent replacement. Manual mark read/unread is available. Archive removes an item from the default feed and cancels undispatched push/digest work without deleting it; All activity and Archived retain access. Archive and read are independent. Default replacements preserve both; an explicit owner setting may make updates unread, but never unarchive them. Neither state is disclosed to the app. Erase is a separate owner retention action, preserving only necessary bounded replay fences and cleanup state.

Trusted controls use the existing 3sln stack through `apps/web/src/shared/stack.mjs`, UI modules, business-logic intents, and providers. Implementation must read the actual vendored APIs before changing integration. No author HTML becomes a host UI template or executable intent.

## Admission and push are separate controls

Connected apps offers “Allow activity from this app” for the existing resource/method consent and a separate “Push from this app” control. Admission defaults off until granted. A granted app's items enter Activity silently; account push and each app's push opt-in default off. OS permission, device enrollment, enabling admission, a global push toggle, or an app requesting `urgent` cannot turn app push on. A separate “Pause all push” control is immediately available without disconnecting apps or discarding feed history.

An app push opt-in is scoped to account, registered app principal, and current connection incarnation. Reconnect requires fresh opt-in. The user chooses selected app tags or explicitly chooses all of that app's activity, including future tags. Selected-tag mode leaves unknown/new tags feed-only; an app cannot bypass that restriction by rotating tags or declaring urgency. App-tag changes never rewrite the rule IDs. Future-tag behavior is stated at opt-in. Renaming a label leaves rules unchanged.

Routing rules match a fixed snapshot: app principal/incarnation, signed app tags, source revision, app-requested priority, and applicable owner/system organization. Owner changes may reduce eligibility immediately; they do not replay old activity into push. A rule can demote or override priority and choose feed-only, immediate push, or digest. Rules may specify per-tag exclusions, minimum effective priority, quiet windows, and a selected enrolled-device set. Default priority is normal; urgent is merely an app claim. The rule editor shows a plain explanation and sample matches, including why an item stayed silent.

Evaluation is deterministic:

1. Enforce account lifecycle/access, live connection/admission generation, app push opt-in, global/account push switches, and enrolled-device consent. Read, archived, quarantined, retracted, expired, deleted, or superseded revision jobs are ineligible.
2. Apply explicit app/tag hard mutes; a matching mute wins over any allow or priority rule. For the remaining eligible scope, evaluate the owner's ordered rules; the first matching rule selects route and effective priority. Without a match, use the route the user explicitly selected at app opt-in; never infer an allow from another app's rule.
3. Enforce quiet hours and channel/device budgets. Default quiet behavior batches eligible arrivals into one digest after quiet ends. An urgent bypass requires an explicit owner rule scoped to that app and tag scope; it still cannot override mute, missing consent, terminal state, or budgets. A quiet-held item that expires or becomes read/archived never contributes to that digest.
4. Reserve an outbox job with item/source revision and rule generation. Immediately before transport, reevaluate the current rules and state, resolve current eligible device subscriptions, and project the current privacy setting. A changed route cancels/rebuckets the job without creating a second delivery intent.

Turning push on or broadening rules applies to future admissions/replacements only. It does not release a historical backlog. Narrowing a rule suppresses pending work. An explicit foreground “review missed activity” opens the feed rather than replaying individual pushes. Updates notify only if the user separately enables update notifications for the app; default off, and read/archive preservation still applies. A newly eligible update gets one event keyed by its source revision, subject to cooldown and collapse. Local postbacks never create new activity push.

Initial proposed policy limits, requiring product/security review:

| Control | Initial host policy |
| --- | --- |
| Immediate push | At most 3 per app/hour and 10/day; aggregate 6/account/hour and 20/day, across devices. One logical notice consumes budget before device fan-out. Automatic retries retain that notice identity. |
| Overflow | Keep all admitted feed items; coalesce eligible overflow into the next permitted digest, with no unbounded individual replay. |
| Digests | Owner selects hourly or daily at an explicit time; default daily at 08:00 when digest is chosen. One account-scoped summary per interval/device; account push budget includes digests. |
| Quiet hours | Optional explicit fixed UTC offset and start/end hours, matching current implementation semantics. Display that DST is not automatic. Equal endpoints mean quiet all day; no automatic release then. Named time zones are deferred. |
| Preview | Generic content-free notice by default. Optional bounded app/content preview is separately consented per account/device; the more restrictive choice wins. |
| Rules/facets | At most 100 routing rules/account; at most 500 remembered app-tag IDs/connection, with bounded paged facets. Existing IDs remain stable; at capacity reject new IDs until owner-managed reclamation, never recycle them into other meanings. |

Digest membership is computed again at send time from still-eligible items, deduplicated by item ID/current app revision. Empty buckets disappear. Choose the latest eligible item when collapsing; a later muted/expired item cannot displace eligible content. Collapse affects notification work only, preserving distinct feed rows. Freeze the digest's bounded candidate membership at job admission; subsequent removals shrink or cancel it, and additions wait for the next interval. At the first transport attempt, freeze the payload and transport idempotency key. If later authorization would forbid any part of that payload, cancel its retry rather than sending changed content under the same key or minting a replacement notice. Counts/app names are included only under preview permission; generic mode says only “New activity.” No digest combines accounts. Default app pushes have no repeating unread reminders. Optional existing email reminders retain separate consent and verified-address/suppression gates; email expansion is not part of this activity change.

The outbox retains atomic admission events, durable scheduling, leases, retry/backoff, dead-job handling, and final authorization from the existing notification service. Device deletion and 404/410 expire subscriptions. Delivery remains at-least-once; a crash after transport acceptance can duplicate a notice. A rule change cannot recall an in-flight send. Collapse or transport idempotency reduces duplicates without promising exactly-once delivery.

## Multi-account destinations and lock screens

Every stored item, index document, rule, cursor, dedup/collapse key, digest bucket, outbox job, device enrollment, prepared form, and cache is scoped to its issuer and account. A browser device subscription may serve several separately enrolled accounts; that never merges their routing state or opt-ins. Delivery failure or sign-out for one enrollment cannot authorize another account. Global OS permission is not per-account consent.

An app session submits only to the account owning its selected approved resource. The SDK reference and response remain bound to issuer, subject, connection, and session generation. Switching the host's visible account cannot retarget an app request. A pending request either completes under its original authorized account or fails; its result must not appear in the replacement account's state.

Push routing carries an opaque local destination locator bound to issuer/account/item/revision. The service worker opens a fixed same-origin activity destination; it never follows an app URL, uses the currently active account as a fallback, or executes an action. At foreground entry, authenticate and resolve that exact account before fetching content. If another account is open, use the account chooser with an explicit destination, without rendering private text; absent or signed-out destinations require authentication, and deleted/unavailable accounts fail closed. Legacy ownerless notifications open a generic account chooser, never an item in the active account. Query parameters and locators are navigation hints, not account authority.

Account switching/sign-out clears feed, search, detail, form, and MessageChannel state, invalidates pending request generations, and closes obsolete previews where supported. Late async results and service-worker messages must be rejected by their original account context. Keep app history per account even when the same app/client is installed elsewhere.

Generic lock-screen notices contain no app name, account handle, tag, subject, count, form values, remote icon, or result. Opaque routing data remains sensitive metadata and must be bounded and excluded from logs. Optional previews can expose private content to the OS/push service and anyone viewing the screen; approval must say so. Apply account/device privacy at final dispatch; an untrusted app cannot override it. No notification button submits a form: it opens the authenticated foreground detail for fresh exact-source review. Expired locators show an unavailable state. Withdrawing preview or signing out cannot retract a notice already delivered; dismiss locally when supported without promising recall.

Authentication, recovery, and provider security notices keep their existing distinct trusted lifecycle paths and consent semantics. They cannot be minted as system alerts by an installed app or silently controlled by an app routing rule. A combined visual entry, if added, must retain the distinct system provenance and policy.

## Existing local behavior and compatibility

Source inspection confirms an existing browser app-to-owner path: `BindleClient.userMessage(reference, input)` in `packages/sdk/src/identity.mjs` calls `app-messages/v1.createOwn`. Its preference fragment assigns `messages`, and the runtime's resource is `${subject}/app-messages`. Permission is explicit, exact Origin is checked against registered client authority, and `createAppNotification` writes signed app admission provenance with the ordinary message blob, index, and notification event. This maps to **create Activity**, with the current SDK name retained as a compatibility convenience. No contact capability or ordinary sender identity is needed.

Current input is exactly `{transactionId, createdAt, subject, body, mimeType?, tags?}`. Preserve its immutable public JSON and reject new fields there. It has no priority, collapse key, expiry, app replacement/retraction, or namespaced-tag wire format. Introduce those only through a reviewed versioned activity contract/preference binding with explicit grants and capability discovery; no URI is published by this design. Do not rename `userMessage` or invent an `actions` input just to rename the feed. Any future helper is host/SDK design, outside the Bindle spec.

The compatibility adapter qualifies the original signed `tags` array under the verified app principal on read/migration. Existing values that do not satisfy the new local-ID grammar remain typed legacy app tags with their exact original value; they are never normalized into a colliding new ID. New-profile callers use the new grammar. Preserve legacy owner-edited flat tags as owner organization without treating them as signed app claims. The old required `app-message` marker and derived `sys:automation` remain compatibility/system metadata; neither is the app facet. Unknown or unverifiable legacy records remain inert historical records outside verified app activity, with no manufactured signature.

Existing defaults already have push and previews disabled globally. The service has leased jobs, suppression, live app checks, quiet hours, and generic/opt-in previews; it does **not** implement the per-app push grant, routing/digest policy, archive model, or lifecycle above. During migration, existing admission consent may carry over, but every app's push gate starts off. Preserve global channel/device enrollment and owner mutes, never synthesize per-app opt-in from them. Cancel/reclassify old queued app jobs under the new policy before enabling dispatch. Operator-provisioned keys and the historical local browser/Worker test records do not prove current production delivery. Production remains disabled under [security gates](../spec/security.md).

The current form/result implementation stays app messaging: original signed HTML, operator-approved destination, fresh review, prepared cookie-free dispatch, durable unknown-outcome fence, retained HTML/status/redirect history. `_blank` forms stay unsupported; `_blank` response hints stay status-only. Local results never gain original signature authority or continuation forms. Node DNS pinning and Worker's public-routing/DNS-screening limitations remain as documented in [message actions](message-actions.md). App replacement requires a new revision-aware form authority path; it must not pretend the old immutable original digest authorizes new bytes.

## Extraction and exact migration list

Retain core app messaging, activity policy, safe content handling, account-private organization, and delivery adapters. Move contact-addressed peer messages, conversations, participants, fan-out/retries, peer read/delivery receipts, and public-email bridge behavior to the adjacent messaging app, whose package/name is still undecided. It may emit ordinary core activity such as “New activity in Messaging,” under its own installed connection. Core must not accept peer envelopes through an activity backdoor, mirror peer bodies by default, or carry conversation transport/state simply because a messaging app is installed. Messaging-owned classification consumes an optional host resource/slot; core activity does not depend on the messaging classifier.

Keep a recoverable read-only legacy copy until transfer verification; rollback restores one authoritative queue, never two. Disconnects, storage accounting, retained operation fences and deletion cleanup must work at every step.

New limits proposed for activity mutations retain 10 attempts/minute and 100/day per connection, intersected with owner work/storage limits, plus a cheap retract-only reserve of 5/minute and 100/day under bounded owner capacity. Creates/replacements cannot spend that reserve. Keep the current 24-hour operation window, 60-second future skew, 48-hour admission receipts and refusal at 256 live account receipts until a reviewed binding changes them. Keep revision/result histories finite: propose 32 app revisions/item, including the terminal event by reserving its slot, separately from the existing bounded local-result history. At the replacement cap refuse further replacements; retraction must remain possible. Proposed explicit expiries may be at most 90 days ahead; absence remains subject to owner retention. These are service choices, not universal Bindle constants.

## Evidence required before implementation completion

The [adversarial design review](../release/activity-design-review.md) records fixes and required regressions. Runtime work needs `npm test` for SDK/core/server changes plus durable Node/Worker admission, restart, quota, revision, expiry, cutover, and outbox tests. UI work also needs DOM/browser verification of filters, archive/read races, opt-in rules, safe forms, stale frames and account switching. Include native/fallback sanitizer paths and service-worker destination cases. Provider transport and real-device/lock-screen behavior need separate end-to-end evidence; a populated key, local fixture, or screenshot is insufficient. `dev:demo` remains loopback-only and supplies no production API or evidence.

No tests were run as proof of new behavior for this documentation-only design. The referenced historical evidence is historical; per-app routing, digests, namespace migration, archive, and app lifecycle changes still require implementation and review.
