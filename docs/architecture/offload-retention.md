# Finite over-quota retention and resumable offload

Status: proposed architecture, 2026-10-13. This document does not enable deletion, writable S3 connections, export endpoints, or a production service. Local reversible implementation may proceed under the existing user authorization. Publication and destructive retention require the evidence and sign-offs below. Reconcile adoption and implementation evidence in [DEVLOG.md](../../DEVLOG.md); unsigned decisions remain provisional.

## Recommended product behavior

Give an account **30 days after a verified downgrade takes effect** to reduce hosted content below its new quota. A scheduled downgrade starts no clock while the larger entitlement remains valid. Pause positive storage growth when over quota; keep login, reads, owner export, deletion, billing and recovery available. Preserve the small identity/authentication records, signing keys and permanent name claims independently of content retention. This is separate from both inactivity policy and seven-day cold metadata shelving.

Provide two explicit choices: **Download a resumable backup** and **Move selected data to connected storage**. The latter reuses an owned connected resource, its existing encrypted credential and a narrowly scoped job authorization, then progressively copies, verifies and deletes only the exact source versions covered by the owner's move authorization. It supports any provider whose actual mediated capabilities satisfy the move requirements; an S3 bucket is one possible destination. A successful upload alone never authorizes source deletion. ZIP may serve small convenience downloads; it is not the large-account export format.

An account backup is not automatically a usable live app resource. Apps may shard a single document over many objects, and their directories contain resource IDs and object versions. Moving their bytes to external storage and deleting the originals can break the running app. Show affected resource assignments and root/index metadata before starting a destructive move. Offer copy-only when the user wants a backup without this effect. Live resource migration needs its own compatibility and grant workflow, described below.

The current baseline catalog is Free 500 MB; Paid 5 GB for $5/year; Plus 100 GB for $35/year; Ultra 1 TB for $250/year, all decimal bytes. Retention evaluates persisted verified entitlement bytes, not hard-coded plan names or a pending future catalog. Hosted objects across every hosted resource and inbox message bytes share that quota. External provider contents do not consume hosted quota.

## Retention episode and cutoff

Persist an account-owned episode containing `id`, `revision`, policy/terms version, causal billing revision, effective downgrade time, initial and current quota bytes, initial usage, absolute `deadlineAt`, notice schedule/results, selected keep units, keep-selection revision, execution cursor, optional bounded extension and resolution reason. Use an injected clock and repository transactions. UI dates are derived from the persisted UTC deadline, with an explicit local-zone rendering; opening a page, replaying a webhook or restarting a Worker cannot recalculate it.

States are `within-quota → grace → cleanup-eligible → reducing → resolved`, plus `paused-safety` for a violated precondition. No state name by itself permits deletion. Eligibility requires current over-quota status, deadline elapsed, release policy enabled, adequate notice/terms evidence and a deletion plan for whole units. Billing ambiguity, a failed authoritative reconciliation or corrupt accounting pauses destructive work. Login and reading stay available.

The first implementation should support account lapse/downgrade events with an authoritative effective time. A malformed billing state or deployment misconfiguration that falls back to Free is not evidence of a user downgrade. Operator catalog reductions also need their own notice policy; a lower catalog value must not quietly start a retroactive deadline. On adoption, existing excess accounts need a fresh notified episode, not backdated cleanup. The owner can actually configure and save a **Keep** selection, inspect its bytes/dependencies, change it before execution and receive validation that it fits; a decorative prompt or nonfunctional setup button is insufficient.

At effective downgrade, issue a persistent account warning and attempt every currently enabled and verified notification channel (email, push, or SMS only if actually implemented/configured). Repeat at seven days and one day before the exact cutoff; retries carry the original deadline. Record attempted, accepted-by-provider, delivered where genuinely evidenced, bounced and viewed separately. An account without email/phone is valid. A recovery file is not a contact channel; a dashboard banner is not delivered notice. No-contact account execution remains gated on a published, reviewed notice policy. Outbound delivery is future product behavior here; this design authorizes no message sending.

Cancellation rules:

- Re-evaluate authoritative current entitlement, usage, billing revision, keep-selection revision and episode revision **in the same transaction as every logical deletion**. Stop as soon as usage fits. A valid paid renewal providing adequate quota resolves the episode before any later deletion commits. Admission/commit races must use the account's common serialization/transaction boundary.
- Reducing stored bytes to fit resolves cleanup need. Retain bounded anti-abuse history so transient plan toggles or briefly fitting usage cannot reset an already funded grace allowance through replay. A real verified purchase/renewal that covers current usage ends the prior episode. A later genuine lapse is a new event; repeated grace subsidies must remain bounded by an operator policy tied to paid service actually earned, never arbitrary webhook count.
- A scheduled cancellation, unpaid checkout, pending product change, stale webhook or recovered session cannot extend grace. Regaining account access should allow export but not silently move a storage deadline.
- Starting an export does not extend retention indefinitely. Permit a proposed single extension of at most seven days only for measured progress or a service-caused outage, with a fixed cap recorded on the episode. Actual transferred and verified unique bytes/items count as progress; retries and an idle job do not. Capacity failures caused by this service require a safe pause and an explicit replacement deadline before irreversible cleanup, never deletion while the promised export path cannot operate. Repeated pauses trigger an incident and funded mitigation, not an unbounded hidden exemption.

### Keep whole data units

Do not choose random/oldest files until usage happens to fit. An app can store indexes and chunks whose integrity requires the entire set. Allow users to select whole known datasets and inbox collections to retain; include dependency/root information in the selection. Dataset membership is trustworthy only when complete and validated by an app-aware integration or explicit owner grouping. Prefix similarity alone does not establish it.

Conservative fallback: each hosted resource is an indivisible unit; each inbox collection is a unit. A single built-in hosted resource can contain several apps, so the fallback may remove more than the excess bytes. State this before adoption and before a deadline. If the owner makes no selection, the proposed published fallback is to retain identity records and remove whole hosted content units until the quota fits, ordered by a fixed documented rule established with the notice (for example, unselected units largest-first with stable IDs as tie-breakers). This is provisional product policy, not permission for an arbitrary executor to choose a rule. Never silently split an unknown dataset to preserve exactly 500 MB.

Selection must fit the current quota or be marked infeasible before cutoff. Whole-unit deletion is a durable multi-step job: write a unit tombstone, remove it from live access, then clean physical blobs in bounded batches. Do not claim multi-object atomic physical deletion. Re-evaluate entitlement immediately before tombstoning each unit; if entitlement changes after tombstoning, stop all not-yet-committed units. Already committed deletions cannot be promised reversible. User-directed provider move and deadline-driven cleanup are separate authorities and separate receipt reasons. A transfer failure never counts as a successful move; any later unbacked retention deletion requires its own disclosed cutoff authority.

## Owner export format and API

Use a versioned, chunked manifest and individually addressable payloads. A compact root identifies issuer, subject, snapshot ID/generation, creation time, expiry, exact selection, totals and hashes of immutable bounded manifest shards. Shards contain stable entry IDs, kind (`object`/`message`/metadata), logical resource/key or message ID, source version/revision, byte length, MIME type, SHA-256, safe relative payload path and dependency/root information when known. Include resource IDs, app root pointers, public descriptors, collections, tags and needed mapping metadata for restoration. Mark unknown app restoration semantics explicitly.

Private physical bucket keys stay server-side. Original names, sender details and metadata are personal data; treat the manifest as private and give users the same destination/privacy notice as for message bodies. Source payload bytes may already contain credentials or other sensitive information; the service cannot promise content export is secret-free. Do exclude service-held OAuth/provider secrets, session tokens, recovery secrets and private signing keys from generated manifest metadata.

Generate payload paths using fixed ASCII namespace plus stable encoded IDs, for example `data/objects/<resource-id>/<entry-id>.bin`; retain the exact logical key in JSON. Never turn a logical key into a filesystem path. Reject absolute/drive/UNC names, traversal, symlink traversal, reserved device names and alias collisions on extraction. Byte-preserving keys must survive Unicode normalization, case-insensitive filesystems and percent/slash characters. Use exclusive file creation under the chosen root and atomic `.part` rename after verification. No file content is rendered as HTML under the service origin.

Proposed owner routes, outside Bindle object-storage:

| Route | Authority and behavior |
| --- | --- |
| `POST /api/exports` | Owner session, origin/CSRF protection and recent reauthentication; create idempotent snapshot with selected resource/collection IDs |
| `GET /api/exports/:id` | Owner status with exact counts, lifecycle deadline and separate copy/delete/cleanup progress |
| `POST /api/exports/:id/grants` | Owner mints short-lived read-only grant for that immutable job; never an owner cookie or general app grant |
| `GET /api/exports/:id/manifest/:shard` | Bounded immutable manifest page, authorized for this job |
| `GET /api/exports/:id/items/:entry` | Streaming attachment with `HEAD`, strong version token and valid single byte ranges |
| `DELETE /api/exports/:id/grants/:grant` | Revoke that grant immediately for future requests |
| `POST /api/offloads` | Owner confirms owned connected destination resource ID/generation, prefix, exact snapshot selection, copy-only or copy-and-delete, and affected apps; accepts no provider credentials |
| `POST /api/offloads/:id/cancel` | Stops new remote work and new source deletions; retains receipts and owned cleanup work |

These are interface proposals, not existing routes. Job/grant lookups always check authenticated owner; unpredictable IDs alone confer no authority. Grant scope includes exact snapshot, allowed entry set, methods, account epoch and expiry. Store token hashes, send bearer material in headers rather than URLs, and redact headers. Default access TTL five minutes; a narrowly scoped revocable renewal handle may survive CLI restarts up to the job's bounded expiry, stored in an OS credential store where available. Renewal rechecks current session/owner authorization and cannot outlive revocation, recovery epoch or retention cutoff. Export grants have no delete, write, connector or signing-key authority. Throttle unauthenticated requests before storage access.

Serve `Content-Length`, `Accept-Ranges: bytes`, stable snapshot ETag, `Content-Range` and correct 206/416 semantics; support `If-Match` and make `If-Range` behavior explicit. Reject excessive/multiple ranges initially. A client must reject a 200 response when expecting resumed 206 bytes and must never append it. Keep authorization checks for each new request and replay. Revocation cannot retract already received bytes; an in-flight stream may finish its already-authorized bounded chunk. Bound stream chunks and abort on expiry/revocation at subsequent checkpoints.

SHA-256 authenticates data against the manifest; it is not a substitute for manifest authentication. Pin the manifest root digest locally after an authenticated fetch. Rehash completed files before trusting local checkpoints, and verify the complete object after assembling ranges. Checkpoints bind account issuer, snapshot/root digest, entry ID, expected source revision/digest, completed byte intervals and verified final output. Retry only missing chunks with bounded concurrency, jitter/backoff and `Retry-After`; expose pause, resume, free disk space and verification failures. A browser tab's lifetime is unsuitable for a terabyte transfer.

### Stable inventory without bucket listing

Current SQL pages describe live state, not a snapshot: objects can change or disappear between pages, and existing collectors do not honor export pins. Merely adding a cursor or saving ETags does not fix this.

Implement bounded snapshot construction with an account generation and a durable before-image journal. At snapshot start, atomically record generation `G` and enable preservation of selected existing versions. Every subsequent content metadata mutation records its before-image for active snapshot construction in the same transaction as its live change. Page through the catalog, combining live rows and journal before-images to reconstruct membership and metadata exactly at `G`; exclude later insertions. Preserve deleted rows and old blob references even when a key disappears before the scan reaches it. Resolve private blob references from authoritative host records, not from a user-supplied manifest. Verify index backfill/readiness before declaring the snapshot complete. No long transaction or network call is held across the million-row scan.

Finish construction by atomically sealing the manifest membership, counts and generation, then transition preservation into per-job pins for exact referenced blobs. A crash resumes from durable cursor/journal state; no part of the snapshot is reported ready until membership is sealed. Bounded hashing/manifest generation follows. Garbage collectors must consult snapshot build preservation and pins before **every** physical delete. All write/delete/restore/maintenance paths participate, including messages, resource removal and owner deletion. Owner-requested immediate erasure cancels the relevant snapshot/pin under a specified policy instead of leaving a hidden export copy.

Bound job count (initially one active snapshot/offload per account), snapshot metadata, journal growth, pinned bytes and lifetime. Over-budget construction pauses new snapshot creation or fails it cleanly; it must not silently drop before-images. Drop stale pins with a durable cancellation/expiry record and queue eligible cleanup. Export pin expiry must not unexpectedly race a granted range request. Pin growth is physical storage cost even when logical live bytes shrink. The implementation may choose a proven SQLite snapshot mechanism instead, but it must demonstrate identical crash/Worker/Node invariants; an assumption that paged reads share a transaction is insufficient.

A read-only downloadable snapshot retains its source pins for the advertised lifetime. A progressive move uses a private migration snapshot whose per-entry pin can be released once the verified destination and source-deletion receipt commit. Do not issue long-lived source-download promises for entries being removed by that move. If any other valid snapshot still pins the blob, physical reclamation waits and the UI reports retained bytes; a move must not falsely claim those storage costs are already gone.

### Tools and interoperability

Start with a small cross-platform custom CLI using this API and local checkpoints. A desktop wrapper can use exactly the same client engine later. The CLI is the path for verifiable per-item receipts, strong manifest integrity and offline restart behavior; browser UI creates and monitors jobs.

Optionally expose a read-only WebDAV projection of a sealed export so rclone can copy it. Support bounded `PROPFIND Depth:0/1`, `HEAD`, `GET` and range reads; reject `Depth:infinity` and every mutating method. Partition large virtual directories into deterministic bounded shards so a standard client can traverse them without proprietary listing pagination or a million-entry response. This owner export view does not add listing to the application storage contract. Generic WebDAV checksum support varies; retain the manifest and run independent verification before a local backup is reported complete. [rclone's WebDAV documentation](https://rclone.org/webdav/) documents the backend and provider-dependent checksum limitations.

Use `rclone copy` semantics for the read-only projection. `rclone move` or `sync` must not cause source deletion or destination deletion implicitly. The server-side offload protocol owns source deletion receipts. SSH rsync requires a different server/transport and is not proposed for Workers. A user may subsequently run rsync between their own local systems; that does not change the hosted service design.

## Connected destination and per-item move

Select an existing owned resource through the normal connection UI, then authorize this job for its current resource ID, generation, bounded logical prefix, read/write methods and byte/object limits. Offload routes accept no API keys or OAuth tokens. Reuse the existing encrypted connection and refresh/disconnect lifecycle. Jobs retain an authorization reference, never a second credential copy. A new S3 destination is first connected normally; it becomes eligible only when its mediated write and verification capabilities actually exist and pass conformance.

Extract or reuse a generic owner resource-operation port so export uses the same key validation, credential mediation, provider driver and conditional-write semantics as normal storage. An owner job is its own scoped principal; it must not fabricate an app grant or call the app RPC route with ambient owner powers. The source inventory remains the host metadata catalog. The destination requires read, write, atomic create-if-absent and trustworthy exact-version retrieval or an equivalent host-managed immutable mapping. It must support strong verification. A provider name, connection status, user assertion or populated credential is not a capability proof.

| Existing destination | Offload eligibility today |
| --- | --- |
| Hosted resource on this same account | Reject for over-quota offload: both copies count against the same quota; ordinary internal copy is a separate action |
| Managed Google Drive | Has host-managed writable immutable objects/mappings; 1 MiB/object, 10,000 logical objects and 10,000 retained versions per resource; candidate only for a fitting selection after integration/conformance |
| S3-compatible or WebDAV | Configured runtime is read-only; show disabled with explanation until writable conditional publication and verification are implemented and reviewed |
| Other/future connected provider | Evaluate actual mediated capabilities and scope; no provider-specific offload code path or unsupported promise |

Use a new random destination job prefix, immutable entry-derived keys and conditional create. Do not overwrite arbitrary existing keys. Probe write/readback within that owned prefix through the resource port; a successful probe alone does not prove all conditional semantics. For providers such as managed Drive, host mapping transactions may supply exact versions; preserve needed mapping exports so recovery does not depend on guessing names. Export format and logical record metadata remain provider-independent. Store manifest shards/root at known keys and export the relevant destination mapping receipts where opaque provider IDs require them.

Preflight checks remaining provider bytes where knowable, maximum object/part size, object cardinality, existing retained versions, pending operations and all manifest/probe/mapping overhead. Unknown external capacity remains an explicit possible mid-job failure, handled by retaining source. The current managed Drive cap holds at most roughly 10.49 GB of one-MiB payloads before metadata, so one such resource cannot receive a terabyte or a million-object account. The existing 100-resource account cap also makes naive one-million-object spreading inadequate once metadata and connections count. Recommend a suitable supported destination or a smaller selected dataset; multi-destination placement is a later explicit feature. No current connector is proven here as a general full-terabyte offload destination.

Respect the destination's maximum object size by splitting larger payloads into deterministic bounded parts, with part offsets/lengths/SHA-256 and a whole original-object digest in the manifest. An inbox message may exceed the common 1 MiB provider ceiling. All parts and the metadata needed to reconstruct that item must be durably written and verified before its source is removed. Include manifest/part/mapping overhead in quota estimates and job budgets. Cross-provider movement uses mediated get/put; do not assume cross-cloud copy or multipart support. Destination-native version retention is useful where available, but verified immutable host mappings may supply the abstraction. Concurrent external deletion remains a user-controlled risk.

The existing resource secret stays encrypted under the service KEK and within its provider lifecycle. Offload neither changes it nor deletes it on job completion. Job authority has bounded expiry and live revocation; credential refresh may continue only for the same reviewed resource binding. A disconnect, changed owner/provider/root/prefix or changed resource generation pauses the job before further effects; restart requires explicit validation of the new binding. Temporary least-privilege credentials and bucket/prefix restrictions remain recommended at normal S3 connection setup. Never echo secrets into UI, walkthroughs, errors, URLs, manifests, receipts, analytics or logs. Do not grant apps broader destination access.

Reuse connector network controls and close their existing deployment gaps: operator-allowlisted public HTTPS endpoints, canonical paths, no userinfo/private/IP/link-local/metadata hosts or nonapproved ports/redirects, and DNS/connection-time egress enforcement against rebinding. Validate the resolved resource endpoint before sending credentials. Use bounded response bodies, timeouts and retries. Unsupported custom providers can use local CLI download plus locally configured tools; server offload remains disabled until the connector passes the same controls.

Per-entry durable state machine:

1. **Planned:** record exact owner/snapshot entry, source resource/key or message ID, source revision/blob reference, size/digest, destination resource ID/generation/prefix, part keys and job authorization revision. Reserve bounded work capacity.
2. **Write pending:** durably record the attempt before the first external request. PUT exact bytes using conditional create and checksum where supported. Persist destination version ID/ETag as opaque identity, request outcome and retry information.
3. **Verified:** GET every exact destination part version and hash all bytes, or accept a provider-validated strong *full-object* checksum under a reviewed conformance profile. Compare length and SHA-256 to the authenticated source manifest. ETag, size, client-supplied metadata, TLS, a 200 response, or multipart/composite checksums alone do not establish this. Verify the destination manifest/root/mapping information needed to restore the entry too; payloads without their reconstruction metadata do not authorize deletion. Persist verification method, destination versions, digests and timestamp in a durable receipt.
4. **Source removal committed:** after remote work, reacquire the account mutation boundary and read current authority. Check job and destination resource generation/scope, owner/recovery epoch, explicit copy-and-delete selection, source version/revision, pin/receipt, current episode and entitlement rules. If the live source changed, retain it and mark the old entry `source-changed`; never delete the new version. On a match, atomically delete/tombstone authoritative metadata, update catalog/logical quota and persist the source deletion receipt and garbage ownership. Do not hold a metadata transaction open during remote upload/verification.
5. **Physical cleanup complete:** remove pins no longer needed, delete the immutable owned blob when unreferenced, and record physical deletion success. Only then decrement physical storage debt. Durable retries resume cleanup after a restart.

For a voluntary move, gaining sufficient paid quota stops automatic retention cleanup; whether to continue the user-requested move is controlled by that move authorization. Default downgrade-assisted move jobs pause before further source deletion when the episode resolves, allowing the user to choose to continue. Keep these checks explicit rather than using a renewal as an excuse to complete stale deletion work.

Destination verification guidance is provider-specific. Amazon documents separate full-object and composite checksum behavior; this design requires validated semantics, not a generic S3-compatible label. [Amazon S3 object integrity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity.html).

### Crash recovery and ownership

Network calls are at least once; logical source deletion and accounting must be idempotent. A timeout after PUT leaves `write-pending/unknown`, not failed-and-safe-to-overwrite. Reconcile only the known job key/version by reading and hashing; adopt it only if exact expected bytes match. Otherwise report collision and retain source. A retry must not blindly delete or overwrite an object that may belong to someone else. An interrupted job resumes from receipts instead of recopying/deleting all entries.

After verification but before source removal, revalidate the exact destination version when needed to reduce the verification-to-delete gap. There is no atomic transaction across providers. Versioning/retention protections and exclusive job-prefix use reduce this risk; the user can still remove their destination copy after a verified move. A changed/missing destination or expired/revoked credentials pauses deletion. Corruption, unavailable source bytes, failed verification and uncertain provider outcomes all retain source. Never erase source to make a failed progress bar advance.

Keep deletion receipts and garbage records long enough to outlive retry/replay/recovery windows. A crash after logical deletion must still have a receipt and owned blob to clean. A crash after physical delete but before checkpoint safely retries deletion of the same immutable ref. Cancellation revokes new transfer/deletion work, releases unnecessary source pins and preserves receipts. Destination data already copied is retained by default; destination cleanup is a separate explicitly authorized operation and can only delete proven job-owned keys/versions. Multipart abort ownership follows the same rule. No broad bucket cleanup or listing is implied.

## Quota, cost and throughput

Expose three measures: **live logical hosted bytes**, **upload reservations**, and **retained physical bytes awaiting pin/garbage cleanup**. Existing quota releases live logical bytes on mapping removal; it does not prove billed bytes have disappeared. Preserve that user-visible quota meaning, but label it accurately and retain physical debt until a durable successful delete receipt. A failed destination verification releases neither source quota nor physical debt. Never discard garbage ownership merely because usage fits or the account moves to Free.

The existing foreground limits are 120 units/app/minute, 240/account/minute, Free 500/hour and 1,000/day, paid 2,000/hour and 10,000/day, with shared logical/physical units and a service ceiling of 10 million/month including reserved archive capacity. A terabyte at the current maximum 1 MiB object size needs at least 953,675 objects. Even one charged operation per object would take about 954 days at Free's daily allowance. Reads/deletes currently have different admission behavior; this arithmetic identifies why simply routing a future migration's writes/checkpoints through foreground admission cannot meet a 30-day promise.

Add a bounded extraction/offload lane with explicit account/job/provider/global limits on requests, bytes, concurrency, retries, snapshot metadata and physical pins. Reserve and account this capacity durably before promising a deadline. It is not an unlimited exemption and must not borrow the existing archive reserve silently. Destination writes require their own accounting; the existing guarded R2 bucket wrapper does not meter external provider PUTs. Stream bodies with backpressure and checkpoint between bounded batches on portable Worker/Node job runners. Admission failure returns accurate retry/progress state while the job stays durable.

Concrete initial capacity proposal: reserve **2.2 million of the existing 10 million monthly service units** for export/move, retain 1 million for archives, and leave 6.8 million foreground units. This is a proposed allocation, not a higher ceiling or deployed configuration. Meter at least one logical item/part-transfer admission plus every destination physical PUT attempt; charge manifest writes and retries too. A million single-part items consume at least 2 million units, leaving 200,000 for metadata/retries only if measured workloads fit. It can fund roughly one such account per month, not arbitrarily many simultaneous Ultra exits. Existing pinned monthly allocation/lease rules must change only via a conserving migration or the next UTC boundary; no new untracked pool. Read-only download gets explicit request/byte budgets even when it makes no destination PUTs. Short-lived leases and queue reservations prevent concurrent jobs from overspending the same capacity.

An initial per-job upper envelope of 4 concurrent network operations, 100 destination write attempts/minute, 100,000 transfer activity units/day and a 30-day deadline supports one million single-part items in roughly 20 days at two units/item if the reserved capacity is actually available. Fair scheduling and provider rate limits may lower throughput, so this envelope is not a promise. Large message splitting, retries or bigger datasets require a preflight recalculation. The service must reserve a feasible slot and show completion estimates before accepting deadline-dependent moves; if several accounts need the reserve concurrently, fund/reallocate capacity within policy or defer destructive retention, rather than silently missing the deadline.

Planning target: 1 TB in 30 days is approximately 0.386 MB/s average transfer and 31,790 one-MiB objects/day, before verification and retries. Full destination readback adds another 1 TB of network transfer. Actual tiny-object datasets may have a much larger request burden; count/metadata limits are independent of byte limits. Establish a supported worst case and prove it in load/recovery tests before enabling retention, including many concurrent downgraded accounts and provider throttling. Alert early when remaining work cannot finish before the deadline; offer local export, a reviewed bounded extension, or capacity intervention.

A 1 Mbps home connection needs about 92.6 days to download a decimal terabyte even before overhead. A 30-day policy therefore needs a usable server-to-connected-provider alternative, not just a resumable local downloader. Destination capability/capacity and funded service throughput must be established before presenting that alternative as available.

Cloudflare's current Standard rate is $0.015/GB-month, so an extra 30 days retaining a full decimal terabyte is about $15 in storage before shared free allowance and other costs. R2 egress is free; requests, Workers/SQLite, destination PUT/storage and possible destination GET egress still matter. [Cloudflare R2 pricing, checked 2026-10-13](https://developers.cloudflare.com/r2/pricing/). This economic reason supports a finite grace period; it does not prove the proposed prices fund every workload.

For one million items, a simple full hashing pass followed by one source read per transfer makes about two million R2 GETs, or $0.72 at the raw $0.36/million Standard Class B rate before allowance/rounding. Destination verification adds about one million reads and up to one terabyte of destination egress at that provider's rates. Durable entry transitions alone are several million SQLite writes, plus indexes, snapshot rows and reads; measure actual rows/CPU on Worker and Node. Benchmark CPU milliseconds per hashed GB and per item, retained SQL bytes per entry, and retry multipliers, then price those measured totals against deployment rates before release. No compute dollar estimate is claimed without those measurements. Source snapshot pinning, local backup/restore traffic and external-provider charges remain separate from the activity-unit ceiling.

R2 binding `delete` has no conditional argument. Safety therefore comes from the atomic host mapping check and an immutable unreferenced physical blob ID, not head-then-delete against a mutable logical R2 key. R2 supports streamed GET/range operations; adapter parity still requires implementation and tests. [Cloudflare Workers R2 API reference](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).

## Live migration and portable identity are separate

A future live resource migration may keep a stable logical resource ID only if the host can switch an audited mapping, preserve exact versions/keys, verify every app's expected contract, and atomically fence concurrent writes. Otherwise issue a new resource ID, export old-to-new mappings/root pointers, and require explicit owner approval for each affected app assignment. Changing backing resources does not authorize widening prefixes, methods, quotas or recipients. Existing read-only S3 configuration cannot transparently replace writable hosted storage. Bind migration job authority and app grants separately to current resource IDs/generations while keeping credentials private in the existing resource connection.

Ordinary content export includes safe public identity information needed to identify its owner, not private signing keys or the recovery secret. Portable identity/keychain export uses the separately protected identity backup workflow with fresh authentication, encryption and a restore test. Recovery files grant recovery authority and must never appear in a plain manifest or shared backup prefix by default. Permanent canonical/paid name claims remain historical nontransferable records; copying a backup does not move or recreate those claims. Content cleanup must not delete credentials, signing keys, recovery state or permanent claim ledgers.

## Bounded implementation phases

1. **Policy and read-only visibility:** persist effective over-quota episodes and exact deadlines behind a disabled execution flag; add previewable notices, whole-unit keep selections, storage debt metrics and owner-only inventory. Verify billing effective-time semantics, backfills and terms migration. No retention execution yet.
2. **Durable export core:** portable job/repository/blob ports, message garbage crash fix, snapshot preservation/pins, immutable manifest and streaming ranges; CLI download/checkpoint/verify. Run actual SQLite Node and workerd fault tests. Add WebDAV only after this API works; it is optional for first export release.
3. **Connected-provider copy-only:** reuse resource credentials and scoped owner operation port, endpoint/egress enforcement, real supported-provider conformance, durable unknown-write reconciliation and full readback verification. Produce a restorable export and verify it outside the source service. Unsupported/read-only destinations remain visibly disabled.
4. **User-authorized move:** exact source CAS, dependency-aware selection, receipt/cleanup accounting, cancellation and all race/crash tests. Prove no source removal occurs without the correct durable verification receipt and current move authority.
5. **Finite retention execution:** notices/terms/backup recovery evidence, funded throughput and independently reviewed cleanup policy. Enable only after security S4/S5 and retention-specific sign-offs. Shadow execution/dry-run comparison precedes any destructive rollout; keep a kill switch and observability for debt, lost deadlines and stalled jobs.

Keep domain transitions portable through injected repositories, clocks, blob readers, existing resource operations/credential vault, budgets and notice ports; use the project's ngin composition after reading its actual APIs. Worker alarms/queues and Node scheduled runners adapt the same transitions. Neither relies on a process remaining alive for an entire transfer. Frontend work uses the vendored 3sln stack and the same status model.

## Critical tests and adversarial exercises

| Exercise | Required outcome |
| --- | --- |
| Renewal/update arrives during remote PUT or immediately before deletion | Current entitlement and authorization win at the deletion commit; no stale automatic cleanup |
| Replace a key while its old version is exporting; delete and recreate same key | Manifest remains stable; only exact old version can be marked moved, new live object survives |
| Million-row inventory while inserts/deletes/metadata edits occur around every page | Complete snapshot at generation G, no phantom/omitted entries, bounded memory and journal |
| Kill Worker/Node before/after every durable transition, especially message metadata delete | Receipt/pin/garbage ownership persists; no double quota decrement, orphan or unverified deletion |
| PUT succeeds but response is lost; destination key already exists with same/different bytes | Exact reconciliation; no arbitrary overwrite or false verification |
| Strong-looking ETag, wrong content, multipart ETag, stale HEAD/checksum metadata | Full validated bytes/checksum required; source retained |
| Destination overwrite/delete between verification and cleanup | Version identity rechecked; unsupported integrity profile blocks destructive move |
| Credential expires, job cancels, session recovery or owner revocation during each phase | New requests/deletions stop; copied destination data/cleanup receipts remain correctly owned |
| Resource disconnect/reconnect or scope/root/generation change; same-account hosted destination | Stale job pauses, no broader provider access; internal copy never claims hosted quota savings |
| Message exceeds destination size, missing manifest shard or opaque destination mapping | Split parts and reconstruction metadata all verify before source removal |
| Drive destination has insufficient key/retained-version capacity; external bucket fills mid-job | Preflight refuses known infeasible jobs; runtime failures retain source with resumable progress |
| Cross-owner job/shard/entry/cursor, stale resource incarnation and malicious manifest IDs | Reject before fetching source or sending external credentials |
| SSRF via IP/IPv6/userinfo/port/redirect/DNS change and signed path escaping | No credential reaches unintended endpoint; fail closed with bounded safe error |
| Traversal, Unicode/case collision, symlink and reserved filename payload names | All local writes remain under export root; no collision overwrites |
| Interrupted/mismatched ranges, 200 on resume, corrupt checkpoint/disk output | Restart only safe ranges; final full digest detects corruption |
| Destination readback blocked, immutable/object-locked source cleanup, expired pins | Source or owned physical debt retained; accurate status and safe retry/incident |
| Grace replay, repeated downgrade/upgrade, catalog shrink, clock rollback, absent contacts | No reset/backdating; notice evidence truthful; destructive work gated |
| Deadline during a genuinely progressing transfer vs idle retries | Bounded extension policy enforced; no implicit indefinite retention |
| Rate/storage cap exhausted; simultaneous Ultra accounts; tiny-object workload | Reserved extraction capacity and fair progress, bounded cost, early deadline alert |
| App indexes/chunks span units, selected keep bytes exceed new quota | No arbitrary chunk purge; infeasible selection exposed before cutoff |
| Restore from export on a separate machine with service unavailable | Byte integrity and mappings verifiable, known app-format limitations documented |

SDK/core/server changes require `npm test`; frontend behavior additionally requires DOM and actual-browser verification. Worker/Node parity needs their real durable adapters, not only in-memory mocks. No terabyte migration, remote S3 account, outbound delivery or production deployment was tested while writing this document.
