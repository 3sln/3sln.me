# Active population for developer contact issuance

Provisional implementation, 2026-10-13. Reviewer: __________ Date: __________ Outcome: __________.

The working definition is authenticated owner use within the last 30 days. This interprets the user's “active users” threshold as monthly activity, not lifetime signup stock. `DEVELOPER_CONTACT_ACTIVE_THRESHOLD` defaults to 1500: below it the policy permits all active owners to request the daily developer contact; at or above it issuance requires the independently checked paid tier. This source does not revoke existing links or run on message receipt. Product confirmation of the definition remains unsigned.

## Portable authority and cost

`env.DEVELOPER_CONTACT_POPULATION.policy()` returns only `{mode, observedAt, validUntil, definition}`, where mode is `all-active`, `paid-only` or `unavailable`. It exposes neither individual activity nor an exact population count to public callers. The owner controller calls `touch(owner, at)` through the injected resource. Node and Worker use the same implementation. Worker reuses the existing AbuseGuard class at 32 stable `active-user-v1/00` through `/31` names, plus one background census coordinator; no new binding or global per-message actor is introduced.

Each shard retains one latest expiry-day row per owner and at most 32 expiry-day count buckets. Distinct owners count once, irrespective of repeated sessions, requests or devices. On acknowledged recording, the owner actor saves its confirmed UTC day, suppressing further source calls that day before the existing 15-minute activity coalescing return. Expiry is the start of the following UTC day plus 30 days; this conservatively counts up to 24 extra hours. Shard records do not enumerate identities during policy reads. The retained owner rows are bounded by the service's 100000 overall admission stock; the shard additionally rejects more than 100000 cumulative owner rows. Expired rows are retained to preserve deduplication without a daily scan.

An aggregate reads the 32 small summaries only on policy refresh. Its process-local cache has an absolute 60-second expiry measured from the start of refresh; reads do not extend it. Different Worker isolates can each refresh, so this is a bounded per-isolate refresh optimization, not a guaranteed globally single refresh. Shard generations are pinned in the completed census: a missing or recreated shard cannot silently become zero. Malformed state and clock rollback produce `unavailable`. A configured threshold change requires new runtime resources; routing/layout changes require migration.

## Truthful initial baseline and reconciliation

The source starts unavailable. It never substitutes lifetime signup count for monthly activity or treats an uninitialized shard as zero. A background census uses the existing durable identity enumeration, at most 100 identities per step. Each selected active/recovering account supplies its identity activity timestamp and a read-only owner-metadata snapshot. It does not warm archived messages, fetch R2 bodies or run search. Pending, suspended and deleted records are excluded at that census observation. Recovering records are conservatively included because a previously active account can be recovering.

The census merges the later known activity with existing shard records; it cannot overwrite a concurrent newer owner touch. Legacy owner activity coalesced for 15 minutes is conservatively advanced by that uncertainty, clamped to the census time. Its temporary excess window is therefore at most 24 hours and 15 minutes. If an existing active identity has no trustworthy activity timestamp at all, the census conservatively starts its window at observation rather than asserting inactivity; that exceptional overcount can persist for 31 days. Invalid supplied timestamps fail the page. An account suspended/deleted after it was counted can remain in the recent-activity upper bound until its current window expires; this source does not promise instantaneous lifecycle subtraction.

The coordinator durably stores a cursor and a bounded lease. Only a completed page advances the cursor; interruption retries that page idempotently. Completion is published after all pages have been merged. A minute alarm continues progress, with the existing scheduled hook as a restart opportunity; Node restores its coordinator alarm at startup. An initial policy read can arm initialization. The Worker identity layout has 64 partitions, so even a small initial census can take about an hour; larger populations take proportionally more bounded steps. Until completion, a free owner receives eligibility-unavailable rather than paid-required. Already eligible paid owners do not depend on this census.

## Optional accounting must not block accounts

Population recording is optional infrastructure, not authentication authority. Before a daily attempt, the owner actor stores a pending activity timestamp. Only a successful source acknowledgement advances its confirmed-day marker. The optional source RPC has a 250-millisecond deadline and invalidation a further at most 100 milliseconds; a timed-out idempotent RPC may still commit later. A failed or uncertain source response preserves the pending record, schedules bounded retries and best-effort invalidates the census. Retry delays progress through one minute, five minutes, thirty minutes, six hours and then one day. Normal sign-in, read, recovery and owner activity continue.

A known invalidation makes new source snapshots unavailable and starts a bounded reconciliation pass. Invalidation during an existing pass requires another full pass before completeness can be claimed. Existing shard records are merged, not cleared. Other processes can retain a previously cached policy for at most its original 60-second lease. If a network partition blocks both the activity write and the invalidation, the remote source cannot know the missing event: its observed count may temporarily lag. This is an explicitly accepted limitation of an optional growth-policy metric; it is not a hard authorization/security population ceiling. Pending retries and census reconciliation repair it when connectivity returns. No account access is withheld to make the metric appear perfectly synchronized.

Failure counts, activity data and census state stay internal. Incoming contact messages, model classification, background fanout and arbitrary unauthenticated traffic do not themselves count as owner activity. No per-keystroke heartbeat or new analytics network service is introduced.

## Verification and remaining gates

Focused tests cover baseline absence, exact threshold comparison, UTC expiry, duplicate concurrent activity, old 15-minute uncertainty, overlapping census/activity, interrupted census leases, shard generation loss, corrupt bounds, clock rollback, nonblocking source failure, retry coalescing and durable Node restart. A real Worker fixture covers the sharded census and owner activity path. Full-core and final integrated review evidence is recorded in DEVLOG. No production population, deployment or developer identity is changed by these tests.

The product definition, production first-census completion, alerting for a stuck census, and explicit migrations after restoration/partial data loss remain operator review gates. No public operator reset endpoint or unscoped census secret is added.
