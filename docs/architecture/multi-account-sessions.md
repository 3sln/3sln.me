# Multiple local accounts in one browser

Status: provisional; first-party console slice implemented locally 2026-10-14 with **independently named per-account cookies**, not the single vault or per-device coordinator described further below. Security sign-off remains pending. This document describes provider-local session handling; it does not change Bindle authorization or require a particular client library.

## Implemented choice: independent per-account cookies (2026-10-14)

The first slice ([cookies](../../packages/runtime/account-cookies.mjs), [routes](../../packages/runtime/account-session-http.mjs), [HTTP wiring](../../packages/runtime/http.mjs)) supersedes the single-vault and coordinator proposals for the provider console. The coordinator was not adopted: a stable coordinator capability copied from an old cookie amplifies into authority over accounts added later (see the blocker below), and rotating/scoping it needs a reviewed protocol this slice does not require.

- **Custody.** One cookie per signed-in owner, `__Host-bindle_account_<owner>` (local: `bindle_account_<owner>`), HttpOnly, Secure (production), Path=/, SameSite=Strict, Max-Age bounded by its session expiry. Value is AES-GCM under a dedicated operator key `SESSION_COOKIE_KEY` (32 random bytes, base64url); associated data binds exact `APP_ORIGIN`, purpose, cookie name and version, so a value renamed to another owner or replayed on another origin fails authentication. Payload is exactly `{owner,token,expiresAt,sessionContext}`; the token's embedded UUID must equal the owner. Authentication precedes JSON parsing. Without a valid key the runtime keeps the legacy single-session cookie unchanged.
- **Selection.** Each private request names its member with `X-Bindle-Account` plus `X-Bindle-Session-Context` (the server session ID, not a secret). The named cookie is decrypted and the context compared **before any identity or account actor is routed**; then the ordinary owner-session check validates the live session. One decrypt per request, no all-member fanout. Only header-less discovery (`GET /api/session`, native subresource GETs) uses the sealed `default` cookie; a header-less private **mutation** is refused with `account_context_conflict`. A missing/invalid default selects nothing; no other member is ever substituted. Tabs persist only `{owner,sessionContext}` in `sessionStorage`.
- **Routes** (first-party only: exact Origin, Fetch Metadata not `cross-site`/`same-site`, no CORS). `GET /api/auth/accounts` validates each observed member (≤ 8) against its owner and returns `{accounts:[{account:{id,handle},expiresAt,sessionContext}],activeOwner,limit,revision,cleanupPending,pickerToken}`; revoked/invalid members are expired from the browser. `POST …/switch {owner,expectedRevision,pickerToken?}` re-validates the target and rewrites only the default cookie; it neither mints nor extends a session. `POST …/logout {owner,…}`, `…/logout-all`, `…/cleanup` revoke owner sessions before claiming success. Mutations require `expectedRevision` (a digest of observed `(owner, session)` pairs) plus either the picker proof (AEAD, 2-minute, bound to that exact snapshot) or the selected member's live CSRF; a stale snapshot returns `vault_conflict` for review, never a silent retry.
- **Installation.** Every successful login/activation/recovery/device approval adds or replaces only that owner's cookie and clears the legacy cookie. A sixth distinct owner is refused with `account_limit` (409) **after** the new session is revoked (compensation), so repeated full-browser logins do not leave orphan sessions. A same-owner predecessor session is revoked; if that revocation fails it enters retry custody.
- **Partial logout.** Unresolved revocations move into a sealed `cleanup` cookie that cannot select, list or authenticate owner requests and lives no longer than its latest session. Every later sign-out retries it; `…/cleanup` retries only it. Members are removed from ordinary selection immediately.
- **Legacy migration.** A valid legacy cookie is honored only when no member/default cookie is present; `GET /api/session` then installs one member and expires the legacy cookie. Any present member/default cookie, even malformed, disables legacy fallback.

**What this choice cannot do.** It has no atomic global account limit: the five-member check reads the cookies of that request, so concurrent installs in two tabs can briefly exceed five (≤ 8 are still enumerated and can be signed out; more fails closed with guidance). Stale responses can still overwrite the `default` cookie (default is discovery only; tab selection is unaffected) or re-install a session the user just created. Cookie header budget is measured, not unlimited: five production members plus default ≈ 2.1 KB, plus a five-entry cleanup cookie ≈ 3.7 KB; an eight-entry cleanup cookie stays below 4 KiB ([tests](../../tests/account-sessions.test.mjs)). Removing a cookie does not revoke a **copied** cookie; only successful owner-session revocation does, so an unresolved cleanup entry remains usable by a copy until retry succeeds or the session expires (≤ 24 h). Inventory is not rate-limited beyond the ≤ 8 bound. No cross-device sign-out is implied. A duplicated cookie name fails closed (401) until it expires, which a same-host localhost app or legacy-browser `__Host-` bypass could abuse. Signing out of this browser does not remove that owner's push enrollment. Without `SESSION_COOKIE_KEY` (production Wrangler secret / Node env) multi-account stays disabled and the legacy single cookie is used; key rotation is not implemented and a key change signs every browser out.

Out of scope for this slice: third-party app account choice and provider-owned authorization entry, app-triggered login/switch/reauth/end-session, embeddable elements and iframes. The sections below remain the design record for those phases; where they describe a single vault cookie or coordinator for the console, the implemented choice above governs.


## Existing behavior and proposed boundary

Today the provider writes one HttpOnly session cookie. Its opaque token contains an owner UUID used to route to that owner's repository, where the session hash, expiry and account status are checked. Successful login replaces the cookie. Sessions have independent server records and expire within 24 hours.

Keep those per-owner records. Add a bounded, authenticated-encrypted host cookie containing at most **five** session entries and one active entry. The vault is transport storage, not an authorization grant: every selected token still requires the existing owner-session check. A switch does not mint a session or extend its lifetime. Five is an initial product limit, not a protocol constant.

Production cookie: `__Host-bindle_accounts`, Secure, HttpOnly, Path=/, SameSite=Strict. The localhost development cookie has a distinct unprefixed name. Do not use Domain, Partitioned storage as a substitute for first-party login, browser storage, URLs, or readable JavaScript session tokens.

## Vault format and routing

Use a versioned AEAD envelope with a key ID, random nonce and authenticated ciphertext. Bind associated data to the exact configured provider origin, cookie name and format version. A dedicated operator-provisioned key/key ring is required; do not reuse onboarding, postback or app-signature keys. Authenticate before parsing inner JSON or selecting any owner actor. Bound encoded input to 3,800 bytes, ciphertext/plaintext size, entry count, token grammar, UUIDs, timestamps, unique owners, and active-entry membership. Reject duplicate cookie names and duplicate JSON fields. A malformed, oversized, unknown-key or unauthenticated vault yields an anonymous response without owner actor requests.

Inner entries contain only `{owner,token,expiresAt}`; the envelope also carries `activeOwner`, `issuedAt` and version. No credentials, pending tokens, email, names, badges or CSRF tokens belong in the vault. The token's embedded UUID must match its entry owner. Derive labels from authenticated account projection. Measure final worst-case cookie bytes in tests; never silently truncate entries. At the fifth account, adding a different account requires an explicit removal choice.

Ordinary account requests decrypt once and select the explicit tab-bound `X-Bindle-Account` member, falling back to `activeOwner` only for initial session discovery. Validate **one** owner session. The expected session context is also checked against that session, so same-owner relogin/recovery cannot silently reuse stale authority. Do not inspect all entries, global identity indexes or every owner's database on that hot path. Expired entries may be removed by their authenticated recorded expiry without actor access; unexpired revocations are discovered when that account is explicitly selected. No fallback to another owner on an invalid active session: show the chooser/sign-in state so a request never unexpectedly targets another identity.

A dedicated first-party chooser request may validate up to five entries to show current authenticated labels and unavailable entries. It is bounded, rate-limited and no-store; this cost is not part of every page/API request. Never expose raw tokens to the browser. Background validation cannot automatically change the active owner.

## Migration, concurrency and lifecycle

Accept a valid legacy single-session cookie only when no vault cookie is present. Validate the legacy session normally, then upgrade to a one-entry vault and expire the legacy cookie. A malformed vault must not fall back to legacy credentials. During a rolling deployment, prefer compatibility readers before enabling vault writers; reverting to an old reader would otherwise unexpectedly sign users out. Key rotation accepts a bounded previous-key window and rewrites using the current key without refreshing owner-session expiry.

Login adds/replaces the authenticated owner's entry, preserves other entries, and selects that owner. Pending setup does not add an entry until ordinary activation succeeds. Account recovery and device approval use the same final session installation path and cannot replace an unrelated account's entry without explicit intent.

A stateless cookie cannot merge concurrent stale responses reliably. The phase-two proposal therefore uses an authoritative per-device coordinator for membership changes, inventory and reconciliation, as detailed below. Serialize account-management UI operations and broadcast only an opaque account-context-change event between first-party tabs. Every owner request carries an expected owner context (UUID is not a secret or grant); a mismatch with the authenticated selected member or its live session context returns a context-conflict response before mutation. This prevents a background tab from silently writing to the newly selected account. Async results are fenced by owner, session/context generation, selected object and request ticket. Abort prepared postback handoffs and destroy message frames/private proposals when the context changes. A later phase may add a durable browser-vault revision if atomic multi-tab membership merging is required; do not claim the stateless draft solves last-response-wins cookie races.

## Switching and logout

Proposed owner endpoint: `POST /api/auth/accounts/switch {owner}`. Require exact provider Origin, current active session and its CSRF token, authenticated vault membership, and a fresh authoritative check of the target token. Verify vault authenticity before either actor lookup. Return only the selected public account, fresh selected-session CSRF projection and expiry; rewrite the active pointer. Target revoked/expired/suspended fails without selecting another account. If the active session has expired, switching needs an explicit chooser challenge bound to the authenticated vault and same-origin browser request, or reauthentication; do not bypass CSRF by accepting a bare target UUID.

`POST /api/auth/accounts/logout {owner}` removes and revokes exactly the selected owned entry. Logout of another saved account requires active-session CSRF plus its authenticated vault membership. `logout-all` explicitly validates/revokes the bounded set, reports partial server failures, and removes confirmed-revoked members from the coordinator. Unresolved members remain encrypted in a retry-only state, with no ordinary active selection; a narrow authenticated vault cleanup capability permits explicit retry even after the active session is revoked. The UI reports incomplete server revocation rather than success. It does not claim other devices were revoked. A separate existing account-level revoke-all-devices operation remains distinct. Logout never silently activates a remaining account. Cookie expiry is no later than the latest contained session expiry; per-entry expiry and revocation remain authoritative.

## OAuth and account choice

On the provider's first-party authorization screen, show which authenticated account would approve the request and offer an explicit account choice. A handle/subject-bound request cannot be reassigned by switching: either choose its exact locally authenticated identity or restart/cancel the request. For OAuth-only request-local selection, authenticate the exact selected member against the vault and validate its live owner session; an arbitrary UUID or supplied token cannot select a session. Consent selects an owner request-locally without changing the console's global active owner. Choosing a different account invalidates any prepared consent state, resource choices and CSRF/context binding and requires a new review for that account. Bind reinspection and approval to the selected session epoch and resource/grant digest. Existing method/resource consent is per owner and client; another owner's consent never carries over.

Before explicit approval, the app receives neither account inventory, chosen identity, session presence nor notification recipient information. The provider may render the picker to its own user, but must not leak it through iframe messaging, timing-specific result payloads, preconsent redirects or app-readable storage. Registered callback origin, PKCE/state and existing exact method consent remain required.

## App-requested account flows

Apps may initiate a provider-hosted intent using existing authorization continuation mechanisms: `login`, `select-account`, `reauthenticate`, or `end-session`. Bind each request to its registered client, exact callback, expiring nonce/state, and PKCE whenever a grant is issued. An app cannot name an arbitrary callback, inspect the vault, choose an unseen owner or cause a provider cookie change through a GET or silent frame request.

SDK-local signout clears/revokes that app's own session and tokens. Ending a provider session requires explicit provider-owned user UI identifying the intended account and scope; it never automatically logs out all saved accounts or other devices. Its callback conveys only `completed` or `canceled`, with request state, without saved-account count or session-presence details.

App account switching starts a new authorization request and creates the chosen owner's client connection/grant after review. It does not retarget an existing handle-bound grant or consent. Reauthentication requires a fresh credential proof bound to the requested operation, chosen owner and session epoch; it preserves existing grant attenuation and notification disable generations. No successful reauthentication implicitly restores disabled methods or expands resource access.

## Notifications and deep links

Stored notification metadata must identify its actual recipient owner independently of the active browser account. With preview disabled, OS text stays generic; enabling previews may include the authenticated recipient's display label according to the user's privacy setting. Notification clicks open a fixed provider route with bounded message/owner identifiers. Those identifiers and advisory action locators are **routing hints, never authority**.

The foreground provider validates the vault before loading content. If the intended owner is inactive, ask to switch and execute the ordinary authenticated switch; if absent/revoked, ask to sign in as that owner. Do not fetch the message under whichever account is active, do not auto-submit a form, and do not mark it read until the selected owner's normal authorization succeeds. The service worker does not receive session tokens or a readable vault. Account labels shown by a notification cannot be trusted as a substitute for server owner checks.

## Third-party frames

Browsers may block provider cookies in app-origin frames even while the provider has first-party sessions. Storage access and partitioned cookies vary by browser and user policy; this design does not depend on either to recover the provider's complete account inventory. A frame unable to authenticate renders a neutral continuation action and opens a provider first-party popup or top-level redirect on explicit user interaction. No silent account probe, token relay to an app parent, wildcard postMessage or credential forwarding.

The popup/redirect uses a bounded expiring request continuation plus exact registered callback/state/PKCE, not session tokens in its URL. The app learns only the authorized result after approval. Popup blocked/closed cases offer a normal top-level link. An embeddable launcher cannot perform final consent: final approval occurs top-level, protecting against an allowed client framing the picker to clickjack another account. Provider framing policy may require a dedicated narrowly embeddable authorization document; the current ordinary console's anti-framing protections are not weakened globally. Actual browser cookie blocking, opaque sandbox origin, popup behavior and opener/message source checks require browser tests before release.

## Phase-two coordinator proposal

A private per-device coordinator holds `{vaultId,revision,members,activeOwner,cleanupState}`. Durable member tokens are encrypted under a dedicated custody key; no plaintext token logs or public projections. Access requires a cryptographically random vault capability carried only inside the authenticated-encrypted cookie. Worker storage is a dedicated Durable Object keyed by authenticated random vault ID; Node uses a serialized SQLite record. Verify the cookie before any coordinator or owner lookup.

The cookie is a bounded authenticated snapshot plus coordinator reference/capability and revision. The coordinator serializes additions, removals and active-pointer changes. Membership operations always use the authoritative coordinator, not the submitted snapshot as replacement data. Foreground inventory reconciles a stale snapshot and returns a fresh cookie. Ordinary owner requests do not call the coordinator: live owner-session revocation prevents stale snapshots from resurrecting removed authority. A same-owner new session replacing an old token must revoke the replaced token before publishing success. Failed replacement/revocation remains pending and honestly reported.

Compare distinct per-account cookies: independently named cookies avoid replacing the entire membership snapshot, but cannot atomically enforce five members, cleanup-all, inventory or eviction; they introduce multiple cookie authorities and more header bytes. They still require authenticated bounded enumeration before owner routing. A coordinator provides one bounded custody and retry authority and is preferred, provisionally. This does not eliminate response-order races: a stale Set-Cookie may overwrite the newest snapshot, but it cannot overwrite the coordinator, and permitted snapshot-scoped foreground inventory repairs it. No guarantee of instantaneous cross-tab display convergence is claimed.

Proposed UI API: `GET /api/auth/accounts` returns `{accounts:[{account,expiresAt,sessionContext}],activeOwner,revision,cleanupPending}` and refreshed cookie, never tokens/capability. Initial `/api/session` adds opaque `sessionContext`; subsequent private calls send `X-Bindle-Account` and `X-Bindle-Session-Context` plus existing CSRF for mutations. Explicit switch POST carries `{owner,expectedRevision}` and active tab context/CSRF; target validation returns selected account/context/CSRF. Account addition is finalized by the existing successful login/activation session installation path through the coordinator. Logout-current/all receives exact context and coordinator revision; conflict triggers inventory/review, not silent retry.

`sessionContext` must be derived from server session identity, not a client timestamp or owner UUID. The precise cryptographic encoding and routing checks require implementation review. Existing handle-bound OAuth requests cannot be moved to another owner/shard: the first slice offers cancel/restart. A private one-use replacement handshake, if later implemented, must create a genuinely new owner-bound request with app state/PKCE preserved safely and no preconsent disclosure; that cross-actor transition is not approved by this draft.

## Required verification and open decisions

Tests must prove authentication rejection before actor routing; maximum cookie bytes; legacy migration and no malformed-vault downgrade; independent per-owner expiry/revocation; active-only hot-path actor count; CSRF and context-conflict switching; one/all logout partial failures; stale response and cross-tab mutation fences; handle-bound OAuth choice with no preconsent app disclosure; recipient notification routing; third-party blocked-cookie fallback without token relay. Include real Node and Worker adapters and multiple browser privacy modes.

Open decisions: exact AEAD/key provisioning format; explicit chooser challenge when the active session expires; session installation conflicts across tabs; maximum account limit after byte measurement; suspended-account restricted picker behavior; browser support matrix and dedicated embeddable surface. No runtime implementation, deployment or cross-browser conformance is claimed by this draft.

### Proposed response/error vocabulary

Switch success: `{account,csrfToken,expiresAt,sessionContext,vaultRevision}`. Logout-one success: `{loggedOut:true,accountsRemaining,cleanupPending:false,vaultRevision}`; logout-all: `{loggedOut:true,cleanupPending,vaultRevision}`. These are first-party provider projections, not app callback data. Remaining-account counts are never returned to app-origin callers. No remaining account is auto-selected.

Conflicts: `account_context_conflict` (409), `session_context_conflict` (409), `vault_conflict` (409). Unavailable target: `account_unavailable` (401). A sixth membership addition: `account_limit` (409), with explicit removal guidance. A successful credential check cannot silently evict another saved identity; installation must not leave an orphan active session on admission failure.

Inventory is a same-origin first-party operation authenticated by the vault capability; exact Origin/Fetch Metadata and no app CORS prevent an embedded app from acquiring account projections. If the active owner expired, propose a short-lived picker nonce in a private HttpOnly cookie, bound to the authenticated vault/revision, followed by explicit Origin-checked switch. This is a distinct chooser authority, not an expired session's CSRF bypass. Exact nonce/CSRF delivery and privacy behavior remain a review gate before implementation.

### Capability scope review blocker

Independent review identified that a stable coordinator capability would turn a stolen old cookie into access to **future** accounts added to that browser. Do not implement a stable unqualified refresh bearer while describing snapshot-scoped authority.

Preferred correction, pending coordinator decision: rotate the coordinator capability on every member/session addition or replacement. Each retained prior capability has an immutable allowed set of owner **and session IDs**; reconciliation intersects that set with current live members and never returns added accounts or replacement sessions. Bound prior-capability retention/count; exhaustion requires fresh sign-in for inventory rather than expanding old authority. A stale snapshot may continue its already possessed live token until expiry/revocation, but cannot upgrade it through the coordinator. Rotation alone without this old-cap scope restriction is insufficient.

Cleanup has a separate narrowly scoped capability, limited to unresolved session revocations and its own bounded expiry. Its cookie lifetime may exceed revoked active-session lifetime; it cannot authenticate ordinary owner requests, add accounts, select new members or return session tokens. Final issuance/rotation/race semantics require independent review before runtime changes.


`activeOwner` is an initial discovery/default preference only. Tab-bound private requests compare their explicit owner/context to an authenticated snapshot member and its live server session, not to the global default. Two tabs may intentionally operate different saved owners. A switch updates the initiating tab's selected context and default preference; it does not revoke another tab's correctly selected member.

Retry-only cleanup hides local access but does not instantly revoke a copied old snapshot if the live owner revocation failed. Only successful authoritative owner revocation fences that token; unresolved cleanup must be reported as such. The five-member limit includes reserved additions and replacement transitions. Bound retained cleanup-only tokens separately and compensate/revoke any newly minted session if installation fails, or reserve coordinator capacity before creating it; no unbounded orphan session creation.

Historical capability scopes constrain **all** operations, not inventory alone: a caller-supplied newest revision cannot let an A-only capability switch, remove, replace or recover an existing B session. A fresh B credential proof can authorize installation of a fresh B session, but cannot return the old B token. A lost installation acknowledgement therefore requires fresh authentication for that newly added owner rather than broadening the old capability. Scope and revision checks precede any target actor work. This is an implementation gate, not yet a verified runtime guarantee.
