## Current implementation checkpoint

The user-selected SDK name is `userMessage`. The implemented owner-local RPC contract is `https://3sln.me/artefacts/contracts/app-messages/v1`, method `createOwn`; its private resource-valued preference uses `https://3sln.me/artefacts/preferences/app-messages/v1`, field `messages`. The built-in resource is `${subject}/app-messages`. Actual machine JSON/registry routes are part of the coordinated artifact work; a local route is not evidence of production publication.

Input is exactly `{transactionId, createdAt, subject, body, mimeType?, tags?}`. The operation UUID equals the RPC transaction; its immutable millisecond timestamp must be less than 24 hours old and at most 60 seconds ahead. Subject/body limits are 120/12000 Unicode code points and 16 KiB total encoded input. MIME is `text/plain` by default or `text/html`. Up to 31 distinct caller tags are allowed; the provider adds required `app-message`, which callers cannot supply or remove during admission. The marker is enforced again after intake rules: 31 other final tags plus the marker fit; 32 tags without the marker refuse admission before blob upload instead of truncating. A later explicit owner tag edit remains ordinary organization and may remove the marker without changing signed provenance. There is **no action-descriptor field**. Apps send ordinary content; forms/actions must use the shared validated renderer/parsing pipeline. Current backend admission does not establish safe interactive HTML forms by itself.

Backend source now enforces transport Origin through HTTP, authority facade, federation controller and resource service, with no absent/null/provider-origin bypass for this method. It intersects fresh method consent with a connection notification generation, permits only its owner, and rechecks live local state at message commit and notification delivery. Settings toggles invalidate old generation snapshots; enabling alone cannot widen a token. The target owner actor serializes Messages disable/disconnect with local admission. Granular federation grant revocation lives in a separate authority: a request already dispatched after its last successful grant check can still finish local admission, while subsequent calls fail. This is an explicit in-flight cutoff, not an atomic cross-actor revocation promise. Existing owner receipt, logical work, physical object writes and storage accounting remain active; a finite connection lane adds 10 admitted attempts/minute and 100/day. Failed downstream work may consume attempts. Receipt metadata is bounded to 256 records/account for 48 hours; the generic RPC journal remains bounded to 256 and 24 hours. Unchanged operations expire before either removed journal could reexecute them. Unknown effects remain indeterminate.

An injected provider-global P-256 signing JWK (`APP_NOTIFICATION_SIGNING_JWK`) signs purpose-separated local admission evidence, checked against the public-only `APP_NOTIFICATION_PUBLIC_JWKS` (at most 8 keys) and cached per configuration instance. No identity private key or global actor is used. Missing/mismatched configuration refuses admission. The issuer's public-key descriptor is `/.well-known/bindle/app-notification-keys.json`; embedded signature metadata is not an independent trust anchor. Historical public keys must remain available. Operator provisioning and production verification are separate gates.

Records use the normal message blob, index, search and notification outbox, with signed registered app provenance and required delivery tags available to owner rules. Current backend tests cover durable SQLite restart, exact replay, quota refusal, unknown write outcomes, key validation, strict Origin and disable races. Frontend SDK, shared form renderer and browser/Worker evidence are coordinated separately; this checkpoint does not claim that rich forms or production delivery are complete.

## Recommendation and supersession

A frontend-only app can ask Bindle to add a notification/message to its **own consenting connection owner's local message stream**, using the existing SDK and an explicitly granted resource method. It needs no contact token/link, app-owned Bindle account or global app signing key. The provider derives the app's registered identity and exact origin from the authenticated connection, validates its permission and content, and records the notification's provenance. Calling an SDK method does not itself establish permission.

This replaces the browser-only-app default in [message sender identities](message-sender-identities.md). The earlier app-identity signing/delegation proposal remains relevant only for an app that deliberately participates as an ordinary federated identity; it is not a prerequisite or hidden mechanism for these local notifications. Ordinary person/application identity messages remain author-signed and capability-admitted. Local app notifications are signed by the provider as admission/provenance records, **not** falsely signed or displayed as a message from an app's ordinary identity. The unified message stream can contain both while retaining their distinct evidence and authority.

The sender label is the registered app name plus exact approved app origin, with an optional validated cached icon. “From this app connection” means the provider accepted a request under that owner's approved connection. It does not prove which JavaScript generated the content, that an app backend endorsed it, or that the app's code has not been modified. The OS notification origin remains the Bindle host/PWA.

## Existing interfaces and proposed addition

The [federation service](../../packages/federation/service.mjs) already registers a client with an exact origin and an allowlist of same-origin redirect URIs, checks an exact redirect URI, uses S256 PKCE and one-use authorization codes, issues issuer/audience/client/owner-bound access authority, and supports live grants and connection checks through its injected adapter. Its token records are not simply caller-asserted JWT claims. The [HTTP adapter](../../packages/federation/http.mjs) checks registered browser Origin and, on supported RPC paths, its correspondence to the token's client. Generic nonbrowser bearer RPC can omit Origin today, and provider-origin calls bypass the token/client origin match; do not claim this is already a browser-exclusive transport or use that bypass for notification admission.

The [SDK](../../packages/sdk/src/identity.mjs) implements PKCE login, callback/state/issuer validation and credential-omitting requests. Its current constructor accepts a client ID and redirect URI; it does not yet provide the proposed notification method or a complete execution-origin/iframe permission protocol. [Resource contributions](../spec/resource-contributions.md) distinguish an owner's connection resource from an app's global identity and contain unimplemented contribution/callback proposals. Reuse the actual resource/grant/RPC machinery, not a claim that every drafted adapter already exists.

Propose `createOwn` on a built-in URI-identified owner notification resource contract, with `client.userMessage` as the SDK convenience method over that same RPC call. There is no separate notification submission endpoint. The implemented names are fixed in the checkpoint above; interoperability still requires the published immutable machine contract. Do not advertise a nonresolving contract URI or add a stub to the registry. This is one resource method, not a second login system, general webhook route or new app-state database.

The SDK call is `client.userMessage(reference, {transactionId, createdAt, subject, body, mimeType?, tags?})`, where `reference` is the approved private resource reference. The SDK resolves only the granted connection-bound resource; it does not accept a contact URL, recipient, owner UUID, sender, `appOrigin`, client ID override, signing key, notification channel or callback endpoint in that call. Normal authenticated resource selection can be part of SDK setup, but it cannot substitute an unrelated owner's resource. A convenience function must enforce exactly the same server-side authorization as raw RPC.

## Authority and admission

The owner separately enables **Messages from this app** in provider-owned consent UI. Login/connection, profile/file permissions, resource contribution and OS notification permission never imply it. Consent shows the registered app's actual ASCII origin, bounded name/icon, self-notification scope and limits. Denial leaves other connection methods usable. Turning Messages on later does not add `createOwn` to an already issued token lacking that scope: require fresh explicit method consent and appropriately scoped access authority; a settings toggle cannot widen an old token. Users may allow storage silently, choose Views/quiet rules and disable device notifications independently. A script cannot provide or check its own consent box on the provider's behalf.

Authority is the intersection of:

1. Live authenticated owner account and exact registered client, issuer and RPC audience.
2. Live owner/client connection incarnation and approved resource assignment.
3. The exact notification contract/method grant and current owner Messages setting.
4. Method-specific browser-origin policy where this browser profile is used.
5. Owner/connection count, byte, work, storage and notification budgets and content/action policy.

Derive owner, client, connection incarnation, registered origin, app metadata revision and grant revision from server-side authority. Reject conflicting or extra request fields instead of using them as display hints. The resource target must belong to this owner/connection even if an app possesses a grant to some other resource. The method cannot fan out, deliver to another account, forge another app's origin or emit an ordinary identity-authored conversation event. It creates no contact grant internally and exposes no contact token through preferences.

A resource-valued preference may hold the private reference to this approved notification resource. Each consumer still needs its own exact method grant; the field is not a public shared mailbox or raw bearer distribution mechanism. No new broadly subscribed preference should leak permission to unrelated apps. Store existing OAuth access credentials only under the SDK's reviewed session handling, not in markup, URLs, push data or arbitrary shared fragments.

Use the existing RPC transaction journal plus a stable application transaction ID and canonical content digest. Deduplication scope includes owner, client and connection incarnation. An admitted identical retry returns its authorized existing result; changed content under the same ID conflicts, and retry does not create another message or notification job. Recheck current authority before replay. Serialize admission/block/incarnation checks and local durable record/outbox creation where the adapter can actually transact; object storage remains a separate bounded operation with explicit recovery. A lost response may be queried/retried only with the same transaction; the recorded outcome can remain indeterminate if the adapter cannot establish completion. Publish a finite deduplication/reconciliation horizon covering permitted authorization and retries. After that horizon, report outcome unavailable rather than silently treating the operation as new. Never automatically resend under a fresh ID or promise guaranteed reconciliation.

Reuse existing owner receipt/work/storage safeguards and add a finite connection notification lane under the owner aggregate; the UI makes frequency/storage costs clear. Provisional spike ceilings: 16 KiB encoded content, 10 admitted attempts/minute and 100/day per connection, all intersected with lower owner limits. Deleting a notification does not refund receipt/work allowance. New connections/clients do not bypass the owner aggregate, and rejected requests must not generate an alert each. Precise plan/config defaults, accounting boundaries and caps on connection cardinality require implementation review. Background jobs and interactive calls share their owner's ceilings.

## What protects the actual app origin

The provider pins a registered client to an exact HTTPS origin and exact allowed callback URIs through its existing registration policy. Notification labels always come from that record. A claimed origin in a body, iframe query, parent message, SDK option or manifest fetched from an arbitrary URL cannot change it. Different apps sharing one origin/path tenancy are not isolated by Origin; treat same-origin scripts as one browser security principal or deploy separate app origins. Distinct client IDs and grants remain checked, but do not claim path-based browser secrecy. Domain/redirect changes require a reviewed registration revision and reconsent/new connection generation, not automatic migration of existing grants.

The SDK's browser profile derives its execution origin from its own realm and verifies it against the approved client origin/callback before starting authorization or notification dispatch. It must not infer identity from the URL that served the SDK module: JavaScript loaded from a CDN executes with its embedding document's authority. An imported SDK in `embedder.example` therefore represents that page, not `app.example`, and cannot obtain a different app's browser flow by setting `appOrigin`. SDK checks help honest clients; the server also checks the token/client binding and exact Origin before mutating anything.

Use method-specific rejection of absent, opaque `null` or mismatched Origin for this browser-only notification profile; preserve existing generic RPC clients rather than silently changing all methods. Require explicit bearer authorization, JSON/RPC schema and exact CORS response origin; no credentialed wildcard or simple native form fallback. Preflight approval alone does not authorize mutation. The HTTP check must run before side effects, not merely withhold CORS response headers after committing. Provider Origin is allowed only if it is the exact registered origin of the authenticated client; the generic issuer-origin exception does not apply. Trusted provider-owned execution must use an explicitly separate injected authority, not a blanket “provider Origin may act as any app” exception. [Fetch CORS protocol](https://fetch.spec.whatwg.org/#http-cors-protocol).

These controls stop a different website from using normal browser JavaScript to relabel itself or use a foreign app token through this endpoint. They are **not cryptographic proof of domain or publisher code**: curl/nonbrowser callers can forge Origin, a bearer holder can invoke an allowed method, and same-origin scripts/XSS can act with the origin's browser authority. PKCE protects an intercepted authorization code and binds its exchange to the verifier; it does not authenticate a public app's secret, make its bundle confidential or prove arbitrary content came from its publisher. [PKCE for public clients](https://www.rfc-editor.org/rfc/rfc7636).

A party lacking the valid approved token cannot gain another owner's authority merely by copying its client ID or Origin. A stolen valid token is different: origin checks alone cannot stop a nonbrowser replay. Short expiry, live revocation, least-privilege self-only scope and safe callback/token handling limit it. Optional DPoP could constrain tokens to a per-installation key, with server nonce/replay/method/URL checks; it would not establish app brand or code integrity, and same-origin malicious code may still invoke the key. Do not embed a shared global secret/private app key or present DPoP as a replacement for recipient consent. This optional profile needs independent protocol/library review; it is not implemented here. [DPoP token constraints and limits](https://datatracker.ietf.org/doc/html/rfc9449).

## Legitimate embedded applications

An actual cross-origin iframe navigated to the registered `app.example` origin executes with that origin, even when embedded by `portal.example`. It may use its own approved connection. Do not require the top-level parent origin to equal the app origin: that would unnecessarily forbid legitimate embedding. Conversely an SDK module executing directly in the parent's realm is the parent's app, not the embedded publisher. An opaque sandbox without a usable app origin cannot obtain this browser profile by claiming an origin string; fail closed and offer the ordinary supported login context.

Use the existing provider authorization flow and a real trusted provider consent surface. Where the embedded integration needs an auth popup or MessageChannel, bind the outstanding challenge/state to client, exact callback, owner choice, requesting window and generation. Check received `event.origin` against the actual approved app/provider origin and `event.source` against the exact known iframe/popup; send only to an exact `targetOrigin`, never `*` for credentials. A navigation, replaced iframe, account change or canceled request invalidates that generation. Parent-provided “appOrigin,” top/referrer URL, declared iframe src, matching window name and origin `null` are not evidence. Never install a promiscuous parent postMessage relay that turns arbitrary requests into authenticated notifications. [HTML cross-document messaging](https://html.spec.whatwg.org/multipage/web-messaging.html#web-messaging).

The iframe retains access/refresh credentials and notification authority in its own approved context. Do not post tokens, contact links, signing requests or a generic notification proxy to arbitrary parents. If the app intentionally exposes a parent API, that is an additional app decision: approve the exact parent origin, bound action schema and scope, require any needed user interaction, and never let the parent replace provider-recorded provenance or choose another owner. No requirement to trust every ancestor is implied by allowing embedding. Clickjacking protection and explicit consent UI remain necessary; third-party storage/cookie restrictions may require a user-opened top-level app/provider continuation rather than silent auth. Browser tests must establish behavior rather than promising all embedded flows work identically.

A parent cannot read a genuinely cross-origin iframe's internal token under normal browser isolation, but the app can deliberately leak it, and same-origin code can compromise itself. Host-side signing of an accepted request does not cure that. The trustworthy statement remains which approved connection the provider accepted, not that the provider remotely attested all browser code.

## Provider-signed local provenance

The provider creates an immutable local notification record containing its record ID, owner audience, registered client/origin, connection incarnation, metadata/grant revision, content digest, transaction ID, admission timestamp and local provenance version. The recorded origin is the registered origin that the provider checked against the request, not independently attested publisher execution. It signs the canonical record under a purpose-separated provider attestation key with a published/verifiable key descriptor when portability is offered. Do not use an OAuth session token as the signature or pretend the provider key is an app/user identity key. Exact key custody/rotation/schema is a review gate; no generic caller-controlled signing method is exposed.

This attests provider admission under a connection, not publisher authorship, real-world brand verification or the truth of “payment received.” Labels must distinguish these local app records from ordinary verified-handle messages. A static client can submit content allowed by its own connection; higher-trust service events require a separate authenticated backend/ordinary identity profile. An app notification forwarded elsewhere remains quoted provider provenance and needs a new independently authorized delivery; its original record cannot act as a global app message or reusable recipient permission.

Store it in the owner's existing logical message store with normal tags, Views, private read state, retention and encrypted archive/export conventions. Local history includes action outcomes without turning them into conversation replies. The provider receipt signature authenticates the record; cached images/HTML never supply new authority. Export includes historical provider verification context, but import must not reactivate a connection, signing API or grant. Provider relocation does not transfer ownership of the old app origin; unsigned metadata changes cannot rewrite old evidence.

## Rendering, actions and notifications

Apply the same isolated/sanitized content and typed action policy as [message actions](message-actions.md). A provider-attested connection can establish the local descriptor's provenance only within the approved method and action profile. Arbitrary form HTML cannot choose privileged endpoints, ask for silent identity signatures or borrow grants. For an independently hosted HTTPS action, verify its separately declared target association/permission; local app admission alone does not authorize arbitrary egress. Return-postback history, optional user identity disclosure and the cookie-free submission boundary remain separate from sending this local notification.

Notification extraction is deterministic, bounded and privacy-controlled; display server-validated app name **and exact app origin**. Do not replace the actual origin with caller-supplied display text or a familiar icon. Registered display metadata can be self-asserted branding; “connection verified” is not a platform/system badge. Icons must already be validated, bounded and cached locally, with a neutral fallback. Never pass a remote app-selected URL directly as OS icon/image/badge/action icon, because notification resource fetching can include credentials. [Notification resources](https://notifications.spec.whatwg.org/#fetching-resources).

Receipt does not guarantee a push/email/OS notification. Recheck Messages permission, connection generation, local block, channel consent, quiet settings and notification budgets immediately before dispatch. Disable cancels undispatched work; reconnect uses a new incarnation and does not revive old tokens. Retain accepted history by owner policy. The target owner authority must check its live setting/generation at the durable admission boundary, not rely only on an earlier HTTP or cached connection check; unsupported cross-actor atomicity must remain an implementation gate. A record accepted just before disable may remain stored, but cannot bypass current suppression to ring later. Notification click actions open the message and use the existing reviewed Submitting/result flow; presentation alone cannot dispatch.

A closed frontend cannot emit future notifications by itself. Existing approved automation/resource jobs or an explicitly authenticated workload may do so under a separately reviewed authority profile. Do not silently add a hosted app runner, transferable offline all-owner credential or background task subscription when granting the interactive SDK method.

## Required implementation evidence

1. Exact resource contract/SDK schema and consent UI: no recipient/origin spoof fields, no contact credential, self-only grant and bounded quotas; publish real JSON only after review.
2. OAuth/browser cases: mismatched token client, wrong issuer/audience, absent/null/forged Origin, intercepted code without verifier, stale connection, disabled Messages and replay/concurrent sends. Explicit nonbrowser forged-Origin-with-valid-token test demonstrates the stated limit rather than claiming it cannot happen.
3. Embedding cases in Chromium/Firefox/WebKit: app-origin iframe works with consent; SDK running in parent cannot relabel itself; wrong `event.source`, wildcard target, navigation replacement, leaked challenge and stale popup fail. Test storage restrictions and no token escape to parent.
4. Durable Worker/Node admission/outbox, quotas, unknown outcomes, disable/reconnect races and history export verification. No separate hot global app actor or per-message external domain verification.
5. Notification presentation and action isolation: actual registered origin visible, remote icon requests absent, private preview settings respected, no actions without independent authority. A same-origin compromised script is documented as within app-origin authority, not magically detected.

Open decisions: exact contract URI and SDK method naming, token/origin browser-profile policy, finite plan limits, app registration/domain-change verification, provider attestation key format and portability, optional DPoP, embedded auth continuation UX and any noninteractive workload profile. All remain unsigned. This design requires no app identity/contact token for frontend-only notifications and makes no claim that Origin is a cryptographic publisher signature.
