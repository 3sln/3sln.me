# Federated conversation resources, owner copies and contact links

Revised on 2026-10-13 following the user's clarification that participants live on different providers and prefer a shared conversation secret plus independently signed identities and recipient-local approvals. This recommendation supersedes both the earlier central ordering actor and the subsequent single policy-signer proposal. It is a design, not implemented behavior, publication or release approval. Human reviewer ___ / date ___ / outcome ___. Reconciliation belongs in [DEVLOG](../../DEVLOG.md); existing [security gates](../spec/security.md) remain in force. Examples use reserved `.example` origins.

## Recommendation and consistency choice

Each participant's provider hosts that participant's **own conversation resource**, containing an independently writable and readable local copy. A sender commits an immutable signed event and durable fanout obligations locally, then delivers directly to the admitted participants' resources. No participant must send ordinary messages through the creator's provider, a shared conversation host or a global sequencer. A Durable Object, SQLite controller or other actor is a provider's local implementation choice, not a conversation-wide protocol authority.

Use causal references and authenticated per-author streams. Preserve concurrent events and expose delivery status. A deterministic display rule can make replicas with the same verified event set render the same reconstructed order, but there is no canonical global acceptance sequence or universally observed timestamp order. A participant can keep composing/sending to its eligible accepted peers while another provider is unavailable; unavailable recipients remain pending or fail honestly.

Recommend **A: a shared conversation secret, independently identity-signed interactions, and each owner's own accepted-peer set**. The secret alone identifies neither an author nor a permitted recipient. Everyone may propose additions or other changes, but each owner decides which peers and supported changes to accept. The genesis signer bootstraps the conversation; it is not a permanent administrator. Ordinary membership changes do not depend on the creator or a central policy signer. This is a directed consent graph with possibly divergent views, not one globally synchronized roster.

Make an email-type first contact the first document of a conversation request. Give each party its own scoped app/resource access and separately admitted delivery permissions; the conversation possession secret itself is shared. Keep signed HTTPS contact endpoints canonical with unchanged HTML GET, token GET and explicit POST meanings. `web+bindle:` is an optional browser enhancement; native `bindle:` is a separate integration. GET, handler launch, login and signup never send or subscribe automatically.

Publish these semantics through the URI-identified conversation contract proposed below. Reuse existing discovery, resource RPC, grants, signatures and bounded journals. Do not add a consensus framework, universal app-state service or mandatory relay provider.

## Alternatives and the actual tradeoff

| Model | What it provides | Dependency/limitation | Recommendation |
| --- | --- | --- | --- |
| One conversation ordering authority, with federated owner copies | A single committed sequence and serialized membership cutover. Cross-provider participants are possible. | Every ordinary write depends on one authority's availability and operator. Local copies do not remove this central write dependency. | Valid optional future profile if users explicitly want that consistency, not the default proposed here. |
| Independent participant resources with signed events | Each provider accepts its owner's writes and retains received copies; direct delivery survives an unrelated host outage. | Concurrent events, directed local approvals, divergent membership views and partial delivery are normal. No universal membership/removal state. | Federation-first default. |
| Global consensus/leader election between providers | Could strengthen ordering under particular trust/quorum assumptions. | Substantial protocol, liveness, deployment and operator burden; still cannot offer every consistency/availability property through partitions. | Out of scope. |
| One provider-local actor per user | Amortizes local account quota, indexing and admission coordination. | A very busy local conversation can delay the user's other work. | Initial local implementation with short commits and bounded work. |
| Provider-local actor per owner/conversation | Isolates hot local replicas; still no cross-provider shared actor. | More local journals/RPC and independent restore/checkpoint work. | Extract hot replicas when measured contention warrants it. |

### A shared secret versus individually issued conversation tokens

| Authorization model | What it buys | What it does not solve | Choice |
| --- | --- | --- | --- |
| **A. Shared secret + independent identity signatures + each receiver's accepted-peer set** | Simple private conversation bootstrap; every participant can propose peers, and every owner enforces their own relationships. Removing a key locally does not require replacing everyone's secret. | A leaked secret is transferable; whitelists and recipient admissions still do the real identity/permission work. No global roster or instant global revocation. | Recommended, matching the user's preference. All three checks are required. |
| B. Initiator-issued per-party tokens | Simple issuer-managed roles, accounting and token-specific revocation; signed cached tokens can verify offline. | Ordinary sends need not contact the issuer, but issuance/refresh and authoritative revocation/governance remain issuer dependencies unless delegated. Tokens alone still do not express each receiver's changing consent. | Useful optional managed-group profile, not the default. |
| C. Identity signatures + bilateral recipient admissions without a shared secret | Removes shared-secret distribution/rotation and preserves local consent. | Gives up the user's shared conversation possession barrier; every public discovery/ingress surface must still prevent probing and abuse. | Technically viable narrower alternative; not necessary to override A. |
| D. Recipient-issued per-peer conversation keys/tokens | Independent receiver-side revocation with precise ingress audiences; can supplement A rather than replace it. | Up to O(n²) pairwise scoped relationships across a group, though bounded groups can support this. Additional key/token lifecycle and no automatic history permission. | Valid adapter/profile choice; avoid general inbox grants, not all pairwise credentials. |

A is secure only if secret possession never bypasses independent author proof, recipient approval, history entitlement or quotas. It is not the current v1 bearer-only path with a nicer label. Shared-secret MACs cannot authenticate distinct people or unequal roles; signatures use independently bound keys. The extra secret can limit unsolicited protocol access, but it cannot stop an admitted participant disclosing it or content it already received. Providers remain trusted plaintext/key custodians under the current deployment model; this is not E2EE.

A conversation identifier may be an opaque canonical HTTPS URI minted by its initiator, but it is an **identifier**, not a mandatory runtime rendezvous. Store its verified descriptor and participant resource bindings locally. Do not dereference its creator host on every send/read or infer that owning its origin grants control of all replicas. Each owner resource has its own URI, issuer, access policy and storage lifecycle. Every replica retains approved peer resource references from independently verified identity/admission evidence; network targets remain pinned and SSRF-checked.

## Grants, identity and admission

Keep these authority boundaries separate:

1. A contact capability permits a bounded first approach to one recipient.
2. An **app resource-access token** permits selected operations on that owner's local conversation resource, bound to its existing OAuth/RPC issuer, resource audience, account/client, approved methods, assignment revision and expiry. It is neither an author identity proof nor a remote inbox credential.
3. A **conversation member proof** combines the shared possession secret with an independently bound participant signature. Effective rights come from the receiving owner's accepted-peer view and supported operation policy, bound to conversation/incarnation and local consent generation. The signature identifies the author; possession of the shared secret cannot create another identity or approval. Any derived member grant remains local to its issuer and scope.
4. A **recipient conversation-ingress grant** is issued/enforced by the receiving provider for its exact owner conversation resource, conversation/admission incarnation, sending participant key and bounded delivery operations. It is separate from owner RPC access and contact-introduction authority. It never grants general inbox access or arbitrary recipient history.

Normal outgoing messages require owner authentication or an appropriately scoped app grant, then an independently verifiable author signature. Peer deliveries require the shared secret under a locally accepted epoch, original independent signature, and the recipient's current accepted-author/delivery admission. A recipient may issue short-lived receiver-audience delivery tokens derived from its live conversation admission and bound to the sending participant's key; token rotation does not create per-token database rows or widen rights. A signature plus the receiver's live admission is the semantic authorization boundary; a protocol profile must state its exact token/proof encoding. The common secret is an additional gate, never sufficient authority at any provider. O(n) member policy/admission state per replica and O(n) direct deliveries per post are explicit costs; avoid an O(n²) set of general-purpose inbox grants.

Distinct bearer credentials alone do not establish author identity or prevent forwarding. The content signature binds conversation/incarnation, operation, immutable payload/attachments, author stream and predecessor, bounded causal parents, the sender's consent-view reference, exact intended audience and operation ID. A separate signed delivery context binds receiver audience, recipient admission incarnation and locally accepted secret epoch; transport credential renewal must not rewrite the immutable content event. Canonical encoding and algorithm versions are published. Live grant/admission checks precede mutation and replay-result disclosure. Token audience is the receiving resource, never “any Bindle inbox.” Retained private material is encrypted; credentials do not enter history/search/notifications/URLs.

First contact consumes only the existing contact grant's permitted MIME/document quota. The receiver stores the first document and pending descriptor atomically with deduplication and accounting. Reply/Accept explicitly establishes its owner-selected collection and limits; a preconfigured narrow admission policy may do so automatically. Receiving the protected shared secret alone creates no effective contribution right at another owner; that owner's approval/proof/admission checks still apply. The creator's own resource exists independently, but it gains no delivery right to a pending recipient beyond the initial contact grant. An approach to a new peer requires applicable contact authority and that peer's signed acceptance; another participant's proposal cannot substitute for either.

The first-contact envelope includes a bounded signed **return-control allowance** from the sender so the approached recipient can return its signed Accept/Decline before ordinary mutual delivery admissions exist. Bind it to conversation/proposal digest, nonce, sender's exact return resource, intended recipient UUID/key, expiry and one response purpose. It authorizes only the small validated consent response, no message body, history read, profile lookup or general inbox storage. Keep its pending row/bytes and idempotent response receipt bounded; a lost response retries the same identifier, not a new acceptance. This resolves the bootstrap dependency without opening normal `deliver` to every unknown secret holder. First ordinary replies wait for the required local and peer admission evidence, and any new-peer introduction follows the same narrow return-control pattern.

A text-only old grant may gain receiver-local thread metadata without being treated as permission for a group invitation MIME or future messages. Full bootstrap is a negotiated bounded profile. Anonymous legacy POST remains a valid one-way document/thread with an unverified/unclaimed sender; it cannot supply an independently owned sender-provider copy. A v2 two-owner request without sender identity/admission fails that requested mode explicitly. Interactive users choose their current account, sign in, finish full signup or select their external provider; the final send is always deliberate.

Forwarding content creates another conversation/copy with truthful provenance. It does not enroll the recipient in the original. Sharing one's normal token must not impersonate the original author. A later delegated contribution profile requires a distinct narrowed key/grant, labeled delegation, and no membership administration or history powers. Proposing a peer never grants that person contact authority or makes existing members accept them.

## Signed event set, delivery and reconciliation

### Public identity-key discovery

The provider/site discovery document and the user's identity document have different subjects. Keep provider discovery at `https://host.example/.well-known/bindle/manifest.json`; it describes protocol endpoints, versions and provider capabilities. An app manifest describes an application/client. Neither is a user's identity/keychain. URL userinfo such as `https://alice@host.example/...` does not select Alice's identity and must not be used for account routing.

The user-selected minimal lookup design is an advertised **`directory_url`** in the host's Bindle manifest. A compatible manifest must provide that field; a consumer must use the advertised endpoint rather than inventing a route. Require a clean same-origin HTTPS URL with no userinfo, query or fragment. Resolve one public name by adding exactly one `handle` query parameter containing the **full handle**, such as `n.42@host.example` or `alice@host.example`:

```js
const lookup = new URL(manifest.directory_url);
lookup.searchParams.set('handle', fullHandle);
```

`URLSearchParams` performs the required URI encoding; callers do not pre-encode and then encode again. The endpoint accepts bounded GET requests, decodes once, rejects duplicate/unknown query parameters and malformed or mismatched-host handles, and normalizes only the existing public namespace's documented spelling rules. Numbered and retained paid aliases resolve to the same stable UUID. It is a single-name lookup, not directory listing, prefix search, an arbitrary-email association lookup or an open resolver for other hosts. A linked private Gmail address is not a provider-owned public handle and must not resolve here. The host-level manifest remains the same regardless of which handle is queried.

Return a bounded minimal result: issuer, canonical full handle, stable UUID/identity URI and an exact identity-document URL; optionally the same purpose-bound public signing-key descriptor when the schema defines it. Recommend a minimal **`identity.json`** representation at a stable UUID-based path such as `https://host.example/entities/UUID/identity.json`. The name describes the subject better than `user.json`, which can suggest a mutable profile dump. Both directory and document URLs use the same approved origin by default and the existing bounded fetch/SSRF/DNS/redirect protections. Unknown/unavailable public handles return 404; rate limits return 429 with bounded Retry-After. Do not create keys/accounts or restore private histories while serving lookup.

Individual public handle lookup necessarily reveals whether a public name resolves; this bounded existence disclosure is the user's requested tradeoff. Apply abuse limits without claiming to hide that fact. Do not expose private identifiers or association metadata beyond the public identity result. Short bounded positive/negative cache lifetimes and ETags must account for current routing/key revisions, inactive/deleted identities and revocation; an old cached result never revives authorization. Aliases resolve through the existing permanent name-assignment model to the stable UUID first. A signed historical name certificate is not current authorization.

The identity document contains **only required public identity, key and protocol metadata**: version/type, exact issuer origin, stable UUID subject and canonical identity URI, document revision, and public key descriptors `{kid, purpose, algorithm, publicJwk, status}` with applicable validity/continuity metadata. Prefer embedded bounded public JWKs initially; a future `jwks` reference must be explicit, same-origin or separately approved, bounded and signature/trust-pinned. Signing and encryption purposes are distinct. Neither the directory result nor `identity.json` includes display name, real/legal name, avatar, bio, email, contact capability, accepted-peer list, private collection or device inventory. The directory's canonical public handle is a routing identity, not a real-name/profile field. Public profile publication, if later requested, requires a separate explicit opt-in resource; it must not widen this minimal identity document.

Project reality: `GET /api/conversations/identity/<UUID>` already returns `origin`, `owner` and a public P-256 JWK through the conversation adapter after an active-account check. It is not yet a general identity-document contract, has no distinct identity-publication opt-in there, and its current call chain can lazily create a missing signing key. The proposed `identity.json` GET must instead read deliberately established public records without generating keys, restoring whole private histories or creating accounts. Unknown/inactive/unpublished identities return bounded appropriate errors rather than materializing anything. Publication policy and historical verification after deletion need explicit review.

Derive this view from the **existing assigned identity keychain**: AccountObject's original ECDSA P-256 signing key and key ID, plus the separate ECDH P-256 encryption key where deliberately published. See [UUID/keychain recovery](../spec/recovery-identity.md) and [identity names](../spec/identity-names.md). Do not generate a second conversation keychain merely for discovery. Publishing an encryption public key does not claim that messages use it or are E2EE. The provider OAuth/JWT signing JWKS is a different issuer key set; WebAuthn/passkey authenticator keys are login credentials and are not automatically general-purpose public identity signing keys. Never serialize private JWK fields, encrypted recovery proofs/files, reset secrets, signing scalars or passkey credential records.

On first contact, obtain the host manifest and its advertised `directory_url`, resolve the full public handle, validate the returned identity URI/UUID/issuer, fetch the bounded public identity document, verify the claimed event/genesis signing key against that binding, and pin the accepted key ID/fingerprint and identity revision. An already-known verified UUID identity can use its pinned document reference directly. A key embedded in a message is not a trust anchor. HTTPS plus the provider's deliberately published binding establishes provider-attested first-use identity; it does not independently prove a real-world person or protect against a compromised provider on first contact. Existing signed contact key/grant checks remain authoritative for contact scope; identity lookup cannot mint or revive that scope.

Use bounded cache lifetime/ETag and retain already-pinned historical verification keys for received event history. Refresh on advertised newer identity revision or unknown key ID, subject to network limits. A changed advertised key does not silently replace a pinned key: require authenticated old-to-new continuity or an explicitly trusted existing recovery/provider-identity rule, and preserve revocation/generation evidence against rollback. Revoked keys cannot authorize new local acquisitions once revocation is known; historical signature verification does not reauthorize an old delivery. Offline cached verification cannot guarantee instantaneous remote key-revocation knowledge. The protocol must disclose that limit and fail closed on contradictory continuity, rather than treating a cache miss or freshly populated key field as identity approval.

### Optional contact-granted presentation

Reuse the existing contact-profile capability path, not a new public profile resolver. `packages/beaming/contacts.mjs` already stores an optional profile with `displayName`, `bio`, `avatar` and the global `discloseToContacts` switch, defaulting to false. Each exact contact grant has a `profileFields` allowlist, defaulting to empty; the older `discloseProfile` option maps to those selected fields. `selectedProfile` requires **both** the global switch and that grant's field allowlist. A different link to the same person cannot enlarge this link's disclosure, and profile sharing is independent of `beamEnabled`.

The signed contact endpoint already supports `GET` with `Accept: application/vnd.bindle.contact-profile+json`. `publicProfile` verifies the exact endpoint through `inspect` (signature, live parent/key and expiry), rejects quarantine, and returns the selected profile or `profile: null`; it does not import a contact, grant beaming, admit a conversation or mint an inbox token. Holding that link suffices for its selected presentation fields, so consent must explain **any holder of this link** can read them. Preserve content-negotiation specificity/exclusions, no-store/no-referrer and bounded responses. See [contact profile specification](../spec/beaming.md) and [reviewed beaming architecture](beaming.md).

The existing URI-identified [profile resource contract](../spec/contracts.md), `https://3sln.me/artefacts/contracts/profile/v1`, separately supports explicitly assigned app access through normal resource/method consent. Reuse that contract for app-facing profile needs, but do not treat a contact capability as a general `profile.read` grant or silently bypass its exact live per-link field intersection. The contact-profile representation and assigned profile resource are related presentation mechanisms with distinct authorization. The current contact-profile `identityURI` is derived from the contact's handle route; consumers must resolve/bind the stable UUID through the specified directory/identity flow rather than treating that display route or a profile field as a cryptographic identity proof.

Names, bios and avatars are self-asserted human presentation, never signing-key authentication, verified legal identity, admission or history permission. Render names/bios as bounded text alongside the public handle/provider identity. If sharing is off, a field is omitted, or its contact grant expires/revokes, show the public handle and neutral placeholder; do not infer hidden field existence or fall back to a less-restricted profile grant. Revalidate before new disclosure and stop reusing stale fetched profile as if it were currently shared. Revocation cannot retract information a holder already saved, and a missing profile must not silently change otherwise independent conversation admission or historical identity validation.

The current browser deliberately presents the avatar URL as an explicit external link rather than loading it automatically. Retain that behavior until safe media presentation is implemented. HTTPS URL syntax alone does not prevent tracking or SSRF. If an inline preview is added, use an owner-controlled uploaded/explicitly imported bounded raster asset or a reviewed grant-enforcing media proxy: enforce approved origins/DNS/redirect rules, byte/pixel/decode limits, safe types and inert rendering, and avoid viewer-triggered callbacks to the arbitrary original avatar host. A cached owned copy must be created with deliberate owner disclosure and served under the same live contact-field authority. Never forward the contact token, cookies or viewer referrer to an image origin, and never execute SVG/HTML or arbitrary embedded resources. An unavailable/declined avatar remains a placeholder, not a reason to broaden access.

### Immutable events and durable fanout

For the initial implementation, each participant provider serializes its **own** author stream locally. Multiple browser devices submit through that local resource. Its event contains a monotonic author counter and previous-event digest; independently offline device signing with multiple substreams is a separately advertised future profile. This avoids pretending that two unsynchronized devices can safely allocate one counter.

An event ID is a digest of the canonical immutable signed payload, excluding randomized signature bytes; author operation IDs provide retry identity. Each event names bounded causal parent IDs and the sender's signed local consent-view reference; receivers check their own consent rather than treating that view as global truth. Signature verification establishes origin/integrity, not truth, fanout completion or freedom from equivocation. If an author signs two incompatible successors at the same stream position, retain conflict evidence and quarantine the affected branch; never silently select the nicer message. A malicious provider can withhold events, and peers can detect only conflicts they observe.

A local append transaction durably commits the signed event, immutable blob references, quota reservation consumption, operation fingerprint and an outbox obligation for every eligible peer in the **sender's immutable accepted-outgoing snapshot**, including its own copy. Eligibility is derived from the sender's local approvals, known recipient admission/visibility evidence and blocks; it is not a freely supplied send-time `to` list. Show approved peers still awaiting reciprocal admission separately as **not sent / awaiting approval**, rather than hiding them behind a delivered result for the eligible subset. If none is eligible, preserve a local draft/pending first-contact workflow instead of implying another user received a conversation message. Return `accepted-local` only for the actual committed obligations. It is not global agreement. A receiver checks the original actor, exact addressed audience, target visibility and its own current approval/admission; the sender's view cannot expand those rights, and the receiver cannot cryptographically prove that a dishonest sender actually enqueued or contacted every peer.

Each receiver atomically stores its owner copy, byte/message accounting, deduplication receipt and index/notification outboxes. Its provider-signed delivery ACK binds conversation incarnation, event digest, receiving owner resource, admission incarnation and accepted content/attachment scope. A relay or sender cannot ACK for another owner. A lost ACK is retried using the same ID. `delivered` requires ACKs from every original obligation; later roster changes cannot shrink the denominator. Separate pending, permanently rejected, locally blocked/cancelled, retry-exhausted and indeterminate outcomes. Read receipts are different.

Direct fanout is O(n) per event, not mandatory all-to-all relay gossip. Bounded `changes`/`history` reconciliation can fetch missing authorized IDs/pages from the author or another entitled holder, preserving original signatures. A holder may not relay a document to someone lacking its history entitlement, and relay identity never replaces the original author approval check. A sender's complete disappearance can make events it alone retained unrecoverable; recipient copies retain the events they actually acknowledged. Do not promise global availability or complete recovery from a single surviving partial replica.

Parents arriving late create bounded pending dependency records. Validate proof/size/budget before allocating them, cap outstanding missing IDs, and fetch only from approved participant resources. Unknown parents or consent/admission gaps are unresolved, not permission to follow arbitrary URLs. Use a declared retry/historical replay horizon and per-author compact frontier plus retained exceptions/tombstones, rather than deleting every dedup row and allowing old events to resurrect. Same operation ID with changed payload conflicts; a retry beyond supported retention asks for reconciliation instead of creating a new event.

### Order and concurrent mutations

Causal order means a reply/edit follows its referenced target and each author follows its own signed predecessor. Concurrent events are incomparable by the protocol. A deterministic topological sort with a fixed tie-break on validated event identifiers can provide the same reconstructed order for the same event set. Claimed timestamps are presentation only; clock skew never controls authorization or silently overwrites a message. The live UI anchors by message ID and preserves already displayed positions, grouping late arrivals as additional/earlier context rather than repeatedly reshuffling the user's view. Bounded missing-parent placeholders distinguish unavailable context from a new top-level post. A complete rebuilt history may use the deterministic rule, while incremental live views need not have identical arrival order across providers. Local cursors remain stable pagination tokens, not global sequence proofs. Drafts stay locally pending until actual local durable acceptance and never acquire a fabricated peer order.

| Operation | Proposed conflict/visibility rule |
| --- | --- |
| Message/reply | Immutable signed document; conversation-local parent IDs. Ordinary posts address the complete eligible snapshot of that sender's accepted peers, never peers the sender has not accepted or an arbitrary send-time subset. |
| Edit | Author-signed replacement references message ID and expected revision/event digest. The author's local stream serializes edits; original and every committed revision remain inspectable. A conflicting authored branch is surfaced/quarantined, not overwritten by timestamp. |
| Sender delete | Author-signed tombstone references the message and relevant revision. Show “Deleted message”; an already entitled owner can peek at bytes/revisions they retained. No implicit undelete; later edit cannot hide the deletion without a separately specified explicit restoration feature. |
| Reaction | Authenticated actor-specific add/remove, keyed by `(target message, actor, normalized emoji)` with expected actor reaction revision and operation ID. Different actors do not conflict; one actor's local stream orders its changes. Preserve add/remove history. |
| Local erase | Owner-only deletion of that owner's retained content/history according to scope/retention. Keep minimal anti-resurrection state. It never erases a peer's copy or turns a sender tombstone into a global purge. |
| Delayed old event | Verify original target visibility, actor proof and current receiver-local approval/admission. A valid signature does not override a newer local block/removal. Honest delayed messages can be rejected under the conservative rule below. |

Transparent edit/deletion history is mandatory content behavior, not an optional social signal. The UI shows Edited/history affordances and a deliberate Peek action. Reactions use a bounded normalized Unicode emoji vocabulary with explicit ZWJ/variation/skin-tone handling, text rendering and no arbitrary image URLs/HTML. Bound per-actor choices, distinct emoji per target and retained event bytes; provisional examples are five choices per actor and 16 distinct emoji per message, pending measured limits. Source/author corrections cannot conceal prior copies. Owner local erase, retention expiry and account purge may remove their own history; show unavailable content rather than silently restoring it from peers.

A target's visibility governs edits, tombstones, reactions and receipts. A newcomer does not gain old content or deleted-message peeking by joining. History sharing requires explicit bounded target/range and revision visibility permitted by the holder's rights and accepted by the receiving owner. Accepting a new peer alone does not authorize history sharing. The sender computes an event's audience from its accepted-peer set intersected with known target entitlement/recipient admission, never an arbitrary caller-supplied `to` list. The exact visibility evidence accompanies the event without disclosing other owners' private collection choices.

Deletion cannot atomically beat every in-flight transfer. Prioritize tombstones and recheck known deletion before starting a body transfer; a received tombstone does not initiate a fetch for its old body. Peek uses already-held bytes/durable owner references, not an unrestricted peer history grant. A recipient whose original transfer was cancelled gains no body access from the marker. Already disclosed in-flight bytes cannot be recalled. Local erase fences all later retries and sync.

Attachments use immutable digest/length/MIME references, staged upload reservations and safe content validation. Receiver ACK covers attachments only after it owns durable verified bytes or an equivalent independent retention reference. An expiring sender URL is insufficient. No arbitrary URL fetches. Local reference counting, quotas and orphan GC remain independent; sender delete cannot delete recipient-owned attachment references.

## Local peer approval, proposals and shared-secret lifecycle

The immutable signed genesis identifies the conversation, creator identity/key, contract/profile, proposed initial participants and safe bootstrap settings. Generate a fresh cryptographically random secret of at least 256 bits; the signed genesis binds its initial epoch identifier and digest so a substituted unsigned secret cannot accompany an otherwise valid genesis. Its protected admission envelope carries the shared secret and proposed initial whitelist/state to specifically approached recipients. Keep that envelope encrypted at rest and excluded from normal rendering, search, previews, notifications and exports that omit capabilities. Subsequent transport sends secret proof/credentials only in the exact protected header/body profile, never in URLs, logs or ordinary event documents. A generic old text grant cannot be expanded by hiding this control envelope in its body; use an explicitly permitted bootstrap profile. Each recipient independently validates the creator's identity through the existing trusted contact/admission path. An included key cannot authenticate itself merely by appearing in genesis.

The genesis whitelist is a **proposal**, not a command to populate everyone's accepted-peer list. Each owner signs its own consent updates at its own resource. `A accepts B` means A allows B's eligible contributions into A's copy and regards B as eligible for A's outgoing audience, subject to B's separate admission; it does not imply `B accepts A`, `C accepts B`, or a transitive relationship. Show pending/accepted-by-me/peer-confirmed/blocked states accurately. One party may accept a proposed peer later or never. Lists of proposed participants are untrusted suggestions until proof and consent checks complete.

Any accepted participant can submit a signed bounded proposal to add a peer or change a supported conversation setting. A proposal binds conversation, proposer, operation, target verified identity/resource, proposal ID, referenced view and expiry. Recipients may accept, reject or defer individually; their signed responses bind the exact proposal digest and their own consent revision. Each resource serializes its own acceptance CAS, with no global revision. A peer appearing in another owner's accepted list is not authority at this owner. Unsupported proposed policy semantics are rejected, never interpreted as executable rules or implicit permission expansion.

Normal direct delivery requires the original author to be on the receiver's current accepted list and not blocked, valid independent author proof, accepted shared-secret context and current recipient ingress admission. Secret-holder Charlie who is not accepted by Alice cannot make a message appear in Alice's conversation by claiming Bob's name or relaying through Bob. Alice's own outgoing messages never go to Charlie until Alice has accepted him. Conversely, Alice accepting Charlie does not force Charlie to accept or retain Alice's messages. Complete fanout means the sender's immutable eligible local audience, not a universal global participant set.

### Pending peers and storage abuse

Possession of the secret does not grant a free pending mailbox, profile lookup, history access, participant enumeration or a warm-object budget. Unknown/unaccepted actors are rejected by default with a uniform bounded response before retaining body bytes. A receiver may explicitly enable a narrowly bounded proposal/quarantine allowance using existing contact scope and work/storage budgets; that is consent to that limited inbox function, not automatic display or participation. Cap pending counts/bytes/expiry and verify identity before allocation. Link previews and genesis parsing never reserve unbounded storage.

Messages authored before the recipient accepts can remain in the author's own outbox/archive within that author's quota, but must not be automatically replayed into the newly admitted recipient. Default admission starts with future contributions under a new local admission incarnation. The immutable signed event audience binds the relevant recipient admission incarnations/acceptance digests, not only recipient names; an event lacking the new acceptance cannot become a new-admission post by replacing its outer delivery envelope. Later history fetch/re-share is a separate explicit authorized action with bounded target IDs/ranges. Proof of “joined” or possession of an old shared secret cannot fetch old deleted content or force backfill. A later grant must not validate an earlier event merely because a sender relabeled its transport envelope.

An author stream predecessor can refer to content the new peer may not read. Use a bounded signed header/frontier proof anchored to the new admission and explicit unavailable-history markers; verifying stream continuity never grants the missing body's contents. Do not recursively fetch every predecessor as a condition for reading a newly authorized message. Counters/digests can reveal limited activity metadata, which the profile must disclose and minimize. An author deliberately republishing old text as a newly signed document is distinguishable from protocol replay only to the extent existing retained evidence allows; shared-secret rotation cannot prevent that human disclosure.

### Local removal, conflicting proposals and partitions

An owner can remove/block a peer immediately at its own resource, independently of every other host. This invalidates that peer's ingress admission, removes it from this owner's future outgoing audience, cancels unsent local obligations as explicit cancellations and stops social disclosures/subscriptions. Block wins over stale acceptances, proposals, shared secrets and queued work. The other peers may still choose to communicate with that person; there is no claim of conversation-wide expulsion. Signed removal/block notifications can inform them without disclosing private block reasons, but cannot overwrite their choices.

Removal does not erase earlier owner copies, revisions or disclosed bytes. Reject newly acquired events from a locally removed original actor even if forwarded by a currently accepted peer; a signed timestamp does not prove pre-removal delivery. An honest event sent earlier but arriving after local removal can be rejected. Reacceptance needs explicit consent and a fresh local admission incarnation, defaults to future contributions and does not revive cancelled work or automatically release old history/signals.

There is no global policy fork to resolve. Simultaneous proposals and different owners' accept/reject decisions can coexist. Each owner's own signed consent stream and author stream must reject conflicting reuse of local revision/operation IDs; contradictory signed successors from one owner are equivocation evidence, quarantined rather than merged into broader permissions. Different owners having different accepted-peer sets is expected behavior, not a fork. Any proposal promising a single global policy value must instead specify its per-owner effect or be rejected as outside this profile.

The network cannot provide immediate propagation of a user's changes, but this model does not require remote convergence for local safety: the receiving owner's current approval always controls delivery to that owner, and the sender's current approvals control its own outgoing audience. A sender with stale evidence of a recipient's acceptance may attempt delivery; that recipient rejects it. Already in-flight bytes can have been disclosed before a block commits. Do not describe another owner's deliberate choice to continue talking to a removed peer as a failed global revocation guarantee that this profile never makes.

### Secret leakage and rotation

Local identity removal is effective without rotating the common secret because every receiver checks independent identity and its own live approvals. Secret leakage alone cannot forge an approved identity, obtain unapproved history/profile, or bypass current ingress admission. An approved identity's compromised signing key is a distinct incident requiring local key/admission revocation and authenticated key continuity; changing only the shared secret does not fix a compromised retained member who receives the replacement.

Any eligible participant may propose a new random secret epoch, distributed privately over independently authenticated approved channels. No old-secret-only endpoint reveals the new secret. Each owner independently accepts a rotation proposal and locally sets allowed epochs; there is no authoritative universal latest epoch or required creator signature. Conflicting rotation proposals cannot be silently merged into permanent acceptance of every key. Surface disagreement and retain bounded retry state; explicit per-owner selection/reconciliation is required. If some owners decline or are offline, submissions across the split may pause/fail until compatible accepted epochs exist. The product must show that availability cost instead of pretending rotation expelled someone from all other owners' views.

The immutable content event excludes transport secret epoch so a retry to another already-entitled recipient can use that recipient's accepted epoch without changing event identity or reauthoring history. The signed delivery context binds event digest, recipient, admission incarnation, selected epoch and replay bounds. Live consent and original event/history entitlement are still checked; this separation cannot be used to backdate old content into a new admission. Ongoing accepting members can deliberately share replacement secrets or plaintext; rotation never promises to prevent collusion or erase prior content. Defer automatic multi-epoch reconciliation until its bounds and user semantics are reviewed.

## Receipt admission, optional classification and rejection alerts

Receipt admission and content classification have independent controls. Every recipient has a plan-scaled aggregate receipt allowance, and each contact link has an additional owner-configurable limit. Classification is a separately budgeted paid feature, initially off for every link and independently off for the public-email bridge. Enabling it on one ingress never enables it on other links, admitted conversations or the whole account. The [email bridge](public-email-bridge.md) adds SMTP-specific abuse controls to this shared policy.

### Existing protection and proposed counters

The current implementation is already guarded. [HTTP ingress](../../packages/runtime/http.mjs) applies the normal message/network limiter; [contact grants](../../packages/messaging/contact-tokens.mjs) have lifetime `maxMessages`, `maxBytes` and per-message limits. [Account receive](../../packages/runtime/accounts.mjs) verifies the live parent grant, recognizes an existing receipt, validates content/scope/collection, checks storage quota and admits covered work before blob storage. Blob writes also pass the account storage-write budget. The controller currently aliases logical work to [the combined activity/storage-write budget](../../packages/runtime/storage-write-budget.mjs), with minute/hour/day activity bounds, durable nonrefundable logical and physical-attempt debits, and small prepaid service allocations across sixteen partitions. The legacy `AccountWorkBudget` class is not the current receive path. The supplemental runtime receipt-admission slice below now adds dedicated plan-scaled owner/parent windows; it is narrower than the accepted-count reservation design that follows. The current [message classification](../../packages/messaging/messages.mjs) is a single finite enum, not the multi-label result below.

Add a portable `ReceiptAdmission` policy using the existing atomic window/store interfaces, clock, entitlement lookup and injected work admission. Its configuration has explicit plan entries for accepted message count and admitted bytes per minute, hour and day, maximum individual message bytes, plus owner/link overrides that may only lower the plan's limits. Publish the concrete values after load/cost testing; do not derive them implicitly from a monthly covered-work number. Keep lifetime link ceilings and storage/work protections in force. An upgrade changes current ceilings without clearing usage; downgrade immediately applies lower limits to already recorded windows, without retroactively deleting accepted messages or resetting counters.

| Layer | Counter identity and scope | Required behavior |
| --- | --- | --- |
| HTTP/network attempt guard | Existing trusted-network/route policy | Runs before expensive token/body work. Retain normal guard behavior for all direct contact/token POSTs; a new owner limiter does not replace it. SMTP uses its own trusted transport and perimeter controls. |
| Aggregate recipient receipt | Stable owner UUID + fixed window epoch | Counts accepted message content and admitted bytes across aliases, links and receiving resources. Splitting resources or rotating a link cannot multiply this allowance. |
| Contact-link receipt | Owner UUID + stable live parent grant/lineage + window epoch | Additional message/byte windows and existing lifetime ceilings. Signed endpoint encodings, attenuated child tokens and replacement/rotated tokens of the same logical link share this identity; URL strings and random bearer tokens are not independent buckets. A genuinely new owner-created link still shares the aggregate owner cap. |
| Public-email lane | Owner UUID + bridge incarnation with persistent owner usage | Additional finite SMTP attempts, bytes, pending work and sender/domain safeguards; re-enabling cannot reset the owner's window usage. |
| Admitted conversation delivery | Owner UUID + recipient admission/lane | Still consumes applicable owner receipt/work/storage capacity. It uses its own participant admission bounds, not a silently expanded or repeatedly consumed original contact-introduction grant. |

Explicitly define the charged unit: a new incoming document or content revision consumes a content receipt and its admitted bytes; attachment bytes belong to that admission even when uploaded in segments. Reactions, delivery ACKs and protective control operations have separate bounded operation/work costs; ephemeral signals retain their separate small quotas. Reframing one document as many chunks must not evade the byte allowance, and retries must not charge the complete attachment repeatedly.

After authenticating the live grant/admission, check the existing idempotency receipt and immutable payload digest before reserving another receipt slot or scheduling classification. An authorized identical replay returns its established result without a new accepted-message, storage or classifier charge. It still passes the normal request guard and any already incurred nonrefundable attempt-work cost. A revoked/expired capability cannot use deduplication to read a receipt; a reused operation ID with a different digest conflicts. Invalid unauthenticated callers cannot allocate owner/link counters or trigger owner alerts merely by naming a UUID.

Reserve owner and link count/byte slots atomically in the same local owner journal under an operation/reservation ID, so concurrent requests cannot each observe spare capacity. Reservations count against current windows while pending. Use provider-controlled UTC window IDs, a bounded reservation TTL and a reservation generation/fence; caller dates never choose a window. At commit, if the window changed, atomically move the reservation to the current owner/link windows only after rechecking both limits, or refuse before acceptance. An expired/released reservation cannot commit through a stale worker. Clock rollback cannot reset usage: fail closed until the stored frontier can advance safely. Commit the accepted debit together with the message/receipt; reconcile crashed reservations against durable acceptance before releasing only provably unused receipt/storage capacity. Never refund covered work already consumed. Restore/export includes necessary bounded counters/frontiers so restart, shelving, token rotation and provider-local restore do not erase live admission history. Across provider migration, carry usage for active windows or enforce a conservative initial bound; no global cross-provider rate coordinator is required.

HTTP rate refusal is a bounded `429` with `Retry-After` for window limits where safely known; lifetime exhaustion needs a distinct stable reason and must not promise that waiting renews a revoked/exhausted link. Do not reveal another ingress's traffic, plan, identity or classifier results. SMTP keeps its documented rejection semantics. Count only accepted content in accepted-message metrics; separately label attempted, limited and invalid traffic. Erasing or offloading stored content does not replenish receipt-rate usage; it affects retained-storage accounting separately. Limit state is bounded by known owner grants, fixed window buckets and expiry; no per-attempt rows, per-message alarms or new globally hot database. Local owner transactions serialize owner/link receipt updates; existing sharded leases cover provider work/spend. This atomic accepted-receipt design assumes the current owner actor also commits the message. Future separate conversation actors cannot claim a cross-DO transaction: keep quota/message commit co-located, or separately review durable reservation/reconciliation before splitting them.

### Current supplemental runtime slice: admitted attempts

The first implementation is [MessageReceiptBudget](../../packages/runtime/message-receipt-budget.mjs), injected into account contact receipt and stored conversation-event receipt. Conversation invitations already pass through contact receipt. It meters **admitted new message attempts and their payload bytes**, not successful messages: debit happens after validation/storage-quota checks and before covered work or blob writes, and a downstream failure keeps the debit until window expiry. Established authorized receipt replay bypasses it; failed attempts without an established receipt may consume again. Blob bytes/physical write operations remain separately guarded and nonrefundable. This deliberately avoids claiming an atomic R2/message/accepted-count transaction or implementing the reservation/refund design above in this slice.

The provisional fixed UTC defaults selected for this implementation are supplemental ceilings, not promised throughput; existing HTTP, lifetime contact, combined activity and physical-write limits may bind earlier. A boundary can admit up to two fixed-window allowances in a short interval; the existing burst/physical-write controls still apply.

| Plan | Owner attempts minute / hour / day | Owner payload MiB minute / hour / day |
| --- | --- | --- |
| Free | 30 / 300 / 1,000 | 16 / 128 / 512 |
| Paid | 120 / 1,000 / 5,000 | 64 / 512 / 2,048 |
| Plus | 240 / 2,000 / 10,000 | 128 / 1,024 / 4,096 |
| Ultra | 240 / 2,000 / 10,000 | 256 / 2,048 / 8,192 |

Each contact parent's default is half the corresponding owner count/byte ceiling; conversation events use the owner aggregate after their existing participant/source authorization. The current one-MiB message bound intersects the rate ceilings; valid current conversation text events are already much smaller. Rotated minted child tokens share the verified parent ID. This slice does not yet implement a UI for independent per-link overrides or a new cross-parent replacement-lineage mechanism; genuinely new parents still share the owner aggregate.

`MESSAGE_RECEIPT_LIMITS` accepts a JSON object or JSON string keyed by any subset of `free`, `paid`, `plus`, `ultra`. Each supplied plan requires `owner` and `contact`; each requires `minute`, `hour`, `day`; each window requires nonnegative safe-integer `messages` and `bytes`. Contact ceilings may not exceed owner ceilings. Unknown/malformed fields fail closed; omitted plans retain defaults. Zero disables that configured lane without a misleading retry time. If a payload cannot fit an otherwise empty byte window, return a size/allowance error without `Retry-After`. Ordinary window exhaustion returns `429` with the latest applicable reset; bounded parent-state exhaustion has its own capacity reason/reset.

The owner transaction persists one validated record, at most 256 active-day contact parents and at most 120,000 encoded bytes. New-parent exhaustion refuses safely rather than allocating unbounded state. Expired contact windows are pruned on admitted work; rejections persist no alert/counter rows. Backward clocks, corrupt records and owner mismatch fail closed. Current shelving leaves this account metadata hot, so restarts/shelving preserve usage; complete encrypted owner-bucket backup/migration remains the broader proposed work. Owner account snapshots expose `messageReceiptAdmission` status with unit `admitted-new-message-attempts`; no classifier or outbound notification dispatcher was added.

### Paid, per-ingress multi-label classification

Owner policy stores `classification.enabled` and its revision on each contact parent grant and separately on the bridge; defaults are false, including copied/new links. An account master switch may disable all classification but cannot silently opt every link in. Require current confirmed paid entitlement and that exact live ingress policy before enqueue and again before invoking the model. Downgrade, disable or link revocation stops queued classification, leaving accepted content and manual labels intact. Receipt acceptance remains available under its own plan allowance when classification is unavailable. Necessary MIME validation, malware/automation safety checks and reply suppression are not an implied paid classifier opt-in.

Keep inference limits distinct: classifier calls per minute/hour, input tokens and estimated spend per billing period, queue depth/age, owner-selected per-link or bridge subbudget, and the hard owner/provider classifier cap. Reserve before invoking, include prompt/schema tokens, and never borrow silently from another link's allocation. The reservation covers fixed question/category schema and instructions as well as selected body text; adding labels changes the token cost. Record what bounded excerpt was examined and whether it was truncated, without claiming to have classified unexamined attachments or history. Use prefunded shard leases without refunding consumed work or ambiguous provider requests. A classifier timeout or exhausted allowance yields `not-run`, `deferred` or `failed` with a bounded reason, not `not-spam`; heuristic/manual receipt handling continues. Reclassification is explicit, versioned and charged. Duplicate deliveries reuse the matching input-digest/policy/model result instead of scheduling new inference.

Use a bounded versioned set of independent labels: `spam`, `conversation`, `outreach`, `promotion`, `transactional`, `receipt`, `automation`, `email-verification`, and `authentication-code`, with unknown/insufficient-evidence state. Several labels may apply—for example promotion plus outreach, or transactional plus verification/code. Scores are independent evidence, not probabilities of mutually exclusive categories; do not force their sum to one. Store a separate local `classificationResult` with schema/model/policy revisions, input digest, label scores, processing state and owner corrections. Preserve the existing `classification` enum for compatibility through an explicit owner-approved projection; do not silently replace it with an incompatible object or treat a missing label as proven absence.

Routing disposition (receipt, pending invitation, quarantine), priority and notifications are separate owner policies consuming this evidence. Classification never creates a signed author, accepts a peer, widens a capability or commands deletion. Detect obvious auth-code/verification automation deterministically first and omit/redact secrets before any optional inference. Model input and output are bounded inert data; arbitrary message instructions and generated strings cannot become rules. Classification results are recipient-private metadata unless the owner explicitly shares them, not immutable sender-authored conversation events or a public sender reputation feed. Exact labels/schema and rule matchers require versioned capability discovery through existing resource contracts, not a private classifier-only login/API.

### Coalesced rejection alerts

Offer owner-only “Receipt limits reached” alerts, with push/email individually off by default and the ordinary notification master switch taking precedence. Aggregate only after a verified active ingress is legitimately attributable to an active owner. Unknown/forged/revoked-link abuse may contribute to bounded provider telemetry, but must not wake arbitrary accounts or generate emails to purported senders. SMTP-disabled/suspended accounts produce no rejection notifications or signup prompts. An accepted message's normal notification and a refused attempt's limit summary are different event types; current message-backed notification eligibility cannot simply be reused without an explicit bounded account-summary extension.

Maintain one bounded owner summary per reporting window with capped reason counters and a bounded top-link list or overflow count. A threshold transition schedules one durable summary job; subsequent refusals update/coarsen the same record without creating another job. Under sustained overload, sampling or saturating counters is acceptable: report “at least” or approximate counts instead of spending unlimited work to count every rejected request. If admission cannot afford a telemetry update, discard that update without changing the refusal or scheduling extra work.

Propose at most one push summary per owner per hour and one email digest per day, further constrained by notification preferences, quiet hours, device-count cap and provider-wide notification/spend caps. Global pause or budget exhaustion may suppress an optional summary; these alerts cannot consume the reserve for essential security mail. Many links, changed reasons and rotating tokens cannot bypass the owner cooldown. Messages say only that some deliveries were limited and link to an authenticated settings/status page; include no sender text, raw link token, subject, body or attacker-selected URL. Email goes only to the owner's currently verified notification address, never the rejected sender, and the setting does not grant permission to send activation or marketing mail. No per-refusal email or recursive alert about an alert's failure is permitted.

At claim, freeze a bounded report snapshot and ordinal; subsequent counter increments move into the next coalesced reporting window and must not invalidate the claimed snapshot or starve notifications indefinitely. At claim and immediately before send, recheck active account status, current notification consent, channel/address/subscription validity, authority/source/settings generations, quiet hours and the reserved notification budget. Persist owner/channel cooldowns and consumed or outcome-unknown ordinals across preference toggles and restarts; reserve each capped device transport attempt, not only the logical summary. Suspension/deletion invalidates queued jobs; resumption does not replay a stale storm. Owner disabling the offending link can cancel its pending detail without losing an honest aggregate status. Use the existing durable scheduler/outbox patterns, not an alarm for each refusal. Lost external send responses remain outcome-unknown and cannot justify unrestricted retries. Preserve bounded protective block/disable/erase/read/export capacity when receipt or classification allowances are exhausted.

## Local storage, actors and free-account cost

All shelving happens **per provider and owner replica, into that owner's storage bucket**. A provider can start with its existing account actor for local quota/admissions/author stream/outbox; move a hot owner/conversation into a dedicated local actor when measurements show contention. It must not instantiate a shared cross-provider sequencer merely because Cloudflare offers per-conversation object IDs. Reads use the owner's copy when other providers are unavailable.

Keep compact admission/revocation/frontier metadata accessible, immutable cold transcript segments in the private owner-bucket namespace below, and a bounded transactional hot journal of uncheckpointed events and pending work. Restore known segment/page references, not whole histories or global bucket listings. Same-provider physical deduplication is permissible only with independent logical ownership, quota, authorization and retention; peers receive their own durable copies. Search indexes are derived and reauthorize against current local owner visibility; edits/tombstones suppress stale results, and invitation/grant material never enters search or notifications.

### The owner's bucket is the backup boundary

The user requirement is one user-owned storage namespace containing files, messages, conversations and required restoration metadata. Cold conversations must **not** live exclusively in a separate authority/archive bucket outside that account's backup. Use reserved system keys, for example:

```text
.bindle/account/manifest.json
.bindle/account/generations/<generation>/...
.bindle/conversations/<opaque-conversation-id>/<generation>/...
.bindle/messages/<opaque-message-id>/...
.bindle/resources/<opaque-resource-id>/...
```

These paths are proposed local storage layout, not public conversation identity/RPC requirements. Map validated opaque IDs to keys; never splice a caller-supplied URI/path into the namespace. The account manifest is a minimal, integrity-protected root/checkpoint leading to versioned encrypted manifest shards, conversation segments, attachment mappings, owner settings/organization, local approval/block graphs, admission incarnations, replay/frontier state and recoverable pending-work records. Keep detailed sensitive metadata encrypted to the owner alongside the payload. A compact bootstrap header may expose only the locator/key/version information needed to find and decrypt those records, with the metadata limits already stated below.

The existing hosted adapters use shared physical `BLOBS` storage with per-owner object paths and a separate `ARCHIVES` adapter. That is an implementation fact, not the desired final backup boundary. The proposed hosted **owner bucket** can be a logical namespace inside a shared physical bucket; the authenticated user's complete backup view must include their reserved system namespace and ordinary files regardless of internal mappings. Reconcile or move existing separate-archive data into that owner view before claiming complete bucket backup. Internal caches/replicas may exist elsewhere, but no required cold restore object or authoritative mapping may exist only there.

A user-selected external object-storage bucket/resource is a different backing choice from the hosted logical bucket. It qualifies as the same owner-bucket boundary only after its scoped write/read/conditional-publication, integrity, durability, size and restore capabilities are actually verified. A merely configured credential, read-only connector or a link to an external folder is insufficient. Storage placement failures retain durable pending work/source copies and visible incomplete status; they never acknowledge a complete user-bucket archive or trigger source deletion. Exact external bucket/root binding and incarnation are recorded so reconnecting another root cannot silently change the backup destination.

Reserve `.bindle/` from ordinary app object-storage capabilities. Enforce that restriction server-side across relative-key normalization, reads, writes, deletes, copy/move, optional listings, ranges, presigning and batch operations; hiding it in a UI is insufficient. App resource scoping must not manufacture access through traversal, aliasing, overlapping child resources or a broad parent reference. Owner-directed backup/migration tools receive a separately explicit system-export authority, not an automatic widening of app grants. No application may rewrite the signed account head, inject consent records or evade byte/work quota by writing directly to the system namespace. An owner using their own upstream bucket-admin credentials can still damage their backup; integrity checks must detect corruption rather than treating those raw writes as authorized account-state changes.

This placement rule does **not** silently encrypt or change the bytes of every ordinary app file exposed through the object-storage contract. Preserve those files' established semantics. Conversation/system archives use the required owner-key encrypted codec; a comprehensive encrypted migration/export container may wrap additional file bytes without rewriting the live app objects. Account manifests also record external-resource mappings and references, but those references are not backups of third-party bytes. A complete-data export must explicitly copy every accessible selected external file or report the missing/inaccessible class; no claim of “all data” follows from backing up only native file IDs.

### Hot journals and a consistent bucket backup

Actors' in-memory state is disposable. Before returning accepted, each local operation must exist in a durable transactional journal with its payload reference, safety state and outbox obligation; incremental checkpointing then writes covered state into the owner's reserved bucket namespace. Durable SQL may hold a bounded uncheckpointed tail, but it must not become an indefinitely excluded second authoritative archive. Configure bounded age/bytes and backpressure when checkpointing cannot make progress. Never clear the durable hot journal until its exact generation is verified in the owner bucket. A lost compute instance can recover from that journal/head; reconstructing exclusively from a prior bucket checkpoint reaches only that checkpoint's declared recovery point.

The proposed default ACK waits for the durable provider journal, **not** for a new bucket object on every message. A process/actor restart recovers its persisted tail; loss of the entire durable journal before checkpointing is not covered by the older bucket snapshot. An optional strict bucket-before-ACK profile would need an independently durable bucket journal entry for every accepted operation and has a different latency/write-cost budget. Do not advertise that stronger guarantee for the default. The explicit backup cut below closes the journal-to-bucket gap for its declared revision before reporting completion.

An explicit **complete bucket backup** requests a consistent cut: establish an account/replica snapshot fence, flush or include every accepted pre-cut hot-tail record and referenced payload, snapshot pending outboxes/ACKs/approval/replay state, and atomically publish a finalized account manifest only after all referenced encrypted objects verify. Bounded shard generations can supply this cut without one giant in-memory snapshot; concurrent post-cut writes remain in the next generation. If the hot tail or referenced connector bytes cannot be captured, report an incomplete backup and retain source state. Restore uses the published root and exact referenced generations, not whichever files happen to appear during a bucket listing.

A raw bucket copy while writes/checkpointing continue is not automatically an atomic or complete backup. A user may back up the immutable finalized generation/root after the explicit cut, pinning it against GC; include the pinned root/version and all referenced bytes. External-tool snapshot adapters can offer equivalent semantics only when verified. No committed user data may be discarded on the assumption that an uncoordinated listing copy captured it. Pending messages restored from a backup retain original identifiers and require current recipient admission before retry; an old snapshot must not resurrect a deleted copy over a newer known local erase frontier or reactivate stale credential authority. A fresh offline destination cannot know about later erases absent from its declared backup recovery point; preserve that limitation rather than claiming the snapshot contains future deletion state.

The recovery file holding the decryption key remains independently possessed and decryptable, outside the bucket's self-encrypted dependency. The intended recovery set is **a verified complete owner-bucket snapshot plus the appropriate independently saved recovery/key material**, along with any explicitly disclosed external-data gaps. Neither a bucket without its key nor a key without the account data is a full backup. Restoring durable user data does not itself recreate old provider DNS, passkey RP/session or OAuth/connector authority.

### Per-owner archive encryption and portable ciphertext

Cold conversation archives **must be encrypted to the owning user's public encryption key**. A raw archive download, export or provider transfer sends the encrypted representation; opening it requires that user's recovery/restore file unlocked locally, or an already unlocked authorized copy of the corresponding private encryption key. Do not silently substitute a plaintext export for convenience. Interactive authenticated conversation viewing remains a separate operation through the owner's resource; this archive requirement does not make every UI response ciphertext.

Reuse the assigned keychain already returned by internal `identityKeychain`: its separately generated **ECDH P-256 encryption key and `kid`**, preserved in the answer-encrypted v2 identity recovery file. Do not use the ECDSA signing key, passkey, shared conversation secret, genesis digest, handle or answers as the data-encryption key. The shared secret remains a conversation possession gate. A provider encrypting its own owner's archive can obtain the established public key from local keychain records without a network lookup or new key creation. If another authorized party must encrypt to that owner, `identity.json` can publish the deliberately established **encryption-purpose** public descriptor; validate issuer/UUID, purpose, `kid`, key fingerprint and pinned continuity before selecting it. Do not blindly encrypt to a newly substituted key found in a mutable document.

Each owner's replica is encrypted independently. Alice's archived copy uses Alice's recipient key and Bob's uses Bob's; access to one ciphertext does not give the other person's key. Use independent data keys/envelopes per owner even when plaintext documents match. Do not undermine that boundary by deduplicating one plaintext/key across owners. Same-owner immutable ciphertext references can be shared under independent retention accounting where safe.

**Custody limit:** today the provider stores both private identity keys encrypted under its own `KEY_ENCRYPTION_KEY` and can decrypt them. Its runtime also handles plaintext events and indexes. This proposal protects cold objects and portable exports from a storage holder lacking the private key, but it is **not end-to-end encryption against the provider**. It does not claim that only the user can open hosted copies or that a provider compromise cannot expose them. Losing the user's file may lose the user's independent offline access even if a trusted provider still has a recoverable key; never introduce an undocumented operator reset/bypass to promise recovery.

### Hybrid segmented envelope — proposed format, not implemented cryptography

Public-key cryptography wraps small random keys; it does not encrypt a large transcript directly. Prefer a reviewed [HPKE RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html) implementation for wrapping, with proposed suite DHKEM(P-256, HKDF-SHA256), HKDF-SHA256 and AES-256-GCM. The [IANA HPKE registry](https://www.iana.org/assignments/hpke) identifies these choices; selecting them does not establish implementation conformance. Wrap a fresh 256-bit symmetric DEK per immutable owner/segment, then encrypt bounded data chunks with AES-256-GCM and full authentication tags. Do not invent an ECDH-output-as-AES-key construction. Actual suite identifiers, library, canonical bytes, nonce construction and cross-runtime test vectors require separate cryptographic format review before code/publication.

The independently versioned portable archive profile must specify these records precisely:

| Record | Required binding and verification |
| --- | --- |
| Immutable content header | Format/version/suite, owner stable UUID and identity namespace, conversation ID/incarnation, archive/segment random ID, content generation, chunk size/count limits and domain separator. Handles/aliases never enter cryptographic ownership or AAD. |
| Recipient key envelope | Encryption `kid`/fingerprint/purpose, HPKE encapsulation and wrapped DEK. HPKE context binds the content-header digest, owner/conversation/segment/version and recipient-key descriptor. Only explicit same-owner key-rotation rewrap may alter this envelope; ciphertext content identity stays fixed. |
| Data chunk | AEAD associated data binds content-header digest, owner UUID, conversation, segment/generation/version, chunk index and exact plaintext length. A fresh DEK and nonce namespace belong to exactly one immutable encryption attempt; counters are unique within its strict bound. Cut-and-paste across users/conversations/segments, reordered chunks and changed lengths fail authentication. |
| Finalization record | Separate authenticated record commits exact chunk count, total plaintext/ciphertext lengths and ordered chunk/digest commitment, including empty segments. Missing finalization or missing/extra/reordered chunks fails; EOF is not proof of completeness. |
| Finalized archive manifest | Independently signed by the exporting owner's established signing identity or an explicitly trusted export signer, binding all header/envelope digests, owner/conversation, archive generation, exact ordered segment IDs, ciphertext hashes, byte counts and finalization references. The signing identity is pinned independently; an archive-supplied key is not a trust anchor. |

Public-key encryption alone does not authenticate who made an archive: anyone with the public recipient key can encrypt new garbage. Manifest signatures establish the approved exporter's binding, and original signed conversation events retain their independent provenance after decrypt. A valid old manifest can still be a rollback; offline authentication does not establish “latest” without a separately retained trusted head/checkpoint. Do not overwrite a newer local consent/revocation/tombstone frontier merely because an older archive decrypts successfully.

An interrupted immutable upload can resend its exact ciphertext bytes. If any plaintext/header changes, generate a fresh segment ID, DEK and nonce namespace; never resume by encrypting different plaintext at a reused key/nonce position. Fix nonce counter encoding and exhaustion bounds in the format; leave ample limits below algorithm maxima. Keep recipient-wrap metadata separately authenticated from the immutable data header so an authorized **same-owner** DEK rewrap need not reuse payload nonces or re-encrypt unchanged chunks. A rewrap creates a new signed manifest/envelope revision, not an in-place untracked key substitution.

Segment/chunk boundaries support multi-gigabyte exports with bounded memory, backpressure, range resume and independently verified ciphertext hashes. Stream download/transfer without decrypting. During decrypt, authenticate each chunk before releasing it to staged output, bound decompression/decoded sizes and parsing, and verify finalization plus the complete manifest before committing an imported transcript. Partial output is explicitly incomplete/untrusted as an archive and cannot silently become authoritative account state. Do not buffer the entire archive, decrypt recovery answers in a worker log, or import executable message markup during reconstruction. Strict decoding rejects unsupported versions/algorithms and duplicate or ambiguous fields; all adapters use the published byte encoding and fixtures.

### Offline opening, key rotation and moving copies

The offline opener uses the existing recovery envelope's answer/passphrase-derived decryption locally to obtain the preserved encryption private key. No answers, private recovery payload or private key are sent to an archive store or remote import provider merely to open the file. Validate recovery schema/key correspondence and owner identity; verify the recovery/provider proof using an independently trusted saved verification key when offline. The current online browser recovery flow and the proposed offline archive reader are different capabilities; the offline reader is not implemented merely because key material is already portable.

Archive decryption is independent of consuming an account-reset credential. An expired/used reset token does not mathematically revoke an encryption private key, and possession of that key does not authorize login, reconstruct a deleted account, restore revoked grants or bypass live recipient consent. Import transcript/history and safe owner metadata as a separately authorized operation; ordinary portable archives omit account login/reset tokens, OAuth credentials and live peer-ingress grants. Restoring history must not auto-send messages, disclose old read receipts or revive memberships.

Preserve decryptability across encryption-key rotation. Existing recovery files currently contain one encryption key, so a future rotation must either retain an explicitly versioned historical decryption-key set in tested recovery material, or rewrap every retained segment DEK to the new key and verify a usable replacement export/recovery file before old key material can be retired. Record both key IDs and exact coverage; partial migration is visible. A fresh recovery file is not proof that all external old copies were rewrapped. Never destroy the only decrypting key based on a database flag.

Routine same-owner migration/offload can copy the ciphertext unchanged when the stable UUID/key ownership is preserved; mutable handles and storage-provider addresses do not affect decryption. Import at another provider does not require handing that provider the private key for a **storage-only** move. If the user wants the new provider to index/decrypt/serve the transcript, disclose that separate custody transfer and authorization. A deliberate copy to a **different owner** must verify that owner's public encryption-key binding and re-encrypt under a new owner/segment context; it is not an unchanged opaque move or permission inferred from conversation membership. Sharing old content remains subject to history entitlement and explicit consent.

If the old encryption key or plaintext/DEKs were compromised, mere rewrapping cannot retract old ciphertext/key copies. Re-encrypt affected new retained data with fresh DEKs and authenticated key continuity when remediation requires it, while stating that previously disclosed material remains accessible to its holder. Conversation-secret rotation is unrelated to archive decryption-key rotation.

### Verified encrypted offload and metadata boundary

Reuse the existing [offload/retention design](offload-retention.md) and ordinary scoped object-storage operations for encrypted movement. Copy the finalized manifest, recipient envelopes, every referenced segment/chunk and necessary reconstruction metadata. A destination custody receipt binds exact destination resource/incarnation and immutable version, ciphertext length/digest, source archive generation and manifest digest. A provider acknowledgment or plausible ETag alone is not proof of durable matching bytes. Verify the full destination representation by the adapter's reviewed immutable-checksum/readback profile, preserve durable receipts and recheck source/destination generations before any authorized source cleanup. Partial/unknown/corrupt transfers keep the source. Manifest/envelopes must remain retrievable with the ciphertext; moving payload chunks while deleting the only index/wrapped key loses the archive.

Ciphertext movement does not need a decryption key or a plaintext round trip. A verified custody receipt proves retained matching ciphertext under its stated storage guarantees, **not** a successful decryption/recovery drill, message-delivery ACK, human read receipt or continuing recipient consent. Before enabling destructive moves, test the complete package with the intended recovery key in an independently run restore drill and the normal failure-injection/backup gates. Do not require uploading the user's recovery answers to satisfy that gate. Preserve the minimal catalog/checkpoint needed to locate offloaded archives and prevent stale work from deleting unrelated versions.

The cold envelope hides payload contents from a storage-only holder, but public/stored headers, object lengths/counts, key IDs, stable owner/conversation identifiers and access timing can reveal metadata unless separately minimized/encrypted. Keep semantic details such as subjects, participant names, previews and attachment names inside encrypted payloads. Compact online admissions, dedup/frontiers, quota ledgers, notification queues and lexical/semantic search indexes may still contain plaintext metadata/content in the current provider trust boundary. Document and budget their retention separately; encrypting an R2 archive does not encrypt a search index, eliminate cached previews or protect already-sent notifications. Minimize those projections and do not claim whole-account confidentiality from this archive feature.

Cloudflare's object lifecycle does not imply an always-running charge per dormant conversation. Objects restart/evict without reliable shutdown hooks. Commit accepted work durably before responding and checkpoint explicitly; never rely on eviction callbacks. [Cloudflare lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)

A safe local cold transition is:

1. Rate/size/proof checks precede expensive restore. A well-formed revoked credential can require loading compact current admission state, and denied traffic remains budgeted.
2. Acquire the adapter's local writer/lease and conditionally advance a durable writer generation in that owner-replica's cold head before serving mutations. Retain checkpoint reference and anti-replay/revocation anchors. A restart cannot keep the previous head ETag while creating a newer hot tail that old async work could overwrite.
3. Commit immutable event/body references, author position, quotas, dedup and complete local outbox atomically. External upload/transport happens outside the short commit lock with generation checks. Failed staged payloads enter bounded GC.
4. Write bounded immutable checkpoint segments for a fixed journal revision; read-verify digests/schema/owner/incarnation. Publish the local current pointer conditionally against the expected head generation/ETag. Object storage and SQLite do not form one transaction; retain hot data until publication is verified.
5. Cleanup compares **writer generation and covered hot revision transactionally**. Matching an uploaded manifest alone is insufficient. Concurrent work leaves a hot tail. A Node successor fences predecessors before accepting writes; delayed callbacks cannot unlink live shared SQLite files.
6. Keep compact hot pending retries durably scheduled until acknowledged, rejected or bounded retry exhaustion. Only when all state is checkpointed and no automatic work remains may the actor delete its alarm and clear all local storage. The cold head retains the fencing/revocation/frontier anchor. Set in-memory state cold and reacquire a new durable generation on future work. An in-memory flag is not a distributed fence. If the adapter cannot prove these conditions, retain a tiny persistent anchor and forego full deletion.
7. GC old generations only after replacement verification, retention grace and no active reader/export leases. Never restore an earlier snapshot over newer local erase/revocation/frontier state. Recovery with an unreconciled accepted tail remains read-only/unavailable rather than losing acknowledged data.

Explicit `deleteAll()` is needed to remove residual DO storage, with separate alarm deletion; SQLite's atomic clear does not make R2 publication atomic with it. Never clear an account controller that still owns unrelated data. [Cloudflare storage lifecycle](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/), [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)

Use an adjustable idle/dirty threshold and segment batching. Neither whole-history rewrite per message nor weekly wakeups of every permanently idle replica are acceptable defaults. There is a head-write cost on writer acquisition and O(n) fanout per post; measure both. Every user pays logical retention for their copy; authors sponsor their own delivery retries under finite work budgets. Owner quotas can reject a peer after that peer accepted locally, producing partial delivery.

Encrypted archives, system checkpoints, manifests, recipient-key envelopes and retained generation overhead count against the owner's logical storage quota, including the reserved `.bindle/` namespace. Account for actual retained encrypted bytes and avoid double-charging one immutable object referenced by several same-owner manifests. Separately track temporary reservations and physical cleanup debt. Preserve a bounded essential reserve for revoke/leave/block/erase records and safe cleanup so quota exhaustion cannot trap an owner in an unwanted relationship or prevent deletion; it is not unlimited free archive storage.

Bound room creation, active replicas, retained events/bytes/history, group size, churn, pending invitations/dependencies, attachment sizes, delivery attempts/age, reconciliation pages and export work. Protective leave/block/revoke/local erase retain a bounded reserve even at quota exhaustion. Current implementation bounds (100 rooms, 1,000 events/operations, 4 MiB source retention, 512 queued jobs, 32 members) are not new product guarantees. Use existing sharded abuse/work controls; no global counter on every message. Measure cold reads/writes, CPU, SQL rows, object operations, retained physical bytes, retries, notifications and lexical/semantic index work. Free accounts need a finite provider subsidy envelope, not unlimited replay/storage/heartbeat promises.

## Optional social signals and device notifications

Read receipts, typing and online/activity status default independently **off** for outgoing disclosure. Provide separate account defaults and per-conversation overrides; global Disable and block/leave override every conversation. Local read/unread state works regardless. Push permission/verified setup delivery is unrelated consent. No exact device IDs, location, IP, draft contents, per-keystroke stream or historical last-seen archive is disclosed by default.

Signal audiences are the sender's locally accepted peers with appropriate known admission and target entitlement, subject to both ends' current consent and blocks. A block immediately stops that provider's disclosure; no proposal or another member's accepted list can override it. Presence describes only this conversation, not the user's other account activity.

Typing/presence use authenticated short-lived leases through the optional public profile. A provider-local or bounded delegated relay may deliver them directly to eligible peers; no mandatory central presence host. Example initial bounds: presence refresh every 15–30 seconds with 60-second expiry; typing refresh at most every five seconds while input continues with ten-second expiry. Foreground/recent-interaction only, multi-device aggregation locally, TTL on crash/mobile suspension, and no status derived from a push worker running.

Do not wake a cold conversation merely for presence or polling. Publish only to active eligible subscriptions under finite subscriber/rate/byte budgets; new late subscriptions do not receive activity history. No R2 write, SQL mutation, alarm, durable outbox or group-wide push per heartbeat. Clients expire leases locally; lost ephemeral state becomes unknown. Disconnect revoked subscriptions promptly; previously disclosed information and in-flight lease signals cannot be recalled. Reject unauthenticated enumeration.

Read receipts are separate from signed provider delivery ACKs. A conforming client emits them only after an actual foreground view under enabled policy; they remain an authenticated participant/client assertion, not proof of human attention. Use explicit message IDs or per-author read frontiers with exception sets for gaps, never a nonexistent global `lastReadSequence`. Only entitled actually viewed messages qualify. Coalesce at the participant level without exporting device identity.

Enable sharing prospectively: no historical read-state upload or retrospective watermark. A currently open message requires a new deliberate read/view action after enablement. Disable stops future emission, invalidates queued disclosure-generation checks and clears unsent work; it cannot erase receipts already delivered or fabricate unread status. Private Mark unread is not a public unread event. Receivers retain already received receipts under their own retention; sender auxiliary receipt caches may be bounded. Receipt work has its own bounded delivery budget/expiry, no infinite retry, receipt-of-receipt loop or default ordinary-message notification.

Message notifications use existing per-owner durable outboxes and safe IDs/opt-in previews, coalesce bursts and stop invalid subscriptions. Devices sync their own provider's local cursor; no permanent socket to each participant or cold conversation is required. Notifications never contain reusable capabilities, imply reading, or bypass message visibility/deletion state.

## Public URI-identified conversation contract

Proposed immutable identifier: `https://3sln.me/artefacts/contracts/conversation/v2`. The coordinator publishes an actual versioned schema/artifact only in subsequent implementation work. This file does not publish it. Keep the v1 submission schema unchanged and identify its older central/shared-secret semantics explicitly. The **contract URI**, **conversation identifier**, and **each owner's resource URI** are distinct. No DO ID, R2 key, SQLite path, queue address or central provider is part of the public contract.

All features below use existing resource RPC and exact live method/resource grants, with participant proof/admission additionally enforced at peer boundaries. The following is the proposed logical method surface. A method's resource role is advertised; an owner-facing local resource can orchestrate protected peer calls without giving apps raw delivery credentials. Unknown methods/profiles/fields/algorithms fail explicitly.

A conversation is an ordinary resource-valued preference/assignment where an app needs one, and authorized automation adapters call the same advertised methods through existing resource RPC. Existing OAuth/consent/session machinery grants app access; there is no conversation-only login or token bypass. The effective app permission is the intersection of its live resource/method grant, current owner assignment, the member's supported rights/local approvals and the recipient's admission for any remote effect. An automation granted `append` cannot `propose` a new peer, acquire another conversation, enable optional social signals or modify another author's event. Resource references remain opaque provider-issued identities rather than caller-selected network endpoints.

Required v2 profiles: independently writable participant replicas, first-contact/admission, signed author streams/causal documents, transparent edits/tombstones, reactions, owner-local controls, encrypted cold/archive portability and verifiable delivery ACKs. Optional profiles: exported read receipts, typing and presence. Provider capability discovery advertises each exact optional profile, method and transport/expiry bounds; unsupported calls fail rather than silently disappear. Messaging works with all social signals disabled. The archive codec is an independently pinned format referenced by this contract, not an undocumented implementation detail.

Schemas define `message`, `edit`, `tombstone`, `reaction.add/remove`, signed proposal/local acceptance/admission/leave controls, local changes, delivery ACKs and separate social signal types. Durable mutations bind operation ID/payload digest and applicable expected revision. Local cursors are not portable global ordering proofs. Ephemeral activity uses bounded lease/update identifiers without durable per-heartbeat journals. Reuse exact existing MIME and attachment schemas by immutable reference. Public HTTP shortcuts and UI actions are adapters of this contract, not private alternative semantics.

## Contact-link user experience

Show the intended recipient/provider, current sender account, scope and a draft before the final Send. Link claims decoded by JavaScript are provisional presentation until the issuer validates them. A subject or nickname is not verified identity. Keep typed text through the supported continuation window; do not upload attachments or create the conversation on GET.

Store a random context identifier in clean same-origin URLs; possession alone must not disclose the stored capability. No raw endpoint, draft or token goes into `return_to`, OAuth state, recovery files, analytics or service-worker caches. Bind again and revalidate after account change. Clear context after success, cancellation or expiry; offer an explicit user-controlled draft export if navigation would lose data. Do not put secrets in localStorage or general reactive state.

Keep the signer-bearing HTTPS URL's existing unavoidable first-request disclosure explicit: the `sig` query reaches the recipient issuer and may appear in upstream logs unless scrubbed. Set no-store/no-referrer before rendering, redact query logs at each hop, suppress third-party assets/prefetch and remove the query with `replaceState` promptly. ## Browser and app handoff feasibility

The web registration rules accept safelisted schemes or custom `web+` followed by lowercase ASCII letters. `web+bindle` fits; arbitrary `bindle` does not. `registerProtocolHandler` uses a secure same-origin handler template containing `%s`, and the browser may request user permission. The callback is navigation, not a privileged IPC/authentication channel. [WHATWG custom handlers](https://html.spec.whatwg.org/multipage/system-state.html#custom-handlers), [MDN registerProtocolHandler](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/registerProtocolHandler)

For a supporting installed PWA, the minimal illustrative manifest entry is:

```json
{"protocol_handlers":[{"protocol":"web+bindle","url":"/contact/open#intent=%s"}]}
```

The handler lives inside the app's scope on its HTTPS origin. Use `%s` only for a **nonsecret** intent such as `web+bindle://contact?recipient=https%3A%2F%2Falice.example%2Fentities%2Fopaque-id`. It is a locator, not permission to contact that person. Fragment placement reduces HTTP query exposure but does not conceal data from the browser, handler application, OS dispatch path, history or extensions; never wrap a signed endpoint or conversation credential into that URI. Custom-scheme handling is top-level; iframe navigation is not a supported launch plan. [Chrome PWA protocol handlers](https://developer.chrome.com/docs/web-platform/best-practices/url-protocol-handler)

| Environment | Evidence-based plan |
| --- | --- |
| Desktop Chromium/Edge PWA | Manifest protocol handlers are documented; installation and OS/browser permission/default selection matter. Verify actual supported OS/browser versions before advertising. |
| Firefox | The imperative web API is available according to Mozilla compatibility data; do not infer installed-PWA OS registration from that API. |
| Safari/macOS and iOS web app | Mozilla compatibility data marks the imperative API unsupported. Use HTTPS; native universal-link integration is separate. |
| Chrome Android | Mozilla compatibility data marks the imperative API unsupported. Do not assume desktop manifest/OS behavior on Android; use HTTPS/native verified app links where available. |
| Native application | Can register `bindle:` subject to platform rules, but another app may register the same custom scheme. Prefer domain-associated HTTPS links for a companion native app. |

[Microsoft's manifest guidance](https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/how-to/handle-protocols) and [installed-app test procedure](https://learn.microsoft.com/en-us/microsoft-edge/devtools/progressive-web-apps/protocol-handlers) support the desktop test path. [Mozilla's maintained Navigator compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/Navigator.json) supplies the API distinctions. Apple's [custom-scheme documentation](https://developer.apple.com/documentation/xcode/defining-a-custom-url-scheme-for-your-app) explicitly describes scheme collisions and recommends [universal links](https://developer.apple.com/documentation/xcode/allowing-apps-and-websites-to-link-to-your-content). These are documentation findings as of 2026-10-13, not browser tests performed for this proposal.

Request registration/launch from a clear user click, expect browser/OS prompts, and retain the web fallback. Do not probe installed handlers with hidden iframes, timed redirect loops or visibility heuristics that claim success. A browser permission prompt is not consent to send, join, share an inbox or transfer a credential.

### Minimal safe external handoff

The baseline universal fallback is the signed HTTPS page plus an explicit Copy contact link / paste into the chosen Bindle composer. Copying a link knowingly transfers its introduction authority; UI must identify that effect. This needs no new protocol. The app validates the full canonical endpoint and uses existing token GET/contact POST or compatible conversation RPC.

A smoother **web-to-web** enhancement opens the user-selected provider's verified HTTPS contact UI, then transfers the endpoint in a message body through a narrow handshake. Check exact chosen origin, expected window, fresh nonce and version; use exact `postMessage` targetOrigin, never `*`. Show that the selected provider will receive contact authority. Bind the review to the recipient and selected account/profile; a changed selection or navigation requires a new handshake/review. The receiving page handles the content as a draft, revalidates issuer/signature/live scope, and binds it to the account the user selects. It never reflects the raw endpoint in errors, `window.name`, redirects or referrer-bearing URLs. If opener isolation, popup blocking or navigation destroys the channel, fall back to explicit copy/paste; do not relax origin checks. The known UI endpoint may be an optional bounded descriptor in existing provider discovery after review, not a new service registry or arbitrary caller-specified redirect.

A custom-scheme launch alone does not provide that trusted channel or the original browser's cookies. For the first release it opens a nonsecret intent and asks the user to import/paste the contact link. Automatic credential-bearing deep links are rejected. A later brokered transfer, if the extra friction warrants it, must use a short-lived one-use handoff record bound to the source context, selected destination origin/app key, recipient and operation. Redemption requires destination proof plus source confirmation; intercepted URL material alone grants no contact, history, account or contribution power. Reuse existing exact resource grants/RPC/journals, and review that narrow exchange before implementation. A random bearer code with expiry alone does not meet this condition. No generic app-state subsystem is justified by this handoff.

## Portable implementation and migration

Keep protocol policy in `packages/conversations`. Inject transactional local journal/repository, writer/lease fencing, conditional cold storage, signing/verifying, sealed secrets, clock/random, quota/work admission, scheduling, peer transport and owner content/search/notification adapters. Worker types stay in Worker code; Node supplies equivalent SQLite/files/scheduler adapters. A local author commit and every recipient commit have crash-safe outboxes/receipts. In-memory callbacks are not recovery machinery.

Use actual vendored ngin APIs: Providers obtain/release resources, Actions implement `execute` and report on dispatch feeds, Queries implement `fetch` or `boot`/`kill`. `Provider.fromSingleton` can supply an already-created portable service. `flush`/`dispose` are not crash-consistency boundaries. Browser integration keeps existing owner-flow guards, dodo rendering and query-backed state; no second state framework. Discovery advertises verified resource implementations/profiles, never provider brand guesses.

Moving an owner replica transfers its local copies, author/local-consent chain heads, frontier/tombstones, receipts and cold segments. Establish a signed old-to-new participant resource/key binding and newly authorized recipient delivery admissions; freeze that author's old writer generation before the new one accepts. This is per-participant continuity, not migration/election of a conversation-wide sequencer. Other members continue their own writes during migration and report pending delivery to that member. Exact migration and key-recovery schemas remain a gate; do not silently redirect bearer grants or replace pinned keys from a mutable discovery document.

### Complete account portability goal

The goal is to move the user's durable identity and **all exportable account data** to another compatible provider or self-hosted instance, preserving stable UUID, assigned signing/encryption keys and history. Contact links tied to the old provider need reissue. This goal is broader than the currently implemented recovery file or proposed conversation archive; do not claim that a populated backup/download button already delivers it. Current retained-account recovery explicitly does not reconstruct missing accounts or import arbitrary provider state.

Use a versioned encrypted **migration-package profile** over the existing identity/recovery, conversation, profile/preferences, object-storage and connector export resources. It is a manifest/container plus mappings and staged import rules, not a new generic app-state service or hidden protocol replacing those contracts. Obtain authenticated owner authorization and a coherent bounded snapshot/fence, then record completeness for each selected data class:

| Data class | What must survive the package |
| --- | --- |
| Stable identity/key continuity | UUID, original identity URI/issuer provenance, public key descriptors and needed historical signing/encryption verification context; separately protected recovery/keychain material, with exact key IDs and archive coverage. Names/certificates remain distinct from private keys. |
| Conversations | Immutable signed genesis/events, every retained edit/deletion/reaction revision, attachments, per-owner encrypted manifests/segments, author chain heads and visible provenance. Retention gaps remain explicit. |
| Local safety and synchronization | Accepted-peer views, signed acceptances/proposals, blocks, admission incarnations, anti-replay frontiers/exceptions, erase tombstones, verified ACKs and durable outbox obligations/outcomes. Migration must not forget a block or recreate an already delivered message. |
| Personal organization/settings | Private read/unread state, tags, folders/collections, mute/disclosure settings, notification preferences and saved contact annotations allowed by owner retention. Imported social disclosures remain off until reviewed; no historical read-receipt backlog is emitted. |
| App files and resources | Actual accessible object bytes plus logical resource/key mappings, versions/digests, attachment references and app-owned reconstruction metadata provided by their existing contracts. An old URL/native file ID alone is not the file. Preserve assignment/configuration history without silently activating new-provider grants. |
| Connector/account configuration | Safe provider/resource descriptions, scopes and mappings; optional privileged credential/journal material only in a separately marked owner-encrypted migration section when permitted/exportable. Provider binding, status and required reconnect steps are retained. |

Keep the independently decryptable recovery file **outside** the archive encrypted to its own public key, so unlocking is not circular. A migration archive can reference required encryption key IDs, but may not contain the only copy of the private key needed to open itself. Never publish private JWKs, answers, account reset tokens or `KEY_ENCRYPTION_KEY`. The ordinary transcript archive omits live credentials; a comprehensive privileged migration section can preserve necessary historical secrets in encryption to the user's migration/archive key, with strict format/scope and inactive-import semantics. A copied old token is not proof it remains authorized at either provider.

Provider-encrypted connector records are not automatically portable: ciphertext sealed under the old `KEY_ENCRYPTION_KEY` cannot be opened by a new host merely because the user restored their identity keys. An authorized exporter must decrypt permitted source credential records within the old trusted boundary and re-encrypt them to the user-owned migration envelope, without exporting the provider master key. If that operation or a third party's export permission is unavailable, report exactly which credentials require reconnect and preserve independently accessible data/mappings. Do not call an unreadable copied credential blob a complete migration.

### Identity location changes and reconnect work

A provider move changes **location and host-bound access**, not necessarily the stable UUID or cryptographic user identity. The preserved user signing key can sign a bounded move announcement linking old/new identity-document and participant resource URIs, unchanged key fingerprint/UUID, a migration incarnation and validity context. Previously accepted peers verify it against their pinned user key and independently accept/update routing; the old host need not be online to verify that saved-key continuity. Peer acceptance is asynchronous and cannot override a local block. Directory publication at the new provider attests the new location, not ownership of the old provider's namespace.

The move does not make old HTTPS URLs resolve after the old host disappears. People with only an old contact/profile URL and no previously trusted identity key/portable proof may need the new public handle/link. Preserve original URI provenance in events and archive AAD; do not rewrite signed history to pretend it originated at the new host. A new handle and old paid-name certificate do not transfer authority over the old host's aliases, DNS, signing issuer or permanent-name ledger. If the destination already has an incompatible account at that UUID, fail the import rather than merge users.

Operational continuity therefore requires these explicit reconnect steps even when durable user data is preserved:

| Binding | Move behavior |
| --- | --- |
| Contact links | Reissue on the new provider; old issuer/audience/signature/live-grant state cannot be made portable by copying a URL. |
| Passkeys/passwords/sessions | Passkeys are RP/origin bound and must be enrolled for the destination. Establish new credentials/session cookies under destination policy; the old recovery reset token is not a destination login credential. Do not assume password/session verifier portability. |
| App OAuth/resource grants | Issuer, audience, redirect/client registration and opaque resource references may change. Preserve assignments/history for review, remap logical resources and obtain destination consent/tokens rather than treating stale bearers as live. |
| External connectors | Reauthorize where OAuth client/project/provider scope changes; validate destination access to each required external object. Old refresh tokens are not universally reusable. |
| Google Drive `drive.file` | Another OAuth project may lack access to files reachable by the old app. Preserve durable logical-key/native-file/version maps and verify every needed read/write under the destination client; copy required bytes while source access exists when necessary. A successful new OAuth login is not proof of old-file access. |
| Push devices/notification services | Recreate destination subscriptions and test delivery; copying preferences does not transfer working origin-bound push endpoints or verify delivery. |

Thus “lose only live contact links” is a durable-data portability aspiration, not a claim that passkeys, OAuth, connector permissions and URLs remain live unchanged. Reconnection can preserve user data while reestablishing those services. External files the source cannot read or an app's opaque format the destination cannot interpret need explicit incomplete/unsupported entries, not a false no-data-loss guarantee. Follow the existing [managed Drive design](google-drive-integration.md) and [offload design](offload-retention.md) for mapping and destination-verification boundaries.

### Copy, verify and activate before source deletion

Stage a resumable encrypted package with immutable manifest/shards and durable ciphertext verification receipts. At destination, first verify the complete signed package and checksums, then perform an authorized decrypt/restore drill with the intended user key, validate content/attachment mappings, original event signatures and owner safety state, and reconcile active outboxes/ACKs before enabling the new writer. Where the destination remains storage-only, an independent local opener performs that drill without disclosing keys to it. Source removal is a separate authorized final step after verified coverage and the existing retention/offload safeguards, never inferred from upload success.

An orderly cutover fences the old local author/consent writer and records its last durable frontier; the new writer starts at the next permitted incarnation/frontier, with peers seeing a signed continuity record. Restoring a file while the old provider continues to write without a coordinated fence is a concurrent recovery/fork scenario, not a completed seamless move. Retain evidence and pause conflicting author branches rather than duplicating sends or discarding acknowledged events. A fully offline recovery may announce a new routing incarnation to saved peers, but cannot claim it recovered events that never reached its backup or prove the old service stopped.

Because the original provider held private identity keys, preserving those same keys does not cryptographically revoke that provider's knowledge. Signed location continuity works within the existing trusted-provider/observed-equivocation model; hostile-provider exclusion requires a separately reviewed key/custody transition and cannot be promised by moving ciphertext. Older encryption keys may still be required for external archives even when new signing/delivery keys are adopted. Import never overwrites newer local revocations with stale backup state, reactivates revoked ingress/OAuth grants or silently deletes the source's only decryptable history.

For v1 upgrades, either coordinate a disclosed profile transition with compatible members or create a successor v2 conversation and explicitly import entitled historical documents with provenance. Preserve v1 source-signature attribution, original IDs and delivery state. Unsupported providers stay visible; do not route all new writes through a hidden v1 authority and call it decentralized. Revocation of old credentials is explicit and must not revive them on rollback.

## Phases and verification

1. **Reconcile the public profile:** review shared-secret plus independent proof/local approval, directed consent semantics, proposal/rotation behavior, signature/causal/audience schemas, delivery ACKs and v1 compatibility. Update normative specs/artifacts and DEVLOG before claiming v2. This document changes no code or public artifact.
2. **Two-provider vertical slice:** use independently hosted owner resources, authenticated first contact, explicit acceptance and distinct admissions/grants. Stop the creator's provider and verify the other already-admitted participants can commit and exchange posts without it; creator delivery remains pending. Verify every remaining owner can propose/accept peers without the creator, while no acceptance changes another owner's list. Use three members to avoid mistaking a pair with its sole recipient offline for a useful federation test.
3. **Content and partition semantics:** concurrent messages, missing causal parents, reordered retries, author forks, concurrent divergent local approvals, stale-admission post/removal races, recipient local block during source outage, late joins without old history, transparent edit/tombstone/reaction retention and local erase anti-resurrection. No fabricated universal order or read guarantees.
4. **Local durability, archive crypto and migration:** Node and actual workerd fault injection around stage/commit/delivery/ACK/checkpoint/head-generation/cleanup/restore; cross-implementation HPKE/AEAD/archive fixtures, wrong key/purpose/UUID, chunk substitution/reorder/truncation, nonce retry safety, rollback and offline recovery with the service unavailable. Verify complete ciphertext movement plus independent decryption/mapping restore before deletion, old-key coverage, connector reconnection and author cutover. Measure bursts, cold restore, finite retries, quotas, bounded dependency fetch and free-account cost. Choose local actor placement from contention and measured overhead, not assumed global topology.
5. **Browser continuation and optional signals:** same-provider signed-in/out, complete signup/recovery interruption, alternate provider, account switch, revoked contact, draft restoration and explicit final send. DOM and real-browser tests for mobile/accessibility, inert GET, CSRF, no secret leakage; installed/uninstalled protocol handlers, Safari/iOS/Android fallback and hostile postMessage. Verify signals-off defaults, prospective receipts, disclosure cancellation, mobile TTL and no per-heartbeat durable writes/alarms/cold wakes.
6. **Conformance and release:** publish immutable contract only alongside actual implementations and exact supported profiles; independently implemented providers, SSRF/DNS/redirect/response bounds, recovery/backup/retention drills and measured load. Implementation changes require `npm test`, Worker and browser suites. Configured services, local tests, actual external-provider delivery and human release sign-off remain distinct evidence.
