## Superseded frontend-only notification default

The later user decision in [app notifications](app-notifications.md) supersedes this document's recommendation to require an ordinary app identity, sender signing delegation or recipient contact capability for frontend-only app notifications. That path now uses a direct SDK call under the owner's approved app connection and notification resource grant, with provider-signed local admission/provenance and server-recorded app origin. No contact link/token is involved. Its record is not an app-identity-authored federated message. The sections below remain useful for ordinary identity messaging and optional deliberately identity-bearing apps; their browser-only default, every-message-author-signature scope and rollout order must not be implemented for the newer local notification path. Existing legacy behavior remains as described, without relabelling unverified messages.

## Recommendation for ordinary identity messaging

An application that sends messages has an ordinary Bindle identity: stable UUID, provider-attested public handle, established identity keychain and minimal identity document. The identity may live on an existing shared Bindle provider; each app does not need to operate its own directory or provider. Do not introduce a different `senderKind: app` trust system. A person, organization or application uses the same signed-message verification and recipient-controlled admission. An app's role as software is a presentation/connection fact, not a weaker signature or stronger delivery permission.

Require every message in the new signed-message profile to authenticate its exact author, content, behavior-affecting metadata and intended delivery context. Show the verified public handle beside an optional authorized display name/avatar or app icon. Verified means that the signature and identity binding check out; it does not mean that the provider endorses the sender, content, action or organization. Delivery still requires a separate recipient-issued capability and live recipient policy. The recipient can allow or disallow messaging from a connected app independently of connecting that app, assigning resources, enabling OS notifications or approving any callable method.

A browser-only app cannot safely contain the shared private key for its global sender identity. Support a narrow provider-mediated signing delegation bound to an approved app connection and recipient. The app's actual identity must authorize that delegation; the recipient's approval alone cannot confer somebody else's identity. No ordinary owner session, OAuth client ID, app manifest or fetched public key grants arbitrary signing authority. Keep private keys, delivery capabilities and delegation records in existing protected identity/connection storage, not a new app-state subsystem.

## Identity, connection and delivery are different objects

| Object | Subject and authority |
| --- | --- |
| Sender identity | Ordinary stable UUID and assigned keys. A verified public handle resolves it; the handle does not become its cryptographic primary key. |
| App manifest / registered OAuth client | Describes software and its verified client/origins. An explicit verified association binds it to a sender identity; a self-declared `identity` field alone is insufficient. Multiple verified clients may serve one identity. Preserve publisher identity, original client/installation, recipient UUID and any separately approved user-on-behalf-of assertion as distinct provenance fields. |
| Owner's app-connection resource | That owner's relationship with the app and approved exact contract methods/bindings. It is not a second global app identity, account, keychain or public sender directory entry. |
| Sender signing delegation | Sender-authorized permission for a trusted signer/workload to sign a specific message profile under bounded connection/audience/purpose rules. It is not a recipient inbox capability. |
| Recipient delivery capability | Recipient-issued permission to submit permitted message types/bytes within rate, tag and lifetime constraints. It may additionally bind the sender UUID and connection incarnation. Possession alone does not authenticate the sender. |
| Notification policy | Recipient-owned channel, quiet, privacy, priority and allow/block settings. Neither a valid signature nor a delivery capability grants permission to ring a device. |

Reuse [resource contributions](../spec/resource-contributions.md), the existing resource-valued preference model and [callable bindings](callables-and-user-commands.md). An app can be an identity and also expose independently granted resources; those roles do not collapse. A grant to read profile or write files never implies send-message permission. Resource contribution, app installation and verified OAuth redirect control also do not imply notification consent.

## Source reality and version boundary

Current generic contact receipt accepts capability-authorized bytes and bounded caller-supplied `senderMetadata`. The signed contact URL authenticates the recipient's grant, not that supplied sender name. Current [conversation v1](../../packages/conversations/index.mjs) has signed owner envelopes and source-signed events, but its configured bearer contribution policy can accept an unsigned `actor: bearer`; a source signature on the resulting event does not transform that bearer into a verified author. These are not implementations of universal author signatures. Existing notification plumbing does not establish general verified-app branding.

The proposed [conversation design](conversation-contact-design.md) supplies independently signed participant events and minimal directory/key discovery; it remains a design. The [message actions design](message-actions.md) adds authenticated descriptors and optional identity disclosure on action submission. Neither is a published universal signed-message contract today. App-connection contribution and broader callback/delegation profiles also have unimplemented gates.

Introduce an explicit versioned signed-message envelope/profile and negotiate it on contact/ingress admission. Do not silently reinterpret legacy `text/html`, unverified sender metadata, v1 bearer contributions or email as verified identity traffic. New Bindle-native messaging uses the signed profile; retained legacy records remain labelled unverified with active forms and verified-sender notification branding disabled. An email bridge can sign its own ingestion provenance, clearly retaining the external sender as unverified; it cannot sign as that mailbox's owner. Deciding when to stop admitting legacy unsigned contact payloads is a migration/product gate, not an assertion that today's APIs already satisfy “every message signed.”

## Directory, identity keys and presentation

Use the provider's advertised `directory_url` and exact `?handle=<full encoded public handle>` lookup from the conversation design, for applications as well as people. Resolve the stable identity/document, validate the public key's purpose and pin continuity. The provider manifest remains host-level; the app manifest remains software metadata; `identity.json` remains the subject's minimal public identity/key/protocol document. No alternate app-only directory or second signing keychain is necessary.

Retain the privacy decision: do not add real name, avatar, private email or arbitrary profile fields to `identity.json`. Resolve optional presentation through the existing profile contract or contact-granted disclosure with its live field intersection. An app may deliberately publish a bounded icon in its verified software manifest, but the host must verify the manifest-to-sender association before using it as that sender's branding. Missing/declined/revoked presentation falls back to the verified handle and a neutral icon. Identical names/images never merge identities or override a block.

Render “verified sender” independently of self-asserted display text: stable handle/provider context and a trusted verification indicator outside sender HTML/CSS. Historical messages retain their original handle claim and verification evidence; a handle move or later profile change does not rewrite the signature. Current profile can be shown separately with an explicit current label. Verification proves control under the established provider/key trust model, not a legal identity or freedom from compromise.

Notification previews use the deterministic privacy-limited heuristics in the action proposal. Prefer a locally cached, validated bounded raster image whose disclosure is authorized. No notification delivery, lock-screen display or sender lookup should trigger arbitrary avatar-host tracking. The Notifications standard fetches notification resources with credentials included and no-cors, so never pass sender-controlled URLs directly as icon/image/badge/action-icon values. Use only the previously validated bounded local asset or neutral fallback, never a lazy redirect to the sender; the OS still identifies the host/PWA origin, not an independently verified app origin. [Notification resource fetching](https://notifications.spec.whatwg.org/#fetching-resources). A deliberate import/proxy path must enforce MIME/decode/byte/origin restrictions and contact/profile authorization; an untrusted URL is not safe just because it is HTTPS. Never put delivery capabilities, user profile secrets or signer credentials in push payloads. On missing key/provenance, show a generic/unverified entry or hold notification pending bounded verification; never briefly show trusted branding and correct it later.

## Exact signed envelope and delivery binding

Finalize machine schemas and test vectors before publishing any canonical URI. A proposed envelope has a strict domain-separated purpose/version and canonical representation, using the assigned identity signing key or its verifiable narrowly delegated signer. Reject duplicate/unknown semantic fields, ambiguous encodings and unsupported algorithms; define body hashing over exact accepted bytes and an explicit MIME/encoding so reserialization cannot alter the signed meaning.

The authenticated payload binds at least:

- Stable author identity URI/UUID, key ID, signer/delegation reference and identity revision needed for verification.
- Stable message/operation ID, revision and creation context; mutation target and predecessor digest for edits/tombstones/actions where applicable. Signed time alone is not replay prevention or proof that a message predates revocation.
- Exact body digest/length/MIME, attachment manifest digests and immutable sender metadata, including subject, requested allowed tags, action descriptors, notification hints and presentation-resource references. Recipient-added tags/classification/read state remain separately identified local metadata, never falsely attributed to the author.
- Recipient identity and exact ingress audience, permitted profile, recipient delivery-grant ID/incarnation or an opaque immutable admission binding, expiry and transaction ID. Bind action descriptors to this same message revision and audience; they cannot be transplanted to another body or recipient.
- For conversations, immutable intended audience snapshot and conversation/event identity, plus the recipient-specific delivery envelope referencing that event. This avoids signing a different author event for each destination while still preventing envelope substitution.

The shared author event must not expose other recipients' secret grants or private inbox URLs. Keep each grant/capability in a separately protected transport field; sign a nonsecret stable authority reference or a cryptographic binding of an unguessable credential, never embed the raw credential in publicly retained content. The final profile must select one exact binding scheme and canonical bytes; it must not let the sender choose a weaker alternative at runtime.

A signature cannot prevent someone from saving/forwarding the content. A valid signature for recipient A does not authorize delivery as the original sender to B. B needs its own delivery admission and an explicit newly authorized envelope; an ordinary user forward is signed by the forwarder and may attach original evidence as quoted history. Conversation fanout uses only the author's immutable approved audience and each recipient's own consent. Do not treat a recipient identity match as a general inbox permission.

Verification happens before trusted presentation, normal message persistence and action activation, behind cheap size/HTTP/attempt guards. Resolve only bounded pinned issuer/delegation references; no arbitrary message-supplied key URL fetches or unbounded chain traversal. At admission, check current recipient permission/block state, live grant/incarnation, signature/delegation validity and all existing owner/link/work/storage budgets. Then durably deduplicate by stable sender/recipient/operation/profile and canonical signed payload digest; randomized signature bytes do not define event identity. Same operation/body replays its authorized receipt; changed body conflicts. Authorization is rechecked before replay; accepted retries do not create new notifications/storage charges. Unknown/failed downstream effects remain governed by the current conservative admitted-attempt budget semantics.

Current per-owner serialization can atomically commit local policy/dedup/message metadata; object writes and remote sender authority are separate operations. Do not invent a cross-provider atomic revocation guarantee. A received copy stores verification evidence and local admission time; future verification outages do not retroactively falsify that previously established evidence, and historical evidence does not authorize a new delivery.

## Signing choices, including frontend-only applications

| Profile | Where authority comes from | Limits |
| --- | --- | --- |
| App service signs as its ordinary identity | Its operator controls an established signing key or an explicitly delegated workload key. | Requires secure key custody and an independently authorized workload. A client secret embedded in shipped JavaScript is not secure custody. |
| Trusted provider signs via app-authorized delegation | App identity grants that provider an exact signing profile; recipient independently enables a connection and messaging. Provider intersects both with live caller/binding/recipient policy. | No browser-held global key. Provider is a trusted delegate, not proof that code ran at the app's server. Recipient approval cannot create the app's side of the delegation. |
| User deliberately signs as themselves | Explicit reviewed user action and a narrowly authorized user-signing interface. | The author is the user, with app execution provenance separately recorded. It must not be presented as a message authored by the app. No ambient session signing. |

Recommend the second profile for browser-only apps. The app operator establishes its ordinary identity and authenticates an association with its registered client/manifest through a signed challenge or equivalent already authenticated identity operation. It explicitly delegates a constrained message-signing purpose to named provider signer keys (or a narrowly specified verified enrollment policy). This is not broad delegation to anyone publishing a matching manifest. A provider handling an unrecognized app cannot infer that delegation from the recipient's connection alone; it must use a reviewed cross-provider enrollment or leave app-identity sending unavailable.

The provider receives an authenticated call through the existing app resource/RPC grant, identifies the original registered client and exact owner connection, and checks its approved send method, current connection incarnation, sender delegation, recipient messaging toggle and delivery grant. It builds the canonical envelope itself from strictly validated input. The browser cannot select another author, provider signer, recipient, key ID, contract/method or hidden grant. The provider signs the bound message with its delegated signer and attaches the proof chain. The verifier establishes the app identity's authorization of that signer and checks scope/audience/expiry; a generic provider signature alone is insufficient to claim an app author. Keep the chain short and purpose-specific, distinct from OAuth session/JWT keys and passkey authentication.

A public-client OAuth session proves that a caller holds a bounded approved connection token; it does not prove untampered application code or distinguish a malicious user of that public client. Consequently a browser-only delegation initially sends only to the consenting connection owner, with explicit content/rate/profile limits. It must not let any user who installs the app sign arbitrary global app announcements or contact other owners as that app. A separately reviewed workload is needed for trustworthy service-origin events such as “payment received.” Display “via approved app connection” when that distinction matters. Higher-trust claims cannot be inferred from the ordinary sender handle alone.

A static app that is closed cannot itself generate future reminders. Background messages need an already authorized resource method/job or real backend workload with the same bounded authority. Do not add an arbitrary hosted JavaScript runner, app-state store or generic `sign(bytes)` method to solve this. The user-signing action proof in the forms proposal is a different purpose; a postback signature cannot become a reusable message-sender delegation.

## Recipient control and capability placement

Offer **Allow messages from this app** separately from app connection and OS notification permission. Default it off until explicit messaging consent, except a narrowly described owner-created automation whose creation review explicitly includes it. Show the verified sender identity, connection, intended message types, estimated frequency, expiry and quiet/notification controls. Permission to store a message and permission to show a push notification stay separately configurable. An allowed app may have silent or View-filtered delivery; priority claims never bypass recipient policy.

Keep the recipient delivery capability in the provider's encrypted private execution binding for that owner/connection. Expose only an opaque resource reference and exact scoped `send`-style contract method through the existing private resource-valued preference model; final URI/method schema is a publication gate. A common preference name means shared interface, not a shared public bearer secret. Other apps with access to the owner's resource pool do not automatically read the capability or invoke that method. Assignment of the field is separate from consumer method consent. Do not persist raw contact links in generic app-visible settings, manifests, forms, notification data or public descriptors.

For an app backend delivering directly, disclose a dedicated bounded recipient grant only through explicit consent, encrypted authenticated provisioning and protected backend storage. Bind that grant to the established sender identity and app-connection incarnation in the new profile; copied capability alone cannot impersonate the sender. Reuse parent contact/admission lineage and quotas rather than minting a fresh unlimited link per send. A signing key compromise and capability leak are different incidents; both must be independently revocable. A manifest can advertise supported methods, never supply itself with the recipient's authority.

Disabling app messaging invalidates its recipient-side connection/admission generation immediately at that receiver, cancels undispatched local notification work and prevents new sends even with a copied old grant. Re-enabling issues a fresh generation; old tokens do not revive. Disconnecting the app disables related send bindings/delegations locally. Blocking the sender UUID means blocking the accepted authority/key-bound principal; it overrides all its app connections and contact links at that recipient, across verified key rotations/location continuity. A foreign provider asserting the same UUID cannot auto-merge identities, inherit trust, clear the block or replace pinned keys; require independently verified continuity and reject conflicting bindings. A convenience “disable all connected-app messages” control applies to known approved connection/delegation provenance, not a self-declared app/human flag; ordinary identities cannot be classified reliably from that flag. Revoking one contact capability leaves unrelated explicitly approved capabilities alone; deleting a saved message neither revokes the sender nor refunds receipt-rate allowance. Already accepted remote effects/messages cannot be recalled, and a sender's retry cannot override local block.

Notification jobs recheck current recipient block/messaging/channel settings before dispatch, and cannot reclassify rejected delivery as an unread message. Quiet hours, device permission, owner budgets and bounded dedup apply as today. No per-message global database or global app-identity hot actor is required; sender identity/delegation can be verified under bounded cached validity, while recipient revocation is checked in the recipient's own authority. Publishing stricter cross-provider revocation freshness requires a specific availability/caching tradeoff, not a claim of instantaneous knowledge.

## Rotation, recovery and migration

Use the existing assigned identity keychain; signing and encryption keys remain different purposes. Preserve historical public verification keys and signed rotation/continuity records, with status/effective context. A provider-generated new key without continuity is a changed trust binding, not silent proof of the same sender. A compromise declaration can mark historical verification uncertain over an affected interval; an attacker-controlled signed timestamp cannot resolve that interval. Previously verified receipt evidence remains inspectable without asserting that every old signature was created before compromise.

Rotate delegated workload/provider signer keys independently through fresh app-authorized scope. Do not use a delegation to extend its own expiry or add new recipients/methods. Key/grant revocation affects new admissions according to local-known state and bounded verified cache lifetime. Exact TTLs, delegation chain depth and emergency revocation behavior require schema/conformance review. No cached profile/avatar or matching handle can restore revoked cryptographic authority.

Recovery of an ordinary app identity uses the established recovery/keychain mechanisms and operator-controlled secret storage; no keys in app bundles, public manifests or OAuth redirect URLs. Restoring an old backup does not roll back newer known delegation/recipient revocations or activate old connection tokens. Export historical verification evidence and identity continuity, separately protect private recovery material, and reissue host-bound delivery/resource permissions after migration. A stable UUID and preserved keys can authenticate a signed location move to pinned peers, but do not transfer ownership of the old provider's handle namespace or make its old URLs keep resolving. Moving a provider-custodied key does not revoke that provider's historical knowledge of it.

## Service identities and bootstrap

An ordinary identity need not mean a passkey prompt for every automated message. Recommend human administrators initially establish the app identity through normal credential, verified contact and tested recovery setup, then authorize a narrowly scoped workload credential/delegation for unattended sending. Admin login credentials and workload signing authority are separate. The current generic system-bootstrap invitation still requires ordinary setup and does not create a passkey-free service-account shortcut, admin privilege or sender endorsement.

If genuinely nonhuman provisioning is required, define a separate audited operator enrollment profile before implementation: authenticated operator ownership, exact identity/namespace reservation, workload public-key proof, bounded machine authentication, encrypted recovery/escrow custody, rotation/revocation, administrator transfer and billing/abuse obligations. It must not be selectable with a public `isApp` body flag, self-declared manifest, protected handle or unsigned import. No shared operator bootstrap key belongs in runtime app code, and a bootstrap role badge is not message-signing delegation. Unknown provisioning/recovery state fails closed; namespaces and stable UUID ownership cannot be silently reassigned. This is an open operational decision, not a second identity type or an implemented machine signup API.

## Phases and decisions

1. Publish a reviewed versioned envelope/authority profile only after canonical fixtures prove body/metadata/action/recipient binding, replay rules, algorithm constraints and legacy labels. No new registry stub now.
2. Implement ordinary identity verification and recipient-bound admission on the existing owner path; verify quotas, blocks, historical key evidence and notification provenance before adding app delegation.
3. Add exact app-manifest identity association, a narrowly delegated provider signer and private connection send binding. Test hostile public clients, changed app origins, recipient mismatch, disconnect/reconnect and no arbitrary signing or secret exposure. Keep service-authored assertions distinct from public-client-origin requests.
4. Add bounded profile/icon presentation and deterministic notification extraction, testing no tracking fetch on read/push, no spoofed trusted chrome and fallback to handle/placeholder.
5. Verify rotation, compromise, recovery, migration, expired-cached delegation and durable notification/outbox races on Worker/Node and independent providers. Introduce unattended workload provisioning only after its separate custody/ownership review.

Open decisions: exact signed-message contract/carrier and legacy cutoff; app-to-client association proof and cross-provider delegate enrollment; finite signing/delegation validity and rate limits; private preference/contract method schema; scope of service-origin claims versus public-client-generated content; optional app icon publication; and nonhuman bootstrap/recovery custody. These require product/security signoff. The recommendation is ordinary sender identities with purpose-limited delegation and independent recipient control, not a privileged app sender category.
