# Now
- We need to unify the app and integrations concepts, they should be covered under one umbrella and UI, though there will be two different kinds of implementations: built-in and third party.  Built in integrations are things like Google Drive, implemented within the provider app itself.  Third party are... well basically what we have for apps now, though not necesarily providing a front-end at all, other than an auth/connector endpoint, etc.  Both kinds get the same setup/config UI and should rely on config fragments to manage; the app/integration manifest should specify a webhook where we can send preference updates for changes after initial setup.  We need a design/spec to let integrations/apps declare provided resources; probably not directly as a list, but as a search/filter/browse type endpoint where we can ask it if it provides resources that satisfy a particular protocol, or send a search string + filter constraints, etc.  We need a good design for this kind of thing.  I think it should allow for the bindle provider to make the connection/introduction/etc, but the resource provider and the thing using it communicate directly; likely putting a third party resource into a preferences field should give not only credientials and resource id, but also the rpc endpoint, to the consumer.  The bindle provider should own the credentials that couples the two ends, so it can sever them on demand, sending an invalidation request to the provider to cancel the consumer's credentials.  This needs to be robust.
- We need to make sure our message sending/receiving system is robust, and very well architected.  Providers likely need to limit the number of participants in a conversation, since each one needs an http request per participant per message.  We need robust error handling, to surface any delivery issues to the user.  For group conversations we should indicate how many participants received, errored, pending, etc; let the user resend to those who missed the message, etc.  Because sending messages can involve waiting for acknowledgement from many involved parties, a send request should probably actually just go into a queue on the user's DO, and they get sent when opportune; with an SSE streaming events back to the client.  Whatever the actual design ends up being, or maybe a good one already exists, it needs to cover edge cases like these + we need a spike into other likely scaling issues or edge cases in similar domains that might apply to us; because we likely haven't thought of everything, this spike will give us an idea of where to look for issues in any design/impl we end up with.  We should also probably consider a bulk host-level (optional) message receiving endpoint that a host/provider can declare in their manifest, which allows a single message to be multi-cast to all receivers under the same host/provider.

# Later
- Invoicing/billing/subscription system.  We don't handle payments, charging, any kind of money for the user or vendor, we want zero KYC obligations.  But we let apps/vendors register the user's subscriptions into their account, with links to things like the subscription description, management UI, a way to check balances/status or for them to push it to us, etc.  Same for invoices, let them show balances, status, maybe attach a document or a link.  Needs design work.  It just gives users a central place to keep track of bills and subscriptions, cancel them, check status, etc.
- AI models, we'll need to design a way to expose them as a service, let the user manage their intelligence profiles (what model/backend to use for what kind for what kinds of requests), let preference fragments point to models and tell us what kinds of constraints are requried (profile for autofilling/choosing the field, model type (LLM, decisions, json, whatever)); most of this can probably be accomplished by leveraging the existing contract system, even if the rpc interface is the same between contracts, the semantics and expectations can be different, for example a resource that satisfies a 'smart' version and a 'dumb' version of the same kind of thing.  We can define our own contracts for some of the more common model kinds and uses, and leave anything else to the community.  What I'm thinking is that we can provide integrations for OpenAI, Claude, Cloudflare Workers AI, etc that allow the user to create and manage AI model resources... we need a good way to let integrations create/manage resources, probably simply by letting third party integrations provide a url to their resource management UI, and a way for them to let us/bindle provider know when things change.
